前几天看了 Lee Robinson 在 Stanford CS146S 的一堂课（[讲座发布帖](https://x.com/leerob/status/2108650243365736855)），主题是常驻、主动的 Agent 是怎么工作的。Lee 之前在 Vercel 负责开发者体验，后来去 Cursor 做 Agent 产品，现在在 SpaceX 做 Grok Bot。这堂课讲的就是 Grok Bot 这类产品的架构。

这门课第一周的作业，是让每个人写一个最小的 Agent：一个模型，在循环里调用工具。它已经很能干了，但你一合上笔记本，它就停了。这堂课讲的是下一步：把这个小内核搬到云端，给它一台自己的电脑和一套记忆，让 Slack、邮件、定时任务都能唤醒它，连续干上几天甚至几周。

讲座快结束时，Lee 提了一条原则，前后只讲了不到一分钟：delete the product，删掉产品。我回头再看前面讲的架构，发现几乎每一个设计都能用这条原则解释。

所以这篇文章分成两半。前一半跟着讲座拆一遍常驻 Agent 的架构；后一半聊「删掉产品」：删的是什么，为什么删了反而更好，哪些东西不能删。[上一篇讲 Harness 的文章](/blog/20260912---codexharnessevolution/post)聊的是哪些东西会被模型学走；这一篇从一个具体的产品形态出发，看「删」这个动作本身该怎么做。

<TldrCard>
- 常驻 Agent 的内核仍然是「模型在循环里调用工具」，变化在外面那一圈：触发器、队列、持久化状态，和一台按需唤醒的云端电脑。
- 它的很多设计都在做减法：客户端和服务器之间只有一个工具，工具只给名字，重活交给子 Agent。

- 一块东西该不该删，要靠评测来判断，而不是靠感觉。

## 一、常驻 Agent 和普通 Agent 差在哪

Lee 先回顾了一下我们是怎么走到今天的。最早是复制粘贴：从 ChatGPT 里复制代码，再粘回编辑器。后来有了跑在终端里的 Harness，模型可以自己改文件、跑命令。再后来有了专门的 App，可以在云端同时跑很多个 Agent，但人成了瓶颈，每一条命令都要等你审批。现在是第四个阶段：常驻 Agent。

和我们平时用的 coding agent 相比，它的差别主要在这几点：

- **它跑在云端。** 你合上电脑、它自己重启、中途崩溃，都不影响它继续干活。
- **它有自己的电脑。** 一台云端的 Linux 机器，有桌面、文件和浏览器。
- **唤醒它的不只是你。** Slack 里有人 @ 你、收到一封邮件、到了某个定时任务的时间，都可以把它叫起来。
- **它更像一个同事。** 不需要每条消息都立刻回复，在后台把事情做完，有重要的进展才回来找你。Lee 的原话是 "It knows when to be quiet."
- **它要连续工作很久。** 不是几个小时，而是几天、几周，甚至几个月。

交互方式也跟着变了。以前是提示、等待、审批一条 shell 命令、再提示；现在你可以随时插话，先说「去看一下这个帖子」，紧接着补一句「其实周四再做也行」，它能理解这两句话说的是同一件事。命令的审批也交给了另一个独立的模型：发邮件、发 Slack 这类操作，都由它先检查一遍。Lee 提到，在盲测里这种自动审查多数时候比人做得更好，因为人审了几百条命令之后，很容易变成机械地点「同意」。

这类产品大多做成 bot 的形态，Lee 给的解释很简单：大家都会发短信。和 AI 协作被简化成给朋友发消息，只是对方真的会去把事情做完。他还顺口说了一句，后面会反复用到：**模型越强，界面反而越简单。**

为什么是现在？Lee 列了几项模型能力上的变化：能在长时间运行中持续遵循指令，配合压缩可以稳定跑上数小时甚至数天；能把耗 token 的工作交给子 Agent；工具调用基本可靠了，可以像给新同事开权限一样，把 shell、文件甚至整台电脑交给它；能像人一样操作屏幕，没有 API 的网站也能用；很擅长用 grep 这类命令从文件里找回信息；你演示一遍，它就能把做法沉淀成 skill、记忆或者定时任务。Lee 对这一段的总结是 "everything is computer"：所有东西都可以落到一台电脑和一堆文件上。

## 二、架构：触发器、服务器和一台会休眠的电脑

常驻 Agent 的内核依然是第一周那个最小的 Harness：模型在循环里调用工具。变化在外面那一圈。Lee 把它分成三段：左边是各种触发器，中间是服务器，右边是 Agent 自己的电脑。

<AgentArchitecture />

先看左边和中间。消息从不同的来源进来，先经过一个队列和路由器：去重，按来源决定优先级，短时间内连续收到的几条消息合并成一轮，再用一些启发式规则判断这件事要不要去打扰用户。这一点和真实的同事很像：一个同事每有一点进展就来找你汇报，你会觉得很烦，大多数任务一天更新一次状态就够了。

优先级里最重要的一条是：**你直接发给它的消息，高于其他一切。** 你说「把这个活动的日期改一下」，正在跑的 Agent loop 就应该停下来，先处理你这句话，其他来源的消息排到后面。

右边是 Agent 的电脑，一台 Firecracker 虚拟机。选它是因为快照方便：用的时候启动，用完做快照然后休眠，下次再从快照恢复。电脑不能一直开着，一是太贵，二是世界上也没有那么多电脑能给每个人常开一台。这台机器上有文件、Chrome 和多个虚拟桌面，同时跑好几个 bot 时，每个 bot 用一块屏幕；你也可以随时连进去看它在做什么，必要时自己接管。命令都跑在这台隔离的机器里，碰不到你自己的电脑。

### 为什么 Agent loop 放在服务器上

一个很自然的问题是：既然 Agent 有自己的电脑，为什么不把循环也放进电脑里？

常规的理由是薄客户端、厚服务器那一套：更新 Agent 只需要改服务器，不用等 App Store 审核；转录、生图这类重计算在服务器上更快；服务器怎么扩容，业内早就有成熟的做法。

但 Lee 认为最关键的理由是另一个：**如果循环跑在虚拟机里，你就没办法独立于 Agent 去关掉这台虚拟机。** 状态都放在服务器上，虚拟机就可以随时重建。比如出现了一个紧急的 Linux 零日漏洞，需要给虚拟机打补丁，直接重建就行，Agent 不会因此停机。

### 用持久化工作流，而不是任务队列

每一轮循环的结果都写进数据库。客户端发出消息后，服务器先确认收到；客户端订阅变化，收到信号就拉取最新的数据。中间要做去重，避免重试导致同一条消息出现两次。

长任务怎么跑？普通的任务队列有一个问题：执行到第三步时基础设施出了故障，重启之后，前两步要从头再来一遍，重放这两步可能会很麻烦。所以他们用的是持久化工作流（durable workflow），具体是开源的 Temporal：每一步的结果都持久化下来，失败之后直接从第三步继续，重试是安全的。Lee 的说法是，这在分布式系统里算是已经解决了的问题，不必从零造轮子，只是要自己维护它的基础设施。

## 三、Harness：客户端和服务器之间只有一个工具

Grok Bot 的 Harness 和普通 coding agent 最大的不同，是客户端和服务器之间只有一个工具：SendToUser。

<ThinClient />

不管用的是手机 App、桌面 App、邮件还是 Slack，客户端和服务器之间都只靠这一个工具来回传消息。某种意义上，客户端只是在给服务器「发短信」。shell、读写文件、调用云端 Agent、录屏这些重工具，全都放在服务器上。客户端收到消息后，再决定用什么形式呈现最合适：需要登录就弹出登录表单，需要付款就接上支付，发邮件这类不可逆的操作先给你一份草稿确认，不需要回话的时候，回一个表情就够了。

这个设计已经能看出后面那条原则的影子：加一个新渠道，不需要改 Agent 的任何东西，只是多了一个会收发消息的客户端。

### 工具只给名字

上下文窗口就是模型的工作记忆，而且有上限。每个工具都有名称、描述和参数 schema，接上 Google Drive、Gmail、YouTube 这些连接器之后，工作还没开始，窗口就已经被占掉一大块。

他们的做法叫动态工具发现（dynamic tool discovery），也叫 tool search：每次发给模型的消息里只放工具名，模型决定要用某个工具时，再像读文件一样去读它的详细说明。上下文省下来，成本和用量也就省下来了。

### 升级阶梯：先试最便宜的办法

Agent 遇到一个需要查信息或者需要动手的任务，按什么顺序去尝试？Lee 给了一个升级阶梯：**先试最便宜、最可靠的办法，不行再一级一级往上爬。** 下面每个例子都可以点一下，看它会停在哪一级。

<EscalationLadder />

一个靠谱的同事也是这么做事的：先自己把能试的都试一遍，实在不行再来问你。

同样的思路也用在「从屏幕上读信息」上。截图最直接，但效率最低；页面 HTML 更结构化；无障碍树（accessibility tree）能大幅减少 token，也更容易找到要点的按钮和链接。有些网站会弹出对话框，这时还得能直接点击像素坐标。最坏的情况，比如遇到 2FA 验证码，才回到用户这里。

### 主 Agent 保持稀疏，重活交给子 Agent

你和主 Agent 的对话会很长，而且要求回复快，所以主 Agent 要保持「稀疏」：它管理一份待办清单，查看进度，给帮手发消息，或者让帮手停下来。真正耗 token 的工作，比如跑一堆 shell 命令、截很多张图、做一段视频，交给子 Agent 去做。

子 Agent 带着全新的工作记忆出发，中间过程都留在它自己那里，最后只把结果带回来。每个子 Agent 也是一个独立的持久化工作流：做视频的那个因为内存用太多崩了，重启之后接着做，不会丢进度。

无限上下文并不存在，每个模型都有上限。但靠这些办法，产品可以做到让用户感觉不到这个上限，也感觉不到对话越往后质量越差。

### 几条实战经验

Lee 还分享了团队的几条经验，都很具体：

- **不要在一轮中途增删工具。** 这会破坏提示缓存，下一节会讲为什么。
- **工具的描述和 schema 要精简。** 太长就是在浪费上下文。
- **「只给一个 shell 工具」大体是对的，但有例外。** 很多事情都可以用 shell 完成，但如果发现模型 90% 的时间都在用 shell 做同一件事，就值得把它做成一个专用工具：执行起来更高效，审查 Agent 行为的人也更容易看懂。
- **给 Agent 写好错误信息。** 像给人写错误提示一样具体：哪里失败了，下一步该怎么做。Agent 也有开发者体验。

安全方面，即使命令跑在一台隔离的机器上，每条 shell 命令执行之前，也还是要让一个模型审查一遍。收件箱里的邮件、外部的 webhook 都是不可信输入，不能当成用户的指令交给模型。密码这类敏感信息，要通过产品设计让它根本不进入模型的对话。这一块我在[权限隔离那篇](/blog/20260912---agentpermissionisolation/post)里写得比较细，这里不展开。

## 四、上下文工程：缓存命中率就是成本

Lee 认为上下文工程和 Harness 工程基本是一回事：尽量减少 Harness 占用的上下文，既为了效率和成本，也为了效果。

其中最重要的是提示缓存（prompt caching）。Agent 每加一条消息，基本上都是把整段对话重新发一遍给模型。如果前面的部分和上一次完全一样，这部分就能命中缓存，而缓存命中的 token 有很大的折扣。理想状态下，只有最底下新加的那条消息需要按原价付费。

下面这张图可以切换几种情况，看一个小改动会让多少内容失去缓存：

<PromptCache />

所以 Lee 说，**出现缓存未命中，基本上就是系统里的一个 bug。** 他举了一个例子：今年 1 月 OpenClaw 爆红，很多人在模型厂商的订阅套餐里用它。这是厂商没有见过的用法，Harness 也没有为它优化，于是出现了大量的缓存未命中。对一直在跑的 Agent 来说这是很严重的问题，后来做了很多修复才把缓存保住。

具体的做法有这几条：

- 工具定义、系统提示词在多次调用之间保持不变。
- 系统提示词分段，每段做哈希，按固定的顺序拼起来。这样做 A/B 测试、加一段新提示或者一个新工具时，不会打乱其他所有人的提示顺序。
- 预热缓存：用户打开聊天、开始打字的时候，服务器就提前把提示准备好，类似鼠标悬停在链接上时预取下一页。
- 输出很长时不塞进上下文，而是写进文件，需要时再读；截图这类昂贵的工作交给子 Agent。Lee 把这叫作持续地「修剪花园」，既为了成本，也为了模型的召回和表现。

### 趁缓存还热的时候压缩

要长时间工作，就一定要擅长压缩（compaction）。上下文窗口总会被填满，总要做摘要，而所有的压缩都是有损的。怎么压缩才不丢掉重要的细节，Lee 开玩笑说光这个问题就够写好几篇博士论文。

他们有一个很巧的做法：用户聊了十几万 token 之后走开了，模型厂商那边的缓存还会再热一段时间，也许 10 分钟，也许 60 分钟。就趁这段时间立刻做压缩，因为此时处理这段长对话最便宜。用户 30 分钟后回来，直接从摘要继续，之后追加的消息也更便宜。

### 记忆分四层

记忆按「此刻是否相关」分成四层：

1. **核心事实**：每次都要带上的用户信息，比如「永远用小写」，否则某条消息里突然出现大写，会显得很奇怪。哪些事实值得一直保留，需要一套类似垃圾回收的机制来决定。
2. **按日期组织的日志**：过去的对话和工作记录。你问「我上周做了什么」，它自己去查。
3. **临时笔记**：当前正在做的小事，只在接下来半小时到一小时内有用，之后自然消失。
4. **其他一切都放进文件**：模型很擅长跑命令，需要的时候自己去查，而且查得很好。

## 五、训练飞轮：每个 bug 都变成一条 eval

讲座的后半段讲了 Grok Bot 团队怎么让产品和模型一起变好。这是一个两层的飞轮。

内循环是产品团队每天在做的事：模型出了错，比如调用了不该调用的工具，就把它变成一条评测（eval），然后去修 Harness、改提示词，或者发现是推理侧的问题；在评测里确认修好了，再发布。

外循环是每个月或每几个月训练一次新模型：从这些 bug 和失败里学习，在评测上提升团队在意的能力，再放回产品里验证。新模型带来能力上的跃迁，产品就可以用新的方式去用它。推理也按角色来调：你在聊的主 Agent 要低延迟，交给帮手的长任务则不在乎多跑两分钟。

有一类问题他们还在摸索：bot 在群聊里应该怎么表现。这方面的训练数据很少，而几个 bot 在同一个群里互相对话，已经出过不少问题。

Lee 也列了几个还没解决的问题。Agent 要连续跑一个月，模型却每个月都在发新版本，月级别的 Agent 怎么评测？记忆和压缩的算法还有很多可以做。Harness 怎么做到足够安全，不被坏人接管。什么时候该保持安静、什么时候该打扰用户，分寸也还没把握好：「我看你昨天缺课了，我录了音，也做了笔记」，这句话可能很有用，也可能有点烦。

这里要注意一点：外循环只有训练模型的团队能做。对大多数做 Agent 产品的人来说，我们只能做内循环，模型的换代是一个外部变量。这一点后面会很重要。

## 六、删掉产品

讲完训练飞轮，Lee 讲到了这条原则。他说这是他们在 Cursor、现在在 SpaceX 都遵守的一条原则：delete the product。意思是你要真正接受一个假设：今天的模型，是它们有史以来最差的（"the models today are the worst they'll ever be"）。所以半年之后，你可能要把整个 UI 重做一遍。比较好的策略是为下一代模型而建：尽可能少建，只做一个非常简单的接口，让模型替你去思考和行动。

我把它拆成三层意思：

- **心态**：你今天看到的每一个缺陷，不会调工具、会迷路、会遗忘、上下文不够，都应该默认是暂时的。
- **后果**：产品形态的保质期大概只有半年。Lee 自己也说，这场讲座如果放在半年前或一年前讲，内容会很不一样。
- **做法**：少建。给一个极简的接口，比如「发消息」，把思考和行动交给模型，不要用 UI 和流程去替模型做决定。

回头看前面的架构，几乎每一个设计都是这条原则的结果：界面就是发短信；客户端和服务器之间只有一个工具；工具只给名字；重活交给子 Agent，主 Agent 保持稀疏。Lee 在 X 上介绍 Grok Bot 时还提到，它没有模型选择器，也不流式显示回复。他的总结是 "The best UI is none at all"，Grok Bot 能做成现在这样，"primarily because of everything we didn't have to build"（[帖子](https://x.com/leerob/status/2089169319099777364)）。

### 补偿层和承载层

不过「删掉产品」很容易被误读成：产品做得越少越好。我不这么理解。

我会把一个 Agent 产品拆成两层。一层是**补偿层**：因为模型还不够好，才替它做的那些事，包括替它做判断的流程和按钮、意图路由、一长串规则、手写的检索、为某一类任务专门做的小工具。另一层是**承载层**：不管模型多强都需要的东西，包括数据、权限、集成、评测、分发和成本。

「删掉产品」删的是补偿层。补偿层要尽量薄，随时可以扔掉；承载层不但不能删，还要持续加厚。

补偿层的价值会随着模型变强先升后降：

模型弱的时候，补偿层让产品能用；模型追上来之后，它就没用了；再往后，它会变成负担：限制模型、和模型的判断冲突、占用上下文，还要人一直维护。难的是交叉点在哪里，事先很难知道。

## 七、为什么补偿层留着反而有害

如果补偿层只是变得没用，留着也无所谓。问题在于它会主动拖累一个更强的模型。原因主要有四个。

**第一，它写死的是一个已经过期的假设。** 每一个专用工具、每一条预过滤、每一段手写的检索，背后都有一个「模型做不到 X」的假设。Vercel 在回顾他们的数据 Agent d0 时写道："We were doing the model's thinking for it." 他们原来有 17 个专用工具，负责查 schema、校验、错误恢复、规划，后来删到只剩两个：一个沙箱里的 bash，一个执行 SQL 的工具。结果是这样的：

<D0Bars />

这个结果有一个前提，Vercel 自己也写得很清楚：他们的语义层本来就是一份很好的文档。数据层如果一团乱，把文件系统交给模型也救不了，只会更快地得到错误的查询。

**第二，多余的约束会伤害强模型。** Anthropic 的 Thariq 介绍他们删掉 Claude Code 八成以上系统提示时（[帖子](https://x.com/trq212/status/2080710971228918066)），列了几种典型的伤害：系统提示、skills 和用户请求里同时出现互相打架的指令，模型得先花力气去调和；给的示例反而把模型限制在一个固定的范围里；为了防止最坏情况写的强规则，换到另一类任务上就是错的。Every 的 Dan Shipper 在 Opus 5 发布当天也遇到了同样的事：为旧模型攒下的 skills 和新模型配合得很差，他们把 skills 全删了从头开始，Opus 5 的表现明显变好（[帖子](https://x.com/danshipper/status/2080700057892815114)）。

**第三，每次换模型都要重新校准。** Vercel 的原话是 "every model update meant re-calibrating our constraints"，他们花在维护脚手架上的时间，比改进 Agent 本身还多。Box 的 Aaron Levie 也说过，做 Agent 意味着接受未来几年要写大量会被扔掉的代码（[帖子](https://x.com/levie/status/1997152030507556962)）。补偿层有维护成本，而且这个成本跟着模型的发布节奏走。

**第四，界面会把用户留在旧的用法里。** Amp 的 Thorsten Ball 说得很直接："If a feature teaches you to start using agents the old way, we need to remove it."（[帖子](https://x.com/thorstenball/status/2052047198796337562)）Lee 发布 Cursor 3 时也承认，Cursor 2 里频繁挪动 UI 让用户很烦，但 Agent 接手的工作越来越多，已经装不进 IDE 的界面了。

这四点之外，还有一个人性上的原因。前 OpenAI 研究员 Hyung Won Chung 在 Stanford CS25 讲过，结构是因为算力不够才加的，之后要删掉；但大家擅长加结构，却不擅长删（[CS25 视频](https://www.youtube.com/watch?v=orDKvo8h71o)）。

「删掉产品」也不是 Lee 一个人的发明。往前可以追到 Rich Sutton 2019 年的 [The Bitter Lesson](http://www.incompleteideas.net/IncIdeas/BitterLesson.html)：长期来看，能利用算力的通用方法最终胜出，人加进去的知识短期有帮助，长期会变成阻碍。落到 Agent 产品上，过去两年各家陆续说过同样的话：Anthropic 的 [Building effective agents](https://www.anthropic.com/engineering/building-effective-agents) 建议从最简单的方案开始，只在能证明有效时才增加复杂度；Manus 一年里把框架重写了四次，说要做随潮水上升的船，而不是插在海底的柱子（[博客](https://manus.im/blog/Context-Engineering-for-AI-Agents-Lessons-from-Building-Manus)）；Boris Cherny 在 YC 的节目里说，Anthropic 是为六个月之后的模型而建（[帖子](https://x.com/ycombinator/status/2026787362693591205)）。

这些说法里，最能直接拿来用的是 Manus 的 Peak Ji 给的一个指标（[帖子](https://x.com/peakji/status/1948060791636410404)）：在同一个模型家族里，把弱模型换成强模型，你的架构能多拿到多少提升？差值越大，说明架构越能跟着模型一起变好；差值很小，说明补偿层在拖后腿。另外，换成不同家族的模型，表现的差距要尽量小，这说明你没有过度适配某一个模型。

## 八、哪些东西不能删，反而要加厚

如果只读到这里，很容易得出「什么都别做，等下一代模型」的结论，这也是这条原则最容易被误用的地方。Lee 自己在发布 Cursor 3 时就补了一句：删掉产品，不等于把所有好的想法都扔掉，让老用户能顺利适应同样很重要（[帖子](https://x.com/leerob/status/2039771986180649010)）。

我把一个 Agent 产品分成四层，不能删的东西都在最底下那一层：

<ProductLayers />

逐个说一下承载层里的东西。

**评测。** 评测是唯一能告诉你「这块可以删了」的东西。Claude Code 敢删掉八成的系统提示，是因为有编码评测证明「没有可测量的损失」。没有评测，删就是在赌。讲座里的内循环也是这个道理：每个 bug 先变成一条 eval，修完先在 eval 里验证。

**可靠性。** 模型会做，不等于每次都做对。Cognition 曾经想让 Sonnet 4.5 自己写笔记，替代他们自建的记忆系统，结果效果下降了，因为模型不知道自己不知道什么（[博客](https://cognition.com/blog/devin-sonnet-4-5-lessons-and-challenges)）。Lee 那条「90% 都在用 shell 做同一件事，就做个专用工具」的经验也是同一类判断：有些结构是为了稳定和可审查，不是为了补偿模型。

**权限和不可逆操作。** 发邮件之前先确认草稿，每条命令先过一遍审查，不可信的输入不能当指令。这些不是在补偿模型，而是在划清责任的边界，模型再强也要有。

**成本和缓存。** Manus 把 KV-cache 命中率看作生产环境里 Agent 最重要的单一指标，缓存和不缓存的价格能差十倍左右。第四节那一整套缓存工程，不会因为模型变强而过时，反而会随着用量增加变得更重要。

**让人能快速核对的界面。** Karpathy 讲过，diff 视图的价值在于借用人的视觉系统，缩短核对的时间（[帖子](https://x.com/karpathy/status/1930326685918081077)）。Lee 说 Cursor 删到最后，编辑器还剩 2% 删不掉，那一部分就是留给人核对和微调的。Hamel Husain 夸 Devin 现在会给出视频作为工作的证明（[帖子](https://x.com/HamelHusain/status/2050363550020055290)），也是同一类东西。

**可读的数据。** 前面 Vercel 的例子已经说明了：删工具之所以有效，是因为投入转移到了文档、命名和数据结构上。

讲座最后，Lee 列了一串新的基础构件：持久化工作流、沙箱、云端电脑、记忆、技能、连接器、语音、支付、身份、评测、可观测性。他说每一块背后都有大量的风投，各有二十来家创业公司在做。把这张清单和上面对照一下会发现，它们几乎全落在承载层里。

还有一个反对的声音值得认真对待：Anthropic 可以为六个月之后的模型而建，是因为他们看得到模型的路线图，大多数创业团队看不到（[帖子](https://x.com/sikt_int/status/2027020232460570874)）。我同意这一点，[上一篇](/blog/20260912---codexharnessevolution/post)里我也写过：模型厂商可以选择「这个先不做，等下一代模型」，我们不行，用户今天就有事情要完成。所以补丁今天该打还是要打。「删掉产品」的意思不是事前不建，而是事后不留恋。Aaron Levie 说得更坦白：你得接受自己做了一些会被扔掉的工作（[帖子](https://x.com/levie/status/2040999580188160023)）。

## 九、我自己的做法

我在粉丝群里有一个 QQ bot，群里大概 800 人。讲座里有一句话我印象很深：bot 在群聊里怎么表现，几乎没有训练数据，这是一个新出现的问题。而一个好的常驻 Agent "knows when to be quiet"。这正是群聊 bot 最难的地方。

按「补偿层要薄、承载层要厚」的思路回头看这个 bot，我会这样分：

- **入口统一成消息。** @ 它、回复它、私聊、定时任务、群事件，都转成同一种消息，进同一个 Agent loop。不再为每种入口写一套逻辑，也不用关键词和指令菜单去做意图路由。
- **要不要说话交给模型判断，但外面加确定性的上限。** 它可以选择不回，或者只回一个表情；但每分钟最多发几条、对同一个人的冷却时间、深夜静默，这些由程序来管。
- **人设写短。** 一段简短的人设描述，加上少量典型的例子；群里的梗和常用说法放进文件，需要的时候再查，而不是在提示词里堆几十条规则和示例。
- **记忆文件化、分层。** 群规和核心事实常驻；成员的情况和按日期的记录按需去查；临时笔记自动过期。
- **治理要加厚。** 管理操作走白名单和二次确认，群消息全部当作不可信输入，所有操作都留记录。这部分在[权限隔离那篇](/blog/20260912---agentpermissionisolation/post)里已经展开过。

放到更一般的 Agent 产品上，我会坚持这几条：

1. **从最强的模型、最短的提示、最少的工具开始。** 先跑通，再按真实的失败往上加东西。
2. **每块补偿层都写清楚过期条件。** 它在补偿模型的哪一项短板，哪一条 eval 能证明它不再需要。这和我在上一篇里说的「加补丁的时候，同时留下一个可以重跑的失败案例」是同一件事。
3. **新模型发布时，裸跑一遍。** 同一套 eval，一遍用完整的配置，一遍只留人设和最基础的工具。裸跑不输的那些规则和 skills，直接删掉。顺便用 Peak Ji 的指标看一下，强模型带来的提升有多大。
4. **工具少而基础。** 发消息、搜索、读写文件、shell；某一类调用占了大头，再把它做成专用工具。
5. **把力气花在承载层。** 对我的 bot 来说，就是群里积累下来的知识和成员记忆、对 QQ 生态的接入和治理，以及一套从真实群聊里整理出来的评测集。这些都是下一代模型冲不掉的。

## 最后

回头看，讲座里的每一个技巧，SendToUser、持久化工作流、升级阶梯、缓存预热、趁热压缩、文件化的记忆，做的都是同一件事：让模型以外的部分尽量薄、尽量稳，这样模型变强的时候，整个产品会自动跟着变好。

「删掉产品」提醒的是另一半：分清楚哪些东西是在补偿今天的模型，哪些是下一代模型也冲不掉的。前者随时准备删，后者每天都在加厚。

Lee 最后给工程师的几条建议里，有一条我很认同：自己动手搭一个。把这堂课的内容用到你自己写过的那个最小 Harness 上：搬到服务器上，加一个队列，接一台能做快照的沙箱，用文件做记忆，每个 bug 写成一条 eval。亲手搭一遍，比读十篇文章更能理解这些部件是怎么配合的。
