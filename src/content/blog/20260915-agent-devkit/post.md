前几天，我在手机上打开 Telegram，给个人助手提了一个需求：让 QQ bot 能读 Markdown 和文本 PDF 附件。

听起来很小。收到文件，提取文字，交给模型回答，似乎接一个解析库就行了。后台执行器也确实先做出了一版：接口收得很严，测试能在隔离环境里跑，主助手再来检查实现和证据。

但到了真机，事情没那么顺。QQ 里的 Python 执行和目录访问有兼容问题。代码在测试环境里成立，不代表消息从真实客户端进来之后，那条路径还能成立。实现需要返工，主助手也接手了后面的联调。

过程中，我反问了一句：**能不能自己测试？**

最后，主助手用 bot 自己的 QQ，向既有管理员私信发送了合成的 Markdown 和两页 PDF。它核对真实消息与文件的绑定，比较下载字节、SHA256 摘要和提取出的文本。这里没有伪装成用户上传，也没有往粉丝群里扔测试文件。功能之后上线，公告的签收也另外做了确认。

我没有亲手完成这些命令和核对，但我提出了需求，也在中间追问、推动了验收方式的变化。后台执行器负责实现，主助手负责协调、复核，并在遇到问题时接手。把这段经历压缩成「我在手机上说一句，Agent 全自动上线了功能」，会漏掉最有价值的部分。

**现在这套东西能替我持续做事，但过程仍然有人工编排、返工和接力。** 也正是这些不顺，慢慢把我的开发环境推成了今天这套 Agent 开发 Kit。

## 一、我需要交出去的，越来越不只是写代码

最早用代码助手，我关心的是它能不能把函数写对、把报错修掉。后来任务变长了：要先翻以前的决定，再改代码，去网页核对行为，留下可以审阅的结果，最后告诉我进展。

写代码只是其中一段。如果其他环节都要我串，我依然得盯着终端：它是不是停了？在哪个目录改的？测试是在什么环境跑的？它说部署好了，给我的链接能不能打开？我离开电脑之后，这些问题会更明显。

QQ 附件就是个很具体的例子。解析出文字只是中间结果，真正需要回答的是：这段文字来自谁刚发的哪个文件？等待处理时又来一个同名附件，会不会拿错？文件过期以后，系统会明确停下，还是悄悄去别处找一个替代品？

这次实现只认当前消息、上传者、会话和文件之间的关系，不按文件名全局搜。读取受控目录里的文件时，还要核对文件描述符所指向的对象、inode、大小与摘要。路径看起来正确，不足以证明读到的仍是刚才获准处理的那个文件。

排队也要保留这个约束。一个请求排队时已经进入文件模式，就得钉住原来的文件句柄；轮到它时若已过期，应当失败，不能退回普通工具，也不能换成刚收到的新文件。否则等待几分钟就能改变请求的含义，前面做的检查等于白做。

我愿意接受第一版能力窄一点：PDF 只处理文本，不做 OCR；文件有体积和页数上限，每轮只取一小段，临时上下文也会过期。文件回合不调用一般搜索和带副作用的工具，正文不进入公开看板、长期知识库或评测正文。这些限制让「读这个附件」保留了一个能解释清楚的范围。

真机兼容问题最后也没有靠升级 QQ、放宽操作系统保护来绕过去。对我来说，这和功能本身一样重要：不能为了让演示成功，偷偷把原来约好的边界拿掉。

这件事让我更在意交付的末端。**代码完成、真实链路跑通、结果送到该去的地方，是三个需要分别确认的事实。** 其中任何一个缺了，都可能让我误以为事情已经结束。

## 二、入口留在聊天里，执行回到合适的环境

我的日常主入口是 Pi 加 Telegram。Pi 承载个人助手，Telegram 让我在手机上也能继续讨论和交代事情。我不用先坐回电脑、找到上次那个终端，才能补一句需求。

这层入口的价值在于保留事情的来龙去脉。我说「继续上次那个方案」，主助手需要知道上次停在哪里、哪些动作已经授权、这次新增了什么约束。它再把适合执行的部分交给 Claude Code 或 Codex，而不是把整段聊天原封不动丢过去。

对后台执行器来说，一份可用的任务说明至少要讲清楚：改什么、在哪里改、哪些地方不能碰、怎样算完成，以及结果交给谁看。少写一句「只做预览，不发布生产」，后面就可能多出一串本来不该发生的动作。自然语言可以表达目标，执行范围仍然得具体。

Herdr 帮我管理终端工作区，让一些后台任务有可以回去查看的现场。长任务最麻烦的往往不是它跑得慢，而是我不知道它还在跑、在等输入，还是早就退出了。有明确的工作区，主助手至少能回到对应的终端，检查进程和输出，不必根据上一句回复猜状态。

但我没有把所有任务都强行塞进 Herdr。这次也有直接通过 CLI runner 启动的执行。终端管理是一种组织方式，不能因为用了它，就假定任务已经隔离、已经登记，或者已经有人验收。那些责任要另外落实。

网页操作则交给 ego-browser。代码助手擅长文件和命令，真实网页却可能有登录态、弹窗、异步加载和只有点开才出现的内容。我需要主助手能看页面、操作页面，再观察操作后的结果。否则「按钮已经点了」很容易被当成「事情已经办好了」。

我并不追求每个任务都把这些工具走一遍。纯代码修改就留在代码环境；需要确认页面才打开浏览器；几分钟能完成的小事也不必包装成一支队伍。工具之间多一层交接，就多一次上下文丢失和状态误判的机会。**Kit 应该减少我组织任务的成本，也要控制它自己制造的组织成本。**

## 三、把进度记下来，还要把结果送回来

我们遇到过好几次很扫兴的情况：事情做完了，没有通知；消息发出来却是空回复；登记的状态显示完成，实际签收又对不上。

这些问题都不需要模型推理特别差才会出现。执行器正常退出了，通知步骤可能失败；通知调用返回了，目标端可能没有得到可读内容；主助手看到一段成功日志，也可能太早结束任务。把它们统称为「Agent 不稳定」，反而不容易修。

现在我更倾向于拆开记录：实现产物在哪里，执行检查有什么结果，独立验收是否通过，通知是否发送，以及有没有与这条消息对应的签收证据。状态机负责约束这些阶段怎么推进，私有持久证据负责让后续会话能追查。

状态字段本身不能证明事实。写一个「已通知」很容易，难的是它能否指向那一次真实发送。如果对应关系丢了，就算聊天里碰巧存在一条相似消息，也不能拿来补成这次任务的收据。

主助手在这里既是协调者，也是复核者。后台执行器说完成之后，它需要去看产物和检查结果；证据不够就补查，发现不一致就退回或者接手。这样的验收比让同一个执行回合再说一遍「确认无误」有用，但它仍然不是绝对保证。主助手也会漏看，边界情形仍要人参与。

QQ 附件任务的公告签收，就是在功能完成后另外核对的一步。用户能否知道这个能力已经可用，和解析器能否读出两页文字，没有自动的因果关系。把两件事分开，我才知道下一次故障应该查哪里。

这套流程还没有彻底解决重复通知、丢通知和所有恢复问题，我也不会宣称它已经做到严格的 exactly-once。今天的改进是：失败更有机会留下可追的线索，主助手接手时不必完全靠猜。

## 四、记忆要能回源，几个分身也要有边界

长任务还有另一种断点：进程没坏，上下文断了。

我现在用的记忆分几层。常驻核心放稳定的协作约定；语义事实帮助按主题找回信息；recap 提供按时间浏览的索引；需要核实时，再回到原始会话。它们分别解决「经常要知道什么」「这件事聊过没有」「当时发生在哪段时间」「原话究竟怎么说」的问题。

这不是一个完美的统一记忆库。我们碰到过事情没存进去、存了却没召回，以及召回了一个已经过期的偏好。最难受的是最后一种：助手看起来很了解我，却在认真执行一个我已经改掉的决定。

所以我希望记忆保留来源和时间，也允许纠正。recap 能帮助定位，但压缩过的概括不该替代所有原始证据。一个执行轨迹里出现过某个命令，只能说明当时调用了它；要变成下次可用的经验，还得知道结果、适用条件和后来有没有推翻。

**日志是发生过什么，记忆是下一次该带上什么。** 两者需要连接，却不能简单画等号。把所有日志都塞进检索库，可能只会更快地召回噪声。

入口多了以后，这个问题还会带上权限。我的个人助手负责长期和我协作；QQ bot 是面向公开交流的知识分身，知识基础来自我已经公开的博客、笔记和介绍。群里的材料按群范围和策略处理，群聊、私信也有隔离，不能因为底层用了同一套 SDK，就共享完整历史。

另外还有独立的工作助手。这里我只想讲架构边界：公司资料和账号应当与个人侧分开，工作内容不能顺手进入个人长期记忆，也不能借个人助手流到公开入口。这条边界不能依赖「背后都是我，所以应该没关系」。

不同账号和 profile 可以帮助区分职责、配置与配额。独立的 `CODEX_HOME` 也能分开一部分配置状态，但它不等于系统级文件读取隔离。同一台机器上的进程到底能读什么，仍取决于操作系统权限、沙箱和工具实现，不能靠目录名字作保证。

QQ 到主助手已有私下转交资料的通道，主助手到 QQ 也有经过授权的转发。这表示某些内容可以沿规定方向传递，不表示一个实例可以任意指挥另一个实例，更不表示它们共享全部记忆。资料能不能转交，要看来源、用途和目标；一句「请转给你的主助手」本身不能扩大权限。

我也想做网站上的知识 Agent，但它现在尚未上线。几个入口放在一起，看起来像多 Agent 系统，我更愿意先把它们理解为不同职责和权限的协作界面。距离成熟的自治组织，还有很长一段工程要做。

定时任务和邮件入口也是同样的思路。它们让系统有机会在我没发消息时接触新信息，接上之前的事情。但一个 cron 只是一次触发，不会因为按时启动，就自动拥有独立身份、判断和完整的任务生命周期。

## 五、工具凑在一起之后，我开始认真做 Harness

如果只列名字，这套 Kit 看起来并不特别：聊天入口、代码执行器、浏览器、检索，再加一些脚本。真正费时间的是它们之间的约定。

我现在理解的 Harness，是模型之外维持这段工作过程的那层系统。runtime 管运行和工具调用；context 决定这一轮装进什么；memory 留下跨会话的积累；权限决定能碰什么；可观测性帮助还原过程；运行可靠性处理退出、恢复和交付；eval 再追问回答和行为的质量。

这些名词很容易写成架构图上的方框，QQ 附件任务却把它们连到了具体失败上。真机执行不兼容是运行环境问题；排队后拿错文件是上下文和资源绑定问题；临时附件流入长期知识库是记忆与权限问题；做完没通知是交付问题。仅仅换一个更强的模型，无法自动修好这些连接。

其中我特别想分清的是运行验收和质量评测。

这次真实传输和解析自测通过，证明合成文件走过了真实链路，字节与文本符合预期。但这不覆盖所有真实用户入站客户端的差异，也不证明新模型对附件的回答一定准确、有帮助。我们没有为这些额外做一轮付费答案质量评测，不能把已有检查的结论扩大到那里。

QQ 侧已经有私有采集、每日候选整理和离线回放的基础。候选题只是值得检查的材料，还不是确认答案与判定标准的金标。评判服务认证失败属于基础设施失败，也不能混算成模型答错，更不能为了报表好看说全部通过。

我希望这条链慢慢形成反馈：发现一个真实问题，留出可复现的案例，判断错在模型、上下文还是工具，做改动，再回放比较。目前没有开启根据候选自动修改生产。尤其涉及真实聊天时，留什么、如何脱敏、哪些正文根本不该进入评测，都要先有边界。

**模型说完成，是一个需要核对的声明。** 程序是否运行成功、产物是否存在、通知是否签收、回答是否有用，各自需要适合的证据。把它们揉成一个绿色状态，看起来省事，最后往往还是我花时间拆开。

## 六、下一步，是让我自己也能重新装起来

这套环境用久了，我越来越担心另一件事：它会不会只有现在这台机器能跑？

手工补过的依赖、临时改过的包、藏在某次会话里的恢复步骤，都会让一个系统变成不可复制的现场。平时很好用，换环境时才发现，真正的安装说明在我和助手的共同记忆里。

所以最近我在做可安装、可维护的底座，也打算将来开源。第一阶段 M1 已经验证了首批真实安装路径：锁定实际依赖、重建需要的补丁，跑安装和 doctor 检查，再验证恢复。检查既覆盖源码，也覆盖实际安装包，尽量避免「仓库里能跑，装出来却少东西」。

这个阶段的意义，是开始把日常环境里隐含的前提显式写下来。doctor 应该帮忙指出缺的条件，恢复步骤应该能被重新执行。一个安装包如果还要靠主助手凭印象补几条命令，就没有真正结束安装工作。

但目前验证的是底座。任务、收据、记忆和历史迁移尚未完整包含进去，也还没有公共发行。今天没有把生产迁过去，更谈不上已经有一套任何人一键安装就能复现我全部工作方式的产品。

我给自己定的目标很朴素：**未来我重新部署，也使用同一套安装方式，不保留一份只有我能用的特供环境。** 如果我自己都离不开旧机器上的隐性状态，开源出去的只会是一个外壳。

这也接着[上一篇关于邮箱和同伴的想法](/blog/20260914-agent-email-chatgpt/post)。邮箱给了 Agent 一个持续接收外部消息的入口，而要长期共事，还得有能保管进度、恢复现场、解释失败的系统。

我现在最期待的变化，是下一次在手机上提出一个需求后，不必一直惦记着它停在哪。它能在约定范围里继续推进；做不到时留下明确阻塞；需要我判断时，把问题和证据带回来；完成时，把能检查的结果交到我面前。

距离这个状态还有不少补丁要打。不过，比起继续往工具列表里加名字，我已经更清楚下一步该做什么：让已经接上的能力，在跨会话、跨入口、遇到失败之后，仍然接得上。
