前几天，我在手机上打开 Telegram，给个人助手提了一个需求：让 QQ bot 能读 Markdown 和文本 PDF 附件。

先交代一下这套系统里的三个角色，后面会反复出现。**我**，在手机上提需求、追问。**主助手**，跑在 Pi 上的个人助手，通过 Telegram 和我对话，负责理解需求、拆任务、协调和复核。**后台执行器**，Claude Code 或 Codex，接到任务说明后在代码环境里干活。

需求听起来很小：收到文件，提取文字，交给模型回答，接一个解析库就行。后台执行器也确实先做出了一版，接口收得很严，测试能在隔离环境里跑，主助手检查了实现和证据。按平时的标准，这就算做完了。

但到了真机，QQ 客户端里的 Python 执行和目录访问有兼容问题。代码在测试环境里成立，不代表消息从真实客户端进来之后，那条路径还能成立。实现要返工，主助手接手了后面的联调。

联调卡住的时候，我反问了一句：**能不能自己测试？**

最后，主助手用 bot 自己的 QQ 账号，向一位既有管理员私信发送了合成的 Markdown 和两页 PDF，核对真实消息与文件的绑定，比较下载字节、SHA256 摘要和提取出的文本。全部对上，功能上线。上线之后还有一步：要在群里发公告，公告发出去并且确认送达，这件事才算结束。这一步也是另外核对的。

把这段经历压缩成「我在手机上说一句，Agent 全自动上线了功能」，会漏掉最有价值的部分。我没有亲手敲任何命令，但我提了需求、在中间追问、推动验收方式从「测试通过」变成「真机自测」。执行器负责实现，主助手负责协调、复核，并在遇到问题时接手。

**现在这套东西能替我持续做事，但过程仍然有人工编排、返工和接力。** 这篇想讲的，就是这些不顺教会我的一件事，以及它怎么把我的开发环境推成了今天这套 Agent 开发 Kit。

## 一、一个功能，三个「做完了」

最早用代码助手，我关心的是它能不能把函数写对、把报错修掉。后来任务变长了：要先翻以前的决定，再改代码，去网页核对行为，留下可以审阅的结果，最后告诉我进展。写代码只是其中一段。

QQ 附件这次，「做完了」被说了三次，每次指的都不是同一件事：

- **代码完成。** 执行器交付了实现，隔离环境里测试通过。
- **真实链路跑通。** 一条消息从真实的 QQ 客户端进来，附件真的被读出来、回答真的发回去。第一版在这里断了。
- **结果送到该去的地方。** 功能可用了，用户也得知道它可用。公告发出去、确认签收，才算送达。解析器能读出两页文字，和群里的人知道这个能力上线了，中间没有自动的因果。

**这三件事需要分别确认。** 任何一件缺了，我都可能误以为事情已经结束，然后在几天后从一句「怎么还不能用」里发现它没有。

下面三节按这个顺序讲这次分别是怎么核对的。第五节再回头说 Kit 里的每个工具各管哪一段，第六节说它离「能重新装起来」还差什么。

## 二、代码完成：读的是不是刚才那个文件

「读这个附件」解析出文字只是中间结果。真正需要回答的是：这段文字来自谁刚发的哪个文件？等待处理时又来一个同名附件，会不会拿错？文件过期以后，系统会明确停下，还是悄悄去别处找一个替代品？

这次实现只认当前消息、上传者、会话和文件之间的绑定关系，不按文件名全局搜。读取受控目录里的文件时，还要核对文件描述符所指向的对象、inode、大小与摘要。原因很朴素：检查和读取是两个时刻，中间文件可能被替换或改名。路径看起来正确，不足以证明读到的仍是刚才获准处理的那个文件。

排队也要保留这个约束。一个请求排队时已经进入文件模式，就得钉住原来的文件句柄；轮到它时若已过期，应当失败，不能退回普通工具，也不能换成刚收到的新文件。否则等待几分钟就能改变请求的含义，前面做的检查等于白做。

我愿意接受第一版能力窄一点：PDF 只处理文本，不做 OCR；文件有体积和页数上限，每轮只取一小段，临时上下文也会过期。文件回合不调用一般搜索和带副作用的工具，正文不进入公开看板、长期知识库或评测正文。这些限制让「读这个附件」保留了一个能解释清楚的范围。

真机兼容问题最后也没有靠升级 QQ、放宽操作系统保护来绕过去。对我来说，这和功能本身一样重要：不能为了让演示成功，偷偷把原来约好的边界拿掉。

## 三、链路跑通：让它用自己的 QQ 去测

返工之前，验收方式是「测试在隔离环境里通过，主助手看过证据」。真机不兼容说明这个证据不够。我问出「能不能自己测试」之后，验收方式变了。

主助手用 bot 自己的 QQ 账号，向一位既有管理员私信发合成的 Markdown 和两页 PDF。文件从真实客户端进来，走的是用户会走的那条路。收到之后，它核对消息与文件的绑定，再比较三样东西：下载下来的字节、SHA256 摘要、提取出的文本。三样都和发出去的一致，才算这条链路跑通。

有两件事它没有做。没有伪装成普通用户上传，用的就是 bot 自己的身份，收件人也是知情的管理员。没有往粉丝群里扔测试文件，群里的人不应该看到我们的联调过程。

这里我想分清两件很容易混在一起的事：**运行验收**和**质量评测**。

这次自测证明的是：合成文件走过了真实链路，字节与文本符合预期。它不覆盖所有真实用户入站客户端的差异，也不证明模型对附件内容的回答一定准确、有帮助。我们没有为此额外做一轮付费的答案质量评测，所以也不能把「链路通了」的结论扩大到「回答是好的」。

质量这条线，QQ 侧已经有私有采集、每日候选整理和离线回放的基础。但候选题只是值得检查的材料，还不是确认答案与判定标准的金标。评判服务认证失败属于基础设施失败，不能混算成模型答错，更不能为了报表好看说全部通过。目前也没有开启根据候选自动修改生产。涉及真实聊天时，留什么、如何脱敏、哪些正文根本不该进入评测，都要先有边界。

我希望这条链慢慢形成反馈：发现一个真实问题，留出可复现的案例，判断错在模型、上下文还是工具，做改动，再回放比较。但那是下一步。

## 四、结果送达：状态字段不能证明事实

我们遇到过好几次很扫兴的情况：事情做完了，没有通知；消息发出来却是空回复；登记的状态显示完成，实际签收又对不上。

这些问题都不需要模型推理特别差才会出现。执行器正常退出了，通知步骤可能失败；通知调用返回了，目标端可能没有得到可读内容；主助手看到一段成功日志，也可能太早结束任务。把它们统称为「Agent 不稳定」，反而不容易修。

现在我把交付拆开记录，一条任务至少有这几个字段：实现产物在哪里，执行检查有什么结果，独立验收是否通过，通知是否发送，以及有没有与这条消息对应的签收证据。状态机负责约束这些阶段怎么推进，私有持久证据负责让后续会话能追查。

状态字段本身不能证明事实。写一个「已通知」很容易，难的是它能否指向那一次真实发送。如果对应关系丢了，就算聊天里碰巧存在一条相似消息，也不能拿来补成这次任务的收据。QQ 附件的公告签收，就是功能完成之后另外核对的这一步。

主助手在这里既是协调者，也是复核者。执行器说完成之后，它需要去看产物和检查结果；证据不够就补查，发现不一致就退回或者接手。这样的验收，比让同一个执行回合再说一遍「确认无误」有用。但它不是绝对保证，主助手也会漏看，边界情形仍要人参与。

这套流程还没有解决重复通知、丢通知和所有恢复问题，我也不会宣称它做到了 exactly-once。今天的改进是：失败更有机会留下可追的线索，主助手接手时不必完全靠猜。

## 五、Kit 里每个工具，各管哪一段

如果只列名字，这套 Kit 看起来并不特别：聊天入口、代码执行器、终端管理、浏览器、记忆，再加一些脚本。真正费时间的是它们之间的约定：每个工具管哪一段，边界在哪，交接时什么不能丢。

**Pi 加 Telegram，管入口和来龙去脉。** 我不用先坐回电脑、找到上次那个终端，才能补一句需求。我说「继续上次那个方案」，主助手需要知道上次停在哪里、哪些动作已经授权、这次新增了什么约束。它再把适合执行的部分交给执行器，而不是把整段聊天原封不动丢过去。一份可用的任务说明至少要讲清楚：改什么、在哪里改、哪些地方不能碰、怎样算完成，以及结果交给谁看。少写一句「只做预览，不发布生产」，后面就可能多出一串本来不该发生的动作。

**Claude Code 和 Codex，管执行。** 纯代码修改就留在这里，不必经过别的环节。

**Herdr，管现场。** 它帮我管理终端工作区，让后台任务有可以回去查看的地方。长任务最麻烦的往往不是跑得慢，而是我不知道它还在跑、在等输入，还是早就退出了。有明确的工作区，主助手至少能回到对应的终端，检查进程和输出，不必根据上一句回复猜状态。但我没有把所有任务都塞进 Herdr，这次也有直接通过 CLI runner 启动的执行。终端管理是一种组织方式，不能因为用了它，就假定任务已经隔离、已经登记、已经有人验收。

**ego-browser，管页面。** 代码助手擅长文件和命令，真实网页却有登录态、弹窗、异步加载和只有点开才出现的内容。主助手需要能看页面、操作页面，再观察操作后的结果。否则「按钮已经点了」很容易被当成「事情已经办好了」。

**记忆分四层，管跨会话的接续。** 常驻核心放稳定的协作约定；语义事实按主题找回信息；recap 提供按时间浏览的索引；需要核实时，再回到原始会话。它们分别回答「经常要知道什么」「这件事聊过没有」「当时发生在哪段时间」「原话究竟怎么说」。我们碰到过事情没存进去、存了却没召回、召回了一个已经过期的偏好。最难受的是最后一种：助手看起来很了解我，却在认真执行一个我已经改掉的决定。所以记忆要保留来源和时间，也允许纠正。**日志是发生过什么，记忆是下一次该带上什么。** 一个执行轨迹里出现过某个命令，只说明当时调用了它；要变成下次可用的经验，还得知道结果、适用条件和后来有没有推翻。把所有日志都塞进检索库，只会更快地召回噪声。

**权限和分身的边界，前面写过，这里不重复。** 个人助手、QQ bot、工作助手各有入口和权限；资料可以沿规定方向转交，但一句「请转给你的主助手」不能扩大权限；独立的 `CODEX_HOME` 分开的是配置状态，不是系统级文件隔离。这些在[上一篇讲权限隔离的文章](/blog/20260912---agentpermissionisolation/post)里逐条展开了。定时任务和邮件入口同理：它们让系统有机会在我没发消息时接触新信息，但一个 cron 只是一次触发，不会因为按时启动就自动拥有独立身份和完整的任务生命周期。

我并不追求每个任务都把这些工具走一遍。需要确认页面才打开浏览器，几分钟能完成的小事也不必包装成一支队伍。工具之间多一层交接，就多一次上下文丢失和状态误判的机会。**Kit 应该减少我组织任务的成本，也要控制它自己制造的组织成本。**

回到 QQ 附件这一次，可以把每个失败对应到 Harness 的某一层：真机执行不兼容是运行环境问题；排队后拿错文件是上下文和资源绑定问题；临时附件流入长期知识库是记忆与权限问题；做完没通知是交付问题。仅仅换一个更强的模型，无法自动修好这些连接。**模型说完成，是一个需要核对的声明。** 程序是否运行成功、产物是否存在、通知是否签收、回答是否有用，各自需要适合的证据。把它们揉成一个绿色状态，看起来省事，最后往往还是我花时间拆开。

## 六、能重新装起来，才算 Kit

这套环境用久了，我越来越担心另一件事：它会不会只有现在这台机器能跑？

手工补过的依赖、临时改过的包、藏在某次会话里的恢复步骤，都会让一个系统变成不可复制的现场。平时很好用，换环境时才发现，真正的安装说明在我和助手的共同记忆里。

所以最近我在做可安装、可维护的底座，也打算将来开源。第一阶段 M1 已经验证了首批真实安装路径：锁定实际依赖，重建需要的补丁，跑安装和 doctor 检查，再验证恢复。检查既覆盖源码，也覆盖实际安装包，尽量避免「仓库里能跑，装出来却少东西」。

这个阶段的意义，是把日常环境里隐含的前提显式写下来。doctor 应该能指出缺的条件，恢复步骤应该能被重新执行。一个安装包如果还要靠主助手凭印象补几条命令，就没有真正结束安装工作。

边界也说清楚：目前验证的是底座。任务、收据、记忆和历史迁移尚未完整包含进去，也还没有公共发行。生产环境还没有迁过去，更谈不上一套任何人一键安装就能复现我全部工作方式的产品。

我给自己定的目标很朴素：**未来我重新部署，也使用同一套安装方式，不保留一份只有我能用的特供环境。** 如果我自己都离不开旧机器上的隐性状态，开源出去的只会是一个外壳。

这也接着[上一篇关于邮箱和同伴的想法](/blog/20260914-agent-email-chatgpt/post)。邮箱给了 Agent 一个持续接收外部消息的入口；要长期共事，还得有能保管进度、恢复现场、解释失败的系统。

我最期待的变化，是下一次在手机上提出一个需求后，不必一直惦记着它停在哪。它能在约定范围里继续推进；做不到时留下明确阻塞；需要我判断时，把问题和证据带回来；完成时，把能检查的结果交到我面前。

距离这个状态还有不少补丁要打。不过，比起继续往工具列表里加名字，我已经更清楚下一步该做什么：让已经接上的能力，在跨会话、跨入口、遇到失败之后，仍然接得上。
