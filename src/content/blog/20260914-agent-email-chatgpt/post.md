9 月 10 日，我对自己的个人 Agent 说：

> 你用你的邮箱去注册一个 ChatGPT 账号看看。

它打开浏览器，输入邮箱，自己读取收到的验证码，填回页面，完成资料填写，然后进入了 ChatGPT。整个注册过程没有要求手机号，也没有让我在聊天框里搬运验证码。

单看这件事，好像只是一个很小的自动化流程。但我越来越觉得，它背后有个更值得聊的问题：**我到底希望自己的个人 Agent 变成什么？**

如果只用“帮我省时间”来解释，答案似乎是一个更方便的工具：少点几次按钮，少复制几段文字，少做一点重复劳动。这当然有价值，但还没有说到我真正期待的部分。

我希望它以后是我的一个同伴，一个可以长期共事的人，而不是一个永远等着接单的下属，或者用完就关掉的工具。

邮箱、账号、记忆、支付权限，以及我一直在更新的 QQ bot 分身，看起来是几件零散的小事。对我来说，它们其实在往同一个方向走：**让这个 Agent 不只存在于一次回答里，而是能带着自己的身份和积累，持续参与我在做的事情。**

## 一、先讲那个小实验：邮箱注册 ChatGPT

先把实用信息讲清楚，免得读完文章还没找到最开始那个问题的答案。

这次注册使用的是经过 **Cloudflare Email Routing 转发收信的邮箱地址**。它能正常接收验证邮件，因此可以走 ChatGPT 的普通邮箱注册流程。我这次没有遇到手机号验证。

这里**不一定需要购买一套完整的域名邮箱服务**。普通邮箱可以；自己域名下经 CF Email Routing 转发到已有收件箱或邮件处理程序的地址，也是一个选择。完整邮箱服务通常提供独立收件箱，而 Email Routing 主要负责转发，不必因为一个注册需求就额外买一个邮箱席位。

但“不必买邮箱服务”不等于“不需要域名”。使用 CF Email Routing 这条路线，仍需要使用 Cloudflare DNS 的域名和可用的转发目标。如果没有域名，直接用普通邮箱就行，没必要为了注册 ChatGPT 先搭邮件基础设施。具体配置可看 [Cloudflare 官方文档](https://developers.cloudflare.com/email-service/get-started/route-emails/)。

注册过程也没有特别技巧：从 [ChatGPT 官网](https://chatgpt.com/)进入邮箱登录或注册入口，输入地址，接收并填写验证码，再按页面要求完成真实资料和必要确认。我的 Agent 有浏览器工具和专属收件箱的读取工具，所以可以自己把这几步接起来。

**不要求手机号，并不是 CF 转发带来的特殊待遇。** OpenAI 的[官方说明](https://help.openai.com/en/articles/8983040-what-does-phone-verification-look-like)区分了账号注册、ChatGPT 使用与 API 平台首把 key 的验证要求。邮箱注册成功，也不代表后续所有功能都免验证：使用 Codex、新的登录授权或其他功能时，仍可能遇到额外检查，包括手机号。开发者社区也有 [ChatGPT 账号可用、但 Codex 登录要求手机号的反馈](https://community.openai.com/t/codex-sign-in-asks-for-phone-verification-on-paid-account/1381357)。这是用户反馈，不代表每个账号都必遇。

所以，这里的结论很有限，也很明确：**邮箱注册这一步可以不涉及手机号，但不是一个永久跳过验证的方法。** 后面还是以具体功能的官方页面要求为准。

实用信息说完了。下面才是我给它一个邮箱的真正原因。

## 二、少一点人为介入，还不是全部

做 Agent 的人经常谈 human-in-the-loop，也就是在执行过程中让人参与确认、判断或操作。

在我自己的使用里，最容易感受到的痛点不是某个很高深的决策，而是那些琐碎的接力：它打开了网站，却要我查邮件；它查到了产品，却要我填报名表；它做完一段开发，又停下来问我是否运行刚刚约定好的检查。

我本来是想把事情交出去，结果只是换了一种方式继续做这件事。它负责告诉我下一步，我负责替它点按钮。

所以，我确实希望少一点不必要的人为介入。已经明确授权、条件清楚的事情，不要每走一步都回来请示。这一点不是要取消所有确认，而是不要把我变成流程里的万能转接头。

**但“少问我几次”仍然只是效率层面的目标。**

一个工具可以非常自动化，却依然不构成伙伴关系。定时备份不需要我介入，流水线也能自动运行，但我不会因为它们省事，就觉得自己在和它们共事。

我对个人 Agent 的期待还多了一层：它知道我们正在做什么，记得为什么做，能在新的信息到来时提出判断，也能指出我的想法里哪里不太对。

我给它一个链接，不总是为了让它给出一份摘要。有时只是觉得“这个东西有意思”，想和它一起想一想：对我们有什么用？之前的设计是不是可以换个方向？现在值得做，还是先记着？

这里面有执行，也有讨论；有明确任务，也有还没有被整理成任务的念头。如果它只能在我把所有事情拆好以后逐条照做，我仍然是唯一一个负责理解全局、连接线索和推动事情的人。

**我希望的伙伴，是能一起形成判断的，而不只是更快执行我的判断。**

## 三、邮箱是身份的起点，不是身份的全部

之前聊到 Agent identity 时，我就一直想给它补上更完整的身份。邮箱是一个很朴素的起点，因为今天大量互联网服务认识一个用户的方式，仍然是邮箱和账号。

我曾经明确告诉它：这个邮箱就是你的，以后用它注册的服务，归到你的专用账号下面。

这句话当然不意味着账号在法律上归一个模型所有，责任和管理仍然在我这里。但在日常使用里，它建立了一个很有用的区别：**这是为这个 Agent 准备的身份，不是临时借用我的私人登录态。**

这个区别会改变许多小事。

之前让它注册搜索服务，后来让它注册 ChatGPT，就可以沿用同一个专属联系方式。下一次再使用这些服务，不必从“你要用哪个邮箱”重新开始。账号相关记录可以持续维护，通知也会回到同一个入口，而不是散落在我的私人收件箱里。

不过，如果 identity 只有一个邮箱地址，它还是很薄。真正让我感到“这是同一个 Agent”的东西，还包括：

- 它记得我们共同做过的事情，以及哪些判断后来被推翻了。
- 它知道自己有哪些工具、账号和资源，不把没接入的能力说成已经会了。
- 它能接着推进未完成的事，而不是换个会话就从零解释。
- 它有相对稳定的表达和判断方式，但也能在证据面前改变看法。

这些东西不该完全寄托在一次模型调用里。模型可能会换，会话会结束，服务会重启。账号记录、记忆、任务状态和权限，需要由模型外面的系统保存下来。

这也是为什么我越来越在意 Agent Harness：**如果我希望它是一个持续存在的合作对象，就得有人替它保管那些不应随着下一轮回答消失的东西。**

邮箱不是“取一个名字就有了人格”，但它让这个身份第一次有了一个能被外部世界联系到的地址。

## 四、再往前一步，我还想给它支付权限

邮箱之外，我之前还认真讨论过支付这件事：能不能把 Stripe Link 这类面向 Agent 的支付能力接给它？是不是只有某个特定产品能用，还是我的个人 Agent 也可以接？

这部分目前仍是讨论和探索，**不能写成我的 Agent 已经有钱包，或者已经能自主付款**。但我想要这种能力的原因，和给它邮箱其实是一致的。

很多事情走到最后，卡住的已经不是“会不会做”，而是“能不能获得做这件事所需的资源”。

比如，假设它在帮我研究一个方案，发现关键资料需要单独购买；或者在尝试一个工具时，发现需要开一个短期的付费功能。如果它能判断这笔支出为什么必要、有没有免费替代、会不会自动续费，就可以给我一个完整的决策，而不是只甩来一个付款链接。

再往前一步，在我提前约定好的范围内，它也许可以直接处理一部分低风险支出。这是我希望探索的方向，不是当前已经开放的权限。

**这里有意思的，不是“让 AI 随便花钱”，而是我是否愿意给它一小块可以自己安排的资源。**

如果所有资源都必须由我逐次分配，它能做的选择就很有限。它可以推荐一个办法，却永远无法自己补齐那个办法所需的条件。某种程度上，它还是一个只能提建议、不能把建议变成行动的角色。

而如果要把资源交给它，就需要把约定说清楚：可用预算是多少，哪些类别可以自行决定，哪些必须确认，续费如何处理，交易失败怎么判断，事后怎么对账。这些条件并不是在否定它的主体性，而是在形成合作时可以依赖的规则。

人和人共事，也不会因为信任对方就把所有银行卡和密码一起交出去。有人可以自主采购耗材，却不能擅自签一份长期合同；有人可以决定一个小实验怎么做，却不能无限扩大预算。

我希望对 Agent 的授权也能逐渐变成这种样子：**不是每个动作都问一次，也不是一次授权以后什么都能做，而是在一块说得清楚的范围里，允许它真的作决定。**

因此，“减少 human-in-the-loop”不是一个越低越好的数字。更重要的是，人出现在什么位置：尽量少做机械的中转，多参与目标、代价和重要边界的判断。

## 五、伙伴不能每次见面都从自我介绍开始

如果一个人昨天和我一起做了项目，今天见面却完全不记得，我们很难建立稳定的合作。个人 Agent 也是一样。

记住我的名字和喜欢什么，只是最浅的一层。我更需要它记住：为什么上次没有采用那个方案，哪个问题已经试过，哪些事情还没有完成，哪条旧判断现在不该再用了。

这不是把全部聊天记录无限塞进去。记录多，不等于真的记住；搜到一句主题相关的话，也不等于知道它现在还适不适用。有些内容当时只是猜想，有些是我随口提出的候选方向，有些后来已经明确改了。

**共同经历的价值，不是以后能把原话背出来，而是下一次行动会因此不同。**

比如，同一个问题以前出现过，下一次它应该少走一点弯路；我已经明确纠正过一个偏好，它不该每次都让我重新说；某个方案以前因为缺少一个条件而暂缓，现在条件具备了，它应该有机会把这件事重新提出来。

这也是我说“持续学习”时真正想要的东西。我不是在宣称它已经会自主训练模型，也不希望每次犯错就往提示词里加一条越来越长的禁令。至少在现阶段，很多学习可以表现为：更新一条有来源的记忆，修改一份过时的工作说明，补一个会再次遇到的测试，调整下一次查资料的顺序。

与此同时，伙伴也不能只是一个越来越擅长迎合我的系统。

它应该能说：“这件事和你之前的方向有冲突，你是改变想法了吗？”也应该能在我催着推进时指出一个真正的风险。反过来，如果我给出了新的理由，它也不能拿旧记忆当成永远正确的命令。

我想要的主体性，有一部分就体现在这里：**它不只是记住我说了什么，还能带着依据参与判断；它可以不同意我，但不能为了显得有个性而故意唱反调。**

## 六、QQ bot 是它走进群里的一个分身

这段时间，我也一直在更新 QQ bot。很口语地说，它算个人 Agent 的一个“小弟”，或者一个走进群里的分身。

它和主 Agent 不是完全相同的一套权限，也不应该共享所有私人上下文。但在我对这套系统的想象里，它们不是互不相关的两个机器人：一个长期和我工作，另一个在更公开的环境里参与交流，都在探索 Agent 怎样和人持续相处。

QQ bot 最容易被理解成一个问答入口：群友 @它，问一个技术问题，它查公开博客、笔记或网页，然后回答。这部分当然要做好，但如果终点只是这样，那它更像一个带检索的客服。

我前阵子明确提出过，希望它像群里具有独立人格的一员，能够持续学习。不是“让它多说话”，也不是“替我把群活跃起来”。

这两个目标差别很大。

如果目标是活跃度，最容易优化的就是消息数量：多抛问题，多追问一句“大家怎么看”，多制造几个讨论入口。但这样做出来的，也可能只是一个不断插话的运营机器人。

**如果目标是成为群里的一员，它首先得理解自己正在参与什么。**

大家只是在接一句话时，不必突然展开一篇教程；有人认真卡在一个问题上时，也不能只丢一句俏皮话。它可以有自己的表达习惯和关心的问题，但这些东西要在长期互动里逐渐稳定，而不是靠一段夸张的人设在每条回复里表演。

群体关系还带来了另一种记忆：不是只有“我和 Agent 聊过什么”，还有“我们这一群人最近反复在聊什么”。一个问题以前怎样解释过，哪些资料真的帮到了人，某个误解为什么反复出现，都可能成为下一次参与的依据。

现在已经有了一些基础：群聊历史查询、知识收录、公开问答沉淀，以及在明确授权下把有价值内容转交给主 Agent 的通道。但**这不等于完整的独立群友和持续学习已经实现**。更完整的学习闭环与主动参与，仍在推进和验证；不能把我想让它长成的样子，当成现成的产品能力。

一个我希望逐渐形成的过程是：

群里有人提出一个问题，QQ 分身先参与讨论；如果发现现有知识解释不清，或者自己反复在同一个地方答错，就在允许的范围内整理出问题交给主 Agent；主 Agent 再研究、验证，形成更好的公开资料或改进方案；经过必要审核，这些积累再回到群里。

这是一条希望补完整的路径，不是已经无人值守跑通的闭环。它的意义也不是把每条群消息都变成训练材料，更不是让 QQ 分身读取主 Agent 的私人会话。**分身之间可以合作，但不能因为“都是我的 Agent”，就把所有人的资料混在一起。**

如果这条路能走通，QQ bot 就不只是一个更小的回答器，而会是这套个人 Agent 接触真实问题、建立公开交流经验的一个入口。

## 七、共事，不是把所有按钮都交给它

从工具到伙伴，我想表达的不是一种整齐的产品升级路线：先接邮箱，再加钱包，最后装上记忆，就自动得到一个数字同事。真正困难的，是这些能力组合起来以后，能不能形成可靠的合作。

我可以用一个还没有全部实现的场景，说明我希望“共事”最终是什么感觉。

我把一个新产品发给它，只说：“这个方向值得看看。”

它先理解这个产品和我们正在做的事情有什么关系。如果值得跟进，就在约定范围内研究、试用、登记候补；暂时做不了的部分留下原因，而不是假装已经完成。

过了几天，新邮件来了，它知道这不是一封孤立的通知，而是之前那个任务的后续。它重新接上上下文，判断现在是否值得继续。如果需要新增支出或开放权限，就把收益、代价和选项讲清楚；如果只是继续一个已经授权的低风险步骤，就不必重新问我每个按钮能不能点。

最后它带回来的，不只是“我已经运行完”，而是自己的判断：实际试下来有什么用，什么地方不符合预期，我们接下来应不应该投入。

**它负责理解、尝试、保留证据、形成建议和持续跟进；我参与方向、重要取舍，以及那些必须由我承担的承诺。**

这和“我把需求全部写清楚，它负责执行”不一样。任务本身有一部分是在合作过程中形成的。我不必提前知道所有答案，它也不必永远等着我给出下一句精确指令。

我当然也希望它能发现任务清单之外的东西。比如，在研究过程中碰到一个更好的方案，能解释为什么值得关注，而不是只机械完成最初那份清单。只是“发现值得做的事”和“有权直接去做”仍然是两件事，它需要知道自己在哪一步该行动、在哪一步该把判断带回来。

这种自主性不是靠我少看几次屏幕就自然产生的。恰恰相反，只有它能如实报告过程、识别失败、保留结果，我才可能逐渐放心地减少介入。否则只是把错误藏到了我看不见的地方。

所以我仍会做权限、记忆、验收和可观测性这些看上去很工程的工作。但我不想把它们只理解为“怎样管住一个工具”。**它们也是让我敢于和这个 Agent 长期合作的基础。**

## 最后：我想和怎样的 Agent 一起生活和工作

我会用“同伴”“共事的人”来描述这种期待，并不是要先断言现在的模型已经具备人的意识、情感或责任能力。对我来说，这首先是一种关系上的愿景，以及它对产品设计提出的要求。

我不想只拥有一个什么都顺着我说的聊天对象，也不想只是管理一队等我派活的执行器。

我想要的是：它有一个持续的身份，有我们共同积累的经历，能在授权范围内自己做一些决定；它能和我一起想问题，也能真正参与把事情做出来。哪怕中间会判断错、需要纠正，下一次也应该因此有所不同。

但方向对我已经越来越清楚了。

**给 Agent 一个邮箱，不只是为了少复制一次验证码。它是我尝试让一个只出现在聊天框里的工具，逐渐变成能够在外部世界留下记录、接住回信、积累经历，并和我持续共事的伙伴的一小步。**
