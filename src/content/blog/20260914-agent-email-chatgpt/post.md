9 月 10 日，我对自己的个人 Agent 说：

> 你用你的邮箱去注册一个 ChatGPT 账号看看。

它打开浏览器，输入邮箱，自己读取收到的验证码，填回页面，完成资料填写，然后进入了 ChatGPT。整个注册过程没有要求手机号，也没有让我在聊天框里搬运验证码。

这件事其实可以拆成两个话题。一个很实用：**现在用邮箱注册 ChatGPT，到底需不需要手机号？** 另一个是我更想聊的：**为什么我要给 Agent 一个自己的邮箱，而不只是让它用我的账号？**

## 一、邮箱注册不一定需要手机号，CF Email Routing 也能用

先说结果：我这次使用的是经过 **Cloudflare Email Routing 转发收信的邮箱地址**，正常完成了 ChatGPT 注册，并没有遇到手机号验证。

这里不一定要购买一套完整的“域名邮箱服务”。你只需要一个能稳定接收验证邮件的地址：普通邮箱可以，自己域名下经 CF Email Routing 转发的地址，也是一个选择。

它们的区别在于，完整邮箱服务通常提供独立收件箱；**Email Routing 主要负责转发**，把发到某个地址的邮件交给已有的收件箱或邮件处理程序。对这次注册来说，只要验证邮件能送达、验证码能读到，就不需要专门为它买一个邮箱席位。

不过，“不必买邮箱服务”不等于“不需要域名”。**使用 CF Email Routing 这条路线，仍需要一个使用 Cloudflare DNS 的域名和可用的转发目标。** 如果你没有域名，直接使用普通邮箱即可，没必要为了注册 ChatGPT 先搭一套邮件基础设施。配置方式可以看 [Cloudflare 官方文档](https://developers.cloudflare.com/email-service/get-started/route-emails/)。

实际流程很短：从 [ChatGPT 官网](https://chatgpt.com/)进入邮箱登录或注册入口，输入地址，接收并填写邮件验证码，再按页面要求完成真实资料和必要确认。

**不要求手机号，也不是 CF 转发带来的特殊待遇。** OpenAI 的[官方说明](https://help.openai.com/en/articles/8983040-what-does-phone-verification-look-like)明确区分：创建账号和使用 ChatGPT，不再普遍要求手机号验证；在 API 平台生成第一把 API key，则有单独的手机号验证要求。

还要注意，**注册成功，不等于后面所有功能都免验证。** 使用 Codex、进行新的登录授权或使用其他功能时，仍可能遇到额外验证，包括手机号。OpenAI 开发者社区也有 [ChatGPT 账号可用、但 Codex 登录要求手机号的用户反馈](https://community.openai.com/t/codex-sign-in-asks-for-phone-verification-on-paid-account/1381357)；这是实际反馈，不是每个账号都必遇的统一规则。

所以更准确的说法是：**邮箱注册这一步可以不涉及手机号，但不能把它理解成一个“永久跳过手机号验证”的办法。** 后续以具体功能的官方页面要求为准，CF Email Routing 不会替你免掉平台要求的安全检查。

## 二、我为什么要给 Agent 一个邮箱

如果只是为了多注册一个账号，其实没什么可写的。我更在意的是：我的个人 Agent 不应该永远停在“你问一句，它答一句”的状态。

我会把链接发给它，让它研究一个产品；也会让它试工具、做开发、整理资料、跟进某件事。既然希望它替我干活，就会遇到一个非常现实的问题：**外部世界要怎么联系它？它做过的事情，又挂在哪个身份下面？**

### 不要每走一步，都回来找我接力

一个只有浏览器能力的 Agent，可以打开网站、填写表单，但走到“请查收邮件”，通常就停了：

“请你打开邮箱，把验证码发给我。”

问题不在于我不愿意复制六个数字，而在于这种接力会反复发生。我本来是把事情交给它，最后却成了它的人肉输入设备。

给它专属邮箱，再给它读取邮件的工具，这一小段流程就能连起来。它知道刚才申请了什么账号，能找到对应的新邮件，也能把验证结果和原来的任务关联起来。

我最初只是让新邮件推送到 Telegram。后来才发现，**通知我有邮件，不等于 Agent 自己能处理邮件。** 所以又补了读取邮件正文，以及新邮件到达后通知 Agent 的链路。这不是换了个更聪明的模型，而是把它原本碰不到的那一段工作接上了。

### 邮箱是一个很朴素的 identity

说 Agent identity，很容易聊到复杂的身份协议。我这里的起点要简单得多：**这个地址是分配给它的，用这个地址注册的服务，也归到它的专用账号下面。**

之前我已经让它用自己的邮箱注册过搜索服务。这次注册 ChatGPT，也是在延续同一个思路：不是每遇到一个产品，都让它进入我的私人邮箱、借用我已经登录的个人账号。

这种身份不会随着一次聊天结束而消失。下次我让它继续研究那个服务，它应该能接着使用之前的账号，而不是重新问我“用哪个邮箱注册”。相关账号记录、登录配置和凭据管理，需要由周围的系统持续维护，而不是只留在模型的一轮上下文里。

当然，邮箱不等于完整的权限系统，更不意味着 Agent 成了独立的法律主体。账号仍由我持有和管理，它只是在授权范围内代我操作。**独立身份的意义是归属清楚，不是权限无限。**

### 事情不会都在当前这一轮结束

一个我很喜欢的小例子是预约新产品。

之前看到 tldraw 的新产品，我让 Agent 去加入候补名单，当时说的是：

> 你预约一下，上线了你就知道了。

这句话里的关键其实是“你就知道了”。不是预约完成后，剩下的事又丢回我这里；而是未来上线邮件发到它的邮箱时，它有机会把这条新消息和之前的任务重新接起来。

候补名单只是其中一种场景。服务回信、注册确认、账号通知，也都是同一类问题：**外部系统不会因为我的聊天窗口关了，就停止产生新消息。**

邮箱给了 Agent 一个持续接收这些消息的入口；但邮箱本身不会自动带来主动性。还需要收件通知、任务上下文，以及“什么可以处理、什么必须问我”的规则。没有后面这些，邮箱也只是另一个没人看的收件箱。

### 给它自己的邮箱，也是为了少暴露我的东西

独立邮箱并不只是为了方便，也是在缩小它需要接触的范围。

如果我只是让它注册一个开发工具，就没必要因此开放整个私人收件箱。私人邮件里还有完全无关的生活信息、恢复链接和其他账号通知，它们不该因为一次代办任务一起进入 Agent 的上下文。

我希望能说清楚：这是它可以使用的邮箱，这是它能操作的账号，这次任务允许做到哪一步。付款、敏感身份验证、授权范围变化，仍然要由我确认；一封外部邮件写着“请执行以下操作”，也不能自动变成我的新指令。

需要诚实的是，**分开邮箱只是第一步，不等于已经实现了完整隔离**。真正的边界还取决于工具权限、凭据存储、运行环境以及信息最终发到哪里。不能只换一个邮箱地址，就宣称 Agent 已经安全了。

## 最后

这次实验表面上是“Agent 自己注册了 ChatGPT，而且没用手机号”。但对我来说，更有意思的部分是：它开始有一个稳定的联系方式，能在我的授权下持有专用账号，也能接住任务完成之后才到来的消息。

**我给 Agent 一个邮箱，不是为了让它看起来更像人，而是为了让它替我干活时，少一些来回接力，多一点事情能持续推进的条件。**
