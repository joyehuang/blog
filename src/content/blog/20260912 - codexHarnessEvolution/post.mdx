我给个人 Agent 派过一个很普通的任务：去后台改一段代码，改完通知我。

执行器确实把代码写完了。但通知没有准确地回到我这里——主助手不知道它做完了，我也不知道。代码躺在那儿，任务却没有交到我手上。我还得跑回去问：到底做完没有？现在能用吗？

从那以后，我对「Agent 完成了任务」这句话变得很谨慎。会写代码、知道下一步该干什么，只是任务的一部分。用户把事情交出去之后，系统还得记住它、跟进它、核对结果，最后把结果送回来。**少了最后这段路，前面做得再好也只是「代码在」，不是「事情成了」。**

带着这个心情，我读了 The Pragmatic Engineer 9 月 10 日发的[《Building Codex with Tibo Sottiaux》](https://newsletter.pragmaticengineer.com/p/building-codex-with-tibo-sottiaux)。整期访谈里我最在意的是 Tibo 对 Harness 的一句描述：**Harness 总是比模型领先一点。** 模型已经有了某些能力，外围程序先帮它把这些能力用稳；等训练跟上来，某些帮助就可以撤掉。

这句话对做 Agent 的人是个很直接的追问：我们今天认真搭的东西，有多少会被下一代模型吸收？如果模型自己就会跑测试、会持续工作、会守住目标，Harness 还剩什么？

我的答案是：**欢迎模型吃掉补丁，但删代码之前，先分清那段代码原来在解决什么。** 提醒模型跑测试，和确认测试真的通过，是两件事；帮模型记住目标，和让任务在进程退出后能恢复，也是两件事。前者是模型的行为，训练能补；后者是系统里必须真实发生的事，换谁实现都得有人负责。

这篇文章就沿着这条线来读整期访谈。先说明一点：Tibo 讲的东西我会尽量按他的原话转述；他对内部能力的描述——尤其是评审水平和长任务时长——只代表嘉宾在节目里的说法，不能当成所有 Agent 都已经具备的能力。我自己的推论和个人系统里的实践，会单独标出来。

**TL;DR**

- Harness 不是某个框架，是围绕模型的程序和执行环境。判断一段工程该不该留，不看它在哪个仓库，看它沿着任务承担了什么责任。
- 模型会吃掉的是**行为补丁**：提醒跑测试、别中途停、守住目标。模型吃不掉的是**执行事实**：测试到底跑没跑、进程退出后从哪恢复、文件能不能打开、消息到底送没送到。
- 删补丁不用赌下一代模型：把失败案例写具体，留一套小的回归任务，新模型来了对照着跑，拿证据删。
- 验收要走到用户看得见的地方，送达要有证据。「后台正常」「已发送」都只能证明它对应的那一步。

## 一、先别画架构图，沿着一项任务找责任

假设我让 Agent 修一个页面问题，并给我一个能打开的预览。

它要理解我想改的行为，找到对应代码，读项目约定，调工具编辑文件。改完之后，跑必要的检查，生成预览，打开页面确认用户看到的确实是这一版，最后把正确的链接交给我。

这条链路上，模型在不断做判断：先读哪个文件、报错意味着什么、要不要换方案、哪些检查足以支持结论。但真正读文件、起进程、保存任务状态、向外部服务发请求的，是运行着的程序。

**这里说的 Harness，就是围绕模型运行的程序和执行环境。** 它把用户输入和相关资料交给模型，提供 Tools，把模型提出的操作接到真实系统，再把执行结果带回下一轮。任务一复杂，它还要管权限、上下文、暂停恢复、验收和输出。

不用把这个词理解成某个固定框架。一段本地循环、一个后台任务服务，加上它们依赖的执行环境，都可能在承担这些工作；数据库、操作系统和消息平台同样参与了完成任务。关键不是「东西在不在同一个仓库里」，而是**沿着任务找责任**：入口要知道用户让谁做什么；上下文要让模型看到相关、且允许读取的信息；Tools 要把操作准确接出去；执行环境要限制它实际能做的事；输出要对应已经发生、能够核对的结果。安全和权限贯穿始终，不是在某一层贴个标签就算做完。

回到开头那次通知断点。后来我把**执行完成、独立验收、真实送达**拆成三条记录，各自留可核对的证据。这样至少能回答：代码写完了，还是已经检查过了？通知是还没发，还是发送失败了？当前这句「完成」来自哪一步？

系统没有从此不出错。但出错的时候，我能看见的东西变了——以前只有一句含糊的「完成」，现在知道任务停在什么地方。这个差别，比再给模型加一句「请认真负责」实际得多。

这也是我读整期访谈的起点：讨论 Harness 该变大还是变小之前，先问一句——**用户交出去的事，究竟由谁负责完成？**

## 二、「领先一点」到底领先的是什么

Tibo 回顾了 Codex 的起点。他加入 OpenAI 后最初做的是研究基础设施——数据存储、分析、理解训练过程。推理模型出来之后，他开始关心一个具体问题：能不能用模型来加速这些工作本身？

于是团队一边训练内部模型，让它更熟悉内部的 Python 代码库、代码风格和架构偏好；一边搭小型 Agent，让它实际参与基础设施开发和研究工作。这些尝试后来和 Autonomous Software Engineer 方向的工作合到一起，逐渐长成了 Codex。

这个起点很重要，因为它给「模型和 Harness 一起设计」提供了实际含义：**当 Agent 在任务里做不好时，团队能同时检查训练和外围程序。** 它不理解项目惯例，可能需要更合适的训练；它根本拿不到相关文件，问题在上下文和工具；它知道该检查什么，却总在改完文件后就结束，可以先调指令和执行流程。这些因素一起决定用户看到的结果，只盯其中一个是不够的。

它也解释了为什么一个模型能力演示，和一个能交给别人用的 Agent 产品之间，往往差着很多工作。演示的人知道该给哪些文件，知道环境缺什么，知道什么时候该追问。换一个用户，这些隐含的配合就不一定存在了。

Tibo 对早期云端 Codex 的评价也很坦率：使用摩擦偏大，没有真正找到产品市场契合点（PMF）。他没有在节目里逐项拆解摩擦的来源，我也不打算把后面谈到的环境配置问题倒推成当时失利的完整解释。但这里有个提醒很清楚：**团队相信模型能力、产品也做出来了，仍然不等于用户愿意持续用。** 用户还要决定这次任务值不值得交出去——准备环境、解释背景、等待、追问，每一项都在影响这个决定。

我的个人系统规模很小，但会碰到同一种体验问题。后台 worker 写得再快，结果回不来，我就得重新充当调度员。任务是拆出去了，我的注意力一点没省下来。

所以我更愿意用一个指标来看 Agent 有没有用：**用户还要补多少协调工作。** 每次都要提醒它继续、提醒它测试、提醒它发链接，说明产品仍然把一部分未完成的工作留在用户身上。训练能减少其中一些提醒；Harness 该把能由程序完成的衔接接好。

把早期产品的故事和「领先一点」放在一起看，领先的意义就清楚了：**把模型当前的能力变成更容易使用的工作方式。** 它有时是一条很短的指令，有时是一段需要长期维护的系统能力。这两种东西的命运完全不同，下面分开说。

## 三、模型能吃掉的：行为补丁

节目里最好懂的例子来自主持人：早期让 Codex 改代码，它会改，却不一定主动运行已有测试。后来再用，它开始自己测了。这个变化来自指令，还是来自模型？

Tibo 的回答是，两者接力。早期在开发者指令里提醒它跑测试；模型训练改善后，它更能理解用户说「完成这项修改」时的真实期待，就不需要同样强的提醒了。他也说，随着模型进步，开发者指令和 Harness 的一部分实现会缩减。

我把这类东西叫**行为补丁**：模型已经有基础能力，只是在何时使用、怎样坚持、什么时候停止上不够稳定，外围先帮一把。总在中途结束，就在结束前提醒它核对目标；遇到工具报错容易放弃，就告诉它先分析错误再选替代办法。这些规则针对的是模型在任务里的判断和行为，训练确实有机会让它自然做对。

但「跑测试」这一个例子里，其实还能再分出两层。

「改完应该检查」是一种**工作习惯**。「跑的是哪个提交上的测试、进程有没有退出、退出码是什么、哪些检查没跑」是**执行事实**。前者可能越来越不需要提醒，后者仍然需要程序去取得结果。模型学会了主动测试，也不代表每次都该跑同一套命令——改文章、改接口、改数据迁移，验证方式各不相同。更强的模型可以帮你选更合适的检查，**但它不能靠理解力把一个尚未执行的检查变成已通过。**

这就是我不愿意把「Harness 缩小」直接读成「Harness 消失」的原因。一个补丁能不能删，要看它承担的功能。移除一段重复提醒，可能让模型更自由、更高效；移除获取测试结果的步骤，则会让系统失去证据。

### 长时间不跑偏，和故障后接着做，是两件事

访谈后半段又回到这个主题。主持人提起用于长任务的 `/goal`，Tibo 解释它曾帮助模型围绕单一目标持续工作；而他描述新一代模型时说，模型可能已经不再需要同样的额外机制来保持目标，甚至谈到工作数天或一周。

这段要保留归属：这是嘉宾对他们观察到的模型能力的描述，节目没有给出任务集、运行条件和失败数据让读者复现，更不能改写成「现在随便一个 Agent 都能可靠工作一周」。

但就算接受最乐观的假设——模型能持续专注一周——它解决的也是「接下来该做什么」。另一组问题它碰不到：

- 执行进程突然退出，谁把它再拉起来？
- 重新启动之后，从哪里知道已经完成了哪些步骤？
- 一条消息已经发出去，但保存结果之前程序中断了，重试时怎么避免盲目再发一遍？
- 预算耗尽，用户从哪里知道任务被迫停下？

这些都需要系统里真实存在的记录和行为。模型可以读记录、分析恢复方案，但不能从已经消失的上下文里凭空恢复事实。

所以我会同时保留两样东西：任务目标的文字说明，和程序保存的进度。前者帮后续执行者理解目的，后者告诉它哪些事确实发生过。某种强制续跑的循环可以退休，任务记录不行。

这也影响我怎么看长任务的报告。一个模型「持续进行了很多轮工具调用」，并不自动证明任务在有效推进——它可能在反复检查同一件事。**持续时间是观察项，完成结果才是判断依据。** Harness 如果只负责让循环永远不停，可能只是在延长一个错误方向。

### 懂得遵守权限，不等于有了权限

再看一个最简单的例子。用户让 Agent 读一个项目，指令里写着「不要读取其他目录」。模型理解得再好，这句话本身没有改变进程能打开哪些文件。

如果执行环境只允许访问这次任务需要的文件，即使模型误选了路径，程序也能拒绝。反过来，执行环境权限过大，模型今天没有误用，只能说明这一次没出事。

这不是说安全只归操作系统管。入口要识别请求者和任务范围，上下文不能混进不该提供的资料，Tools 要检查操作，执行环境要限制实际访问，输出还要避免把允许阅读的信息发给不该收的人。模型的判断是其中的帮助，规则得由系统落实。

我也不认为这些能力必须永远由今天这个 Harness 项目亲自实现。权限可以交给外部服务检查，任务状态可以放进数据库，隔离可以由操作系统或云环境提供。实现位置会变，依赖可以换，**但责任必须有人承担。**

判断一段工程是不是临时补丁，我现在用一个很实用的问题：**假设模型已经完全理解用户意图，这段程序是否仍然需要实际做事？** 如果它还要限制文件访问、保存状态、接收发送回执——答案通常很清楚。

## 四、怎么删补丁，而不用赌下一代模型

Tibo 说，研究和工程团队会一起讨论：这个问题该在 Harness 里解决，还是通过训练解决？训练能解决的话，大概什么时候可用？有些问题，他们会决定先不做工程绕行，直接等模型改进。他还特别警惕为了绕开某个模型缺陷，写出庞大而复杂的代码。

我认同这个警惕，但不能忽略他们的条件：他们能参与训练，也拿得到内部路线信息。独立团队面对的是一个外部模型服务，既不确定某个问题是不是正在被训练解决，也不能把别人的发布时间当成自己的交付承诺。用户今天有任务要完成，不能只得到一句「下一代模型可能会更好」。

可反过来，如果把每个失败都变成一条永久规则，几个月后很容易攒出一套互相打架的流程。

我的折中做法——这是我从访谈推导出来的工程方法，不是节目公开的 Codex 内部流程——是**保留能说明问题的失败案例，让补丁可以被单独比较和删除**：

1. **把问题写具体。** 不要只记「模型不够主动」，要记：它完成了文件修改，但没有运行任务要求的验证；或者它只给了一份计划，就结束了本该执行的任务。任务要求、当时可用的上下文和工具结果，才是以后比较时有用的信息。
2. **说明这次补丁究竟改变什么。** 只想解决过早结束，就别顺手把所有执行步骤都固定下来。否则新模型来了，旧问题即使消失了，也不知道删哪一部分会影响什么。
3. **新模型可用后，对照着跑。** 相同任务、相近条件，分别保留和移除补丁，看它实际完成了什么、是否满足原来的边界、花了多少调用和等待。不要只比最终回复是不是更自信、更完整——一段很漂亮的完成说明，也可能对应一个没有更新的页面。
4. **留一套小的回归任务。** 真实任务有波动，一次成功不够说明旧问题已经解决。小项目不需要评测平台，但至少把最常见、最容易复现的几个失败留下来，模型或指令一变就重跑。涉及私人资料的，用脱敏输入或能重现同类问题的替代场景。
5. **反过来也要查：补丁有没有挡住新模型。** 强制它每次按固定顺序读一长串文件，曾经能避免漏看背景，现在可能让很小的修改也绕一大圈；反复追问「你确定完成了吗」，可能让它在任务结束后做额外且无必要的改动。

所以我想保留的是失败经验，不是旧流程本身。经验告诉我曾经在哪摔倒，回归案例告诉我现在还会不会摔倒，补丁只是一个可替换的解决办法。

没有能力做完整对照的时候，退而求其次：把某条规则限制在需要它的任务里，减少对其他任务的影响。一条规则应当有理由、有适用范围，并且允许以后重新判断。只因为「之前出过一次事」就永远叠规则，最后会把 Agent 变成一个需要人类不断解开限制的系统。

更强的模型理应让一些工程变简单。对我来说，Harness 成熟的一个标志，就是**能拿出证据说「这段提醒已经没必要了，删」。**

## 五、模型吃不掉的另一样东西：这个项目为什么长这样

模型就算越来越懂得怎么完成任务，它怎么知道这个项目为什么长这样？

程序里可能写着一项任务定时执行，注释也清楚。但当我要调整频率时，只看代码，不知道原来的选择是为了降成本、适配某个外部限制，还是一个早就过期的临时安排。我需要的是**决策理由，以及这个理由现在是否仍然成立**。这类信息常常散在讨论、文档和后来的修改里。模型的通用能力再强，也无法知道没有提供给它的项目历史。

Tibo 谈 OpenAI 内部协作时提到，新同事问问题，经常会被建议先问 Codex。按他的描述，内部 Codex 连接了 Slack、文档和代码，可以帮人了解项目状态、负责人，以及某项决定为什么发生。团队也把更多讨论放到内部公开频道，让文档在组织内有较广的可见范围。（「公开」是组织内部可见，不是互联网公开；节目也没披露权限实现，不能据此推断所有人和所有 Agent 都能无差别读取。）

我更在意的是背后**信息习惯的改变**。如果一个决定只存在于某个人脑子里，再好的检索也找不到。团队愿意把讨论、理由和变更留下来，Agent 才有材料可用。能访问工具只是前提，组织有没有留下有用的记录，同样决定答案的质量。

### 摘要要把人带回证据

在个人 Agent 里，我把需要的背景分成三类处理——这是我的实践判断，不是 Tibo 给出的记忆系统设计：**稳定偏好**可以长期保存，比如希望输出简洁还是详细；**项目当前状态**要查最新记录；**重要决策**要能回到当时的资料。

这三样如果都被压成几句「长期记忆」，很快就混在一起：几周前的项目状态变成永久事实，一次临时选择变成不许改动的偏好，模型自然会作出听起来合理、实际早已过时的判断。

所以我希望摘要回答的不只是「现在是什么」，还有「这个说法来自哪里」「什么时候确认的」「哪些部分尚未确认」。尤其是尚未确认的部分，不能在多轮摘要里悄悄消失。

开头那次通知断点正好能说明这一点。记忆里如果只写「任务已完成」，下一次主助手接手时，它可能直接相信已经交付。若记录的是「执行完成，验收与送达需要分别核对」，后续工作就有明确的落点。

这不是说要把全部日志每轮重新塞进上下文。模型应该先拿到足够短的当前说明，再按问题读相关证据。更大的上下文窗口会缓解容量问题，却不能自动解决过期、矛盾和权限——把更多内容放进去，甚至可能让几个时期的说法同时出现。系统需要帮模型区分它们，而不是期待模型从一堆没有日期和来源的句子里猜出哪个更新。

### 项目记录者：有用，但要有边界

访谈里还有个让我印象很深的细节：Codex 在与 ChatGPT 整合的项目中，也充当了项目记录者，持续整理讨论、争议和决定。主持人随即表达了对持续被 AI 观察的不适。

我理解这种两面性。一份好的项目记录，能让后来的人知道当时比较过哪些方案、为什么放弃某个方向，少走很多重复路。但「以后可能有用」不足以成为记录一切的理由。

对我自己的系统，我愿意保留的是完成当前任务和解释重要决定所需的资料。读取什么、能保存什么、谁能再读、结果能发到哪里，都要明确。**允许助手在私人任务里读一段内容，不等于允许它把原文搬进公开文章或共享报告。** 从个人助手走向协作系统，上下文不只影响回答准不准，也决定信息会流向谁。一个内部知识入口的成功经验，不能简化成「全库接上 RAG，再让所有人随便问」。

## 六、验收要走到用户看得见的地方

我维护过一个 QQ 公开看板。有一次，后台已经入库，但从审核到公开展示的衔接没走通，用户看到的还是旧内容。

更值得反省的是，主助手最初根据后台状态，把「后台正常」说成了「用户可见更新正常」。后来核对最终的公开页面，才把这两件事分清。

这个例子不需要什么复杂算法：**数据库里多了一条记录，和读者在页面上看到更新，是两个不同的事实。** 需求是让用户看到新内容，验收就得走到用户页面。日志成功只能证明日志对应的那一步。

带着这个例子，Tibo 对 Code Review 的看法就很好理解。传统 PR 里同时装着很多讨论：代码对不对、安全有没有问题、大家理不理解这个模块、需求到底值不值得做。随着实现检查越来越自动化，这些讨论有机会被拆开。

他举的评审例子是深入几层依赖，发现第三方库的实际行为与文档不一致，从而找出当前代码里的逻辑问题。他也描述了内部的自动安全检查，并用「超人类」来形容一些评审基准上的表现。这个方向值得重视，因为它超出了改变量名、挑格式的浅层评审。但节目没有给出题集、误报率和漏报率，我不会把它写成「AI 评审已经能保证没有漏洞」——能提出深入的检查线索，和能对任何代码作出可靠结论，中间仍有距离。

我从这段拿到的做法，是把评审时的问题摆得更清楚：

- **动手前**，先确认意图和对外约定：用户希望看到什么变化，什么行为必须保留，做到哪里算完成。
- **动手后**，再验证实现是否满足这些要求，必要时深入依赖和安全检查。

两部分都可以让 Agent 帮忙，但不该互相替代。一份代码如果正确实现了错误的需求，多跑几遍单元测试也发现不了；反过来，需求写得很漂亮，代码却错误理解了某个依赖，也得实际检查才知道。

### 把验收条件写到用户能感知的位置

以那个公开看板为例，「入库成功」适合成为后台步骤的检查项；整个任务的完成条件，还要包括经过必要审核、公开页面可见、展示的内容正确。把这些混成一个「成功」状态，后续无论交给人还是 Agent，都容易过早停止。

好的验收也不意味着每个任务都堆一堆测试。改一句文案，直接确认渲染结果；改状态转换，覆盖对应的成功与失败情况；改对外发送行为，检查发送范围与回执。检查应该对应具体变化及其后果。

我还会特别看一件事：**执行者的结论和验收证据，是不是来自同一处。** worker 说「已完成」，主助手再把这句话改写成「已验证」，并没有增加任何验证。独立验收的意义，是重新对照任务要求，去检查产物或用户端的状态。

独立不一定要再开一个 Agent。人打开最终页面、程序核对部署对应的提交、检查实际输出，都能提供新的证据。相反，第二个 Agent 如果只是阅读第一个 Agent 的总结，很可能重复同一个误判。

这件事对写博客也成立。文件写好了，构建通过了，预览服务起来了，文章 URL 返回成功了，正文确实是这次的内容了——这些事实各有各的作用。只看到部署状态正常就告诉读者「文章能读」，仍然可能跳过最后一段路。

所以我希望评审自动化省掉的是重复劳动，同时让关键问题更容易被问出来：这个变化真正抵达用户了吗？它带来的行为，是我们原本同意的吗？

## 七、送达也是一件需要证据的事

整理这期访谈的时候，我让主助手通过 QQ bot，把完整解读以合并转发的形式发到两个群。系统拿到了发送回执，也确认群里出现了对应的卡片。

但当前用的接口不能展开自己发出的合并卡片全文，所以没有完成全文读回核验。记录里保留了这个区别：**已发送；卡片已看到；卡片内部全文尚未通过读回验证。**

这件事很小，却是我现在很在意的交付细节。拿到 ACK，只能支持它所确认的那一步；群里看到卡片，比只有发送请求多了一份证据；全文能否展开逐字核对，又是另一个检查。没有读回能力时，我不希望系统为了让状态好看，把「已验证」直接设为真。它应该保留已经知道的事实，也保留没能验证的部分——以后换了接口、补了检查能力可以继续核对，现在就如实报告当前的证据范围。

这和公开看板是同一个判断习惯，只是发生在输出端。**用户看到的东西才是交付的一部分。** 模型再懂发送流程，也得靠实际接口和观察结果才知道事情走到了哪里。

### 关键是用户可以离开

Tibo 在节目中描述的方向，已经不止是代码编辑器：了解用户目标与日程、访问所需资源、通过自然语言和语音交互的个人 Agent。这是产品方向，不是所有部分都已经落地。他自己的用法倒很具体：在会议间隙对着手机说出问题，让 Agent 查资料、整理报告或探索代码。以前可能先记下来等有空，现在可以先把任务发出去。

我关心的变化是：**用户能不能离开当前界面。** 任务如果必须靠我盯着聊天窗口、保持电脑开着、反复输入「继续」，委托就仍然不完整。

但从手机发起任务，不代表执行已经离开笔记本。远程入口可能只是遥控器，真正的工作还在本机；云端执行则要在另一套环境里运行，需要代码、依赖、工具，以及完成任务所需且允许提供的资料。主持人这里的反对意见很实际：本地已经有数据库、服务器和各种配置，为什么还要折腾云环境？Tibo 的判断是，Agent 能承担更多环境搭建与维护的工作，从而降低过去云开发环境的使用门槛。

我觉得方向有道理，但「模型会配置」只解决部分成本。哪些数据可以过去、凭据由谁提供、网络能访问哪里、结果怎么带回来，仍然是实际问题。所以我不追求个人系统把所有任务都放云端，更合理的是**入口与执行位置分开**：需要本地资源的任务留在合适的环境，需要更多计算或长期运行的任务放远端。用户只需要知道任务在哪里能继续、什么时候需要自己介入，不必记住每个进程的细节。

节目谈 Codex 与 ChatGPT 整合时，Tibo 也描述了本地 Agent 与托管云端系统之间的差异——基础设施、运行方式、插件和库都要整合。对外看只是多了一个入口，里面却要把能力放到另一种规模和运行条件下。共用核心是接入新界面的基础，但还不够：状态怎么呈现、任务怎么继续、结果怎么返回，都决定用户是否真的得到同一种能力。

我的系统没有这样的规模，但检查问题是一样的：从一个聊天入口派出的任务，后台做完了，另一个负责汇报的助手知不知道？用户回到对话里，能不能拿到准确状态？这些衔接没做好，接再多入口，只是增加更多看不见任务的地方。

## 八、代码变便宜了，边界反而更值钱

Tibo 一方面认为维护和重构正在变便宜，另一方面又强调好的抽象和边界仍然有用。表面上有点矛盾：既然随时能重写，为什么还要花时间设计？

把**改写成本**和**后果**分开，就不矛盾了。

一个通知模块可以换语言、换库、换存储。但如果它在重试时把消息发给了错误的人，或者把尚未验收的任务宣布为成功，影响不会因为代码写得便宜就消失。重写代码的成本在下降；恢复外部状态、重新解释发生了什么、重建用户信任，仍然要付出真实的代价。

Tibo 描述依赖升级这类工作能更多地自动化，一些过去不愿启动的维护任务可以在较短时间内完成（他谈到的几小时等时长，是他的观察与判断，不是普通项目的工期保证）。但他同时强调，模块边界划得好，内部就能快速变化而不牵动其他服务。我很认同，尤其在多个执行者一起改的时候。

假设一个执行器负责产出文件，另一个模块负责核对结果，第三个模块负责通知。执行器可以随便改内部实现，只要它交出的产物和状态仍然清楚；通知模块不该只看到进程结束，就自行推断验收通过。这些约定不必写成读不懂的大文档，几句具体的话就很有用：

- 执行完成只代表产物已生成；
- 验收通过要附对应证据；
- 发送失败不能改成已送达；
- 重试前先核对上一次操作的结果。

每句话都对应真实行为，开发者才知道修改时必须保留什么。边界的价值也不在于永远不变——原来的划分确实阻碍新需求时，可以一起调整。但要知道这次是在改内部细节，还是在改其他部分依赖的行为。模型能快速生成代码，反而更需要这个区别，否则很容易无意中扩大改动范围。

### Rust 值得学的是选择理由，不是语言

这正好回到节目较早谈的语言选择。Tibo 解释为什么用 Rust 时，主要提到正确性、效率、团队经验，以及编译期检查能带来的帮助；他还特别强调，把 Agent 核心和产品界面分开。同时他也明确承认，TypeScript 或 Python 路线同样可能成功，只是后来可能需要重写。

所以我不会因为这期访谈就建议谁换语言。比「Rust 更适合 Agent」更值得记住的是：**一个 Agent 核心应该能脱离某个终端或聊天界面运行。** 今天从 CLI 接任务，明天从手机接任务，不应该因此复制整套工具执行、权限和状态逻辑。

对我的个人系统，问题更具体：pi、Telegram 这样的入口，与后台执行器、任务通知，能不能清楚衔接？换一个入口，能否继续查看和跟进同一项任务？如果所有状态只留在某个聊天会话里，换入口就很容易丢掉任务背景。用同一种语言也能把这些关系分清，用不同语言也可能把它们耦合得很紧。

### 并行、开源、换模型：都是边界问题

访谈还谈到，过去团队规模逐步增长，工程师有时间补文档和协作方式；现在大量 Agent 可能很快加入一个项目。我不把这读成「每个项目都该开很多 Agent」——并行会带来上下文同步、修改冲突和验收成本。真正有帮助的是让可以独立的工作独立起来：接口清楚、产物明确、改动范围有限，一个执行者改内部实现时，其他人不用跟着重读整个系统。好的边界让并行成为一个选项，而不是逼大家靠频繁聊天避免互相踩脚。

开源也是。Tibo 的态度比较开放：用户想试另一个模型，不该被迫换掉整个工作环境；代码已经开源，仅仅为了接入不同提供商而维护一个 fork，也是额外成本。开源对团队本身有帮助——新成员可以提前读代码和 PR，用户能参与改进，团队能直接看到社区怎么用——但他同样谈到代价：开源和内部代码之间的额外边界、功能尚未正式发布就被复制，以及大量低质量贡献带来的维护负担。我喜欢这部分的具体程度：开源本身也要运营。让 Agent 更容易生成贡献，并不会自动让维护者更容易判断每个改动有没有用。

而支持其他模型，则把 Harness 的另一项责任显露出来：既要保留选择，也要承认选择之后的差异。一个 API 请求能成功返回，只说明基础接入走通了。同样的工具说明、错误反馈、上下文整理方式和停止提示，不一定适合每个模型——一个模型拿到工具结果会主动继续，另一个可能更容易停下来解释；某条对旧模型有用的指令，也可能干扰新模型。（这是我对跨模型使用的工程判断，不是节目给出的对比实验。）

所以第四节那套失败案例和回归任务，换模型时也能直接用：看它是否仍会过早结束、是否准确使用工具、是否满足相同的验收要求。这不要求小项目一开始就支持所有模型，抽象过度同样是维护负担。只要核心的任务记录和产物不被某一个聊天界面、某一种回复格式锁死，就已经给未来留出了空间。**单纯把模型名变成一个配置项，只完成了最容易看到的那一部分。**

## 九、工程师要练的，是把问题追到能验证的位置

聊到最后，还是会回到工程师自己。模型会写更多代码，会检查实现，也开始参与架构判断，我们该把时间投在哪里？

Tibo 的建议是：保持好奇，快速理解陌生系统，不断提出好问题，真正理解你所服务的人。他也说自己仍然享受手写代码，只是更愿意用工具去解决更多问题。

我不想把这读成「以后只要会提需求」。要提出一个好问题，往往先得知道系统是怎么工作的：不了解进程和存储，很难意识到持续推理与故障恢复的区别；不理解测试覆盖了什么，就容易把全绿当成用户体验正确；看不懂依赖，就没法判断评审模型指出的问题成不成立。

手写代码仍然能帮助建立这种理解，也仍然是直接修改和实验的手段。只是我们不需要用写了多少行来证明自己对系统负责。读代码、跑实验、理解错误、核对真实结果，同样是工程工作。我也不打算把架构当成模型永远碰不到的安全区——Tibo 已经明确说，模型对长期维护和架构的思考在改善。未来模型给出更好的设计建议，我希望自己用得上，并且知道怎么判断它适不适合当前项目。

对我最实用的练习，是把一个宽泛判断继续追问下去：

- 「后台正常」具体指哪个步骤？
- 「验证过了」看的是什么证据？
- 「这个补丁必须留着」对应哪一个仍然存在的失败？
- 「换模型更好」是回复更像我喜欢的风格，还是任务确实完成得更好？

这些问题没什么华丽术语，却会直接改变下一步的行动。问清后台与页面的区别，就会去打开用户页面；问清发送与全文读回的区别，就不会误报已验证；问清补丁解决的是什么行为问题，就有机会在新模型上把它删掉。

模型越强，越能帮我们把猜测变成实验——以前因为实现成本高而搁置的比较，现在做得起了。但实验仍然要选对问题：一个内部函数测得更快，推不出整个任务交付更快；多开几个 Agent 更忙，也推不出结果更好。

回到那句「Harness 总是比模型领先一点」。我更愿意把它当成一种工作方式：**先帮模型跨过当前任务里的障碍，等它自己具备了相应能力，再撤掉不必要的帮助，把精力放到下一个真实问题上。**

其中有些工作会很快过期，删掉就好；有些会变得更容易实现，可以换一种更简单的做法。但只要我们还希望用户把任务交出去、再带着可靠的结果回来，权限、背景、恢复、验收和交付，就仍然要有人落实。

我希望自己的 Agent 越来越少需要我催。同时，当它告诉我「完成了」，我也希望能沿着记录找到产物、检查和送达的结果。

模型越来越强，给了我们更多把事做成的能力。Harness 要做的，是让这些能力真正走完从一句请求到用户手里的那段路。
