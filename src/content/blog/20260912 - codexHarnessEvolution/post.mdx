The Pragmatic Engineer 上周发了一期播客，[Building Codex with Tibo Sottiaux](https://newsletter.pragmaticengineer.com/p/building-codex-with-tibo-sottiaux)，主持人 Gergely 和 Codex 负责人 Tibo 聊了一个多小时。里面有一句话我反复想了好几天。

主持人问：早期的 Codex 改完代码不会主动跑测试，几个月后它开始自己跑了，这是改了指令还是改了模型？Tibo 的回答是，Harness 在某种意义上总是比模型领先一点。模型已经具备某种能力，但还不够稳、不够高效、行为也不一定符合用户预期，于是先在外面搭几根拐杖，让它把事做到位。等下一代模型训练好了，一部分拐杖就可以撤掉。他说，随着模型进步，他们观察到 developer message 在变短，Harness 也在缩小。

节目末尾 Gergely 坦白说，作为开发者，听到这个有点泄气：我今天认真做的东西，下一版模型自己就会了，然后就可以删掉。

我做个人 Agent 也有一年多了，第一反应和他一样。但多想几遍之后，我觉得这句话只说对了一半。会被模型吃掉的那部分确实会被吃掉，而且吃得比想象中彻底。可 Harness 里还有另一部分工作，模型再强也替代不了，甚至模型越强，这部分越重。麻烦在于这两部分平时混在同一个代码库里，长得也差不多，不拆开看就容易一起悲观，或者一起乐观。

这篇文章就是想把它们拆开。

<TldrCard>
- Tibo 说的「拐杖」，共同点是在替模型的判断兜底：什么时候该跑测试、遇到报错要不要放弃、长任务怎么不跑偏。这类东西，不管代码量大小，训练都能吸收。
- 分辨的办法是一个思想实验：假设模型的判断已经完美，这段代码还有没有事做？有，它就不是拐杖。
- 剩下来的至少有三类：模型靠变聪明拿不到的**事实**，模型不该自己决定的**边界**，以及模型不在场时的**连续性**。它们不随模型能力消失，反而随模型做的事变多而变重。
- 独立开发者没法像 Codex 团队那样等下一代模型。每根拐杖应该带着它自己的到期检验：留住它当初解决的失败任务，新模型来了去掉它再跑一遍，用结果决定删不删。

## 一、拐杖到底在补什么

先看 Tibo 在节目里给的几个例子，它们有一个共同点。

第一个就是跑测试。早期版本改完文件就结束，团队的办法是在给模型的开发者指令里提醒它。后来的模型更能理解「完成这项修改」在用户心里包含什么，提醒就不需要了。

第二个是 `/goal`。这是 Codex 里一个让模型围绕单一目标长时间工作的机制。Tibo 说它当初是必要的，否则模型跑着跑着就偏了；但新一代模型已经不需要它，你直接说「去做一周」，它就能做。

第三个是他给团队的一条原则：如果你在为了绕过模型的某个缺陷写一万行代码，你大概做错了。

这三个例子，一个是一句提示词，一个是一整套循环机制，一个是规模上的警告。代码量差得很远，但补的是同一种东西：**模型的判断**。什么时候该做什么、要坚持多久、遇到意外怎么选。模型手里的信息其实是够的，它看得到有测试目录，看得到任务要求，它只是没有稳定地按那个信息行动。拐杖做的事，就是把「你该这么做」直接塞进它的决策里。

这也解释了为什么训练能把它们吸收。训练改的正是模型在给定信息下会怎么选。信息本来就在上下文里，只差行动的稳定性，那么把行动练稳，拐杖自然就多余了。`/goal` 这么大的一块机制也会消失，说明大小不是判断标准，性质才是。

所以我先给这类东西一个名字：行为补丁。它的定义和写在哪里无关，提示词、循环、重试逻辑都可能是；它的定义是「如果模型判断得更好，就不需要存在的东西」。

顺着这个定义，下一个问题就很自然：假如模型的判断已经好到不需要任何补丁，Harness 里还剩什么？

## 二、一个判断标准：假设模型的判断已经完美

我用一个具体的任务来推。这个任务是假设的，但也是我平时最想交给 Agent 的那种。

睡前我对 Agent 说：仓库里有个 bug，报错信息在 issue 里，你去修，跑完测试开个 PR，早上告诉我结果。然后我合上电脑去睡觉。

现在假设模型的判断完美：它会读对文件，改对地方，知道该跑哪些测试，遇到意外能选出最合理的下一步，不会跑偏，也不会半途宣布完成。在这个假设下，把整条链路从头走一遍，看每一步还剩什么事必须由程序来做。

它要读代码、改文件、跑测试。判断再好，也得有一个真实的 shell 和文件系统让它操作。这是最显而易见的一层，模型不可能靠想象执行命令。

测试跑完了，结果是什么？「测试通过」这四个字，在模型那里是一个判断，在系统那里是一个退出码。哪怕模型的判断完美，退出码也不是它推出来的，是程序从进程里取回来的。模型能做的是解读这个数字，产生这个数字的是那次真实的运行。

它要开 PR，这一步要往远端仓库推代码，需要凭据，也需要有人事先允许它推到这个仓库、以这个身份、开 PR 而不直接合并。这些许可不来自模型的判断，来自我。

从凌晨两点到早上八点之间，模型只在被调用的那几秒里存在。中间进程可能被杀、机器可能睡眠、额度可能用完。谁负责记住任务做到哪一步，谁负责在恢复之后不把同一个 PR 开两次，谁负责在额度用完时停下并留下记录，都不是「判断」能解决的，因为那段时间根本没有模型在判断。

早上八点，我收到一条「已完成」。这条消息值不值得信，取决于它是从哪来的：是模型对自己工作的总结，还是程序对照测试结果、PR 链接、CI 状态之后生成的。前者在模型判断完美的假设下也只是一个陈述，后者才是我能直接点开核对的东西。

把上面这一遍走完，剩下的东西可以归成三类。执行工具那一层我先放一边，它确实不会被训练吸收，但它正在被标准化成公共设施，MCP、沙箱、云端虚拟机都在做这件事，Gergely 在节目末尾也提到，下一代模型总不至于重新发明一遍 MCP。真正值得一个个讲清楚的是另外三类：**模型靠变聪明拿不到的事实，模型不该自己决定的边界，以及模型不在场时的连续性。**

这三类的共同点，是它们都在模型的判断外面。这就是我判断一段代码是不是拐杖的标准：**假设模型判断完美，它还有没有事做。** 有，就不是拐杖，不管它现在看起来多像。

## 三、模型靠变聪明拿不到的东西：事实

模型的处境有一个很基本的限制：它只能看到上下文窗口里的东西。窗口外面发生了什么，它要么被告知，要么不知道。这个限制和它聪不聪明无关，是位置决定的。

「测试通过了」「文件已经保存」「消息已经发出去了」，这些在模型的回复里都是陈述。它们要成为事实，需要程序去外面取一次：退出码是多少、文件的哈希是什么、发送接口返回了什么。**模型能生成的是关于事实的陈述，事实本身只能从外面取。** 训练可以让陈述更准，不能让陈述变成事实。

这里会有一个很自然的反驳：训练也可以教模型主动去取事实啊。让它养成看退出码的习惯、每次改完文件都读回来确认、发完消息查一次回执，这些都是可以练的行为。

对，而且这正是第一节说的规律：「记得去核对」是判断，会被吸收。但吸收之后，那条取事实的通道还在，程序还是要真的去跑命令、真的把返回值带回来。变化的只是谁发起核对，从提示词提醒变成模型自觉。更要紧的是最后一步：模型读完退出码之后告诉我「测试通过了」，这仍然是模型的一句话。它可能读对了，也可能在一长串输出里看漏了那个非零值，或者把上一次运行的结果当成了这一次的。**只有当程序把那个退出码原样附在最终报告里，我拿到的才是事实，而不是对事实的转述。**

这一点我认为会随模型变强而更重要，而不是更不重要。越强的模型，写出来的完成报告越像真的。它会把该提的检查都提到，措辞也恰当，结构也完整。如果 Harness 把这份报告当成结果直接转发给用户，那么模型越强，用户越难从报告里看出它有没有真的做完。所以我现在倾向于反过来做：最终交付给用户的东西，由程序从事实拼出来，模型的总结只是附在旁边的说明。测试跑的是哪个提交，命令是什么，退出码是多少，PR 链接在哪，CI 是绿是红。这几项不由模型填，由程序查。模型可以在旁边解释「为什么这次改了三个文件」，但「改了哪三个文件」这一栏要从 diff 里来。

同样的道理也适用于「让另一个 Agent 来验收」。如果验收 Agent 读的是执行 Agent 的总结，它做的只是复述。验证要从世界读，不从转录读：去打开那个页面，去查那个部署对应的提交，去跑那条命令。两个模型互相看对方的话，再看几轮也不会多出一个事实。

Tibo 在节目里对 Code Review 的看法，正好能用这个框架拆开。他说传统 PR 评审混着好几件事：正确性、安全、知识传递，还有对意图的讨论。他的判断是正确性和安全这部分会被自动化，实际上他们早期做的独立评审模型，能力已经并进了主线模型；而「你到底想做什么、这件事该不该做」这部分讨论会留下来，并且不一定非得围着代码发生。

用前面的分类看，这段话里其实有三种东西。评审模型对代码正确性的判断，是模型的判断，所以能被主线模型吸收，符合第一节的规律。但他同时提到，内部所有 PR 现在都过自动安全检查，标记出安全问题就阻止合并。这条规则是政策，不管评审用哪个模型，规则都在那。而「你想做什么」是信息，模型判断再好也不知道你没告诉它的意图。一件看起来叫「评审」的事，拆开来是判断、政策和信息三样，只有第一样会被训练吃掉。

意图这一类，我想多说一句。节目里聊到 OpenAI 内部新人问问题，常被建议先问 Codex，因为内部的 Codex 接了 Slack、文档和代码，能回答一个项目现在到哪了、某个决定为什么这么做。抛开公司规模不谈，这件事对个人 Agent 的启发是，Harness 给模型的上下文正在从「你该怎么做」变成「你需要知道什么」。前者是行为补丁，会缩；后者是事实供给，不会缩。一个定时任务为什么设成每小时一次，是为了省钱还是因为上游有限流，这类「为什么」不在代码里，模型再强也推不出来，只能有人把它留下来，再由程序在合适的时候递给它。

## 四、模型不该自己决定的东西：边界

Tibo 描述 Codex 今天的运行方式：默认所有工具调用都在沙箱里执行，如果某条命令需要沙箱之外的权限，会停下来问用户。这个设计我认为不会因为模型变强而取消，原因和「模型会不会犯错」无关。

一条边界如果依赖边界里面那个人的判断来维持，它就算不上边界。这句话对人成立，对模型也成立。哪怕模型每一次都会正确地选择不去读那个目录，「它会正确选择」和「它读不了」也是两件事，只有后者能给出保证。更何况模型并不在真空里判断，它的上下文里可能混进了别人塞的指令，可能同时在替好几个人做事，可能拿到的是过期的授权。这些情况下，「模型判断完美」这个假设本身就站不住，因为它判断的依据已经被污染了。

我之前写过一篇[权限隔离怎么做](/blog/20260912---agentpermissionisolation/post)，把一条请求要过的五个检查点讲得比较细，这里不重复。这里想补的是它和「Harness 缩小」的关系。

边界这一层不但不缩，还会随着模型能力增长。原因很直接：模型能力越强，我们越愿意让它无人值守地做更多事。从「帮我改一个函数」到「去做一周」，中间多出来的每一步操作，都是一个需要回答「它可以吗」的位置。回到睡前那个任务：允许它推到这个仓库，但只能开 PR；允许它读这个项目目录，但不能读隔壁的；允许它花掉多少额度，超过了就停。这些句子每一条都很短，可它们描述的是模型在我睡着的六个小时里能碰到的世界的形状。Tibo 描述的 Codex 方向是个人 AGI，知道你的日程和目标，能替你采取有风险的操作，然后给你推一条通知让你核对。这个愿景越接近，「什么算有风险」「谁来定」「事后怎么撤销」就越是核心工作。

有人会说，这些规则模型也能替你写。能，而且它写得可能比我周全。但写规则和执行规则是两回事。模型可以起草一份「这个任务允许做什么」的清单给我批准，批准之后，把清单变成进程实际碰不到某些东西的，是沙箱、是文件系统权限、是那个只有开 PR 权限的 token。模型在这里的角色是提案人，执行边界的仍然是程序。

边界这一层真正会缩的，是摩擦。今天很多确认弹窗其实是因为我们还不知道该信它到哪一步，所以什么都问。随着经验积累，很多问题会从「问用户」变成「按事先定好的规则判」。但注意方向：决定权是从人手里挪到政策手里，没有挪到模型手里。规则可以越来越细、越来越少打扰人，规则本身仍然在模型外面。

## 五、模型不在场的时候：连续性

「去做一周」这句话里藏着两个完全不同的一周。

一个是模型注意力上的一周：它能不能围绕一个目标持续推理和行动那么久，不跑偏、不遗忘、不半途宣布完成。Tibo 说新模型已经不需要 `/goal` 来维持这个，这是关于模型注意力的判断，我没有理由怀疑他们内部的观察。

另一个是进程上的一周。模型只在被调用的那一刻存在，每次调用之间、每次崩溃之后、每次机器休眠期间，它都不在。一周里这样的间隙有成千上万个。谁在这些间隙里持有任务？

这个问题任何长任务系统都要回答。但在 Agent 这里它容易被忽略，因为模型给人的感觉是连续的：你和它对话，它记得上文，它说「我继续」。这种连续感是 Harness 每一轮把历史重新喂给它造出来的。把喂历史的程序拿掉，模型的每一次调用都是从零开始。

所以连续性这一层要做的事，和模型的注意力没有关系。任务状态存在哪里，用什么格式，恢复的时候模型从哪读。哪些操作做过了，尤其是那些有外部副作用的操作，PR 开了没有、消息发了没有，恢复之后不能盲目重做。额度用完了怎么停，停下来要留下什么，让人或者下一次调用能接上。这些东西的实现可以很简单，一个任务表加几条状态记录就够，但它们的存在不取决于模型。

其中「不盲目重做」值得单独讲，因为它是最容易被模型的自信掩盖的一环。凌晨三点，进程在开 PR 的请求发出之后、结果写回之前挂了。早上恢复的模型看到的是「准备开 PR」这条记录，没有「PR 已开」。如果它直接再开一次，仓库里就多了一个重复的 PR；如果它假设上次成功了，可能什么都没有。正确的做法是先去远端查一次：这个分支上有没有已经存在的 PR。这个「先查再做」的顺序可以教给模型，但那条「准备开 PR」的记录得是程序在发请求之前就写下的，否则恢复的模型连自己曾经走到这一步都不知道。先记意图，再执行，执行完记结果，恢复时把有意图没结果的操作挑出来去外面核对。这套顺序在数据库里叫了几十年 write-ahead，放到 Agent 里一样成立。

Tibo 提到 Codex 正在从默认本地执行扩展到云端虚拟机，将来可能是本地和云端混合。云端执行解决的是「笔记本合上任务就停」的问题，让进程有一个不随你的电脑起落的地方待着。但它是把连续性的责任搬了个位置。云端的进程一样会挂，一样要记状态，一样要在恢复时知道自己做到哪了。

这一层我有一个具体的设计偏好：给模型看的目标说明，和给程序用的进度记录，分开存。前者是一段话，告诉恢复后的模型这个任务是为了什么、做到什么算完；后者是一串事实，哪个文件改了、哪条命令跑了、返回了什么。恢复的时候模型两样都读。目标说明防它跑偏，进度记录防它重做。这两样东西以前可能被塞在同一段「记忆」里，混在一起的结果是，几天前的中间状态被当成永久事实，一次临时选择被当成不许改的约定。分开之后，哪些会过期、哪些是定论，一眼能看出来。

## 六、什么时候删拐杖

前面几节在说什么不会被吸收。这一节回到会被吸收的那部分，因为那里有一个独立开发者和 Codex 团队处境不一样的地方。

Tibo 描述他们的决策方式：发现模型在某件事上做不好，研究和工程一起讨论，这个问题是在 Harness 里解决，还是靠训练解决；如果靠训练，一个月、三个月还是六个月能到。有时候他们会决定 Harness 什么都不做，直接等模型。

这个方式的前提是能看到训练的路线。我看不到。我用的是别人的模型，不知道某个问题正在不正在被解决，也不能把别人的发版日期当成自己的交付计划。用户今天有一个任务要做，「下一代模型可能会更好」帮不上忙。

但反过来，如果每一次失败都变成一条永久规则，几个月后就会攒出一堆互相打架、没人敢删的补丁。更麻烦的是，补丁可能反过来拖累新模型。一条强制它每次动手前按固定顺序读完一长串文件的规则，对旧模型是防漏看，对新模型可能就是让一个两行的修改绕一大圈。一句反复追问「你确定做完了吗」，可能让本来已经做完的模型再去做一些不必要的改动。补丁的成本不只是维护，还有它对更好的模型施加的那份多余的约束。

所以我现在的办法，是让每一根拐杖带着它自己的到期检验。下面说的是我打算怎么做，还没有跑出可以拿来给人看的数字。

加一条行为补丁的时候，同时记下它解决的那个失败：任务是什么，模型当时做了什么，缺了哪一步。这条记录要具体到能重跑，「模型不够主动」这种描述没有用，「改了三个文件之后没有运行仓库的 check 命令就报告完成」才有用。有隐私问题的，换一个能复现同类失败的替代任务。

补丁本身写成一个假设：「没有这条规则，当前模型在这类任务上会漏掉验证」。假设是可以被推翻的，规则很难被推翻，因为没人记得它当初为什么在那。

新模型来了，拿那几个失败任务，分别在有补丁和没补丁的情况下跑。看的是任务完成了没有，边界守住了没有，多花了多少轮，回复写得好不好放在最后。一次通过不算数，这类任务本来就有波动，要跑几遍。

如果没补丁也过了，删。删不掉的，说明它要么还是需要的，要么根本就不属于行为补丁，是前面三类里的东西被误放进了提示词。后一种情况其实很常见，很多「请先确认再执行」的提示词，本质上是权限检查没做在程序里，只好写给模型看。这种情况发现之后要做的是搬家：把检查从提示词挪进代码，然后提示词里那句话就可以删了。

这套办法的代价是要维护一小组回归任务。对个人项目来说不需要搭评测平台，几个最常见的失败案例加一个能重跑的脚本就够了。它换来的是一件事：删代码的时候手里有证据，而不用赌下一代模型的宣传是真的。

## 七、所以 Harness 会变小吗

回到 Gergely 那句泄气的话。我的答案是：看你在建哪一堆。

如果在建的是行为补丁，那它确实会被吸收，而且应该被吸收。它从一开始就是临时的，是模型能力和任务要求之间那段还没合上的缝。缝合上了，补丁完成了它的任务。为此泄气，有点像为脚手架被拆掉泄气。

如果在建的是另外三类，那么担心的方向反了。模型越强，被交给它的任务越大、越长、越少人盯着。每多一步无人值守的操作，就多一个需要核对的事实、一个需要回答的许可、一段需要跨过的间隙。这三堆的绝对量在涨，而且涨的速度取决于模型能力的增长，和我们愿不愿意无关。

所以「Harness 缩小」这个说法，我更愿意换成「Harness 换了成分」。给模型看的那部分在变薄，developer message 会越来越短，`/goal` 这类机制会一个个退休。围着模型的那部分在变厚，事实怎么取、边界怎么守、间隙怎么跨。前者是在教模型怎么做事，后者是在让模型和真实世界之间保持诚实。

甚至 Harness 的代码本身也不重要。Tibo 说维护和重构正在变得很便宜，一个模块只要边界画得对，里面怎么写都可以随时换。Codex 已经在用 Codex 改自己。那么几年后留下来的不会是今天这几千行代码，而是这几千行代码承担的责任，和验证这些责任有没有被守住的那组测试。代码可以由模型重写，责任不能由模型免除。

这大概就是我读完这期之后对 Harness 的理解：它既不是一个会随模型进步而消失的过渡产物，也不是一个要永远堆规则的补丁库。它是模型和世界之间那层负责说实话的东西。模型负责想，它负责让想出来的东西经得起核对。模型越强，这层越薄，也越硬。
