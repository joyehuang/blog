前阵子 The Pragmatic Engineer 有一期播客，[主持人 Gergely 和 Codex 负责人 Tibo Sottiaux 聊了一个多小时](https://newsletter.pragmaticengineer.com/p/building-codex-with-tibo-sottiaux)。整期内容不少，但我最想拿出来聊的只有其中一小段。

Gergely 问：早期的 Codex 改完代码不会主动跑测试，几个月后它自己开始跑了，你们改的是指令还是模型？Tibo 的回答大意是：Harness（模型外面那一圈工程，下一节细说）在某种意义上总是比模型领先一点。模型有某种能力，但还不够稳、不够高效，于是先在外面给它搭几根拐杖；等下一代模型训练出来，就不用再提醒它了。时间一长，他们看到的是 developer message（每一轮开头塞给模型的那段说明）在变短，Harness 也在缩小。

节目最后 Gergely 复盘时说了句实话：作为开发者，这听起来有点泄气。我今天认真做的东西，下一版模型自己就会了，然后就可以删掉。

这段话我听的时候一点不意外，因为我一直也是这么理解这件事的。有意思的是，我和 Tibo 看到的是同一个现象，得出的结论却不太一样：他说 Harness 在缩小，我觉得它一直在变大；Gergely 觉得泄气，我反倒觉得这是这一行最值得干的原因。

所以这篇就借他们的话开个头，后面只聊 Harness 这一件事：我说的 Harness 指什么，我做在模型外面的东西被模型学会之后去了哪，它现在长到了第几层，以及我顺着这些想出来的一个产品判断：什么样的 AI 产品，在和底层模型赛跑的时候跑得赢。都是我自己的想法，不一定对，欢迎拿你自己的项目来对照着看。

<TldrCard>
- **我说的 Harness，是模型之外的一切。** 模型是唯一一件我不用、也没法自己做的东西，所以做 AI 产品，做的其实就是模型外面那一圈。
- **新能力总是先在模型外面试出来，再被训练进模型里面。** 会被模型学走的，是替它的「判断」兜底的那部分；事实、边界、连续性，还有只属于你的上下文，模型再强也替不了。
- **补丁被删，不等于活没了。** 里面那层稳了，卡住我的地方就往外挪一圈，我下手的地方也跟着往外挪一圈。Prompt → Context → Harness → Loop 就是这么长出来的，上一层变成下一层的零件。
- **我把现在的 Harness 拆成三层：产品 / Agent 层、Repo 层、Organization 层。** 最里面那层正在被模型学走、被平台做成标准件；Repo 层刚被认真对待；组织层才开始。Claude Code 团队有成员 70%—80% 的工作已经发生在 Slack 里的 Agent 上。
- **我算的一笔速度账：你补的东西，要长得比模型自己变强的速度快。** 我管这个叫斜率。补得没有模型学得快，产品就在一点点融化。这是我不看好大部分 To C 的 AI 视频衍生应用的原因，也是我觉得开放权重的视频模型会改变这笔账的原因。
- **我看不到训练路线图**，能做的是：把通用补丁当成有保质期的东西，给每个补丁留一份到期检验，把长期的力气花在训练数据够不着的地方。
</TldrCard>

## 一、先说清楚：我说的 Harness 到底指什么

先把词对齐，因为我和 Tibo 后面的分歧，全出在这个词到底指多大一圈上。

我自己做 Agent 的时候，习惯把它拆成四样：大脑、记忆、工具、循环。这里面只有大脑，也就是模型本身，是我不用做、也没法做的。我不会去预训练一个模型，我能决定的只是调用哪一个。剩下的活，记忆怎么存、工具怎么接、循环怎么转、上下文怎么管、出错了怎么兜底，全在模型外面。业内管这一整圈叫 Harness，你可以把它理解成套在模型外面、让它能好好干活的那一整圈东西。LangChain 的 Vivek Trivedy 有句话说得最干脆：Agent = 模型 + Harness，你要么是模型，要么就是 Harness，模型之外的一切都是 Harness。

我想把这句话再往前推一步：**不只是做 Agent，只要你在做 AI 产品，而你又不是训练模型的那家公司，你做的东西就全部是 Harness。** 一个 AI 写作工具的编辑器和版本管理是，一个客服机器人接的知识库和工单系统是，你给自己的个人 Agent 写的那份长长的偏好说明也是。往回看，更早的 Prompt Engineering、Context Engineering 也都算，只是那时候还没人用这个词。

我知道这个定义听起来宽得有点耍赖：什么都是 Harness，那这个词还区分了什么？这个质疑有道理，但我的看法正好相反，宽正是它的用处。它只画了一条线，线里面是模型，线外面是其它所有东西。线里面的东西由训练决定，我碰不到；线外面的东西由我决定，但它们全都躲不开同一个问题：模型下一次变强的时候，这东西还有没有用。我承认自己做的全是 Harness，其实就是承认我做的每一样东西都得回答这个问题，没有哪一块能例外。

这一圈到底有多大分量？我喜欢拿两个「模型没换、只动了外面」的例子来看。

第一个就在开头那期节目里。早期的 Codex 改完文件不会主动跑测试，Tibo 他们当时能做的，是在 developer message 里加一句提醒。模型没换，外面多了一句话，它就开始跑测试了。Harness 最朴素的样子就是这样：模型其实有这个能力，只是时灵时不灵，外面那一圈负责把它稳住。

第二个方向正好相反。Claude Code 的作者 Boris Cherny 今年在 YC Startup School 上讲过（[官方逐字稿](https://www.ycombinator.com/library/UN-boris-cherny-building-claude-code)）：Opus 5 发布的时候，他们把 Claude Code 的系统提示词删掉了 80%。原因是里面大量内容当初是在纠正模型「本该知道却没做到」的行为，新模型自己就做到了。他还提到一个内部用来做对照的「simple 模式」，会把系统提示词连同工具里的提示一起去掉；他们发现，去掉这些之后模型反而稍微聪明了一点，只是作为产品，你仍然需要其中一部分，行为才是用户想要的样子。

两个例子放在一起看：同一颗大脑，用得好不好，外面这一圈说了算，而且两个方向都成立。外面补对了，模型的能力被稳稳地用出来；外面那些东西过时了，反过来会拖累模型。我后来发现，很多看起来是「模型不行」的问题，其实是外面那圈没做好。我自己用某个 coding 模型的时候就碰到过，它的工具调用老是失败，查下来是参数格式对不上，和模型聪不聪明没什么关系。

> **【待补 · 你自己项目里的一个例子：模型没换，只改了外面某一处（上下文怎么喂、工具怎么描述、循环怎么停），效果明显变了。最好有前后对比】**

这里得替 Tibo 说句公道话：他在节目里说的 Harness，比我这个窄得多。他指的是 Codex 团队维护的那个核心 agent harness：护栏、沙箱、工具，加上每一轮开头注入上下文的 developer message。在这个范围里说「它在缩小」，我信。但他的窄定义和我的宽定义之间差出来的那一大块，后面你会看到，正是不缩反涨的部分。

## 二、为什么新能力总是先在模型外面冒出来

Tibo 用的比喻是拐杖。这个词我不太喜欢，原因放到这一节后面讲，先说我和他完全一致的那部分：**一种能力，总是先出现在模型外面，然后才进到模型里面。**

这个顺序过去几年重复了很多次，每一次都查得到。

2022 年大家发现，在提示词末尾加一句「Let's think step by step」，模型做推理题的正确率会明显上升。那两年流行的各种 magic words，「回答前先想一步」「回答前再反思一下」，都是这个路数。这完全是模型外面的功夫，一句话而已。到 2024 年推理模型出来，先想再答这件事被直接训练进了模型，那句咒语就没人再写了。

工具调用也一样。最早让模型用工具，靠的是在提示词里约定一种输出格式，再由外面的程序去解析文本、执行、把结果塞回去，ReAct 那一批做法就是这样。后来厂商把 function calling 做成模型的原生能力，解析文本那层胶水代码就用不着了。

Tibo 在节目里给的例子属于同一类，只是发生在厂商内部。第一节那句跑测试的提醒就是：早期 Codex 不跑测试，他们就在 developer message 里提醒它；后来训练出的模型更能理解用户说「改一下这里」时真正想要的是什么，提醒就删了。他还提到 `/goal`，一个让模型围绕单一目标长时间工作的机制，当初不加它模型会跑偏；按他在节目里的说法，新一代模型已经不需要它，直接说「去干一周」就行。另一个例子是他早期参与做的独立 code review 模型，据他说这部分能力现在已经并进了主线模型。后两条是他对内部情况的描述，我在外面没法验证，只当作方向上的佐证。

为什么顺序总是先外后内？我的理解很简单：因为外面便宜。我改一句提示词只要几分钟，改一段循环逻辑只要一个下午，当场就能看到效果；训练一个模型以月为单位，而且你得先知道要训练什么。模型外面这一圈，就是用来回答「要训练什么」的地方。一种行为值不值得有、做成什么样用户才满意、在哪些情况下会出岔子，这些都是在模型外面、在真实用户手里一点点试出来的。试明白了，它就成了下一轮训练的目标。

Tibo 其实亲口描述了这个过程。他说团队发现一个问题后，研究和工程会一起讨论：这该改 Harness，还是改模型？如果改模型，一个月、三个月还是六个月能拿到？有时候他们干脆决定 Harness 里什么都不做，等模型。这段话是我在这期节目里最看重的信息，因为它从内部确认了一件我在外面只能猜的事：外面试出来的东西，是有一条路通到训练里去的，而且有人在有意识地安排什么东西什么时候走这条路。后面我就管这条路叫「传送带」，上了传送带的东西，迟早会被模型学走。

所以我不太喜欢「拐杖」这个词。拐杖的意思是模型有伤，等伤好了拐杖就扔掉，它从头到尾是个次要的、补救性的东西。可按 Tibo 自己的说法，Harness 是「领先」模型的那一个。领先的东西不该叫拐杖。在我看来它更像下一代模型的需求文档：今天在外面跑通的东西，定义了明天模型里面该有什么。如果非要给它找个比喻，我会说它是一块试验田：新品种先在田里种一季，种成了才大面积推广。没有人会因为品种推广开了，就说那一季白种了。

还有一点，拐杖这个比喻只说到了厂商内部那条传送带，而试验田不止一块。上面「step by step」和 ReAct 那两个例子，都不是从哪家模型厂商内部的路线图里长出来的，它们先是论文和社区里公开的做法，别的 Harness 会抄，模型厂商也看得到。社区里成千上万个开发者写的提示词技巧、工具封装、循环设计，合起来是一块比任何一家厂商内部都大的试验田。哪些做法最后被训练进模型，很大程度上是被这块大田筛出来的。你我平时折腾的那些小技巧，也都在这块田里。

## 三、哪些东西，模型再强也替不了

「做在 Harness 里的能力，最后会被模型学走」，这句话我是认的。但我得给它画个边界，否则它就滑成了「模型外面的东西迟早全没用」，那就不对了。

我观察下来，会被学走的东西有一个共同点：它在替模型的**判断**兜底。什么时候该跑测试，任务做到什么程度算完，长任务怎么不跑偏，遇到报错是重试还是换路。这些情况下，模型需要的信息其实已经在上下文里了，它只是没有稳定地照着信息去做。而训练改的恰恰就是「信息都给你了，你怎么选」，所以这类东西不管写成一句提示词还是一整套循环机制，都能被训练吃掉。`/goal` 那么大一块机制也会退休，说明能不能被学走看的是它干的是哪类活，和代码量没关系。

我自己用的检验办法很土：假设模型的判断已经完美了，这段代码还有没有事做？没有，它就在传送带上。有，它就不在。

照这个办法筛一遍，我数出来至少有三类东西不在传送带上。

**事实。** 模型只能看到上下文窗口里的东西。「测试通过了」在模型嘴里是一句话，在系统里是一个退出码，后者只能由程序去真实的进程里取回来。训练可以让模型更自觉地去核对，但取事实的那条通道必须在外面。而且模型越强，它写的完成报告越像真的，我就越需要让程序而不是模型来填「退出码是多少、PR 链接在哪、CI 是红是绿」这几栏。

**边界。** 能不能读这个目录，能不能往这个仓库推代码，能花多少钱。一条边界如果要靠边界里面那一位的自觉来维持，它就不算边界。这和模型会不会犯错没关系，「它会选择不读」和「它读不了」是两件事，只有后者才算保证。规则可以让模型来起草，但执行规则的得是沙箱和权限系统。

**连续性。** 模型只在被调用的那几秒存在。两次调用之间、进程崩溃之后、机器休眠的时候，任务由谁拿着，做到哪一步了，哪些有副作用的操作已经做过、不能重做，这些都发生在没有模型在场的时间里，它判断得再好也帮不上忙。

这三类还有一个共同点：模型越强，它们越重。模型越强，我们越敢放手让它无人值守地做更长的事，而多出来的每一步，都多一个要核对的事实、一条要回答的「许不许」、一段要跨过去的空档。

这个分类不是我一个人关起门来推的。Boris 在同一场分享里说，他们每出一个新模型就删一轮 harness 里的代码，工具也经常下线（他的原话是 unship），然后有这么一句：**今天 Claude Code 的 harness 里剩下的代码，几乎全是安全、权限和静态分析，外加一堆 UI 代码**，其它的大多已经被他们下掉了。权限和安全是边界，静态分析是从程序那里取回来的事实，UI 是人和模型之间的交互。被学走的是判断，留下的是事实、边界和交互。这差不多就是我这个分类的官方版本，比我自己说有分量多了。Tibo 那边也一样：Codex 默认在沙箱里执行，需要沙箱外的权限就停下来问用户；内部所有 PR 都要过自动安全检查，查出安全问题就不让合并。developer message 在变短，这几样东西没有。

除了这三类，还有一样东西不会被通用的训练学走，那就是**你的**上下文。这一条在第五节和第七节我会反复提，因为它既决定了 Harness 往外长出来的那两层是什么，也决定了像我这样的独立开发者该把力气花在哪。

> **留给你的问题 ·** 把你现在的产品或 Agent 里的每一块，都用那个检验过一遍：假设模型的判断已经完美，哪几块还有事做？剩下的这几块，占你过去三个月工作量的多少？

## 四、补丁删掉之后，我的活去哪了

我做在模型外面的东西，被模型学会之后去哪了？

Tibo 的回答是删掉了，Harness 缩小了。我的回答是：那一块确实删了，但整个 Harness 没有缩小，它往外挪了一圈。这是我和他最实质的不同。

把这几年的工程名词排成一条线看：[Prompt → Context → Harness → Loop](/blog/20260615---frominternshipinterviewstoagentengineering/post)。前两个之间隔了三四年，后面几个几乎挤在一年里。我一直的看法是，这条线上模型这个核心基本是同一种东西，变的是我们下手的那一圈：词 → 上下文 → 环境 → 机制，一圈比一圈靠外。

以前我只会描述这个规律，说不清它为什么会这样。有了上一节「先外后内」那套说法，我觉得现在能解释了。

一开始卡住大家的是「怎么问」，所以大家打磨措辞，发明咒语。等模型把先想再答、听懂指令这些事学会了，抠措辞就越来越不划算，卡点挪到了「模型看到了什么」：任务一长注意力就散，喂多了不行，喂少了也不行，于是有了 Context Engineering。等模型的长上下文和工具使用稳了，卡点再挪到「模型在什么环境里干活」：有没有沙箱、工具、记忆、校验，能不能撑住 long-running 的任务，这是 Harness Engineering。再等模型能稳定地在一个环境里把长任务做完，卡点挪到了「谁来驱动它」：什么时候启动、什么时候停、失败了怎么重来，人不再手动敲 prompt，而是去设计驱动 Agent 的循环，这是 Loop Engineering。

每一次往外走，都是因为里面那一层稳了。它稳了，一部分是被训练学走了，一部分是被做成了标准件。不管哪种，结果一样：那一层不再卡人，新的卡点出现在更外面，新一轮的试也就在更外面开始。

而且**上一层从没消失，只是变成了下一层的零件**。Prompt 没有死，它现在是 Loop 里的一个组件。以前是人手工打磨一条 prompt，现在是 Agent 在循环里自己写 prompt、自己测、自己改。Gergely 在节目末尾其实也碰到了这一点，他说他怀疑事情不只是搭拐杖，还包括造模型要用的工具，下一代模型总不至于重新发明一遍 MCP 或者 skills。我听到这儿很想隔空接一句：对，这些就是已经稳下来、变成零件的那几层。

所以「Harness 在缩小」这句话，在 Tibo 的窄定义里是对的：developer message 确实在变短，`/goal` 这类机制确实在退休。但换成我的宽定义去看 Codex 自己，就在同一期节目里，他讲到内部的 Codex 默认接了 Slack、所有文档和所有代码，新人有问题先被问一句「你问过 Codex 了吗」；讲到他们分析的使用场景已经从 coding 扩到 finance、marketing 这些领域；Gergely 复盘时还提到把原本纯本地的 Codex 并进一套云端托管栈是什么样的工程。这些没有一样在模型里面。给模型看的那几段话在变薄，围着模型的那一整圈在变厚。

有意思的是，这句话的后半句，另一家模型厂商的团队自己补上了。Claude Code 团队 9 月发过一期 22 分钟的内部对谈，[How the Claude Code team uses Claude Code](https://www.youtube.com/watch?v=S-sYlFiGFv8)，出镜的是 Thariq Shihipar、Sid Bidasaria 和 Robert Boyce。里面讲到 Todo List 的来历：大约在 Sonnet 3.5 那个阶段，给模型五件事，它做完三件就放弃了，于是他们加了一个待办列表，效果立竿见影；一年之后，这个东西已经不怎么需要了。讲的人自己总结说，你得对自己造的东西非常不执着（very unattached），因为它们很快就会消失。

这不是嘴上说说，有一条查得到的版本记录。2026 年 8 月 14 日发布的 [Claude Code v2.1.233](https://github.com/anthropics/claude-code/releases/tag/v2.1.233)，release notes 里有一行：`TodoWrite` 和 `TaskCreate` / `TaskGet` / `TaskUpdate` / `TaskList` 这五个待办与任务跟踪工具，在 Opus 4.8、Sonnet 5、Fable 5、Mythos 5 以及更新的模型上不再提供；想要回来，设一个环境变量 `CLAUDE_CODE_ENABLE_TODO_TOOLS=1`。我特别喜欢它的做法：没有废弃，没有替换，名单之外的老模型照旧，只是对新一代模型默认关掉，还留了一个开关。这是我见过的「补丁被默认关掉」最干净的一手案例。当初为了「必须写下来才不会做一半就放弃」打的补丁，到了新模型上已经付不起自己的成本：每个工具定义都是每一轮都要读的 token，也是模型每一步多出来的一个岔路。

到这里，和 Tibo 说的一模一样。但另一位成员紧接着补了一段：这些功能当初做进 harness，很多是为了盖住当前模型的失败模式；模型变好了，就可以把它们拿掉；而与之平衡的是，他们现在在 Claude Code 里做的任务更大、更难了，模型需要新的工具才能在更大的任务上保持连贯，任务的范围一变，要给它的工具也就长得不一样了。

删掉一层，能交给它的任务变大，外面再长一层。我说的「往外挪一圈」，在厂商内部就长这个样子。

公平起见，也说说我这个判断站不稳的地方。名词换得这么快，有一部分是真有新东西，有一部分就是需要炒作，Loop 这个词两样都占。另外，如果真像 Tibo 说的，新模型不需要 `/goal` 就能自己干一周，那 Loop 这一层的相当一部分也已经上了传送带。我不觉得这推翻了「往外挪一圈」，它只说明这一层稳得比我预想的快，下一层会来得更早。

下一层是什么？我猜它在单个 Agent 的外面：多个 Agent 之间、Agent 和人之间、Agent 和组织之间怎么分工、怎么交接、怎么互相验证。上面那期视频让这个猜测有了一些具体的样子，下一节展开。

> **【待补 · 你亲手写过、后来因为模型升级或平台原生支持而删掉的一个补丁或功能：当初它解决什么问题，什么时候发现不需要了，当时什么反应，删掉之后你的精力转去了更外面的哪一层】**

## 五、我把 Harness 拆成了三层

那期视频开头有一个数字，我印象很深。主持的人问大家现在怎么用 Claude Code，一位成员说他 70%—80% 的工作现在发生在 Claude Tag 上，剩下 20% 才会打开 TUI 或桌面端去精修，或者在他想微操自己那几个 Claude 的时候。Claude Tag 是他们做的一个 Slack 原生 Agent。

这个数字很容易被读成「入口从终端换成了 Slack」，但我觉得入口是这里面最不重要的部分。另一位成员在同一段里解释了为什么这个形态管用：它住在 Slack 里，所以能去查额外的上下文，产品背景是什么，团队对这个产品应该是什么样做过哪些决定，而这让它的决策好了很多。他说他现在交给 Claude Tag 的问题，比「实现这个类、写这个函数」复杂得多。

代码仓库记的是系统现在是什么，团队的讨论记的是系统为什么是这样。只有前者，Agent 很容易做出局部正确、整体不合适的修改。视频里谈 code review 的那段也是同一个意思：Claude 写 PR 的时候可能并不完全理解这个 API 为什么这样设计、服务边界为什么画在这里，人类 reviewer 该把精力放在这类更大的问题上，挑小毛病的事交给 Claude 自己处理。

**Agent 拿到了「团队为什么这么做」，才接得住目标，而不只是任务。** 这部分上下文不在模型里，也不在单个产品的 Harness 里，它在团队里。看到这儿我才意识到，「模型之外的一切」这一圈现在已经厚到得分层看了。下面这个三层的拆法是我自己的，那期视频没有这么分，我只是拿他们的实践当材料。三层的名字我沿用英文里常见的叫法：产品 / Agent 层、Repo 层（Repo 就是代码仓库）、Organization 层（整个组织）。

### 第一层，产品 / Agent 层：大家最熟，也最先被模型学走

这是大家最熟的一层，前四节讲的主要也是它。我看一个 Agent 产品的 Harness 做得怎么样，基本就看四件事：Tool 怎么设计，MCP 怎么接，上下文怎么管，记忆怎么存。第一节里那句让 Codex 跑测试的提醒、Claude Code 删掉的那 80% 系统提示词，都发生在这一层。

这一层现在是两头被挤。里面被模型学走（图 1 里写的「内化」就是这个意思）：Todo 工具在新模型上默认关掉了；视频里还讲到 AskUserQuestion 这个工具，作者花了很长时间设计，早期模型不太会调用，后来越调越好，再后来他自己都不怎么用了，直接让 Claude 生成一个带图表和 mockup 的 HTML artifact 来问他问题。外面被平台做成标准件：function calling 是原生的，MCP 是公共协议，记忆在变成各家产品的内置功能。

我不是说这一层不值得做。第三节那三类东西，事实、边界、连续性，大部分就落在这一层，而且会越来越重。只是这一层里通用的那部分，保质期已经很短了。

### 第二层，Repo 层：五个人配五个 Agent 之后冒出来的事

第二层能出现，前提是第一层稳了：coding agent 已经好用到每个开发者都常驻一个，甚至几个。

你可以跟我一起设想一个 5 个人的开发团队，每人配一个 coding agent，一共 5 个。单看每一个 Agent，Harness 都没问题。但放在一起，立刻冒出一批新问题，而且没有一个能靠换更强的模型解决：

- 每个 Agent 只有自己这个会话的上下文。A 的 Agent 刚改了一个接口的约定，B 的 Agent 不知道，照旧约定又写了三个调用。
- 每个 Agent 进仓库都要重新认路。没有一份 repo index（给 Agent 看的仓库地图）告诉它模块怎么分、入口在哪、哪些目录是生成物不要读，它就只能自己翻，翻的成本每个会话付一遍，在团队里再乘以 Agent 的数量。
- 规范只在人的脑子里。提交怎么写、分支怎么命名、什么必须先跑 check、什么文件不许动，人靠默契，Agent 靠不了默契，只能靠写下来的东西。
- 边界没有人画。哪个模块归谁，哪些改动必须过人，两个 Agent 同时动一个文件怎么办。

这些问题的解法都很朴素：一份给 Agent 读的 repo 说明，一套写下来的开发规范，一些明确的边界约定，加上 CI 和分支保护这类本来就有的东西。朴素到很多人不觉得这也算 Harness。但按我第一节的定义，它在模型外面，它决定模型被用得好不好，它当然算。区别只在于写这一层的人变了：第一层是做产品的人写的，第二层是每一个用 Agent 的开发团队自己写的。今天每个认真用 coding agent 的团队，不管自己知不知道，都在做 Harness 工程。

视频里 Robert 讲他做 Claude Tag 时的主要精力，就花在这一层上。他们在大量地用 Claude Tag 开发 Claude Tag 自己，所以他的重点是保证开发环境和 dev loop（改代码、跑起来、看结果的那个循环）对 Claude 来说足够好用，让它能做他作为人类要做的每一件事，把软件构建出来，并且端到端地验证它能工作；软件越复杂、集成越重，这件事就越难。他们的 code review 也是这一层的东西：先大规模 fan out（同时撒出去很多路）去找可能的 bug，再对每个候选从三个不同视角做对抗式复核，把误报滤掉，只把最值得看的交给人。Claude 给 Claude Code 提的 PR 会自己测过，附上截图。

Boris 在 YC 那场分享里讲的两件事，让我更确信这一层值得花力气。一件是 Bun 从 Zig 到 Rust 的重写：Bun 团队的 Jarred 每出一代新模型就把这个题目丢给它试一次，直到有一代做成了。按 Boris 的说法，那是一个 prompt 加一个编排大量 Agent 的工作流，跑了 11 天，中途有人纠偏，但不是一点点手把手带着写。能成的前提不在指令怎么写，在于 Bun 自己和 Node.js 都有一大套现成的测试，做没做对，随时可以验证。另一件是他们让 Claude 维护自己的代码库：其中一个例行任务每天跑一遍，找死代码并自动开 PR 删掉，prompt 只有一句话，用静态加动态分析去找是模型自己补出来的做法。两件事里，人写的指令都很短，撑住结果的是仓库里那套 Agent 自己跑得动的验证。**「能不能验证」比「怎么写指令」更决定成败**，而能不能验证，是 Repo 层的事。

拿第三节的分类来对一下，Repo 层装的还是那三类东西，只是主语从「一个 Agent」变成了「一群人和一群 Agent」：CI 的红绿和谁在什么时候改了什么是事实，模块归属和分支保护是边界，会话与会话之间、Agent 与 Agent 之间的交接是连续性。

> **【待补 · 你自己团队（或你一个人带几个 Agent）在 repo 层的具体做法：给 Agent 读的说明是怎么组织的，哪条规范是被坑过之后才写下来的，边界怎么约定，哪一处做了之后协作明显顺了】**

### 第三层，Organization 层：Agent 开始在整个团队里跑腿

再往外一层，主语变成整个组织，不只有开发，还有运营、增长、设计、法务。

Thariq 在视频里讲的一个例子，是我见过的对这一层最完整的描述。他要做一个新的内部工具，需要很多人的支持。他做的第一件事是问 Claude Tag：我有这么个想法，应该找谁聊，谁可能感兴趣？拿到相关的人之后，让它出 mockup，全在 Slack 里，手机上就能看。然后它做实现。他不确定这个工具是否真的好用，于是加了很多事件埋点，部署到内部，看大家怎么用；Claude Tag 替他盯着，有人给反馈就来提醒他。后来他从事件里看出用户没有走完整个流程，想改进漏斗。他本来想的是「我有个主意，让它照做」，转念改成了让 Claude 去改进这个漏斗、自己出几个方案，他的主意只作为一个例子给进去。他说，就是在这一刻，这件事对他来说真正通了。

这个例子里，写代码只占中间一小段。前面是找人、对齐，后面是埋点、观察、收反馈、改漏斗，这些以前分属产品、运营和增长。他们把其中三样东西明确叫做 Claude Code 里的 primitive（可以理解成最基础的积木）：verification、code review、feedback，最后一样指的是接上你的数据存储或事件存储，指标也好，Slack 也好，GitHub issues 也好。

这一层的 Harness 要回答的问题，和前两层是同一类，只是尺度更大：

- **事实**：真实用户到底用了没有，卡在哪一步。这不在代码里，在埋点和反馈里，得有通道把它取回来。
- **边界**：Agent 可以替谁说话，可以主动打扰谁，能看到哪些频道和文档。视频里说这是他们第一次把用户界面和 transcript 比较彻底地解耦：你在 Slack 里看到的消息，是 Claude 调用一个发消息的工具发出来的，它的内部过程不直接显示，只留一个查看完整 transcript 的链接。Robert 说一开始有点吓人，后来反而觉得解放，因为是 Claude 在选择对他说什么、什么时候说。体验上这是进步，但我想提醒一句，「它选择说什么」和「它被允许说什么」仍然是两件事，后者得由系统来定。
- **连续性**：决策的来龙去脉。三个月前为什么否掉了那个方案，这个定时任务为什么设成每小时一次。人会离职，会忘，聊天记录会沉下去。组织层的连续性，说到底就是「团队为什么这么做」有没有被记在 Agent 读得到的地方。

得老实交代一下：视频里的主角是一个开发团队，运营和增长的部分是我顺着这个方向自己推的，证据比前两层薄。他们自己也没说已经走完了：Thariq 让 Claude 录了一段自己操作 TUI 的过程来验证，看完之后还是自己 clone 下来试了一遍，图个心安；他说以后大概可以不 clone，但那是以后。

### 这三层是怎么一层叠一层的

三层是一层一层叠上去的，每一层能成立，前提都是里面那层稳了，并且把它当零件用。Agent 不好用，谈不上五个 Agent 怎么协同；Repo 层乱着，让 Agent 在组织里替你推进事情就是一句空话。这和第四节那条名词演进线是同一个规律，只是尺度更大。

三层被模型学走的方式也一样，每一层都在重复同一种分化：**通用的机制会被模型学走、被平台做成产品，私有的内容留给你。** 第一层里，工具调用的机制是原生的，你的工具本身是你的。第二层里，读仓库、跑 review 的机制会被 coding agent 产品内置，你们的规范和边界得你们自己写。第三层里，Slack 原生 Agent 这种形态会是平台卖给你的产品，而「你们为什么这么做」只能由你们自己攒。

差别在比例。越往外，私有内容占的比重越大。第一层大部分是通用机制，所以大部分在传送带上。第三层的主体是一个组织自己的决策史，不在任何人的训练集里。所以我才说最里面那层正在被模型学走，而最外面那层才刚开始：它开始得晚，是因为要等里面两层稳；它会留得久，是因为它的主体是别人拿不走的东西。

> **留给你的问题 ·** 你们团队最近一次「为什么这么定」的讨论，现在记在哪里？如果明天让一个 Agent 接手相关的活，它读得到吗？

> **留给你的问题 ·** 如果你们每人配一个 coding agent，现在最先出问题的会是哪一处：认路、规范、边界，还是验证？

## 六、一笔速度账：我补的东西，长得有没有模型快

前面几节合起来，我推出了一个产品判断。它是我自己的判断，可以被反驳，什么情况下不成立我也会写出来。

如果模型外面这一圈，是能力被模型学会之前的那一步，那任何一个 AI 产品都在一场停不下来的赛跑里：你在模型外面补东西，模型在里面把东西学走。用户愿意为你的产品付钱，而不是直接去用模型厂商自己的入口，理由只有一个：通过你能做成的事，比直接用模型能做成的事，多出来的那一截。

这一截今天有多大，我觉得没那么重要。重要的是它在变大还是变小。用大白话说：**你补的东西，要长得比模型自己变强的速度快。** 我借数学课上的词，管这个「长得有多快」叫斜率，后面就这么简称了：你的 Harness 的斜率，得高于基模（底层的基础模型）的斜率。否则你补的速度赶不上它被学走的速度，这一截每过一代模型就薄一点，产品其实是在融化的。

这里要分清两个东西：现在领先多少（水平），和领先得越来越多还是越来越少（斜率）。Todo 列表在 Sonnet 3.5 那个阶段是实打实的水平：有它和没它，五件事做完和做到一半，差别立竿见影。但它是一次性做出来的领先，一年之后模型自己追平了，到今年 8 月干脆在新模型上默认关掉。如果之后不再往上加，这一截迟早被填平。水平高只说明你现在领先，斜率才说明你能不能一直领先。

那 Harness 的斜率由什么决定？我想来想去，是三样东西。

**第一，操作空间。** 模型外面有多少东西可以试，试一次要花多少钱、多少时间，试完能不能让程序自动判断好坏。Coding agent 的 Harness 这一年长得这么快，我觉得很大程度上是因为代码这个东西太适合拿来试了：输出是文本，能 diff，能跑，有退出码，试一次的成本很低，于是循环、验证、fan out 这些机制一层层叠了上去。

**第二，有没有只属于你的信号在喂它。** 私有数据、真实用户的反馈闭环、某个行业的活到底怎么干。通用的 Harness 技巧大家都会，也都会被模型学走；能让 Harness 一直往上长的燃料，是别人拿不到的东西。

**第三，Harness 长出来的那一截，有没有人接着。** 也就是有没有增量市场，说白了就是新多出来的用户和需求。你每多补一层，是不是就多出一批原来做不成这件事的用户，或者多出一类原来做不了的任务。如果需求是一块固定的饼，模型每进步一点就直接替代你一点，那你的 Harness 长得再快也只是在守。

### 为什么我不看好大部分 AI 视频衍生应用

我拿这三条去看了这半年最热的一类产品：以 AI 视频、AI 生图为底座的衍生应用，做设计的，批量生成短剧的，做营销视频的。我对其中 To C 的那一大批不看好。不是因为它们现在做得不好，而是在我看来，它们的 Harness 几乎没有斜率。

先看操作空间。视频生成贵，而且按量计费。以字节的 Seedance 为例，官方公开的 2.x 价格是按秒的阶梯，从 Mini 720p 的每秒 0.04 美元到 4K 的每秒 0.353 美元；2.5 的官方价格据我所知到今年 7 月还没有公布，我不猜。Coding agent 里那种「生成、检查、不行就重来、同时开十路挑最好的」的套路，搬到视频上，每多试一次都是真金白银。再加上输出是一团像素，没有 diff，没有退出码，「这个镜头好不好」很难让程序判断，试起来既贵又难自动化。

结果就是这类产品的 Harness 大多停在很薄的一层：提示词模板、分镜拆解、素材拼接、一个好用的界面。片子质量的每一次明显进步，人物一致性、时长、口型、音画同步，都来自底层模型换代，而不是来自产品自己。模型进步的好处，所有用同一个 API 的竞品同时拿到，模型厂商自己的入口也同时拿到。你的斜率约等于零，基模的斜率很陡，那一截只会越来越薄。更难受的是，产品里最重的那几块工程，恰好是下一代模型最先吃掉的：为了保持人物一致性做的各种绕路，为了凑时长做的分段拼接，外挂的配音和音效流程。

再看有没有人接着。To C 这一侧，可以直接去看短剧市场赚不赚钱。掌阅科技今年 1 月披露了上市以来的首次年度亏损，当时的公开报道（新浪财经、澎湃等有转载）写得很直接：短剧火爆但难赚钱。得说明一下，这条说的是短剧这门生意本身，不是 AI 短剧；我引它是想说，下游的利润池本来就浅。AI 把制作成本打下来了，但它是给所有人同时打下来的，大家成本一起降，利润不会留在制作这一环，会流向流量入口和卖生成量的人。

所以我的判断是：**这半年视频生成热潮里最大的赢家，其实是模型厂商。** Seedance 不管怎么打折、怎么换算成积分和会员，说到底都是在按生成量卖算力，也就是卖 token。至于产品本身，依我自己使用和观察的感受，它并没有在模型上面做出多好的一层视频生成和编辑的 Harness。这一句是我的主观评价，不是测评结论。

### 同样的账，放到生图上为什么好看一点

同样的三条放到生图上，情况好一些。图像的 API 比视频便宜得多，能力也出来得早，这两点直接换来了操作空间：一次多出几张挑一张、局部重绘、分层、用各种条件去控制构图和姿态、把多步流程搭成节点式的工作流，这些在生图上都是试得起的，也确实已经长出了一个不小的工具生态。便宜和早，意味着外面的人有更多时间、更多次数去试，Harness 就有机会长出斜率。

但同样的提醒也适用：通用的那部分迟早会被模型和平台收走。生图产品能留下来的，我猜还是接了私有素材、私有规范、私有流程的那些。

### MiniMax-H3 放出权重之后，这笔账变了

视频这边的转机，我觉得来自开放权重。[MiniMax-H3](https://github.com/MiniMax-AI/MiniMax-H3) 放出了权重（[Hugging Face](https://huggingface.co/MiniMaxAI/MiniMax-H3)），可以用 ComfyUI 或 Diffusers 本地部署，社区实测量化版最低在一张 RTX 3060 12GB 上就能跑。开放的权重原生是 768p 短边、最长约 15 秒，同一次前向里直接带立体声音频。

这件事对 Harness 的意义是，它把「试一次」要多花的钱，从按秒付费变成了电费和时间。前面说视频 Harness 长不出来的第一个原因是试一次太贵，现在这个约束松了：多路生成再挑选、自动检查不合格就重来、围绕自己的素材搭一整条流水线，这些在按秒计费时算不过来的做法，开始算得过来了。权重在自己手里，量化、改推理流程、接进自己的工具链，也都是可以动手的事。我们这些平民玩家，第一次有了在视频上折腾 Harness 的条件。

几条边界我得写清楚，免得你被我带偏。第一，它是开放权重，不是无条件开源：用的是 MiniMax H3 Community License，研究和商用免版税，但有地区限制，目前不覆盖欧盟、英国、美国和韩国。第二，原生规格就是 768p 和 15 秒左右，2K 重生成之类的能力在托管 API 那一侧。第三，成本降下来同样是给所有人降的，它本身不构成护城河。它改变的是「试不试得起」，把斜率从几乎不可能变成了有可能；有没有斜率，仍然取决于后两条：你有没有私有的信号，长出来的那一截有没有人接。

### 我可能在哪里想错了

我不想把这一节写成唱衰，所以把它不成立的情况也列出来。

**这些方向在以下情况我觉得仍然成立：**

- **To B，或者手里有私有数据和私有流程。** 品牌的素材库和视觉规范，电商的商品库，行业的合规审核规则，一家公司内部的制作流程。这时候 Harness 的燃料是别人拿不到的，模型越强，这些东西越好用，而不是越没用。
- **你本来就有 IP 或者分发。** 这时候 AI 对你是降成本的工具，你的护城河本来就不在 Harness 上，上面的分析对你不适用。
- **Harness 做在改得动、查得了的中间产物上，而不是像素上。** 剧本、分镜、时间线、图层，这些是文本和结构，能 diff、能检查、能局部修改。把力气花在编辑层而不是生成层的产品，操作空间大得多。
- **底层成本被开放权重打下来之后**，上面说的那些试法第一次试得起。

**什么情况说明我错了：** 如果有一个 To C 的 AI 视频衍生应用，在底层模型换了几代、竞品都能调同一个 API 的情况下，仍然持续留住用户并且盈利，那就说明它的 Harness 有真实的斜率，而我没看出来。另外我也承认，我对这类产品的观察来自外部，没有任何一家的内部数据；「斜率」在现实里也没法精确测量，基模的进步在不同任务上很不均匀，某个细分场景里基模可能好几代都不碰，那里的窗口会比我说的长。

斜率虽然没法精确量，但可以粗略地估，你可以拿自己的项目试一遍。拿一组你自己场景里的真实任务，每次底层模型换代，跑两遍：一遍用你的完整产品，一遍用「裸模型加最薄的一层壳」。两者的差就是那一截。连续两三代记下来，它在变大还是变小，你自己就能回答。

> **【待补 · 你自己算过或估过的一次 Harness 斜率：哪个产品或项目，拿什么任务比的，换了哪几代模型，那一截是变大了还是变小了。没有精确数字就写估法和结论】**

> **留给你的问题 ·** 过去两次底层模型升级，你的产品比「直接用模型」多出来的那一截，是变大了还是变小了？变化的部分，是你做出来的，还是模型送的？

## 七、看不到训练路线图，我是怎么做的

Tibo 描述的「改 Harness 还是改模型、一个月还是六个月」，是一个只有模型厂商才有的选项。他们看得到训练路线图，所以可以理性地决定「这个不做了，等模型」。

我看不到。我用的是别人的模型，不知道某个毛病是不是正在被修，也不能拿别人的发版日期当自己的交付计划。用户今天有个任务要完成，「下一代可能会好」帮不上他。这是 Tibo 的视角里没有、而我必须自己补上的部分：**同一个循环，站在传送带外面的人该怎么用。**

我的做法有四条，你不一定要照搬，但可以拿来对照。

**第一，我把通用补丁当成有保质期的东西来做，并且按这个预期去算账。** 保质期大概多长，两家都给过经验值。Claude Code 团队说 Todo 列表从必须有到不再必要，用了一年左右；Boris 给普通用户的建议更激进：每六个月把你的 CLAUDE.md 删一次，skills 也删。换句话说，一块通用的 Harness 工作，能值钱的时间差不多就是一两代模型。我说这个不是贬低它，提前一代拿到能力，在这个行业里就是实打实的时间窗口。但它也提醒我，别为一块通用补丁投入要三年才能回本的工程量。Tibo 给团队的那条原则，为了绕过模型缺陷写一万行代码的拐杖，多半是做错了，对我们这些外面的人同样适用，甚至更适用，因为我们连它什么时候过期都不知道。

**第二，每个补丁都带着自己的到期检验。** 加补丁的时候，我会把它解决的那次失败记下来，具体到能重跑：任务是什么，模型做了什么，漏了哪一步。「模型不够主动」这种描述没用，「改了三个文件之后没跑 check 就报告完成」才有用。新模型来了，拿这几个失败任务，有补丁、没补丁各跑几遍。没补丁也过，就删。这件事厂商自己也在做，而且做得更狠。Boris 说他们每出一个新模型就做一次 ablation（消融实验，说白了就是拿掉一块，看效果变没变）：把整份系统提示词删掉，再一行一行加回来，看每一行到底有没有用；工具也是同样的待遇。他们有路线图尚且要这样一行行验，我们没有路线图，更只能靠回归测试知道什么时候该删。不这么做会怎样不难想见：每次失败都变成一条永久规则，几个月后攒出一堆互相打架、没人敢动的提示词，而且旧补丁会反过来拖累新模型。比如一条逼它每次先按固定顺序读完一长串文件的规则，对旧模型是防漏看，对新模型就是让两行的修改绕一大圈。

删不掉的补丁也在告诉我一些事。它要么确实还需要，要么根本不是判断类的补丁，而是第三节那三类东西被我误写进了提示词。很常见的一种：「请先向用户确认再执行」，其实是权限检查没做在程序里，只好写给模型看。这种不该删，该搬家，从提示词搬进代码。

**第三，长期的力气花在训练数据够不着的地方。** 训练学走的是大量用户共有的行为。跑测试、不跑偏、好好用工具，这些对几百万用户都成立，所以会被学走，也所以会被平台和模型公司卷走。正面去做一个通用 Agent，没数据、没入口，模型一更新就失去价值，这条路我一直不看好。

够不着的，是只属于你那个领域、你那个团队、你那个用户的东西：这个行业的活到底怎么干，这个定时任务为什么设成每小时一次、是为了省钱还是因为上游有限流，这位用户说「老样子」指的是什么。这些不在任何人的训练集里，模型再强也推不出来，只能由你一点点攒下来，再由 Harness 在合适的时候递给它。智能可以租，上下文得自己攒。上一节说斜率的燃料是私有信号，第五节说越往外层私有内容占比越大，和这里说的其实是同一件事。Tibo 讲的内部 Codex 接上 Slack 和文档之后新人什么都能问，Claude Code 团队的 Claude Tag 能查到团队做过的决定，值钱的都不是模型，是他们自己的上下文。

这也是为什么我觉得垂类做得越深，反而越要去接通用能力。你的 know-how 做成 MCP、插件、skill，接到别人已经在用的通用 Agent 上，底层怎么换你都不怕。很多产品最后不会以 App 的形态赢，而是以零件的形态赢，这和「上一层变成下一层的零件」是一回事，只是这次你主动去当那个零件。

**第四，我默认脚下的 Harness 本身也会被换掉。** 收走通用 Harness 的不只是模型，还有平台。今天大多数人不会从零写一个 coding agent 的 Harness，而是直接站在 Claude Code、Codex 这类现成的 Harness 上面干活。对独立开发者来说这是好消息，不用自己造一个通用 Harness 了。但脚下这一层自己也在换：v2.1.233 是一次普通的版本更新，升完级，你的 Agent 手里就少了五个工具；Boris 说他们一直在加东西，也一直在下线东西。通用的那部分正在被两头挤，里面被模型学走，外面被平台做成标准件、并且按平台自己的节奏改动。所以你得有自己的测评：底下的模型或 Harness 换了之后，「在我的任务上是变好了还是变坏了」，只能靠你自己的评测回答。好消息是，这套评测、第二条的到期检验、上一节估斜率用的任务集，其实是同一组任务，花一份力气，有三个用处。

## 八、说回「泄气」这件事

最后回到 Gergely 那句话：我做的东西，下一版模型就会了，有点泄气。

我理解这个感受。但我觉得它背后有一个没说出口的假设：一份工作值多少，等于它产出的代码能活多久。按这个标准，这一行确实让人泄气，因为外面这圈代码注定活不长。Claude Code 团队在视频里说得更直白：以前一项技术的保质期以年计，做一个产品，可以相当确信它几年内都成立；现在底下的技术每两个月就变一次，你既要站到前沿之外去感受那条边，又要给今天正在用模型的人提供价值。

可我不这么算账。我做在外面的一个东西被模型学走，意思是它做成了。你在外面跑通的东西进了模型，说明你比模型早一代看到了那个能力该长什么样。代码会被删，但「早一代看到」这件事会留在你身上，而且它直接决定你能不能看到下一层在哪。亲手做过里面那层的人，最先知道它什么时候稳了，也最先撞上外面那层的新问题。在一个名词半年换一拨的行业里，没人有十年的 Loop Engineering 经验，最资深的人和刚入行的人读的是同一条推。资历会过期，这种一层层往外追的能力却是越滚越多的。

那期视频最后一段，Thariq 问另外两个人怀念以前软件工程的什么。一个说他以前从性能工程里得到很多乐趣，钻进系统里把性能一点点抠出来，现在 Claude 做这个比他强得多，他的注意力转到了怎么更快地把新想法变成原型、再变成产品上。另一个说他喜欢抠 UI 细节，曾经花了一天叠径向渐变，就为了在个人网站上复刻 Mac OS 10.4 的 Aqua 按钮，现在他不会再手工做这种事了。但他接着说，这让他想起七八岁时想做游戏、不会写代码，就用 PowerPoint 拼可点击的形状；现在整个软件工程对他来说都够得着了，他不用再因为自己没有某项技术就把一个想法划掉。失去的是在某一层上磨到极致的手艺，得到的是可以去够更外面的东西。我觉得这和我上面说的是一回事。

不过我也不想把话说得太圆。如果你的整个产品就是一块通用补丁，别的什么都没有，那泄气是对的，它是一个很准的信号，告诉你斜率已经输了，该往外走一层，或者往垂类里扎深一层了。为脚手架被拆掉而难过没有必要，但如果手里只有脚手架，那确实该想想楼在哪。这话也是说给我自己听的。

所以我对 Tibo 那句话的完整态度是这样的。Harness 总比模型领先一点，我同意，而且我觉得这正是它该干的活：它是试验田，不是拐杖。领先的部分会被模型追上，我也同意，该删就删，只是删的时候手里要有证据。Harness 因此在缩小，这条我不同意。缩的是已经完成任务的那一层，整个模型之外的活在往外扩，从一个 Agent，到一个仓库，到一个组织。而你站在哪一层、往外长得有多快，决定了你的产品是在被模型学走，还是在被人需要。

名词还会继续换。Loop 之后一定还有下一个词，可能明年，可能下个月。看到它的时候，我大概会问自己四个问题：它指的是哪一圈，这一圈现在在试什么，试出来的东西多久会被里面学走，我在这一圈里的斜率比它快还是慢。这四个问题答得上来，名词就只是噪音。真正值得攒的，是那个能一层层往外搭、搭完敢拆、拆完知道下一层在哪的系统。

如果你读到这里，手边正好有个自己的项目，不妨把文中那几个「留给你的问题」挨个过一遍。要是得出的结论和我不一样，那就更好了，我很想听听。
