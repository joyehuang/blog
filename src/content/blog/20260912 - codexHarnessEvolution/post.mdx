前阵子听了 The Pragmatic Engineer 的一期播客，[Gergely 和 Codex 负责人 Tibo Sottiaux 聊了一个多小时](https://newsletter.pragmaticengineer.com/p/building-codex-with-tibo-sottiaux)。里面有一小段，我听完琢磨了好几天。

Gergely 问：早期的 Codex 改完代码不会主动跑测试，过了几个月它自己会跑了，你们改的是提示词，还是模型？

Tibo 的回答大意是：Harness（模型外面包的那层工程，下面细说）总是比模型领先一点。模型其实有这个能力，只是不够稳，他们就先在外面加一句提醒顶着；等下一代模型训出来，它自己就会了，这句提醒也就删了。时间一长，他们写给模型的那段说明越来越短，Harness 也越来越小。

节目最后 Gergely 说了句大实话：作为开发者，这听着有点泄气。我今天认真做的东西，下一版模型自己就会了，然后就可以删掉。

这个现象我完全认，我自己做 Agent 也一直是这么理解的。但我的感受和他俩都不太一样：Tibo 说 Harness 在变小，我看到的是它越做越大；Gergely 觉得泄气，我反而觉得这是现在做 AI 产品最有意思的地方。

所以这篇就聊 Harness 这一件事。都是我自己的想法，不一定对。

<TldrCard>
- **除了模型，剩下的全是 Harness。** 做 AI 产品的人，做的其实都是这一层。
- **通用的补丁迟早被模型学走。** 提醒它跑测试、给它一个 Todo 列表，这类东西活不过一两代模型。学不走的是：拿真实结果、管权限、记住任务做到哪了，还有只属于你的上下文。
- **但 Harness 没有变小，它在往外长。** 我把它分成三层：产品本身、代码仓库、整个组织。Claude Code 团队里已经有人 70%—80% 的工作是在 Slack 里 @ 一个 Agent 完成的。
- **做产品要算一笔账：你涨得有没有模型快。** 我管这个叫斜率。涨得没模型快，产品就是在慢慢被模型吃掉。这是我不看好大部分 To C 的 AI 视频衍生应用的原因。
</TldrCard>

## 一、Harness 到底指什么

我做 Agent 的时候，习惯把它拆成四样：大脑、记忆、工具、循环。

大脑就是模型，这是唯一一样我不用做、也做不了的东西。我不会去训一个模型，我能决定的只有调哪一个。剩下的全是我的活：记忆怎么存，工具怎么接，上下文怎么管，出错了怎么办。

这一整圈，业内叫 Harness。LangChain 的 Vivek Trivedy 有句话说得最干脆：Agent = 模型 + Harness，模型之外的一切都是 Harness。

我自己的理解还要再宽一点：**只要你在做 AI 产品，而你又不是训模型的那家公司，你做的东西就全是 Harness。** AI 写作工具的编辑器是，客服机器人接的知识库是，你给自己的 Agent 写的那份长长的偏好说明也是。更早的 Prompt Engineering、Context Engineering 也都算，只是那时候还没人用这个词。

这一圈有多重要？看两个例子，模型都没换，只动了外面。

第一个就是开头那件事。早期 Codex 改完文件不跑测试，Tibo 他们就在提示词里加了一句提醒。模型没换，多了一句话，它就开始跑了。

第二个方向正好相反。Claude Code 的作者 Boris Cherny 今年在 YC Startup School 上讲过（[官方逐字稿](https://www.ycombinator.com/library/UN-boris-cherny-building-claude-code)）：Opus 5 发布的时候，他们把 Claude Code 的系统提示词删掉了 80%。因为里面很多话是在纠正老模型的毛病，新模型已经没这些毛病了。他还说，把这些提示去掉之后，模型反而稍微聪明了一点。

两个例子放一起看：外面这圈做对了，模型的本事才用得出来；外面这圈过时了，反过来还会拖累模型。很多看起来是「模型不行」的问题，其实是外面没做好。我自己用某个 coding 模型时就碰到过，它的工具调用老失败，查下来是参数格式对不上，跟模型聪不聪明没关系。

## 二、补上去的东西，模型迟早自己会

Tibo 说的那个现象，过去几年发生过很多次。

2022 年大家发现，在提示词最后加一句「Let's think step by step」，模型做推理题的正确率会明显上升。那两年流行的各种 magic words 都是这个路数。到 2024 年推理模型出来，「先想再答」直接被训进了模型，这句咒语就没人写了。

工具调用也一样。最早是在提示词里约定一种输出格式，外面的程序去解析文本、执行、再把结果塞回去。后来厂商把 function calling 做成了模型的原生能力，那层解析代码就用不着了。

最近的一个例子在 Claude Code。团队 9 月发过一期 22 分钟的内部对谈，[How the Claude Code team uses Claude Code](https://www.youtube.com/watch?v=S-sYlFiGFv8)，出镜的是 Thariq Shihipar、Sid Bidasaria 和 Robert Boyce。里面讲到 Todo List 的来历：大概在 Sonnet 3.5 那会儿，给模型五件事，它做完三件就不干了，于是他们加了一个待办列表，效果立竿见影。一年之后，这个东西已经不怎么需要了。

这不是嘴上说说。8 月 14 日发布的 [Claude Code v2.1.233](https://github.com/anthropics/claude-code/releases/tag/v2.1.233)，release notes 里写着：`TodoWrite` 等五个待办和任务跟踪工具，在 Opus 4.8、Sonnet 5、Fable 5、Mythos 5 以及更新的模型上不再提供，想要回来得自己设环境变量 `CLAUDE_CODE_ENABLE_TODO_TOOLS=1`。当初为了「不写下来就会做一半」打的补丁，到新模型上已经不划算了：每个工具的定义，模型每一轮都得读一遍。

为什么总是先在外面做，再进到模型里？**因为外面便宜。** 改一句提示词几分钟，改一段循环逻辑一个下午，当场就能看到效果。训一个模型要按月算，而且你得先知道要训什么。「要训什么」恰恰是在外面、在真实用户手里一点点试出来的。

Tibo 在节目里也讲了他们内部怎么做：发现一个问题，研究和工程会一起商量，这个该改 Harness 还是改模型？改模型的话，一个月、三个月还是六个月能拿到？有时候他们干脆决定 Harness 里什么都不做，等模型。

Tibo 管这些补丁叫拐杖，我觉得这个词不太准。拐杖是伤好了就扔的东西，可这些补丁干的事更像是在给下一代模型探路：今天在外面跑通了什么，明天模型里就该有什么。而且探路的不只是厂商自己。「step by step」和早期的工具调用，都是先从论文和社区里冒出来的。你我平时折腾的那些小技巧，也算在里面。

### 那什么东西学不走

外面的东西迟早全被学走吗？不是。

我有个土办法，就问一句：**假如模型已经足够聪明，这段代码还用得着吗？**

提醒它跑测试、教它别做一半就停，用不着了，这类迟早被学走。但有三样东西，模型再聪明，也得有人在外面做：

- **拿真实的结果。**「测试通过了」从模型嘴里说出来只是一句话，真正的退出码得程序去取。而且模型越强，它写的完成报告越像真的，我越得让程序而不是模型来告诉我 CI 是红是绿。
- **管权限。**「它会选择不读这个目录」和「它读不了这个目录」是两回事，只有后者才算保证。规则可以让模型起草，但执行得靠沙箱和权限系统。
- **记住任务做到哪了。** 模型只在被调用的那几秒存在。进程崩了、机器休眠了，任务做到哪一步、哪些操作已经做过不能再来一遍，都得外面记着。

而且模型越强，这三样越重。因为它越强，我们越敢放手让它自己跑更久，要核对的结果、要管的权限、要接上的断点都跟着变多。

这不是我关起门来想的。Boris 在那场分享里说，他们每出一个新模型就删一轮 harness 里的代码，然后有这么一句：**今天 Claude Code 的 harness 里剩下的代码，几乎全是安全、权限和静态分析，外加一堆 UI。** 跟我上面列的基本对得上。

还有一样学不走的，是只属于你的上下文：你们团队为什么这么定，你的用户说「老样子」指的是什么。后面两节说的主要就是它。

## 三、但 Harness 没有变小，它在往外长

补丁一个个被删，Harness 是不是就像 Tibo 说的越来越小了？

要看他指的是哪一块。他说的 Harness，是 Codex 团队自己维护的那个核心：沙箱、工具，加上每轮开头写给模型的那段说明。这一块确实在变小，我信。

但同一期节目里，他还讲了另外几件事：内部的 Codex 默认接了 Slack、所有文档和所有代码，新人有问题会先被问一句「你问过 Codex 了吗」；使用场景已经从写代码扩到了 finance、marketing。这些没有一样在模型里面。**写给模型看的那几段话在变短，围着模型的那一整圈在变厚。**

Claude Code 那期视频里说得更直接。讲完 Todo 列表怎么退休，另一位成员马上补了一段：这些功能当初是为了盖住模型的毛病，模型变好了就可以拿掉；但与此同时，他们现在交给 Claude Code 的任务更大、更难了，要在更大的任务上不跑偏，模型又需要新的工具。

删掉一层，能交给它的任务变大，外面再长一层。我[之前写过](/blog/20260615---frominternshipinterviewstoagentengineering/post) Prompt → Context → Harness → Loop 这条线，背后也是同一回事：里面那层稳了，大家下手的地方就往外挪一圈，而上一层并没有消失，只是成了下一层的零件。

那现在外面这一圈长到哪了？视频开头有个数字我印象很深。主持人问大家现在怎么用 Claude Code，一位成员说，他 **70%—80% 的工作发生在 Claude Tag 上**（他们做的一个住在 Slack 里的 Agent，放到国内就相当于在飞书里 @ 一个 bot），只有剩下 20% 才会打开终端或桌面端去精修。

为什么在 Slack 里反而更好用？另一位成员的解释是：因为它住在 Slack 里，能翻到团队的讨论，知道产品的背景、大家之前做过什么决定，所以它做的判断好了很多，他现在敢交给它的问题比「写个函数」复杂得多。

代码仓库里记的是系统现在长什么样，聊天记录里记的是它为什么长这样。只有前者，Agent 很容易改出一个局部正确、整体不合适的东西。

看到这儿我意识到，Harness 这一圈已经厚到得分层看了。下面这个三层的分法是我自己的，视频里没这么分。

### 第一层：产品本身

这是大家最熟的一层。我看一个 Agent 产品的 Harness 做得怎么样，基本就看四件事：Tool 怎么设计，MCP 怎么接，上下文怎么管，记忆怎么存。前面讲的跑测试提醒、被删掉的 80% 提示词、Todo 工具，都发生在这一层。

这一层现在两头受挤。一头被模型学走：视频里讲到 AskUserQuestion 这个工具，作者花了很长时间设计，后来他自己都不怎么用了，直接让 Claude 生成一个带图表的 HTML 页面来问他问题。另一头被平台做成标配：function calling 是原生的，MCP 是公共协议，记忆也快成各家产品的内置功能了。

不是说这一层不值得做，上一节那三样学不走的东西大部分就在这一层。只是这层里通用的部分，现在活不了多久。

### 第二层：Repo

coding agent 好用到人手一个之后，这一层才冒出来。

想象一个 5 人的开发团队，每人配一个 coding agent。每个 Agent 单独看都没问题，放一起就出事了，而且这些事换更强的模型也解决不了：

- A 的 Agent 刚改了一个接口的约定，B 的 Agent 不知道，照着旧约定又写了三个调用。
- 每个 Agent 进仓库都要重新认一遍路：模块怎么分，入口在哪，哪些目录是生成的不用看。认路的成本每次会话付一遍，再乘以 Agent 的数量。
- 规范只在人的脑子里。提交怎么写，什么必须先跑 check，什么文件不许动。人靠默契，Agent 靠不了默契，只能靠写下来的东西。

解法都很朴素：一份给 Agent 看的仓库说明，一套写下来的规范，几条明确的边界，再加上 CI 和分支保护。朴素到很多人不觉得这也算 Harness。但它在模型外面，又决定模型用得好不好，当然算。

我自己这个博客的仓库就是个例子。`CLAUDE.md` 里有一条规矩：**不许直接 push 到 main，先推到分支，让我看过预览再合。** 这条不是我想出来的，是被坑出来的：有一次 Agent 写完一篇文章，顺手就推到了 main，而 main 是自动部署的，那篇文章我还没看过就上线了。Agent 没做错什么，是我没告诉它。现在这条写在那儿，每个新会话进来都会先读到。

视频里 Robert 讲他做 Claude Tag，主要精力也花在这一层：他们大量地用 Claude Tag 来开发 Claude Tag 自己，所以他最操心的是让开发环境对 Claude 足够好用，让它能自己把软件跑起来，自己从头到尾验证一遍。

Boris 讲的另一件事让我更确定这层值得花力气。Bun 从 Zig 重写到 Rust：Bun 团队的 Jarred 每出一代新模型，就把这个题目丢给它试一次，直到有一代做成了。按 Boris 的说法，那是一个 prompt 加一个调度很多 Agent 的工作流，跑了 11 天。能成，靠的不是提示词写得多好，而是 Bun 和 Node.js 本来就有一大套现成的测试，做没做对随时能验。**「能不能验证」比「指令怎么写」更要紧**，而能不能验证，是仓库这一层的事。

### 第三层：整个组织

再往外，就不只是开发了，还有运营、增长、设计。

Thariq 在视频里讲了一个完整的例子。他想做一个内部工具，需要很多人支持。他先问 Claude Tag：我有这么个想法，该找谁聊？拿到名单之后，让它出 mockup，全程在 Slack 里，手机上就能看。然后它去实现。他不确定这工具到底好不好用，就加了很多埋点，部署到内部；Claude Tag 替他盯着，有人反馈就来提醒他。后来他从数据里看出用户没走完整个流程，想改。他本来打算说「我有个主意，你照做」，转念改成了「你去想办法改进这个漏斗，出几个方案」，自己的主意只当作一个例子给进去。他说，就是在那一刻，这件事对他来说真正通了。

这里面写代码只占中间一小段。前面是找人、对齐，后面是埋点、看数据、收反馈，这些以前是产品、运营和增长的活。

这一层的 Harness 要回答的问题也很具体：团队的决定记在哪，Agent 读不读得到？它能替谁说话，能主动去打扰谁？真实用户的反馈怎么流回它手里？

老实说，视频里的主角还是一个开发团队，运营和增长那部分是我顺着往外推的，证据比前两层薄。他们自己也没说走完了：Thariq 让 Claude 录了一段自己操作的过程来验证，看完之后还是自己 clone 下来试了一遍，图个心安。

### 越往外，越是你自己的东西

这三层是一层叠一层的。Agent 本身不好用，谈不上五个 Agent 怎么配合；仓库这层乱着，让 Agent 在团队里替你推进事情就是空话。

每一层被学走的方式也一样：通用的做法归模型和平台，你自己的内容留给你。第一层里，工具调用的机制是原生的，但你的工具是你的。第二层里，读仓库、跑 review 会被 coding agent 内置，但你们的规范得自己写。第三层里，住在 Slack 里的 Agent 是平台卖给你的，但「你们为什么这么定」只能自己攒。

差别在比例。**越往外，属于你自己的东西占得越多，也就越难被学走。** 第三层的主体是一个团队自己的决策史，这不在任何人的训练数据里。

## 四、做产品的人要算一笔账：你涨得有没有模型快

前面说的合起来，可以推出一个产品上的判断。这是我自己的判断，欢迎反驳。

用户为什么要用你的产品，而不是直接打开 ChatGPT 或 Claude？因为用你的，能多做成一些事。问题是模型隔几个月就变强一次，你多出来的这部分，会被它一口一口吃掉。

所以光「现在比裸模型强」不够，**你得涨得比它快。** 我管这个叫斜率：你的 Harness 的斜率，要比底层模型的斜率高。不然每过一代模型，你多出来的那部分就薄一点。

Todo 列表就是个例子。在 Sonnet 3.5 那会儿它是实打实的领先，有它没它差别很大。但它是一次性的领先，一年后模型自己追平了。**现在领先多少不说明问题，能不能一直领先才说明问题。**

斜率由什么决定？我想来想去是三样：

1. **试一次贵不贵。** coding agent 的 Harness 这一年长得这么快，很大程度上是因为代码太适合拿来试了：输出是文本，能 diff，能跑，有退出码，试一次几乎不要钱。
2. **有没有别人拿不到的东西在喂它。** 私有数据、真实用户的反馈、某个行业的活到底怎么干。通用技巧大家都会，也都会被学走。
3. **多做出来的那部分，有没有人买单。** 也就是有没有增量市场：你每多补一层，是不是就多出一批原来做不成这件事的用户。如果需求是一块固定的饼，模型每进步一点就替掉你一点，你涨得再快也只是在守。

### 为什么我不看好 AI 视频的衍生应用

拿这三条去看这半年最热的一类产品：基于 AI 视频、AI 生图做的各种衍生应用，做设计的，批量生成短剧的，做营销视频的。其中 To C 的那一大批，我不看好。不是它们现在做得差，而是它们的 Harness 几乎没有斜率。

先看试一次贵不贵。视频生成是按秒收费的，以字节的 Seedance 为例，官方公开的 2.x 价格从每秒 0.04 美元（Mini 720p）到每秒 0.353 美元（4K）。coding agent 里「生成、检查、不行重来、同时开十路挑最好的」那套打法，搬到视频上，每多试一次都是真金白银。而且输出是一堆像素，没有 diff，没有退出码，「这个镜头好不好」很难让程序来判断。

结果就是这类产品的 Harness 大多很薄：提示词模板、分镜拆解、素材拼接，加一个好看的界面。片子质量每一次明显的进步，人物一致性、时长、口型，都来自底层模型换代，不是来自产品自己。而模型进步的好处，所有调同一个 API 的竞品同时拿到。更难受的是，产品里最费工夫的那几块，比如为了保持人物一致性绕的各种路、为了凑时长做的分段拼接，恰好是下一代模型最先解决掉的。

再看有没有人买单。To C 这一侧，去看看短剧市场赚不赚钱就知道了。掌阅科技今年 1 月披露了上市以来第一次年度亏损，当时的报道写得很直接：短剧火爆但难赚钱。这说的是短剧这门生意本身，不是 AI 短剧，但下游的利润本来就薄。AI 把制作成本打下来了，可它是给所有人一起打下来的，利润不会留在制作这一环。

所以我的判断是：**这半年视频生成的热潮里，最大的赢家是模型厂商。** Seedance 不管怎么打折、怎么换算成积分和会员，说到底都是在卖 token。至于产品本身，就我自己用下来的感受，它并没有在模型上面做出多好的一层视频生成和编辑的 Harness。

### 生图好一点，MiniMax-H3 之后视频也有了转机

同样三条放到生图上，情况好一些。图像的 API 比视频便宜得多，能力也出来得早。一次出几张挑一张、局部重绘、用各种条件控制构图、搭成节点式的工作流，这些在生图上都试得起，也确实长出了一个不小的工具生态。

视频这边的转机，我觉得来自开放权重。[MiniMax-H3](https://github.com/MiniMax-AI/MiniMax-H3) 放出了权重（[Hugging Face](https://huggingface.co/MiniMaxAI/MiniMax-H3)），能本地部署，社区实测量化版最低一张 RTX 3060 12GB 就能跑。

这件事的意义在于，它把「试一次」的成本从按秒付费变成了电费。多路生成再挑、不合格自动重来、围着自己的素材搭一条流水线，这些以前算不过来的做法，现在算得过来了。我们这些平民玩家，第一次有条件在视频上折腾 Harness。

两点提醒：它用的是 MiniMax 自己的社区许可，有地区限制，不是无条件开源，用之前自己看一眼；另外成本也是给所有人一起降的，它只解决了「试不试得起」，你有没有斜率，还是看后两条。

### 哪些情况我觉得还是能做

- **To B，或者手里有私有数据和流程。** 品牌的素材库和视觉规范，电商的商品库，行业的合规规则。这些别人拿不到，而且模型越强它们越好用。
- **你本来就有 IP 或者流量。** 那 AI 对你就是个降成本的工具，你的护城河本来也不在 Harness 上。
- **把功夫花在改得动的东西上，而不是像素上。** 剧本、分镜、时间线、图层，这些是文本和结构，能 diff，能检查，能局部改。

反过来，如果有哪个 To C 的 AI 视频应用，在底层模型换了几代、竞品都能调同一个 API 的情况下，还能一直留住用户并且赚钱，那就是我看走眼了。

斜率没法精确量，但可以粗略估。拿一组你自己场景里的真实任务，每次底层模型换代跑两遍：一遍用你的完整产品，一遍用裸模型加最薄的一层壳。两者的差距连着记两三代，是变大还是变小，你自己就知道了。

## 五、那我自己怎么做

Tibo 他们可以商量「这个不做了，等模型」，因为他们看得到训练计划。我看不到。我用的是别人的模型，不知道哪个毛病正在被修，而我的用户今天就有事要办。

所以我的做法是这三条：

**第一，通用的补丁，当成短命的东西来做。** Claude Code 团队说 Todo 列表从必须有到不需要，用了一年左右。Boris 给普通用户的建议更狠：每六个月把你的 CLAUDE.md 删一次，skills 也删。也就是说，一块通用的 Harness 能值钱的时间，大概就一两代模型。这不是说它不值得做，早一代用上某个能力，在这行就是实打实的时间窗口。只是别为它投入要三年才能回本的工程量。Tibo 也说过，为了绕过模型的毛病写一万行代码，多半是做错了。

**第二，加补丁的时候，顺手留一个能重跑的失败案例。** 要具体：「模型不够主动」没用，「改了三个文件之后没跑 check 就说做完了」才有用。新模型来了，有补丁、没补丁各跑几遍，没补丁也能过，就删。Boris 他们做得更狠：每出一个新模型，把整份系统提示词删掉，再一行一行加回来，看每一行到底有没有用。

删不掉的补丁也有信息量。很常见的一种：「请先向用户确认再执行」，其实是权限检查没做在程序里，只好写给模型看。这种不该删，该从提示词搬进代码。

另外，脚下的平台自己也在变。Claude Code 那次更新就是个普通的版本升级，升完，你的 Agent 手里就少了五个工具。所以这组任务还有一个用处：底下的模型或平台换了之后，在我的任务上是变好了还是变坏了，只能靠它来回答。

**第三，长期的力气，花在自己的上下文上。** 会被学走的，是几百万用户共有的行为：跑测试、不跑偏、好好用工具。正面去做一个通用 Agent，没数据没入口，模型一更新就贬值，这条路我一直不看好。

学不走的，是只属于你那个行业、你那个团队、你那个用户的东西。这个定时任务为什么设成每小时一次，是为了省钱还是因为上游限流？这些不在任何人的训练数据里，模型再强也猜不出来。**智能可以租，上下文得自己攒。**

这也是为什么我觉得垂类做得越深，越该去接通用的 Agent：把你的 know-how 做成 MCP、插件、skill，接到别人已经在用的 Agent 上，底层怎么换你都不怕。

## 最后：说回「泄气」

回到 Gergely 那句话：我做的东西，下一版模型就会了，有点泄气。

我理解这个感受。但它背后有个没说出口的算法：一份工作值多少，看它产出的代码能活多久。按这个算法，这行确实让人泄气，外面这圈代码注定活不长。

我不这么算。我做在外面的东西被模型学走了，说明它做成了，说明我比模型早一代看到了那个能力该长什么样。代码会被删，但「早一代看到」这件事留在我身上，它还决定了我能不能看到下一层在哪。亲手做过里面那层的人，最先知道它什么时候稳了，也最先撞上外面那层的新问题。

视频最后，Thariq 问另外两个人怀念以前写代码的什么。其中一位说他以前喜欢抠 UI 细节，曾经花一整天叠径向渐变，就为了在个人网站上复刻 Mac OS 10.4 的 Aqua 按钮，现在他不会再手工做这种事了。但他接着说，这让他想起七八岁的时候想做游戏、不会写代码，就用 PowerPoint 拼可点击的形状。现在整个软件工程对他来说都够得着了，不用再因为自己不会某样技术就把一个想法划掉。

丢掉的是在某一层上磨到极致的手艺，换来的是能去够更外面的东西。

不过话也别说太圆。如果你的整个产品就是一块通用补丁，别的什么都没有，那泄气是对的。它是个很准的信号：你的斜率已经输了，该往外走一层，或者往垂类里扎深一层。这话也是说给我自己听的。

所以对 Tibo 那句话，我的态度是：补丁会被模型追上，同意，该删就删。Harness 因此在变小，不同意。变小的是已经完成任务的那一层，模型之外的活一直在往外扩：从一个 Agent，到一个仓库，到一个团队。你站在哪一层、涨得有多快，决定了你的产品是在被模型吃掉，还是在被人需要。

如果你手边正好有个自己的项目，可以拿「假如模型已经足够聪明，这块还用得着吗」过一遍。结论要是和我不一样，那更好，我很想听听。
