我给个人 Agent 派过这样的任务：去后台改代码，做完再通知我。执行器确实把代码写完了，但主助手和我没有收到准确的完成通知。

代码在，任务却没有顺利交到我手里。我还得回来问：到底做完没有？现在能不能用？

这件事让我对「Agent 完成了任务」变得谨慎。会写代码、知道下一步该干什么，只覆盖了任务的一部分。用户把事情交出去之后，系统还得记住它、跟进它、核对结果，最后把结果送回来。

读到 The Pragmatic Engineer 在 2026 年 9 月 10 日发布的[《Building Codex with Tibo Sottiaux》](https://newsletter.pragmaticengineer.com/p/building-codex-with-tibo-sottiaux)，我最在意的是 Tibo 对 Harness 的一个描述。他说，Harness 总是比模型领先一点：模型已经有一些能力，外围程序先帮它把这些能力用得更稳定；之后训练改进，某些帮助就可以撤掉。

这对做 Agent 的人是一个很直接的追问：我们今天认真搭的东西，有多少会被下一代模型吸收？如果模型自己就会跑测试、会持续工作，Harness 还剩什么？

我现在的判断是，应该欢迎模型吃掉那些补丁。但在删代码之前，得先分清它原来解决的是什么问题。提醒模型跑测试，和确认测试真的通过，是两件事；帮助模型记住目标，和让任务在进程退出后恢复，也是两件事。

本文沿着这个区别来读整期访谈。我会把 Tibo 对 Codex 的描述、我从中推导的工程判断，以及个人系统里已经核对过的实践分开。文中的内部能力描述只代表嘉宾在这期节目中的说法，尤其是评审水平和长任务时长，不能直接当成所有 Agent 都已具备的能力。

## 先看一项任务怎样走到用户手里

先不急着画架构图。假设我让 Agent 修一个页面问题，并给我一个可以打开的预览。

它要理解我要改的行为，找到对应代码，读取项目约定，调用工具编辑文件。改完之后，它要运行必要检查，生成预览，再打开页面，确认用户看到的确实是这一版。最后，它得把正确链接交给我。

模型在这条链路里不断判断：先读哪个文件，报错意味着什么，要不要修改方案，哪些检查足以支持结论。真正读取文件、启动进程、保存任务状态、向外部服务发请求的，是运行着的程序。

这里说的 **Harness，就是围绕模型运行的程序和执行环境**。它把用户输入和相关资料交给模型，提供 Tools，把模型提出的操作接到真实系统，再把执行结果带回下一轮。任务更复杂时，它也要处理权限、上下文、暂停恢复、验收和输出。

不需要把这个词理解成某个固定框架。一段本地循环、一个后台任务服务，加上它们依赖的执行环境，都可能承担这些工作。也不必为了使用这个词，把所有功能都收进同一个仓库。数据库、操作系统和消息平台同样会参与完成任务。

关键是沿着任务找责任。入口要知道用户让谁做什么；上下文要让模型看到相关且允许读取的信息；Tools 要把操作准确接出去；执行环境要限制它实际能做的事；输出要对应已经发生、能够核对的结果。安全和权限贯穿其中，不能只在某一层贴个标签就算做完。

回到开头那次通知断点。后来我把执行完成、独立验收、真实送达分开记录，并保留可核对的证据。这样至少能回答：代码写完了，还是已经检查过了？通知还没发，还是发送失败？当前的结论来自哪一步？

这没有让系统从此不再出错。但它改变了出错时我能看见的东西。以前只有一句含糊的「完成」，现在能知道任务停在什么地方。这个差别，比再给模型加一句「请认真负责」实际得多。

这也是我理解整期访谈的起点：讨论 Harness 要变大还是变小之前，先问用户交出去的事情，究竟由谁负责完成。

## Codex 的起点，解释了为什么模型和 Harness 要一起设计

按照 Tibo 在[访谈中对早期工作的回顾](https://newsletter.pragmaticengineer.com/p/building-codex-with-tibo-sottiaux)，他加入 OpenAI 后，最初做的是研究基础设施。数据存储、分析和理解训练过程，都属于他熟悉的工作。推理模型出现后，他开始关心一个具体问题：能不能用模型加速这些工作本身？

于是团队一边训练内部模型，让它更熟悉内部 Python 代码库、代码风格和架构偏好，一边搭小型 Agent，让它实际参与基础设施开发和研究工作。这些尝试后来与 Autonomous Software Engineer 方向的工作合到一起，逐渐形成 Codex。

这个起点很重要。它给「模型和 Harness 共设计」提供了实际含义：当 Agent 在任务里做不好时，团队能同时检查训练和外围程序。

如果它不理解项目惯例，可能需要更合适的训练；如果它根本拿不到相关文件，问题在上下文和工具；如果它知道该检查什么，却总在改完文件后结束，可以先调整指令与执行流程。它们会共同影响用户看到的结果，不能只盯着其中一部分。

这也解释了为什么一个普通的模型能力演示，和一个能交给别人用的 Agent 产品之间，往往差着很多工作。演示者知道该提供哪些文件，知道环境缺什么，也知道什么时候该追问。换一个用户，这些隐含的配合就不一定存在了。

Tibo 对早期云端 Codex 的评价也很坦率：使用摩擦偏大，没有真正找到产品市场契合点，也就是 PMF。他没有在节目里逐项给出摩擦的成因，所以我不会把后来谈到的环境配置问题，倒推成当时产品失利的完整解释。

但这里可以得到一个清楚的提醒：团队相信模型能力，已经做出产品，仍然不等于用户愿意持续采用。用户还要决定这次任务值不值得交出去。他要花多少时间准备环境、解释背景、等待和追问，都会影响这个决定。

我的个人系统规模很小，也会遇到同一种体验问题。一个后台 worker 写得再快，如果结果回不来，我就得重新充当调度员。任务虽然被拆出去了，我的注意力却没有真正省下来。

因此，我更愿意用「用户还要补多少协调工作」观察 Agent 是否有用。用户每次都要提醒它继续、提醒它测试、提醒它发链接，说明产品仍然把一部分未完成的工作留在用户身上。模型训练能减少其中一些提醒，Harness 也应该把可以由程序完成的衔接接好。

这让早期产品的故事和那句「领先一点」连在了一起：领先的意义，是把模型当前的能力变成更容易使用的工作方式。它有时是一条很短的指令，有时却是一段需要长期维护的系统能力。

## 能被训练吸收的，到底是哪一部分

节目里最容易理解的例子来自主持人：早期让 Codex 改代码，它会改，却不一定主动运行已有测试。后来再用，它开始自己测试了。这个变化究竟来自指令，还是来自模型？

Tibo 的回答是，两者会接力。早期在开发者指令里提醒它跑测试；模型训练改善后，它更能理解用户说「完成这项修改」时的真实期待，于是无需同样强的提醒。他也说，随着模型进步，开发者指令和 Harness 的部分实现会缩减。这里讨论的是[访谈中模型与 Harness 的共同演进](https://newsletter.pragmaticengineer.com/p/building-codex-with-tibo-sottiaux)。

我把这种东西叫行为补丁：模型已有基础能力，只是在何时使用、怎样坚持、什么时候停止上不够稳定，外围先帮一下。

比如总在中途结束，就在结束前提醒它核对目标；比如遇到工具报错后容易放弃，就告诉它先分析错误，再选择合理的替代办法。这些规则针对的是模型在任务里的判断和行为。训练确实有机会让它更自然地做对。

不过，跑测试这个例子内部，也能再分出两层。

「修改后应该检查」是一种工作习惯。「运行的是哪个提交上的测试，进程是否退出，退出码是什么，哪些检查没跑」则是执行事实。前者可能越来越不需要提醒，后者仍然需要程序取得结果。

进一步说，模型学会了主动测试，也不意味着每次都应该运行同一套命令。文章修改、接口变化和数据迁移的验证方式不同。更强的模型可以帮助选择更合适的检查，但它不能靠理解力把一个尚未执行的检查变成已通过。

这正是我不愿意把「Harness 缩小」直接读成「Harness 消失」的原因。一个补丁是否可以删，要看它承担的功能。移除一段重复提醒，可能让模型更自由、更高效；移除获取测试结果的步骤，则可能让系统失去证据。

### 长时间不跑偏，和故障后接着做

访谈后半段又回到这个主题。主持人提起用于长任务的 `/goal`，Tibo 解释，它曾帮助模型围绕单一目标持续工作。他描述新一代模型时说，模型可能已不再需要同样的额外机制来保持目标，甚至谈到工作数天或一周。

这里必须保留归属。这是嘉宾对他们观察到的模型能力的描述；节目没有提供足够的任务集合、运行条件和失败数据，让读者独立复现这个结论。更不能把它改写成「现在随便一个 Agent 都能可靠工作一周」。

即使我们暂时接受最乐观的假设：模型能持续专注一周，它解决的也是「接下来该做什么」的问题。

如果执行进程突然退出，谁会再启动它？重新启动之后，从哪里知道已经完成哪些步骤？如果一条消息已经发出，但保存结果之前程序中断了，重试时如何避免盲目再发？如果预算耗尽，用户从哪里知道任务被迫停下？

这些问题都需要系统中真实存在的记录和行为。模型可以读取记录、分析恢复方案，却不能从已经消失的上下文里凭空恢复事实。

所以我会把任务目标的文字说明保留下来，也会把程序保存的进度保留下来。前者帮助后续执行者理解目的，后者告诉它哪些事情确实发生过。某种强制续跑循环可以退休，任务记录却仍有价值。

这也影响怎样报告长任务。一个模型「持续进行了很多轮工具调用」，并不自动证明任务有效推进。它可能在反复检查同一件事。持续时间是观察项，完成结果才是判断依据。Harness 如果只负责让循环永远不停，也可能只是在延长一个错误方向。

### 懂得遵守权限，也仍需要权限

再看一个最简单的例子。用户让 Agent 阅读一个项目，指令里写着「不要读取其他目录」。模型理解得再好，这句话本身也没有改变进程能打开哪些文件。

如果执行环境只允许访问这次任务需要的文件，即使模型误选了路径，程序也能拒绝。反过来，执行环境有过大的权限，模型今天没有误用，也只能说明这一次没发生问题。

这并不意味着安全只归操作系统负责。入口要识别请求者和任务范围，上下文不能混入不该提供的资料，Tools 要检查操作，执行环境要限制实际访问，输出也要避免把允许阅读的信息发给不该接收的人。模型的判断是其中的帮助，系统还得落实规则。

我不认为这些能力必须永远由今天这个 Harness 项目亲自实现。权限可以由外部服务检查，任务状态可以由数据库保存，隔离可以由操作系统或云环境提供。实现位置会变，依赖也可以换，但责任必须有人承担。

因此，判断一段工程是不是临时补丁，有一个很实用的问题：假设模型已经完全理解用户意图，这段程序是否仍然需要实际做事？如果它还要限制文件访问、保存状态、接收发送回执，答案通常很清楚。

## 独立团队怎样删补丁，而不用赌下一代模型

Tibo 说，研究和工程团队会一起讨论：这个问题应在 Harness 里解决，还是通过训练解决？如果训练能解决，大概什么时候可用？有些问题，他们可能决定先不做工程绕行，直接等待模型改进。他还警惕为了绕开某个模型缺陷，写出庞大而复杂的代码。

我认同这个警惕，但不能忽略他们的条件。他们能参与训练，也能获得内部路线信息。独立团队通常面对一个外部模型服务，既不能确定某个问题是否正在被训练解决，也不能把发布时间当成自己的交付承诺。

用户今天有一个任务要完成，不能只得到「下一代模型可能会更好」。同时，如果我们把每个失败都变成一条永久规则，几个月后也很容易积累出一套相互打架的流程。

我会采用一个折中的做法：保留能说明问题的失败案例，让补丁可以被单独比较和删除。下面是我从访谈推导出的工程方法，并非节目公开的 Codex 内部流程。

先把问题写具体。不要只记「模型不够主动」，而要记：它完成了文件修改，但没有运行任务要求的验证；或者它只给出一份计划，就结束了本该执行的任务。任务要求、当时可用的上下文和工具结果，才是以后比较时有用的信息。

接着，说明这次补丁究竟改变什么。如果我们只想解决过早结束，就不要顺手把所有执行步骤都固定下来。否则新模型来了，即使旧问题消失，也很难知道删哪一部分会影响什么。

新模型可用后，在相同任务和相近条件下，分别保留、移除补丁。看它实际完成了什么，是否满足原来的边界，花了多少调用和等待。不要只比较最终回复是否更自信、更完整；一段很漂亮的完成说明，也可能对应一个没有更新的页面。

真实任务往往有波动，一次成功不够说明旧问题已经解决。一个小项目未必需要搭复杂评测平台，但至少可以把最常见、最容易复现的几个失败保留下来，在模型或指令变化时重新跑。案例里涉及私人资料，就用脱敏输入或能重现同类问题的替代场景。

这里还有一个容易漏掉的比较：补丁可能防住了旧错误，却阻碍了新模型。比如强制它每次按固定顺序读一长串文件，曾经能避免漏看背景，现在却让很小的修改也绕一大圈。再比如反复追问「你确定完成了吗」，可能让它在任务结束后做额外且无必要的改动。

因此，我想保留的是失败经验，而非旧流程本身。经验告诉我曾经在哪摔倒；回归案例告诉我现在还会不会摔倒；补丁只是一个可替换的解决办法。

如果没有能力做完整对照，也可以先把某条规则限制在需要它的任务里，减少对其他任务的影响。它应当有理由、有适用范围，并且允许以后重新判断。只因为「之前出过一次事」就永远叠规则，最后也会把 Agent 变成需要人类不断解开限制的系统。

更强的模型理应让一些工程变简单。对我来说，Harness 成熟的一项表现，就是能够拿出证据说明：这段额外提醒已经没有必要，可以删了。

## 给 Agent 背景时，最有用的往往是「为什么」

到这里，还有一个问题没解决。模型就算更懂得完成任务，它怎么知道这个项目为什么长这样？

程序里可能写着一项任务定时执行，注释也清楚。但当我要调整频率时，只看代码，未必知道原来的选择是为了降低成本、适配某个外部限制，还是一个早已过期的临时安排。

我需要的是决策理由，以及这个理由现在是否仍然成立。这类信息常常散在讨论、文档和后来发生的修改里。模型的通用能力再强，也无法知道没有提供给它的项目历史。

Tibo 在[谈 OpenAI 内部协作时](https://newsletter.pragmaticengineer.com/p/building-codex-with-tibo-sottiaux)提到，新同事问问题，经常会被建议先问 Codex。按照他的描述，内部 Codex 连接了 Slack、文档和代码，可以帮助了解项目状态、负责人以及某项决定为什么发生。团队也把更多讨论放到内部公开频道，让文档具有较广的内部可见范围。

这里的「公开频道」是组织内部可见，不是互联网公开。节目没有披露完整的权限实现，也不能据此推断所有人和所有 Agent 都有无差别的读取权限。

我更在意的是信息习惯的改变。如果一个决定只存在于某个人脑子里，再好的检索也找不到。团队愿意把讨论、理由和变更留下来，Agent 才有材料可用。能访问工具只是前提，组织是否留下有用记录，同样影响答案质量。

### 摘要应该把人带回证据

我会把个人 Agent 需要的背景分开处理。稳定偏好可以长期保存，例如希望输出简洁还是详细；项目当前状态要查最新记录；重要决策则应当能回到当时的资料。这里的分类是我的实践判断，并不是 Tibo 给出的记忆系统设计。

这三者如果都被压成几句「长期记忆」，很容易混在一起。几周前的项目状态变成永久事实，一次临时选择变成了不许改动的偏好，模型自然会作出听起来合理、实际已经过时的判断。

所以我想让摘要回答的不只是「现在是什么」，还有「这个说法来自哪里」「什么时候确认的」「哪些部分尚未确认」。尤其是尚未确认的部分，不能在多轮摘要里悄悄消失。

开头那次完成通知断点就能说明这一点。如果记忆里只写「任务已完成」，下一次主助手接手时，它可能直接相信已经交付。若记录保留的是「执行完成，验收与送达需要分别核对」，后续工作就有明确落点。

当然，也没必要把全部日志每轮重新塞进上下文。模型应该先拿到足够短的当前说明，再根据问题读取相关证据。这样既能减少无关信息，也不至于把摘要当成永远正确的事实。

更大的上下文窗口会缓解容量问题，却不能自动解决过期、矛盾和权限问题。把更多内容放进去，甚至可能让几个时期的说法同时出现。系统需要帮助模型区分它们，而不是期待模型从一堆没有日期和来源的句子里猜出哪个更新。

### 项目记录者的价值与边界

访谈里另一个让我印象深刻的细节，是 Codex 在与 ChatGPT 整合的项目中，也充当了项目记录者。Tibo 描述它持续整理讨论、争议和决定，留下整个过程的记录。主持人随后也表达了对持续被 AI 观察的不适感。

我能理解这种两面性。一份好的项目记录，会让后来的人知道当时比较过哪些方案、为何放弃某个方向，少走很多重复路。但「以后可能有用」并不足以成为记录一切的理由。

对我自己的系统，我愿意保留的是完成当前任务和解释重要决定所需的资料。读取什么、能保存什么、谁能再读取、结果能发到哪里，都需要明确。允许助手在私人任务里阅读一段内容，并不等于允许它把原文搬进公开文章或共享报告。

这是从个人助手走向协作系统时很重要的变化：上下文不只影响回答准不准，也影响信息会流向谁。一个内部知识入口的成功经验，不能被简化为「全库接上 RAG，再让所有人随便问」。

模型越来越强，确实可能更擅长从杂乱讨论里整理决策。但资料的访问、更新、保留与出处，仍然需要系统配合。它理解得越好，我们越应该给它清楚且可追溯的材料。

## Review 要同时回答「做得对吗」和「该做吗」

在我维护的一个 QQ 公开看板里，曾经出现过后台已经入库，但从审核到公开展示的衔接没有走通，用户仍看到旧内容的情况。

更值得反省的是，主助手最初根据后台状态，把「后台正常」说成了「用户可见更新正常」。后来核对最终公开页面，才把这两件事分清。

这个例子不需要复杂算法。数据库里多了一条记录，和读者在页面上看到更新，是两个不同的事实。如果需求是让用户看到新内容，验收就得走到用户页面。日志成功只能证明日志所对应的那一步。

它也让我更容易理解 Tibo 对 Code Review 的看法。传统 PR 里同时装着很多讨论：代码是否正确、安全有没有问题、大家是否理解这个模块、需求到底值不值得做。随着实现检查越来越自动化，这些讨论有机会被拆开。

在[节目关于评审的讨论](https://newsletter.pragmaticengineer.com/p/building-codex-with-tibo-sottiaux)里，Tibo 举的例子是深入几层依赖，发现第三方库实际行为与文档不一致，从而找出当前代码里的逻辑问题。他也描述了内部自动安全检查，并使用「超人类」来评价一些评审基准上的表现。

这个方向值得重视，因为它超出了改变量名、挑格式的浅层评审。但节目没有给出充分的题集、误报率和漏报率，我不能把它写成 AI 评审已能保证没有漏洞。能提出深入的检查线索，和能对任何代码作出可靠结论，中间仍然有距离。

我从这段得到的做法，是把评审时的问题摆得更清楚。

动手前，先确认意图和对外约定：用户希望看到什么变化，什么行为必须保留，做到哪里算完成。动手后，再验证实现是否满足这些要求，必要时深入依赖和安全检查。

这两部分可以都由 Agent 提供帮助，但不该相互替代。一份代码如果正确实现了错误的需求，多跑几次单元测试未必能发现问题。反过来，需求写得很漂亮，代码却错误理解了某个依赖，也需要实际检查才能知道。

### 把验收条件写到用户能感知的位置

以前面那个公开看板为例，「入库成功」适合成为后台步骤的检查项。整个任务的完成条件还要包含经过必要审核、公开页面可见、展示的内容正确。把这些混成一个成功状态，后续无论交给人还是 Agent，都很容易过早停止。

更好的验收也不意味着每个任务都安排一堆测试。改一句文案，可以直接确认渲染结果；改状态转换，需要覆盖相应的成功与失败情况；改对外发送行为，就要检查发送范围与回执。检查应该对应具体变化及其后果。

我也会特别看执行者的结论和验收证据是否来自同一处。worker 说「已完成」，主助手再把这句话改写为「已验证」，并没有增加任何验证。独立验收的意义，是重新对照任务要求，检查产物或用户端状态。

独立不一定要再开一个 Agent。人打开最终页面、程序核对部署对应的提交、检查实际输出，都能提供新的证据。如果第二个 Agent 只是阅读第一个 Agent 的总结，也可能重复同一个误判。

这件事对写博客也成立。文件写好了，构建通过了，预览服务准备好了，文章 URL 返回成功了，正文确实是本次内容了——这些事实各有作用。只看到部署状态正常，就告诉读者文章能读，仍然可能跳过最后一段路。

因此，我希望评审自动化省掉的是重复劳动，同时让关键问题更容易被提出。它应当让工程师有余力去追问：这个变化真正抵达用户了吗？它带来的行为，是我们原本同意的吗？

## 代码更容易改，边界就更值得提前想

Tibo 一方面认为维护和重构正在变便宜，另一方面又强调好的抽象和边界仍然有用。表面上有点矛盾：既然随时能重写，为什么还要花时间设计？

我觉得把改写成本和后果分开，就很容易理解。

一个通知模块可以换语言、换库、换存储方式。但如果它在重试时把消息发给了错误的人，或者把尚未验收的任务宣布为成功，影响不会因为代码写得便宜就消失。重写代码的成本可能下降，恢复外部状态、重新解释发生了什么、重建用户信任，仍然需要投入。

Tibo 在[维护与架构这一段](https://newsletter.pragmaticengineer.com/p/building-codex-with-tibo-sottiaux)描述，依赖升级等工作能够更多自动化，某些过去不愿启动的维护任务可以在较短时间内完成。他谈到的几小时等时长，属于其观察与判断，不能作为普通项目的工期保证。

但他同时强调，如果模块的边界划得好，内部就能快速变化，而不牵动其他服务。我认同这一点，尤其在多个执行者一起修改时。

假设一个执行器负责产出文件，另一个模块负责核对结果，第三个模块负责通知。执行器可以改变内部实现，只要它交出的产物和状态仍然清楚。通知模块不该仅仅看到进程结束，就自行推断验收通过。

这些约定不必写成让人读不懂的大文档。几句具体话就可能很有帮助：执行完成只代表产物已生成；验收通过要附对应证据；发送失败不能改成已送达；重试前先核对上一次操作结果。每句话都对应真实行为，开发者才知道修改时必须保留什么。

边界的价值，也不在于永远不变。当原来的划分确实阻碍新需求，可以一起调整。但要知道这次是在修改内部细节，还是在改变其他部分依赖的行为。模型能快速生成代码，更需要这个区别来避免无意扩大改动范围。

### Rust 值得学的是选择理由

这正好回到节目较早谈的语言选择。Tibo 解释为什么用 Rust 时，主要提到正确性、效率、团队经验，以及编译期检查能带来的帮助。他还特别强调，把 Agent 核心和产品界面分开。

我觉得这比「Rust 更适合 Agent」更值得记住。一个 Agent 核心应该能脱离某个终端或聊天界面运行。今天从 CLI 接任务，明天从手机接任务，不应该因此复制整套工具执行、权限和状态逻辑。

Tibo 也明确承认，TypeScript 或 Python 路线同样可能成功，只是后来可能需要重写。所以我不会因为这期访谈就建议每个团队换语言。他们的选择建立在自身人员、正确性需求、效率目标和产品演进上，照搬结果未必能得到相同收益。

对我的个人系统，问题更具体：pi、Telegram 这样的使用入口，与后台执行器、任务通知，是否能清楚衔接？如果换一个入口，能否继续查看和跟进同一项任务？如果所有状态只留在某个聊天会话里，换入口就很容易丢掉任务背景。

用同一种语言也能把这些关系分清，用不同语言也可能把它们耦合得很紧。Rust 在 Codex 的具体组织方式里帮助团队形成边界；对我来说，需要先看清要分开的责任，再选适合维护它们的实现。

### 并行之前，先给修改留出空间

访谈还谈到，过去团队规模逐步增长，工程师有时间补文档和协作方式；现在大量 Agent 可能很快加入一个项目，变化的速度也随之提高。

我不把这个观察理解为「每个项目都应该开很多 Agent」。并行会带来上下文同步、修改冲突和验收成本。如果几个人或几个 Agent 都在改同一个共享状态定义，增加数量未必能更快交付。

真正有帮助的是让可以独立的工作独立起来。接口清楚、产物明确、改动范围有限，一个执行者修改内部实现时，其他人不用跟着重读整个系统。好的边界让并行成为选择，而不是要求大家靠频繁聊天避免互相踩脚。

模型越来越擅长架构思考，也可以帮助寻找这种划分。工程师不必把「设计架构」当成只属于人类的保留地，但仍需要理解模型提出的边界，以及它们会怎样影响实际修改和交付。

## 从云执行到个人 Agent，关键是用户可以离开

Tibo 在节目中描述的方向，已经不止是代码编辑器。他谈到了解用户目标与日程、访问所需资源、通过自然语言和语音交互的个人 Agent。这是产品方向与愿景，不能理解成所有部分已经成熟落地。

他自己的使用方式则很具体：在会议间隙对手机说出问题，让 Agent 查资料、整理报告或探索代码。以前可能先记下来，等自己有空；现在可以先把任务发出去。这些属于[嘉宾对个人使用方式与云执行的描述](https://newsletter.pragmaticengineer.com/p/building-codex-with-tibo-sottiaux)。

我关心的变化是，用户能不能离开当前界面。任务如果必须靠我盯着聊天窗口、保持电脑开着、反复输入「继续」，委托就仍然不完整。

但从手机发起任务，不代表执行已经离开笔记本。远程入口可以只是遥控器，真正工作仍在本机。云端执行则要在另一套环境里运行，需要代码、依赖、工具，以及完成任务所需且允许提供的资料。

主持人在这里提出的反对意见很实际：本地已有数据库、服务器和各种配置，为什么还要折腾云环境？Tibo 的判断是，Agent 能承担更多环境搭建与维护工作，从而降低过去云开发环境的使用门槛。

我认为这个方向有道理，但「模型会配置」只能解决部分成本。哪些数据可以过去、凭据由谁提供、网络能访问哪里、运行结果如何带回来，仍然是实际问题。模型可以帮助执行准备步骤，系统需要把允许迁移的范围和可用资源说清楚。

所以我不会追求一个个人系统所有任务都放在云端。更合理的是入口与执行位置分开：需要本地资源的任务留在适合的环境，需要更多计算或长期运行的任务可以放在远端。用户只需要理解任务在哪里能继续、什么时候需要自己介入，不必记住每个进程的细节。

### 合并产品，也是在合并任务体验

节目谈到 Codex 与 ChatGPT 的整合时，Tibo 描述了本地 Agent 与托管云端系统之间的差异。工作包括基础设施、运行方式，以及插件和库等部分的整合。对外看可能只是多了一个使用入口，里面却需要把能力放到另一种规模和运行条件下。

这也呼应 Rust 那段对核心与界面的区分。核心能脱离产品入口，是接入新界面的基础；但共用核心还不够。状态怎样呈现、任务怎样继续、结果怎样返回，都影响用户是否真的获得同一种能力。

我的系统没有这样的规模，但也有相似的检查问题：从一个聊天入口派出的任务，后台已经完成，另一个负责汇报的助手能不能知道？用户回到对话里，能否得到准确状态？这些衔接没有做好，接再多入口只会增加更多看不到任务的地方。

### 送达是一件需要证据的事

在整理这期访谈时，我让主助手通过 QQ bot 把完整解读以合并转发的形式发到两个群。系统拿到了发送回执，也确认群里出现了对应卡片。

但当前使用的接口不能展开自己发出的合并卡片全文，因此没有完成全文读回核验。记录里保留了这个区别：已发送，卡片已看到，卡片内部全文尚未通过读回验证。

这件事很小，却是我现在很在意的交付细节。拿到 ACK，也就是服务返回的确认，只能支持它所确认的那一步。群内看到卡片，比只有发送请求多了一份证据；全文能否展开并逐字核对，又是另一个检查。

没有读回能力时，我不希望系统为了让状态好看，把「已验证」直接设为真。它应该保留已经知道的事实，也保留没能验证的部分。以后换了接口或补了检查能力，可以继续核对；现在就如实报告当前证据范围。

这和前面的公开看板是同一个判断习惯，只是发生在输出端。用户看到的东西才是交付的一部分。模型再懂发送流程，也必须依靠实际接口和观察结果，才能知道事情走到了哪里。

个人 Agent 越主动，越需要这样的清楚反馈。用户不盯着每一步时，更依赖系统最后给出的结论。界面可以简单，背后对完成状态的记录不能含糊。

## 开源和可换模型，让这种判断更重要

如果模型与 Harness 需要共同设计，一个很自然的问题是：那 Harness 是否应该只服务自家模型？

Tibo 在[访谈谈开源与模型选择的部分](https://newsletter.pragmaticengineer.com/p/building-codex-with-tibo-sottiaux)给出的态度比较开放。他认为用户想试另一个模型，不应该被迫换掉整个工作环境。既然代码已经开源，仅仅为了接入不同提供商而维护一个 fork，也会制造额外成本。

开源对团队本身也有帮助。新成员可以提前阅读代码与 PR，用户能够参与改进，团队能直接看到社区怎样使用工具。但他同样谈到代价：开源和内部代码之间的额外边界、功能尚未正式发布就被复制，以及大量低质量贡献带来的维护负担。

我喜欢这部分的具体程度。它提醒我，开源本身也要运营和维护。让 Agent 更容易生成贡献，并不会自动让维护者更容易判断每个改动是否有用。最后还是要回到意图、证据、边界，以及后续维护成本。

支持其他模型，则把 Harness 的另一项责任显露出来：我们既要保留选择，也要承认选择之后的差异。

一个 API 请求能够成功返回，只能说明基础接入走通。同样的工具说明、错误反馈、上下文整理方式和停止提示，不一定适合每个模型。一个模型会在拿到工具结果后主动继续，另一个可能更容易停下来解释它；某条对旧模型有用的指令，也可能干扰新模型。

这些是我对跨模型使用的工程判断，不是节目给出的一组对比实验。它们需要在实际任务中检验。模型能换，和换完之后相同任务仍然完成得好，是两个要分别回答的问题。

因此，前面那些失败案例和回归任务，也能用于模型切换。换模型后，检查它是否仍会过早结束，是否准确使用工具，是否满足相同的验收要求。比较时还要记住，结果来自模型、指令、工具和执行环境的组合。

这不要求一个小项目一开始就支持所有模型。抽象过度也会制造维护负担。只要核心任务记录和产物不被某一个聊天界面、某一次回复格式锁死，就已经给未来的选择留出了空间。

我期待的可替换性，是需要改变时有办法迁移，并且能判断迁移有没有变好。单纯把模型名变成一个配置项，只完成了最容易看到的那一部分。

## 工程师要练的，是把问题追到能验证的位置

聊到最后，还是会回到工程师自身。模型会写更多代码，会检查实现，也开始参与架构判断，我们还应该把时间投在哪里？

Tibo 的建议包括保持好奇、快速理解陌生系统、不断提出好问题，并真正理解所服务的人。他也谈到自己仍会享受手写代码，同时更愿意利用工具去解决更多问题。这些建议来自[访谈结尾对工程师成长的讨论](https://newsletter.pragmaticengineer.com/p/building-codex-with-tibo-sottiaux)。

我不想把它读成「以后只要会提需求」。要提出一个好问题，往往先得知道系统是怎么工作的。不了解进程和存储，很难意识到持续推理与故障恢复的区别；不理解测试覆盖范围，就容易把全绿当成用户体验正确；看不懂依赖，就很难判断评审模型指出的问题是否成立。

手写代码仍然能帮助建立这种理解，也仍然是直接修改和实验的手段。只是我们不需要用手写了多少行，来证明自己对系统负责。读代码、运行实验、理解错误、核对真实结果，同样属于工程工作。

我也不愿意把架构当成一个永远不会被模型触及的安全区。Tibo 在节目里已经明确谈到模型对长期维护和架构的思考正在改善。未来模型能给出更好的设计建议，我希望自己能用上它，并且知道怎么判断建议是否适合当前项目。

对我最实用的练习，是把一个宽泛判断继续追问下去。

「后台正常」具体指哪个步骤？「验证过了」看的是什么证据？「这个补丁必须留着」对应哪一个仍然存在的失败？「换模型更好」是回复更像我喜欢的风格，还是任务确实完成得更好？

这些问题没有多少华丽术语，却会直接改变接下来的行动。问清后台与页面的区别，就会去打开用户页面；问清发送与全文读回的区别，就不会误报已验证；问清补丁解决的行为问题，就有机会在新模型上删掉它。

模型越强，越能帮我们把猜测变成实验。以前因为实现成本高而搁置的比较，现在可以更容易做出来。但实验仍然要选对问题：测一个内部函数更快，不能直接推出整个任务交付更快；多开几个 Agent 更忙，也不能直接推出结果更好。

回到最开始那句「Harness 总是比模型领先一点」。我更愿意把它当成一种工作方式：先帮助模型跨过当前任务里的障碍，等它自己具备了相应能力，再撤掉不必要的帮助，把精力放到下一个真实问题上。

其中有些工作会很快过期，删掉就好。有些工作会变得更容易实现，也可以换一种更简单的做法。但只要我们还希望用户把任务交出去，再带着可靠结果回来，权限、背景、恢复、验收和交付就仍然需要落实。

我希望自己的 Agent 越来越少需要我催促。与此同时，当它告诉我「完成了」，我也希望能沿着记录找到产物、检查和送达结果。

模型越来越强，给了我们更多把事做成的能力。Harness 要做的，是让这些能力真正走完从一句请求到用户手里的那段路。
