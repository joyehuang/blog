前阵子 The Pragmatic Engineer 有一期播客，[主持人 Gergely 和 Codex 负责人 Tibo Sottiaux 聊了一个多小时](https://newsletter.pragmaticengineer.com/p/building-codex-with-tibo-sottiaux)。其中有一小段对话，我觉得比整期其它内容都值得拿出来说。

Gergely 问：早期的 Codex 改完代码不会主动跑测试，几个月后它自己开始跑了，你们改的是指令还是模型？Tibo 的回答大意是：Harness 在某种意义上总是比模型领先一点。模型有某种能力，但还不够稳、不够高效，于是先在外面给它搭几根拐杖；等下一代模型训练出来，就不用再提醒它了。时间一长，他们看到的是 developer message 在变短，Harness 也在缩小。

节目最后 Gergely 复盘时说了句实话：作为开发者，这听起来有点泄气。我今天认真做的东西，下一版模型自己就会了，然后就可以删掉。

这段对话我听的时候没有意外，因为它说的事情我一直就是这么理解的。但我发现自己和 Tibo 虽然看到的是同一个现象，得出的结论却不太一样：他说 Harness 在缩小，我觉得它一直在变大；Gergely 觉得泄气，我觉得这恰恰是这一行最值得干的原因。

这篇文章借他们的话开个头，讲的是我自己对 Harness 的两个判断。

<TldrCard>
- **模型之外的一切，都是 Harness。** 模型是唯一一件你不用、也没法自己做的东西，所以做 AI 产品，做的就是模型外面那一圈。这个定义比 Tibo 在节目里用的宽，宽出来的那部分正是分歧所在。
- **Harness 是实验场。** 一种能力总是先在模型外面被跑通、验证、稳定，然后被训练吸收进模型里面。这一点我和 Tibo 完全一致，他从模型厂商内部确认了这个节奏。
- **被吸收不等于被删掉。** 吸收之后，瓶颈往外移一层，工程对象跟着往外移一层。Prompt → Context → Harness → Loop 就是这么一层层长出来的，上一层从没消失，只是变成了下一层的零件。所以「Harness 在缩小」只在窄定义下成立。
- **独立开发者看不到训练路线图**，不能像 Codex 团队那样选择「等模型」。能做的是：把通用补丁当成有保质期的实验来做，给每个补丁留一份到期检验，把长期投入放在训练信号够不着的地方。
</TldrCard>

## 一、模型之外的一切，都是 Harness

先把词说清楚，因为后面的分歧全出在这里。

做一个 Agent，拆开来无非是大脑、记忆、工具、循环这几样。这里面只有大脑，也就是模型本身，是你不用做、也没法做的。你不会去预训练一个模型，你能决定的只是调用哪一个。那么剩下的所有工作，记忆怎么存、工具怎么接、循环怎么转、上下文怎么管、出错了怎么兜底，全在模型外面。业内管这一整圈叫 Harness。LangChain 的 Vivek Trivedy 有句话说得最干脆：Agent = 模型 + Harness，你要么是模型，要么就是 Harness，模型之外的一切都是 Harness。

我想把这句话再往前推一步：**不只是做 Agent，只要你在做 AI 产品，而你又不是训练模型的那家公司，你做的东西就全部是 Harness。** 一个 AI 写作工具的编辑器和版本管理是 Harness，一个客服机器人接的知识库和工单系统是 Harness，你给自己的个人 Agent 写的那份长长的偏好说明也是 Harness。往回看，更早的 Prompt Engineering、Context Engineering，本质上也都是 Harness，只是那时候这个词还没出现。

有人会觉得这个定义宽到没有意义，什么都是 Harness，那这个词还区分了什么？我的看法相反，宽正是它的用处。它区分的是「模型里面」和「模型外面」，而这条线决定了你手里的东西受什么规律支配：线里面的东西由训练决定，你碰不到；线外面的东西由你决定，但它们全都面对同一个问题，就是模型下一次变强的时候，它还有没有用。承认自己做的全是 Harness，等于承认自己做的每一样东西都得回答这个问题，没有哪一块可以豁免。

这一圈到底值多少，有两组数字可以看。

第一组来自 LangChain。他们的 coding agent 用的是 `gpt-5.2-codex`，一个闭源模型，他们一行也改不了。只重做 Harness 之后，这个 agent 在 [Terminal-Bench 2.0](https://www.tbench.ai/leaderboard/terminal-bench/2.0) 上从 52.8% 涨到 66.5%，排名从 Top 30 开外进了 Top 5（[他们自己的复盘](https://www.langchain.com/blog/improving-deep-agents-with-harness-engineering)）。13.7 个点，差不多是一代模型升级带来的幅度。

第二组来自 Databricks。他们 2026 年 7 月公布过一次内部评测：在自己的千万行代码库上，[同一个模型、同样的思考强度，只换 Harness，部分任务的单次成本相差超过 2 倍，完成质量基本一致](https://www.databricks.com/blog/benchmarking-coding-agents-databricks-multi-million-line-codebase)。差别主要来自各家管理上下文的方式，其中一个每轮发给模型的上下文只有另一个的约三分之一。

两组数字说的是同一件事：同一颗大脑，Harness 决定它被用得好不好。很多看起来是「模型不行」的问题，其实是外面那圈没做好。我自己用某个 coding 模型的时候就碰到过，它的工具调用老是失败，查下来是参数格式对不上，和模型聪不聪明关系不大。

> **【待补 · 你自己项目里的一个例子：模型没换，只改了外面某一处（上下文怎么喂、工具怎么描述、循环怎么停），效果明显变了。最好有前后对比】**

注意 Tibo 在节目里说的 Harness 比这个窄得多。他指的是 Codex 团队维护的那个核心 agent harness：护栏、沙箱、工具，加上每一轮开头注入上下文的 developer message。在这个范围里说「它在缩小」，我信。但窄定义和宽定义之间差出来的那一大块，后面会看到，正是不缩反涨的部分。

## 二、Harness 是实验场

Tibo 用的比喻是拐杖。我更愿意把 Harness 叫做实验场，两个词指向的是同一个现象，但含义差得不少。

先说现象，这一点我和他完全一致：**一种能力总是先出现在模型外面，然后才进到模型里面。**

这个顺序在过去几年里重复了很多次，而且都能查到。

2022 年大家发现，在提示词末尾加一句「Let's think step by step」，模型做推理题的正确率会明显上升。那两年流行的各种 magic words，「回答前先想一步」「回答前再反思一下」，都是这个路数。这是纯粹的模型外工程，一句话而已。到 2024 年推理模型出来，先想再答这件事被直接训练进了模型，那句咒语就没人再写了。

工具调用也一样。最早让模型用工具，靠的是在提示词里约定一种输出格式，再由外面的程序去解析文本、执行、把结果塞回去，ReAct 那一批做法就是这样。后来厂商把 function calling 做成模型的原生能力，解析文本那层胶水代码就不需要了。

Tibo 在节目里给的例子属于同一类，只是发生在厂商内部。早期 Codex 不跑测试，他们就在 developer message 里提醒它；后来训练出的模型更能理解用户说「改一下这里」时真正想要的是什么，提醒就删了。他还提到 `/goal`，一个让模型围绕单一目标长时间工作的机制，当初不加它模型会跑偏；按他在节目里的说法，新一代模型已经不需要它，直接说「去干一周」就行。另一个例子是他早期参与做的独立 code review 模型，据他说这部分能力现在已经并进了主线模型。后两条是他对内部情况的描述，外面没法验证，我只当作方向上的佐证。

为什么顺序总是先外后内？因为外面便宜。改一句提示词只要几分钟，改一段循环逻辑只要一个下午，当场就能看到效果；训练一个模型以月为单位，而且你得先知道要训练什么。Harness 就是用来回答「要训练什么」的地方。一种行为值不值得有、做成什么样用户才满意、在哪些情况下会出岔子，这些问题都是在模型外面、在真实用户手里试出来的。试明白了，它就成了下一轮训练的目标。

Tibo 其实亲口描述了这个机制。他说团队发现一个问题后，研究和工程会一起讨论：这该是一次 Harness 改动，还是一次模型改动？如果是模型改动，一个月、三个月还是六个月能拿到？有时候他们干脆决定 Harness 里什么都不做，等模型。这段话是我在这期节目里最看重的信息，因为它从内部确认了一件外面的人只能猜的事：Harness 和训练之间有一条明确的传送带，而且有人在有意识地安排什么东西什么时候上传送带。

所以我不太喜欢「拐杖」这个词。拐杖暗示的是模型有伤，等伤好了拐杖就扔掉，它从头到尾是个次要的、补救性的东西。可按 Tibo 自己的说法，Harness 是「领先」模型的那一个。领先的东西不叫拐杖。它更像下一代模型的需求文档：今天在外面跑通的东西，定义了明天模型里面该有什么。「实验场」这个词把这层意思留住了，实验做成了，结论被收进教科书，没有人会说那个实验白做了。

还有一点，拐杖这个比喻只描述了厂商内部那条传送带，而实验场不止一块。LangChain 在外面重做 Harness 涨的那 13.7 个点，做法是公开的，别的 Harness 会抄，模型厂商也看得到。社区里成千上万个开发者写的提示词技巧、工具封装、循环设计，合起来是一块比任何一家厂商内部都大的实验场。哪些做法最后被吸收进模型，很大程度上是被这块大实验场筛出来的。

## 三、不是所有东西都会被吸收

「Harness 的能力最终会内化到模型里」这句话，我是认的，但它需要一个边界，否则就变成「模型外面的东西迟早全没用」，这不对。

会被吸收的东西有一个共同特征：它在替模型的**判断**兜底。什么时候该跑测试，任务做到什么程度算完，长任务怎么不跑偏，遇到报错是重试还是换路。这些情况下，模型需要的信息其实已经在上下文里了，它只是没有稳定地按信息行动。训练改的恰恰就是「给定信息下怎么选」，所以这类东西不管写成一句提示词还是一整套循环机制，都能被训练吃掉。`/goal` 那么大一块机制也会退休，说明决定能不能被吸收的是性质，和代码量无关。

一个简单的检验办法：假设模型的判断已经完美，这段代码还有没有事做？没有，它就在传送带上。有，它就不在。

照这个办法筛一遍，至少有三类东西不在传送带上。

**事实。** 模型只能看到上下文窗口里的东西。「测试通过了」在模型嘴里是一句陈述，在系统里是一个退出码，后者只能由程序去真实的进程里取回来。训练可以让模型更自觉地去核对，但取事实的那条通道必须在外面。而且模型越强，它写的完成报告越像真的，就越需要由程序而不是模型来填「退出码是多少、PR 链接在哪、CI 是红是绿」这几栏。

**边界。** 能不能读这个目录，能不能往这个仓库推代码，能花多少钱。一条边界如果靠边界里面那一位的自觉来维持，它就不算边界。这和模型会不会犯错无关，「它会选择不读」和「它读不了」是两件事，只有后者是保证。模型可以起草规则，执行规则的得是沙箱和权限系统。

**连续性。** 模型只在被调用的那几秒存在。两次调用之间、进程崩溃之后、机器休眠的时候，任务由谁拿着，做到哪一步了，哪些有副作用的操作已经做过不能重做，这些都发生在没有模型在场的时间里，判断再好也帮不上。

这三类还有一个共同点：它们随模型变强而变重。模型越强，我们越敢让它无人值守地做更长的事，而多出来的每一步都多一个要核对的事实、一条要回答的许可、一段要跨过去的间隙。

除了这三类，还有一样东西不会被通用训练吸收，那就是**你的**上下文。这一条我放到第五节说，因为它和独立开发者的处境直接相关。

## 四、被吸收之后，工程对象往外推一层

到这里可以回答标题里的问题了：做在模型外面的东西，被吸收之后去哪了？

Tibo 的回答是删掉了，Harness 缩小了。我的回答是：那一块确实删了，但整个 Harness 没有缩小，它往外挪了一层。这是我和他最实质的不同。

把这几年的工程名词排成一条线看：[Prompt → Context → Harness → Loop](/blog/20260615---frominternshipinterviewstoagentengineering/post)。前两个之间隔了三四年，后面几个几乎挤在一年里。我一直的看法是，这条线上模型这个核心基本是同一种东西，变的是你下手的那一圈：词 → 上下文 → 环境 → 机制，工程的对象一直在向外扩。

以前我只是描述这个规律，现在可以用实验场来解释它为什么会这样。

一开始瓶颈在「怎么问」，所以大家打磨措辞，发明咒语。等模型把先想再答、听懂指令这些事吸收了，措辞的边际收益就小了，瓶颈移到「模型看到了什么」：任务一长注意力就散，喂多了不行，喂少了也不行，于是有了 Context Engineering。等模型的长上下文和工具使用稳了，瓶颈再移到「模型在什么环境里干活」：有没有沙箱、工具、记忆、校验，能不能撑住 long-running 的任务，这是 Harness Engineering。再等模型能稳定地在一个环境里把长任务做完，瓶颈移到「谁来驱动它」：什么时候启动、什么时候停、失败了怎么重来，人不再手动敲 prompt，而是去设计驱动 Agent 的循环，这是 Loop Engineering。

每一次往外走，都是因为里面那一层稳了。它稳了，一部分是被训练吸收，一部分是被做成了标准件。无论哪种，结果一样：那一层不再是瓶颈，新的瓶颈出现在更外面，新的实验也就在更外面开始。

而且**上一层从没消失，只是变成了下一层的零件**。Prompt 没有死，它现在是 Loop 里的一个组件。以前是人手工打磨一条 prompt，现在是 Agent 在循环里自己写 prompt、自己测、自己改。Gergely 在节目末尾其实也碰到了这一点，他说他怀疑事情不只是搭拐杖，还包括造模型要用的工具，下一代模型总不至于重新发明一遍 MCP 或者 skills。对，这些就是已经稳下来、变成零件的那几层。

所以「Harness 在缩小」这句话，在 Tibo 的窄定义里是对的：developer message 确实在变短，`/goal` 这类机制确实在退休。但用宽定义看 Codex 自己，就在同一期节目里，他讲到内部的 Codex 默认接了 Slack、所有文档和所有代码，新人有问题先被问一句「你问过 Codex 了吗」；讲到他们分析的使用场景已经从 coding 扩到 finance、marketing 这些领域；Gergely 复盘时还提到把原本纯本地的 Codex 并进一套云端托管栈是什么样的工程。这些没有一样在模型里面。给模型看的那几段话在变薄，围着模型的那一整圈在变厚。

公平起见也要说我这个判断的弱点。名词换得这么快，有一部分是真有增量，有一部分就是需要炒作，Loop 这个词两样都占。另外，如果真像 Tibo 说的，新模型不需要 `/goal` 就能自己干一周，那 Loop 这一层的相当一部分也已经上了传送带。我不觉得这推翻了「往外推一层」，它只说明这一层稳得比预想的快，下一层会来得更早。下一层叫什么我不知道。如果要猜，我猜它在单个 Agent 的外面：多个 Agent 之间、Agent 和组织之间怎么分工、怎么交接、怎么互相验证。但这只是猜。

> **【待补 · 你亲手写过、后来因为模型升级而删掉的一个补丁：当初它解决什么问题，什么时候发现不需要了，删掉之后你的精力转去了更外面的哪一层】**

## 五、没有路线图的人，怎么用这个循环

Tibo 描述的「Harness 改还是模型改、一个月还是六个月」，是一个只有模型厂商才有的选项。他们看得到训练路线图，所以可以理性地决定「这个不做了，等模型」。

我看不到。我用的是别人的模型，不知道某个毛病是不是正在被修，也不能拿别人的发版日期当自己的交付计划。用户今天有个任务要完成，「下一代可能会好」帮不上他。这是他的视角里没有、而我必须补上的部分：**同一个循环，站在传送带外面的人该怎么用。**

我的做法有四条。

**第一，把通用补丁当成有保质期的实验来做，并且按这个预期去算账。** 回头看 LangChain 那个例子，「只改 Harness 约等于白嫖一代模型」，这句话反过来读也成立：一块通用的 Harness 工作，价值上限差不多就是一代模型，保质期差不多也是一代模型。这不是贬低，提前一代拿到能力，在这个行业里就是实打实的时间窗口。但它意味着你不该为一块通用补丁投入需要三年才能回本的工程量。Tibo 给团队的那条原则，为了绕过模型缺陷写一万行代码的拐杖，多半是做错了，对外面的人同样适用，甚至更适用，因为我们连它什么时候过期都不知道。

**第二，每个补丁带着自己的到期检验。** 加补丁的时候，把它解决的那次失败记下来，具体到能重跑：任务是什么，模型做了什么，漏了哪一步。「模型不够主动」这种描述没用，「改了三个文件之后没跑 check 就报告完成」才有用。新模型来了，拿这几个失败任务，有补丁、没补丁各跑几遍。没补丁也过，就删。厂商靠路线图知道什么时候删，我们只能靠回归测试知道。不这么做的后果不难想见：每次失败都变成一条永久规则，几个月后攒出一堆互相打架、没人敢动的提示词，而且旧补丁会反过来拖累新模型，一条逼它每次先按固定顺序读完一长串文件的规则，对旧模型是防漏看，对新模型就是让两行的修改绕一大圈。

删不掉的补丁也有信息量。它要么确实还需要，要么根本不是判断类的补丁，而是第三节那三类东西被误写进了提示词。很常见的一种：「请先向用户确认再执行」，本质上是权限检查没做在程序里，只好写给模型看。这种不该删，该搬家，从提示词搬进代码。

**第三，长期投入放在训练信号够不着的地方。** 训练吸收的是大量用户共有的行为。跑测试、不跑偏、好好用工具，这些对几百万用户都成立，所以会被吸收，也所以会被平台和模型公司卷走。正面去做一个通用 Agent，没数据、没入口，模型一更新就失去价值，这条路我一直不看好。

够不着的是只属于你那个领域、你那个团队、你那个用户的东西：这个行业的活到底怎么干，这个定时任务为什么设成每小时一次、是为了省钱还是因为上游有限流，这位用户说「老样子」指的是什么。这些不在任何人的训练集里，模型再强也推不出来，只能由你沉淀下来，再由 Harness 在合适的时候递给它。智能可以租，上下文得自己攒。Tibo 讲的内部 Codex 接上 Slack 和文档之后新人什么都能问，说的其实是同一件事：那套东西值钱的不是模型，是 OpenAI 自己的上下文。

这也是为什么垂类做得越深，反而越要接通用能力。你的 know-how 做成 MCP、插件、skill，接到别人已经在用的通用 Agent 上，底层怎么换你都不怕。很多产品最后不会以 App 的形态赢，而是以零件的形态赢，这和上一节「上一层变成下一层的零件」是一回事，只是这次你主动去当那个零件。

> **【待补 · 你自己的 Agent 或垂类项目里，一条模型无论多强都拿不到、必须由你沉淀下来再递给它的上下文。要具体到一条，不要泛泛说「领域知识」】**

**第四，默认 Harness 本身也是可替换的。** 吸收通用 Harness 的不只是模型，还有平台。Vercel 今年 6 月给 AI SDK 加了一层 harness 抽象，Claude Code、Codex、Pi 可以像换模型一样换，一个 API，各跑各的沙箱。Harness 被官方做成了可替换的标准工程层，意思是通用的那部分正在被两头挤：里面被模型吸收，外面被平台标准化。对独立开发者来说这倒是好消息，你不用自己造一个通用 Harness 了。但它同时要求你有自己的测评。Databricks 那组数字说明，换一个 Harness，成本可以差两倍；如果换起来只要改一行配置，那么「在我的任务上哪个更好」就只能靠你自己的评测回答。这套评测和第二条的到期检验其实是同一组任务，一份投入，两个用处。

## 六、关于泄气

最后回到 Gergely 那句话：我做的东西，下一版模型就会了，有点泄气。

我理解这个感受，但我觉得它背后有一个没说出口的假设：一份工作的价值等于它产出的代码能活多久。按这个标准，这一行确实让人泄气，因为外面这圈代码的寿命注定很短。

可实验场里的账不这么算。一个实验被吸收，意思是它做成了。你在外面跑通的东西进了模型，说明你比模型早一代看到了那个能力该长什么样。代码会被删，但「早一代看到」这件事会留在你身上，而且它直接决定你能不能看到下一层在哪。亲手做过里面那层的人，最先知道它什么时候稳了，也最先撞上外面那层的新问题。在一个名词半年换一拨的行业里，没人有十年的 Loop Engineering 经验，最资深的人和刚入行的人读的是同一条推。资历会过期，这种一层层往外追的能力是复利的。

不过我也不想把话说得太圆。如果你的整个产品就是一块通用补丁，别的什么都没有，那泄气是对的，它是一个准确的信号，告诉你该往外走一层，或者往垂类里扎深一层了。为脚手架被拆掉而难过没有必要，但如果你手里只有脚手架，那确实该想想楼在哪。

> **【待补 · 你亲历的一次「被覆盖」：自己做的某个功能，后来被新模型或平台原生做掉了。当时什么反应，回头看那段工作留下了什么】**

所以我对 Tibo 那句话的完整态度是这样的。Harness 总比模型领先一点，同意，而且我认为这正是它的本职：它是实验场，不是拐杖。领先的部分会被模型追上，同意，该删就删，删的时候手里要有证据。Harness 因此在缩小，不同意。缩的是已经完成任务的那一层，整个模型之外的工作量在往外扩，每吸收一层，外面就多出一层。

名词还会继续换。Loop 之后一定还有下一个词，可能明年，可能下个月。看到它的时候，我大概会问三个问题：它指的是哪一圈，这一圈现在在试什么，试出来的东西多久会被里面吸收。能回答这三个问题，名词就只是噪音。真正值得攒的是那个能一层层往外搭、搭完敢拆、拆完知道下一层在哪的系统。
