我有一个 QQ 粉丝群，平时主要聊 AI 和 Agent，现在有八百人左右。今年暑假，我在群里发起了一场 Agent 项目比赛，叫 Summer of Agents：大家自由组队，花一个暑假做一个 Agent 项目，最后上来展示。

比赛原本应该在暑假结束，因为我自己的时间一再调整，最后的展示拖到了 10 月 4 日晚上。报名的有 45 组，当晚上来展示的有十几组。我和另一位评委降星驰在飞书会议里听大家轮流共享屏幕，同时开着直播。每组 5 分钟展示，评委问 3 到 5 个问题，从晚上八点不到一直聊到十一点多。

评到一半我发现，几乎每个项目我们都在问同一个问题的某个版本：

> 那为什么不直接用 Claude Code 或者 Codex？

所以这篇不逐个点评项目，也不按出场顺序记流水账。我想把那晚反复出现的几个追问整理出来，它们背后是几条对所有做 Agent 产品的人都适用的判断。项目只拿来当例子；前三名的代码都已开源，链接放在下面的结果里。

<TldrCard>
- 越通用的需求，越是模型厂商的主场；越具体的需求，越是个人开发者的机会。
- 做 Agent 产品，默认对手是用户电脑上的 Claude Code 和 Codex。能做成 Skill，就别做 Harness。
- 一句话讲不清楚产品，通常是还没想清楚。最便宜的检验：你自己连续用了吗？
- 有外部裁判的任务，才能放心堆 token。没有裁判，先去找裁判。
- 技术在贬值，对业务的理解不会。
</TldrCard>

## 先说结果

| 奖项 | 项目 |
| --- | --- |
| 第一名 | [Shiori Agent](https://github.com/YinFengWindy/Shiori-Agent)（windy）：以角色为核心的个人 Agent |
| 第二名 | [Speech Agent](https://github.com/JoshuaChen2008/TMspeech2.0)（猪鼻星）：语音字幕 + 个人记忆 |
| 第三名 | [Legion](https://github.com/lizaixi01/Legion)（在希）：多 Agent 管理系统 |
| 最佳 Demo 奖 | Obsidian 笔记关联插件 |
| 鼓励奖 | 明账 AI 记账（作者是一位 2026 级新生）、人事 Excel Agent（作者是非计算机专业的上班族） |

第一名是当晚完成度最高的项目，没有之一。Demo 奖不看项目本身的技术能力，只看 5 分钟里的表达、展示和问答。拿到这个奖的同学并没有报名，是刚关注几天、看到直播临时上来连麦的，结果展示和表达是全场最好的。原本还设了一个「抽象奖」，因为有两组实在太抽象，被我们当场取消了。

## 一、越通用的需求，越是模型的主场

评完回头一数，一大半的项目落在这几个方向上：

- **记住你**：把你说过的话、和 AI 聊过的内容沉淀成记忆；
- **帮你整理知识**：陌生领域的知识地图、笔记自动关联；
- **陪着你**：角色扮演的 Personal Agent、桌宠；
- **24 小时看着你**：后台收音、监听 Coding Agent 的对话日志、主动出来给建议。

第一个项目还没评完，我就忍不住问了一句：你们怎么都喜欢做 24 小时监听类的产品？

这些方向扎堆，原因不难理解。它们都是开发者自己每天在痛的地方：上下文一压缩，细节就丢了；笔记记了几千条，用的时候找不到；同时开着三四个会话，要在 tab 之间来回切。从自己的需求出发做项目，本身没有问题，我也鼓励。

问题在于，**你最痛的地方，往往也是模型厂商最在意的地方。** 记忆、上下文管理、多会话并行，正是各家每个月都在往产品里加的东西。在这几条赛道上，你的对手不是另一个学生项目，而是下一次模型和产品更新。

反过来看，被降星驰评为「这么多参赛作品里最有可能有人付费」的，是一个数学建模 Agent。它的赛道小而具体，有明确的交付物（一篇能直接提交的论文），也有明确的结果（拿没拿奖）。降星驰的评价大意是：你甚至不用把服务卖给别人，自己跑出结果来收钱，大概率都能收成功。

人事 Excel Agent 也是同一个道理。算工资、汇总各部门交上来的表，没有哪家模型厂商会专门为你做这件事。

**越通用的需求，越是模型的主场；越垂直、越具体的需求，越是个人开发者的机会。**

### 想做 24 小时在线的产品，先想清楚难在哪

这不是说 24 小时、主动型的产品不能做，而是动手之前要知道难点在哪里。

降星驰在点评 Speech Agent 时给了一个区分，我很认同：

- **工具类软件**：用户在某个场景下主动打开它，换来一个明确的收益；
- **环境类软件**：一直在后台，平时几乎感觉不到，像窗外的风景或者桌上的一盏灯，等你回看的时候才显出价值。

两类软件对产品的要求完全不同。环境类软件首先要做到的，不是能力有多强，而是在不打扰人的前提下提供价值。

另一个难点，是一位做桌面 Agent 的参赛者自己说出来的：上下文和记忆压缩都不是最难的，最难的是它**什么时候该出场**。我的补充是，只读屏幕上的内容，推断不出你需要什么帮助；你的行为信号反而更有用，比如反复选中某几个词，或者鼠标在一段文字上来回停留。降星驰的看法更保守：真想弄懂一个东西，人会去和 ChatGPT 来回深聊，桌面上自动弹出的讲解帮不上太多。两种看法落到同一个结论上：这是触发时机的设计问题，不是模型能力的问题，而且它很难。

也有人主动避开了这个难点。Obsidian 插件选择一天或一周整理一次，不做实时监控，理由是实时运行有隐私风险，也不够稳定。这是一个成熟的取舍。

## 二、你的对手是已经装在用户电脑上的 Claude Code

这是当晚出现次数最多的问题。我问一个做记忆系统的参赛者时，是这样一步步问的：

> Codex 和 Claude Code 是当之无愧的 T0 级（第一梯队）Agent，虽然为 Coding 而生，但越来越通用，你承认吧？它们的上手门槛，从配置到发出第一个 prompt，比你的产品低，你也承认吧？那用户为什么要用你的产品，而不是 T0？

这不是为难人。2026 年做 Agent 产品，前提已经变了：**用户手里已经有一个足够强、门槛足够低的通用 Agent。** RSS 摘要、读其他会话的历史、学一个新领域，很多功能让 Codex 起一个定时任务，就能做到七八成。

所以问题从「我能不能做出来」，变成了「为什么不是它来做」。当晚能接住这个问题的回答，大致有三种。

**第一种：把独特的能力做成插件，接进头部 Agent。**

做「陌生领域知识地图」的那组，被问到平时学新东西时用不用自己的项目，作者承认还没用过。我当时说得很直接：换成我，也会直接打开 ChatGPT，这一点大家应该都有共识。这时更好的路是反过来：如果你在某个垂类上真有独特的能力，就把它做成 Skill 或 MCP，接进 Claude Code 和 Codex 里。

这条路还有一个常被忽略的好处：**曝光**。Claude Code 和 Codex 的用户每天都在增长，接在它们上面的东西，天然能被更多人看到。

**第二种：有一个通用 Agent 不适合做的具体理由。**

我问过明账的作者：你自己就在用 Hermes 这类个人 Agent，为什么不把记账做成它的一个子功能？把 CSV 直接发给它，手机上就能处理，不是更方便吗？

作者先给的理由是隐私，账单不想上传。这个理由我没有接受：只要接了外部的 AI 服务，数据就会离开本机，存在自己电脑上和存在自己的 VPS 上，差别没有想象中大。第二个理由我接受了：Hermes 太重了，而明账更接近一个记账 App，不是一个 Agent。作者的使用习惯也支撑这一点：隔一段时间集中导一次账单，在电脑上批量整理，自己保管账本。这个答案的好处在于**具体**，说的是重量和使用场景，而不是「我的更好用」。

**第三种：承认它就是一个自己用的项目。**

这完全没问题，但要诚实地把它归到这一类。降星驰说得很清楚：「我对个人项目和但凡有商业化想法的项目，要求是不一样的。」做本地音乐播放器的那位，作为个人开源项目，做到五百、一千个 star 是很有希望的。这和它能不能赚钱是两件事，别混在一起评价，也别混在一起要求自己。

### 能做成 Skill，就别做 Harness

第三名的多 Agent 管理系统 Legion，是我们问得最多的一个项目。它的核心是一个 Manager 拆任务、分给最多 64 个 Codex 子 Agent 并行执行，再统一验收。

降星驰的担心很现实：

> 模型迭代一轮，就会把很多 Skill、甚至 Harness 淘汰掉。你怎么保证自己不被淘汰？

例子是现成的。Superpowers 这类流程型 Skill，在模型还比较弱的时候几乎人人都装；新一代模型出来以后，用的人就少了很多。「能开 64 个子 Agent」本身也不构成差异：Codex 的子 Agent 数量改一下配置就能调上去，Kimi Code 一次能开几十个 Agent 并行。

我给的建议是一个优先级：

**能做成 Skill，就别做 MCP；能做成 MCP，就别做 Plugin；最后，才考虑独立的 Harness 或独立产品。**

每往后走一步，你要维护的东西就多一层，被模型更新覆盖的风险也大一层。现在 Claude 这一类模型的迭代周期，已经短到一个月左右。一个三个月后可能被模型自带能力覆盖的独立 Harness，和一个三个月后仍然能被各家 Agent 调用的 Skill，价值不在一个量级。

所以对这个项目，我的核心问题只有一个：**你这套分工和验收的规则，为什么不能是一个 Skill？** Skill 的本质，就是给 Agent 一个额外的专家技能包，这正是这个项目在做的事。降星驰又补了一句：Claude Code 和 Codex 都有 Hook，可以处理规则性的约束，你还得证明 Skill 加 Hook 解决不了你的问题。

顺便给正在找实习的同学一个建议：别拿 Coding Agent 或 Harness 当面试项目。多 Agent 编排的复杂度不亚于分布式系统，面试官会问的，正是上面这些问题。

### 让 Agent 也能用上你的产品

「接进头部 Agent」还有另一面：不只是你的能力接进去，也可以是**让 Agent 能用你的产品**。

我问过做记忆系统的那位参赛者：你的产品对 Agent 友好吗？回答是设计时完全没考虑过，最初只是想给自己搭一套知识体系。这个回答在做记忆和知识库的项目里很有代表性。

但看看我们群就知道，bot 越来越多，我相信很快会比真人还多。群里有人在做「网页一键转 Markdown」这类工具，目的就是让 Agent 能更好地读。你的产品产出的东西，能不能被别的 Agent 低成本地读取、调用、写入？一个结构化的输出、一个 MCP 接口，可能比一个漂亮的看板更能让你成为别人工作流里的一环。

## 三、一句话讲不清楚，往往是还没想清楚

降星驰几乎对每个人都问了这个问题：

> 如果只给你一句话，加一张宣传图，你怎么介绍你的产品？

大部分回答都不太理想。「一个套了角色扮演皮的 Personal Agent，主要提供情绪价值」「一个让你看到曾经没注意到、但有用的内容的工具」，这些听起来像功能描述，不像别人愿意转述的一句话。我当时说得比较直接：如果你面对的是投资人，这句话没有任何吸引力。

经典产品的口号，往往连一整句话都不是，只是一个很短的词组。但这件事的重点不在文案。**一句话讲不清楚，通常说明你还没想清楚**：用户是谁，解决什么问题，和别人差在哪。

这里有一个很有意思的对照。最佳 Demo 奖给了 Obsidian 插件的作者，讲得自信、流畅，在场几乎没人比得上。但恰恰是这个产品，被我问出了一个自相矛盾的地方：

- 出发点是：用户记了几千条笔记，但不会回去翻；
- 用法却是：点进某一条笔记，看看它关联了哪些旧笔记。

如果用户本来就不会回去翻，这个入口就不成立。我当时的建议是换一条主线：创作一个新主题时，我常常不知道这个朦胧的想法该打什么标签，也想不起它和哪些旧笔记有关，这才是真正需要 AI 帮忙的地方。

**讲得好，不等于想得清。** 表达是一个放大器，它放大的是你已经想清楚的那部分。

### 两个最便宜的检验

**第一，你自己在用吗？** 我问了好几个人：你平时用它吗？连续用超过三天了吗？测试不算。

能回答「在用」的项目，在后面所有问题上都明显更站得住。明账的作者自己就是「隔一段时间集中导账单」的人；做 AI 对话记忆的作者，真的会去翻记忆、画思维导图。反过来，作者自己都不用的项目，评委很难知道该从哪里问起。

**第二，在你出现之前，有没有人在用很别扭的办法满足这个需求？** 这是降星驰给的检验方法。例子是外卖：美团出现之前，就有肯德基宅急送，有商家接电话、自己派人送餐。效率很低，但需求真实存在。

反过来，「只要我做得足够方便，就会有人来用」是一个不成立的逻辑，因为任何东西都可以这么说。**真正重要的需求，哪怕很不方便，也会被人想办法满足。**

想知道目标用户的痛点，也不用闷在家里猜。我当时说：群里 800 个人，你发个十块钱红包，都会有二十个人认真回答你。这不是鼓励大家发红包，意思是用户离你很近，直接去问。

## 四、先找到裁判，再堆 token

回到多 Agent 管理系统。被问到「和别人的差异在哪」时，作者最后讲到了验收层：不是让另一个 LLM 判断做得对不对，而是接一个外部的验证程序，比如电子设计里专用的验证工具、算子的性能评测。分数上去就保留，没上去就淘汰，再分配，再迭代。在一个算子优化任务上，它就是这样一轮一轮把分数往上爬的。

我当时的第一反应是：那不就是测试吗？

复盘的时候我才意识到，这恰好是它做对的地方。我们最后给了它第三名，认可的是它的出发点；而这个出发点真正的价值，不在能开 64 个子 Agent，而在于**它选的任务有裁判**。

这也解释了 Coding Agent 为什么最先成熟：**代码有测试，测试就是裁判。** 有了裁判，才能放心地堆 token、堆并发，让 Agent 自己往上爬。算子优化、硬件设计、形式化证明，都属于这一类。

没有现成裁判的领域，就要先找一个：

- 数学建模的结果没有绝对的对错，论文的用词好不好也很难量化。我问到这一点时，降星驰的回答很干脆：数学建模能拿奖就行。**比赛本身就是裁判。**
- AI 自动整理的知识库对不对、笔记关联得准不准，就没有裁判。降星驰问过做记忆的那位：AI 自动处理了你的知识库，人怎么知道它做得对不对？能当裁判的只有人，而人恰恰是那个「不会回去看」的角色。

所以动手之前，值得先问自己一句：**谁来判断它做得好不好？** 答案可以是测试、比赛成绩、用户付费，也可以是你自己连续在用。想不出裁判的时候，先别急着堆 Agent。

## 五、技术在贬值，懂业务的人在升值

当晚让我印象最深的，是拿了鼓励奖的那位人事管理同学。

毕业两三年，做人事管理，不是计算机专业，今年五六月才开始学 AI 和编程，项目的代码大部分是自己手写的。在我们群里，手写代码常被调侃成一种过时的做法，但放在这位同学身上，我只觉得佩服。项目把算工资、汇总各部门表格的工作，拆成了几个原子工具：读 Excel、写 Excel、把员工信息表转成数据库、查询员工数据库。

作者说了一句我很认同的话：

> 想在工作上用好 AI，其实还是需要对自己的工作有非常足够的了解。

最早的版本是一个把所有表头写死的专用工具，能用，但完全不通用。后来作者才意识到要把工作步骤原子化。这件事技术上并不难，难的是你得知道这份工作里，**哪些步骤可以拆开**。

这也是那晚我反复讲的观点：**做 Agent，产品能力的重要性远远大于技术能力。** 你可以反驳说以前也是这样，这一点我承认。但现在多了一个原因：Agent 是一个增量市场，而技术本身在 AI 面前正在贬值，对业务的理解不会。降星驰也提到，最近取关了很多讲技术细节的博主，因为教你 CSS 怎么写、某个细节怎么优化的内容，已经不需要专门去学了。

拿记忆举例。记忆可以做得很简单，直接塞进系统提示词；也可以做得很复杂，各种召回策略，再结合成本、速度和回答质量一起权衡。但不是每个场景都需要最高级的那一档，你的场景用不上，就别硬上。技术选择一定要有理由，而不是「AI 告诉我用这个」，或者「我第一个知道的就是这个」。

所以我的建议是：**想成为一个合格的 Agent 开发工程师，先成为一个合格的 Agent 产品经理。** 这个数字没有什么依据，但你起码应该深度体验过 20 个 Agent 产品，而且不能只有 Coding Agent。

降星驰另外补了两条很实用的建议：

- **让 AI 起一个定时任务，每天扫一遍 Product Hunt 排名前 10 到 30 的 Agent 产品。** 想创业的话，对赛道保持敏感非常必要。
- **用户量到 10 万之前，别考虑架构优化。** 小团队的架构，核心就一件事：省钱。

## 最后：这可能就是社群的意义

说点比赛之外的。

评审开始之前，我很消极。提交企划的人本来就不多，加上时间一拖再拖，我一度做好了「半小时就冷场收尾」的准备。结果一聊就是三个多小时，后面实在太晚，还稍微提了速。

整场下来，我对大家的参与非常满意，也很有成就感。直播间的反馈一直很热烈，甚至有人说，这是今年最快乐的一个晚上。

我想这也许就是社群的意义。哪怕群里的 Agent 越来越多，人和人之间的交流，依旧是最好的那部分。办这场比赛，对我来说是第一次尝试；对群里很多人来说，以前做项目可能只是为了面试、找实习，很少有机会在群友面前展示，被问一些平时没人讨论的问题。

而且这种交流从来不是单向的。坐在评委席上，看起来是我们在输出，但从大家的回答和讨论里，我也学到了很多。这篇里的不少观点，就是被你们的项目「问」出来的。

这次也有不少人因为家里有事、时间冲突，或者作为新人觉得自己还不够独立做完一个项目，最后错过了。这次叫 Summer of Agents，现在已经 10 月，夏天算是过去了。如果后面顺利，也许还会有一场 Winter of Agents。真有下一次的话，希望能见到你们。
