## 写在前面

副校长是我给粉丝 QQ 群做的问答 Agent，跑在一台个人电脑上，经 NapCat（OneBot v11 协议）接入 QQ。它的主模型是订阅额度制的，额度用完就切到一个便宜的备用模型。它有几十个功能：群聊问答、引用解读、看图、读私有文件、公告、日报周报、投稿、拒答拉黑、娱乐模式开关。[之前一篇](/blog/20260912---agentpermissionisolation/post)写过它的权限隔离，这一篇写的是它的回复链路本身。

过去两周，它陆续出了十几次事故：合并转发刷屏、主线程卡死、文件对话「粘住」之后所有聊天都进了文档模式、额度用完时一刀切。每一次我都去看了日志，定位到出事的那个函数，在那里补一条规则，再加一条测试。每一次补丁都是对的，事后回查也都还在位。但事故没有停。

2026 年 9 月 24 日，我决定先不修了，让一个独立的 Agent 会话对整条回复链路做一次只读评审，然后由我的个人助手（下文叫它主 Agent）独立复核评审结论。评审说的一句话，我后面反复想起：**每个局部模块其实都写得相当谨慎，问题不在某个模块写得烂，而在同一条规则在好几个地方各写一份。**

这篇文章讲的就是接下来一天里发生的事：五个真实问题是怎么在「每一行代码都没错」的情况下出现的，一次完整链路重构怎么做，测试为什么会漏，以及主 Agent 怎么把第一版交付拦下来、返工之后才上线。先把分工说清楚：评审、实现、独立验收是三个不同的 Agent 会话，实现和过程档案整理由 Claude Code（Opus 5.5）完成，我做的是授权、拍板那些需要 owner 决定的事、看验收结果；这篇成稿也是和 AI 一起写的。文中所有事故场景都做了匿名和合成处理，代码只保留最小示意。

## 一、三个「每一行代码都没错」的场景

先看三个用户视角的场景。它们是评审用离线复现确认的，每一个背后的代码单独看都没有问题。

**场景一：引用一条带 @ 的消息，得到「这条引用我没读全」。**

群友引用了另一位群友的发言，那条发言开头 @ 了某个人。主模型额度正好用完，请求落到备用模型上。备用模型回了一句「这条引用我没读全」。可正文其实完整读到了，只是引用里多了一个 @。如果提问本身带了一个 QQ 表情，它会回「这个附件没读取成功」。主模型正常的时候，同一条消息毫无问题，所以平时看不出来，偏偏在最需要备用模型的时候出错。

代码为什么这样写：引用展开的解析器对不认识的消息段类型一律标为「没读全」，这是保守的；备用路径看到这个标记就拒绝作答，也是保守的，因为备用模型确实不该从没读完整的材料里编答案。两处都对，合起来就是一句撒谎的错误提示。

**场景二：重启之后，它「想起」了本不该记的话。**

平时，额度用完的提示、「不予回答」这类短拒答、私有文件问答的占位行，都不会进入问答记忆。这是实时写入路径明确做的过滤。但进程重启后，启动迁移会从会话日志里把记忆「重新推导」一遍，而迁移代码用的是另一套更早、更松的过滤规则，只认三句旧版报错文案。于是重启后，下一轮模型会看到「答：主模型额度暂不可用……」，把它当成自己说过的话。

同一段对话，中途重启过一次和没重启过，机器人记住的东西不一样。这是「运行路径和恢复路径是两套代码」最直接的后果。

**场景三：用户看到了回答，机器人不知道自己说过。**

长回答走合并转发。平台偶尔会返回失败码，但卡片其实已经进群了。这里的处理其实是对的：不重发正文，补一句「送达状态未确认」。但这条回答在会话日志、问答记忆、引用回读索引里一个字都不留。用户接着问「第二点展开讲讲」，机器人没有这段记忆；用户引用那张卡片，回读索引里查不到。

三个场景的共同点：错误提示说的不是真实原因，而每一段代码局部看都是谨慎的。评审最后确认了五个这样的问题，另外两个是主群走了另一套排队逻辑（保护队列只对源码里写死的两个群生效，用量最大的主群反而没有等待上限和超时提示），以及上下文拼装靠位置猜、靠截断压（群聊行截到 200 字、回答截到 300 字都不加标记；主群「去掉当前问题」的方式是「去掉最后一行」，遇到「文字+图片」的提问就把问题本身再塞回背景，遇到纯引用的提问就误删别人的一行）。

## 二、为什么补丁修不好：同一条规则有好几份

把五个问题摊开看，它们的形状是一样的。

「哪些内容可以成为记忆」这条规则有三份：实时写入一份，只留正常回答；启动迁移一份，只排除三句旧文案；「最近回答」缓存恢复一份，完全不过滤。每次事故补的是出事那一份，其余副本没人同步。

「一个消息段算不算读到了」这条规则也有三份：引用展开的解析器一份，处理器对直接消息的类型白名单一份，备用模型的判定只读这两个标记、主模型完全不看。

队列有两套，保护队列在两个写死的群号上，其余群和私信走旧的串行链。上下文拼装有两条路径，保护队列那条在入队时就按 ID 排除了当前消息，所以是对的；旧链那条按「最后一行」猜，所以是错的。同一件事两条路径两种做法。

还有一个更根本的：回复函数结束时没有返回一个明确的「本轮结果」。模型失败变成「通知文案加几个布尔值」，投递失败变成异常，两者最后在同一个地方分叉处理，下游的会话日志、问答记忆、缓存、索引只能各自推断这一轮到底发生了什么。推断的规则，自然又是各写一份。

这就是补丁修不好的原因。补丁修的是症状所在的那个副本，而下一次事故会从另一个副本冒出来。评审给的方向是「边界重整」：不引入新框架，不拆服务，不另建队列或存储，在现有文件里收敛出四条边界。

<ChainBoundaries />

四条边界分别是：A 输入规范化，消息段分类和控制命令识别各做一次；B 轮次权限，租约、中止信号、预算、队列策略收进一个对象；C 执行与结果，回复函数返回明确的结果类别，工具副作用声明挪到工具定义旁边；D 呈现、投递与提交，一个提交函数是会话日志、问答记忆、缓存的唯一写入者，一个留存函数是唯一的规则。

方向定了，但顺序更重要。评审建议先只加测试。

## 三、先让测试看见问题

五个问题全部是在「测试全绿」的状态下存在的。所以第一步不是修，是让测试先能看见它们：在当前代码上应当失败，在必须保留的行为上应当通过。

原来的测试为什么漏了，评审逐条列过，每一条都落实成了新测试的设计：

- 十几个入口集成测试都把会话记忆换成了固定对象，「每次启动重新迁移」这段代码从来没有在端到端测试里跑过。新测试用两个真实的 Node 进程共用一个数据目录，一个不重启，一个重启，比较下一轮的上下文快照。
- 「引用不完整」的旧用例用了一个虚构的消息段类型，断言提示文案正确，于是通过了，但通过的理由是错的。真实的 at、face、mface 从没进过夹具。新语料用真实协议形状：@、@全体、表情、@ 加表情、markdown、超级表情、未知类型、非转发卡片、跨聊天引用。
- 队列只在保护队列的群上测，从来没有测试断言「哪个群走哪条队列」。
- 投递测试只数发送次数，不看事后状态。「用户看到了、机器人不知道」根本不在断言范围里。新测试检查四个存储的事后状态：会话日志、问答记忆、引用回读索引、投递表。
- 夹具里的配置会被悄悄改写。好几个测试把合并转发阈值写成 0 想强制走转发，但代码只接受正数，0 被当成默认的 200。新 harness 显式用真实阈值。
- 只测单轮。之前的分块事故和文件路由事故，也都是单次函数正确、连续使用出错。

为了让这些测试可信，先做了一个隔离运行器：每个套件在一次性源码快照里跑，HOME 为空，网络、监听端口、快照外写入、非 node/python3/git 的子进程全部拒绝。测试 harness 只在最外层边界放桩：QQ 连接是假的 WebSocket，部署配置是注入的，模型 SDK 会话是本地传输。额度错误由**真实 SDK 的流解析器**在一个本地假 fetch 上生成，所以备用判定、工具围栏、额度状态、记忆、迁移、会话日志都是真的。这一点后面会重要。

六组不变量测试在旧代码上按预期失败：重启等价 5 项、消息段语料 12 项、上下文拼装 8 项、投递结果 2 项、队列 1 项、通知器隔离 2 项。而对照组，比如完整 ACK 的轮次、图片轮不留正文、/stop 只停当前，全部通过。

跑消息段语料时还发现了一个评审没写的对称问题：健康的主模型路径下，超级表情和未知类型被**静默丢弃**了，模型根本不知道这里缺了东西。备用路径把 @ 当成没读全是一种错，主路径把超级表情当成不存在是另一种错，两种错都来自「没有一个统一的分类」。

这一阶段有一次返工。后台跑「基线」测试时，实现方已经在改源码，快照取的是工作区而不是基线提交。发现后给运行器加了「从指定 git 提交取源码」的选项，基线重跑。教训很小但很硬：基线必须从提交取，不能从工作区取。

## 四、把规则收成一份

之后按依赖顺序修：留存规则、消息段分类、上下文拼装、结果对象与提交、队列配置化与权限对象、工具副作用与控制命令。每一步单独提交，单独跑全量回归，和基线的失败集合逐项比对。

### 留存规则：一个函数，三处调用

一轮回答结束时，结果类别在回复函数里判定一次：正常回答、宿主通知、拒答、私有文件。这个类别写进会话日志的 bot 行。之后所有「这条内容可不可以成为记忆或背景」的判断都调同一个函数：

```ts
type OutcomeKind = 'answer' | 'notice' | 'refusal' | 'private_document'

function retainPolicy(o: {
  kind: OutcomeKind
  privateKnowledge?: boolean
  delivery?: 'complete' | 'uncertain'
  bodyAvailable?: boolean
}) {
  const none = { qaMemory: false, recentAnswers: false, documentMemory: false }
  if (o.bodyAvailable === false) return none
  if (o.delivery === 'uncertain' && !rememberUncertainAnswers()) return none
  if (o.kind === 'private_document') return { ...none, documentMemory: o.delivery !== 'uncertain' }
  if (o.kind !== 'answer') return none
  return { qaMemory: true, recentAnswers: !o.privateKnowledge, documentMemory: false }
}
```

实时写入、启动迁移、缓存恢复三处都调它。以后新增多少种通知文案，都不需要再改迁移的正则。

旧日志行没有类别字段怎么办？用一个**只朝「排除更多」方向**的推断：所有宿主提示文案直接由生成提示的那个函数枚举出来，不再手抄正则，加上短拒答、私有占位、输出上限截断的半截回答，命中的一律不留。其余保持旧行为。

已经被旧迁移导进问答库的那些行怎么办？评审建议加一个「排除」列，上线时打标记。最后选的是读时按同一规则隐藏：零数据写入，不需要上线时的数据迁移，旧代码仍然能打开数据库。代价是每次读多做一次文本判断，最多两百行，可以接受。原始行一条不删，是否最终清理是 owner 的事。

验收用的就是重启等价测试：同一段对话，一个进程不重启，一个进程中途重启，下一轮的上下文快照逐字相同。5 项失败变成 8 项全过。

### 消息段：一次分类，主备两条路径看同一个视图

消息段分成五类：可读文字；可表示的标记，也就是 @名字、@全体成员、标准 QQ 表情、骰子和猜拳结果、戳一戳，它们的含义可以完整写成一个标记；附件，交给图片和文件各自的链路；容器，也就是引用和转发；未读，包括超级表情、未知类型、非转发的卡片。

```ts
// 一份分类，引用展开、直接消息检查、备用判定都读它
type SegmentClass = 'text' | 'representable' | 'attachment' | 'container' | 'unread'

if (type === 'at')    return { cls: 'representable', text: qq === 'all' ? '@全体成员' : `@${name}` }
if (type === 'face')  return { cls: 'representable', text: `[QQ表情:${name || id}]` }
if (type === 'mface') return { cls: 'unread', text: `[超级表情${summary}：图像未读取]` }
```

关键的取舍在「未读」这一类。评审特意提醒过：不能把所有超级表情、自定义表情、图片都当成无害装饰直接丢掉，它们可能承载提问所需的视觉信息。所以 @ 和标准表情写成标记，不算没读全；超级表情保持「未读」，并在提示词里如实写出这个缺口，主路径的模型也会看到一句「这里有一个图像没读取」。备用模型「不从未读完整的材料作答」这条既有策略一个字没放松，只是它现在看到的是和主路径同一个视图。

这一步也有一次撤回。实现方顺手让引用里的 CQ 字符串（字符串格式的旧式消息）也按消息段解析，现有的一个测试立刻失败：一段 `[CQ:image,…]` 字符串变成了可取的图片，扩大了引用的读取面。这不是这个问题需要的，回退，保持原来「含 CQ 码即不完整」的保守行为。

消息段语料 12 项失败变成 20 项全过。

### 上下文：按 ID 不按位置，截断要留标记

上下文拼装收成一个函数，是唯一会缩短背景的地方。缓存一律存全文，在拼装时按「新行优先」分配预算；被截的行写「…（截断，原文约 N 字）」，超出预算的更早行写「更早的 N 条因长度未带入」。当前消息按 turnId 排除，图片行也带 turnId；问答记忆和「最近回答」按 turnId 去重。主群和保护队列两条路径调同一个函数。

两个没选的方案：只把 200 改成更大的数，仍然是静默截断，下次还会有人以为那是全文；在写入缓存时截断，重启恢复和实时缓存又会不一致。

这里抓到了一个实现方自己引入的回归。新模块从「群拒答」模块导入一条规则，而某个现有测试用只导出一部分的假模块替换了「群拒答」，整个测试文件加载失败。修法不是在新模块里再抄一份正则，那正是要消灭的多副本，而是把规则定义挪到新模块、旧模块转导出。单独一个提交，说明里写清是修复前一个提交引入的回归。

### 队列和权限：默认值一个都不动

队列策略改成读配置，不再写死群号：配置为关走旧的串行链，也是回滚路径；配置为开走保护队列，数值只能调低；不写就沿用现在的两个群。**默认值与上线前完全一致**，主群和私信仍是旧链，保护队列群仍是 90 秒总时限。主群要不要进保护队列、时限取多少，是 owner 决策，本次没有改；现有校验不允许超过 90 秒，想要 240 秒必须连同校验和测试一起改。

回复函数里九处手拼的「还能不能继续 / 发送 / 记录」判断，改成一个轮次权限对象的四个命名检查。工具、文件句柄、数据来源的细粒度授权留在原处，不被它替代。/stop 仍然只中止当前回答、不清排队，有测试锁住。

## 五、「发出去了」和「记下来了」是两件事

第三个场景值得单独一节，因为它牵出的问题最多。

先把状态说清楚。投递有四种结果：完整 ACK，每一段都拿到了平台的回执；unknown，发送开始了但没有拿到完整回执，比如合并转发返回失败码、超时；not_sent，发送前就中止了；late_ack，超时之后回执才到。

对 unknown 的正确处理已经在位：**不重发**。因为卡片可能已经在群里了，重发就是刷屏，而刷屏正是之前的一次事故。补一句「送达状态未确认」也是对的。缺的是记录。用户看到了回答，追问时机器人不知道自己说过什么，这个状态在原来的投递测试里根本不存在，有三条测试甚至**明确断言会话日志里没有 bot 行**，把「用户看到了、机器人不知道」写成了预期行为。

所以新契约是：unknown 的普通文字轮，会话日志留恰好一行，标注「送达未确认」；它是否进入问答记忆和「最近回答」由一个开关决定，**默认关闭，保持现状**，因为这是评审列出的 owner 决策，实现方不擅自改默认。私有文件、私有知识、引用、图片轮的回答正文继续不留。没有真实 ACK 就不建立引用回读索引，不伪造消息 ID。迟到的 ACK 只对账：更新投递表、清掉「送达未确认」的标注，不重发，不回放。

### 一个函数不等于跨存储原子性

这是整次重构最容易写错的一段。提交一轮回答要写 SQLite（问答记忆、投递表）和 JSONL（会话日志），两者之间随时可能崩溃。把三处写入收进一个 `commitTurn` 函数，只是让规则只有一份，不等于跨存储的原子性。

做法是三步。先在 SQLite 里、和投递状态**同一个事务**写入权威提交记录；再按 turnId 幂等地写会话日志、问答记忆，每写完一步记一次进度；下次启动时读权威记录，补齐没写完的步骤。恢复只写记录，**从不发送**。

<CommitGaps />

隐私约束要说准确。文件、私有知识、引用、图片轮的回答正文不进入权威记录。具体实现是：提交函数在写入前把这类轮次的会话行文本替换成占位符，不带问答对；存储层另有两道防护，这类轮次的投递草稿正文非空、或提交记录带着问答对或正文标志时，直接拒绝写入。这不是对任意字段的内容扫描，不能说成「任何地方传进正文都会被拦」。

### 崩溃矩阵第一次全绿，但它漏了

崩溃矩阵的设计是：普通文字轮、不确定投递轮、图片轮，各自在每个写入间隙被杀掉，然后另起一个进程重启恢复。每个用例都是子进程在那个间隙收到 SIGKILL，不是 mock 一个异常。第一版矩阵 12/12 全绿。

一个第一次就全过的崩溃测试，值得怀疑。实现方故意制造了两个缺陷来测这个测试：关掉启动恢复，被抓到了，9 项失败；关掉「防止重复追加」，**没被抓到**。原因是所有注入点都在「记进度之后」，「已追加、未记进度」这个最危险的间隙根本没测。补上两个注入点后，同一个缺陷被精确抓到，3 项失败，正好落在新间隙上。矩阵变成 18/18。

测试数量不是证据，能让测试失败的反例才是。这句话后面还会再出现一次，那次是在验收方那边。

还有一次撤回。实现方一开始让迟到的 ACK 顺带建立引用回读索引，现有测试明确禁止，因为「迟到 ACK 只对账」是既定约束。撤回，列为待决。三条断言「没有 bot 行」的旧测试改成新契约「恰好一行、标注不确定、默认仍不进记忆」，理由写在提交说明里，这是有意的契约变化，不是顺手改测试让它过。

### 工具副作用：按对象身份声明，不按名字

主模型在一次网页搜索之后失败，用户会收到「刚才操作的结果还没确认，我先不重复执行，请先核对操作结果」。一次搜索没有什么「结果」需要核对。原因是副作用分类只认两个只读工具，其余一律「未知」，而未知和有写操作共用一句提示。

修法不是扩大白名单。声明挪到每个工具定义旁边，按对象身份绑定：

```ts
declareToolEffect(historySearchTool, 'read',
  '同步扫描本地群聊日志；只更新本地计数器与请求内私有标记；无网络、无费用')

// 名字相同的复制品不是被审阅过的那个工具
toolEffectOf({ ...historySearchTool }) === 'unknown'
```

逐个读了实现才声明。只读本地数据的才算只读；对任意 URL 发 GET、调用外部计费服务的，即便看起来只是「读」，也保持未知，不在备用模型上重放，因为重放的费用要 owner 拍板。提示措辞随之分开：确有写操作时仍请用户核对；只是有未审阅的工具时，只说「无法确认能否安全重做，所以没有自动改用备用模型」，不再暗示存在某个「操作结果」。

这一阶段还把同步读大文件改成了 SQLite 索引查询和从最新日志文件往前的尾读，把几种控制命令的识别收成一张表，并给「私有标记只收紧不放宽」补了锁定测试。写上线计划时又发现一个回滚隐患：旧代码的启动迁移按 turnId 配对会话行，回滚后会把新代码写的「送达未确认」行和无正文占位行当作普通回答导入记忆。修法是这类行把 turn 放在一个旧代码不认识的字段里，并用**原样保留的旧迁移代码**跑一遍新数据，证明它会跳过。

到这里，实现方交付了第一版：两轮全量回归，32 个套件通过，另外 5 个失败的套件与基线逐项相同，0 新增失败。

## 六、第一轮验收被拦下

主 Agent 没有接受这一版。

它的验收方式和实现方不同：不读实现方的报告，在一份独立的源码快照上，在禁网络、禁止生产目录写入的操作系统沙箱里，用自己写的探针跑。探针得到的三个数字，直接构成了三个阻塞。

### 阻塞一：我自己又犯了一次同类错

默认关闭「记住未确认回答」的开关时，问答记忆里确实没有那条回答。但日报用的当日 transcript 能原文读到它，历史检索工具也能命中它，而且两处都没有任何「送达未确认」的标记。

根因说出来有点难堪：第一版只让「记忆」遵守了这条规则，却没有把会话日志的其他读者当成同一条规则的副本。日报、历史检索、看板摄取、旧卡片匹配、管理员转交，每一个都在直接读会话日志。这正是这个项目最初要消灭的那类问题，在重构的过程中又被写出来了一次。

返工审计了会话日志的全部消费者，把「哪些行只供私有审计」定义在留存规则旁边的同一个文件里，所有派生读者统一应用；私有审计读取是一个显式的、带状态的入口。验证用的是「真实提交、逐个下游读者」的集成测试：真实入口产生一条确认送达、三条未确认（群文字、群图片、私聊）、一条开关打开时的回答，然后逐个调用真实的读者，断言普通回答全部可见、未确认回答全部不可见、审计档案保留状态、图片轮的正文连审计档案里都没有。这个测试在第一版上失败于「未确认回答出现在了派生面」，是真实泄漏，不是断言写错。

### 阻塞二：隔几天再崩一次会重复

崩溃恢复时，投影写到「今天」的日志文件，但去重只查几个固定日期。停机一周，恢复时又崩一次，同一轮就会出现两行。主 Agent 的探针数字是 before 1、after 2。第一版的崩溃矩阵全部在同一天里跑，所以没有发现。

修法：恢复投影一律写到记录自身时间戳所在的日文件，去重只查这一个确定的位置，并匹配聊天类型、群和用户。新测试覆盖跨越一天到一年的多次重复崩溃、午夜前一秒的记录、同一 turnId 属于另一用户时不误判。

### 阻塞三：「与基线相同的失败」不是验收

这一条最值得写。

第一版报告里说，5 个失败套件与基线逐项相同，其中一个真实 SDK 用例被归因为「依赖个人 HOME，在空 HOME 下 SDK 走不到桩」，另外几个套件在隔离环境里挂起或失败，「均为基线状态」。听起来像一个安全的结论：反正它们本来就失败，与本次改动无关。

主 Agent 不接受这个结论，要求真正跑通。实现方给模型层临时加了诊断打印（随即还原），发现真实 SDK 会话在资源加载阶段就被中止了，中止它的是**实现方自己在阶段 0 加的离线守卫**。SDK 会逐级向上查找 .git 目录来定位仓库根，守卫对快照外的元数据探测直接抛异常，而不是回答「不存在」。所有真实 SDK 会话在到达模型边界之前就死了，会话列表是空的，于是「额度用完切备用」这条最关键的链路从来没有真正跑过。「依赖个人 HOME」是没有追到底的错误归因。

修法只改守卫的一处语义：被拒绝的元数据探测返回 ENOENT 或 false，像在一台空机器上一样；内容仍然不可读，写入仍然被拒。不是放开凭据，不是开网络，不是删断言。修完之后，额度的真实 SDK 主备切换用例、模型思考套件、原来挂起的投稿套件，全部真正跑通。

剩下几个套件的失败逐个定位，全是夹具问题：一个夹具每次调用都用同一个工具调用 ID，而工具围栏按设计拒绝重复 ID；一个夹具修改娱乐开关时没有发送者本人的明确命令，而权限对象修好之后要求它；一个多进程夹具每个进程阶段都从 1 开始编号消息，被持久化的「重复消息占用」丢弃；一条断言写在投递层新增的状态提示之前。每一处都是改夹具让它符合真实协议，没有放松任何产品断言。然后用修复后的夹具在**未改动的基线源码**上重跑，同样跑通，说明夹具修复本身没有偏袒候选版本。

测试基础设施本身也会说谎。一个过严的守卫让关键测试安静地失败，而「与基线一样失败」听起来像是一个安全的结论。独立验收者用自己的探针，不读实现方的报告，才把它拦下来。

### 另外几处

主 Agent 还要求了四项补充检查。上下文预算没把标签、截断标记和分隔符算进去，它的例子是预算 50 个码点、实际输出 71；返工后所有输出都计入预算，同一个例子得到 15，放不下有意义的片段时只输出一句省略说明，另加 400 轮随机属性测试覆盖中日韩文字、代理对、ZWJ 表情和多行。一段纯文本的迟到 ACK 被当成整条回答送达；返工后只有每一段都拿到真实 ACK，迟到 ACK 才把整答升级为已确认，否则只记录消息 ID 作为证据，状态保持 unknown。记忆读取对新记录仍走旧的文本推断，并忽略了「送达未确认」字段；返工后问答表加了可空的 outcome 列，新行明确写入类别，只有没有类别的旧行才走推断。最后一项是底稿里两处说法不准确，已更正，本文用的是更正后的版本。

返工中又有几次返工。一个单测曾用新代码的写入函数模拟旧数据，新写入正确带上类别之后这个测试失效，改用原样保留的基线代码写旧行。一个新的读取函数把内部字段带进了返回行，导致转交主助手的内容改变，改回原有形状。每一处都记在过程档案里。

第二版提交之后，主 Agent 再次独立验收。它在独立快照里重跑了 40 个离线测试套件，全部通过，运行前后源码稳定；把自己第一轮的探针原样复放，旧提交上重现出与第一轮完全相同的数字，新提交上关闭。这一轮验收核实了实现会话的全部消息都来自同一个模型，没有子代理，没有换模型。

## 七、上线：备份副本、旧代码和回滚边界

验收通过不等于可以上线。上线前主 Agent 做了两件离线的事。

第一件是用生产 SQLite 的在线备份副本和私有日志副本做隔离迁移演练。结果是原有问答行逐行未变，新增 0 行，投递表原行未变，没有待重放的提交记录；若干条旧有的不合规记忆在新规则下被隐藏，原始数据一条不删。第二件是在同一个真实数据库副本上，用原样保留的基线代码读、写、迁移，再回到新版读，兼容验证通过。这才是「回滚路径存在」的证据，而不是提交说明里的一句「可以 revert」。所有备份和真实数据只在本机私有目录，不进入文章、代码或任何公开产物。

然后是受控上线。上线前和切换代码后都确认接收处理、问答队列、文件通知和 QQ 动作为空，用现有的进程管理器重启流程。没有注入故障，没有往群里发测试问答。入口没有原子暂停，所以「空闲检查」只是说重启前一刻观察到空闲，不能说成消除了重启期间消息到达的竞态。发布公告有真实 ACK，并从群历史读回确认恰好一条普通文字、窗口中无重复。默认模型、账号、娱乐开关、队列默认、/stop 语义、配置都核对了哈希未变。

有一件事第一次检查时没有发生。新版的会话库升级是懒加载的，新进程第一次实际使用记忆时才执行。首次无扰检查时还没有新的自然消息进来，所以那时不能把副本演练写成「生产迁移已经完成」。后来一条自然到达的消息触发了升级，只读观察到 1 条新问答行带有明确的结果类别，0 条是非回答类别，没有待补齐的提交。这条附记替代了最初的懒迁移保留意见。

到写这篇文章为止，以下生产场景**没有主动制造，也还没有自然发生**：真实的额度耗尽，平台返回失败码但卡片已进群，自然的进程崩溃后恢复。离线测试里这些路径走的是真实入口、真实处理、真实 SDK 解析器，但模型是本地传输桩，QQ 是假连接。那是回归测试，不是付费模型的质量评测。

回滚边界要写清楚。增量 schema 的兼容已经验证，但直接回到旧代码会恢复旧的过滤行为，被读时隐藏的那些旧行会重新出现在上下文里；新版运行期间如果产生了「仅供审计」的行，旧版的历史检索、日报、看板会把它们当成普通记录显示。所以回滚前必须先只读计数、评估，不能盲目还原旧日志、删除原始数据或抹去新增记录。旧代码回滚不是零风险，它只是一条被验证过存在的路。

## 八、这次实践对我意味着什么

[前一篇写 Harness](/blog/20260912---codexharnessevolution/post) 的时候，我说人和 Agent 之间的协作机制会越做越大。这次是一个具体的样本：一个 AI 在改另一个 AI 驱动的系统，我在中间做的是授权和拍板。回头看，真正起作用的机制落在五个很具体的地方。

**真实状态。** 阶段 0 的第一条教训是基线必须从提交取，不能从工作区取。上线前的教训是「生产迁移已完成」只能在观察到之后写。整篇文章最费力的地方是区分三种状态：离线已证实、实际已上线、生产自然场景尚未发生。

**授权。** 待 owner 决定的事项从头到尾没有被顺手改掉：主群的队列时限、未确认回答是否进记忆、迟到 ACK 是否建索引、带费用的只读工具能否重放、超级表情要不要接视觉、旧的污染行要不要清理。实现方有两次「顺手多做了」，都被现有测试挡住并撤回。默认值一个都没动，这比多修一个问题重要。

**上下文。** 五个问题的根子都是上下文在多处各自推断。收成一份之后，规则只需要改一次；但第一轮验收证明，「收成一份」这件事本身也会漏，会话日志的其他读者就是被漏掉的副本。

**工具副作用。** 备用模型能不能重放一个工具调用，取决于那个工具的实现被人读过没有。按名字白名单不行，按对象身份声明才行。声明之外的一律未知，未知就不重放。

**可验证结果。** 崩溃矩阵全绿不算，故意注入缺陷能被抓到才算。「与基线相同失败」不算，在基线和候选上都真正跑通才算。实现方的报告不算，验收方用自己的探针复现出同样的数字才算。主 Agent 第一轮拒绝的三个阻塞，每一个都是报告里看不出来的。

我不想把这写成一个全自治的故事。评审、实现、验收是三个不同的会话，人在每个环节之间拍板；上线用的是现有的重启脚本，没有新平台；离线证据不等于线上验证。它也不是一个「彻底没有 bug」的故事，第七节列的那些没发生的场景，就是下一次可能出事的地方。它只是一个把「修一处坏一处」停下来的过程，以及这个过程里每一次被拦下的记录。

### 还没做的和待决的

- 主群是否进入保护队列、总时限与等待上限取多少。现状旧链 180 秒模型预算、300 秒外层硬超时、无等待上限。
- 「可能已送达」的回答是否进入问答记忆。开关默认关闭。
- 迟到的真实 ACK 是否建立引用回读索引。现状不建立。
- 带外部费用的只读工具（网页搜索、网页抓取、外部视觉）能否在备用模型上重放。现状保持未知、不重放。
- 私有标记是否改为按来源划界。现状保守传染，且有测试锁定不能按轮数或时间放宽。
- 背景预算的具体数值。现状单行 1200、整块 6000、bot 回答 1500 个码点，集中在一处常量。
- 超级表情是否接入视觉读取。现状保持未读并如实标注。
- 已被旧迁移导入的问答行是否最终清理。现状读时隐藏，不删。

如果你也在维护一个自己的 Agent，并且发现自己在同一个系统上连续打了好几次补丁，我的建议只有一条：先别修下一个，去数一数那条规则被写了几份。
