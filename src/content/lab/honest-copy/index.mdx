## 拆开看它怎么做到的

`writeText` 会在这些情况下 reject（通常是 `NotAllowedError`）：页面没有焦点、不在 HTTPS 下、被嵌在没有授权剪贴板权限的 iframe 里，或者调用前先 `await` 了别的东西，把用户点击带来的“激活状态”耗掉了。左边的按钮这时依然显示“已复制”，用户粘贴出来的却是上一次的内容。

右边的做法分三步：

```ts
async function copy(text: string) {
  try {
    await navigator.clipboard.writeText(text) // 1. 等结果
    return 'copied'
  } catch {
    if (legacyCopy(text)) return 'copied' // 2. 兜底：临时 textarea + execCommand('copy')
    return 'failed' // 3. 都失败就直说
  }
}
```

- **先等，再打勾**。等待期间显示“确认中…”，正常情况下这一步只有几毫秒，用户根本察觉不到。
- **兜底要看返回值**。`document.execCommand('copy')` 已经被标记为废弃，但仍是覆盖面最广的退路；它返回 `true / false`，不检查返回值就等于又撒了一次谎。用完要把临时 textarea 删掉，把原来的焦点和选区还回去。
- **失败要有出路**。光说“复制失败”不够，demo 里会顺手把代码选中，用户按一下 ⌘C 就行。

按钮上的文字切换用的是本站的模糊 + 缩放过渡，几个状态叠在同一格里，按钮宽度不会跳。

## 什么时候不该用

- 兜底不是用来绕过权限的。浏览器明确拒绝了，`execCommand` 通常也会失败，这时候老实说失败就好。
- 密码、密钥这类敏感内容，与其自动写进剪贴板，不如给一个可选中的文本框，让人自己决定。

## 出处

`writeText` 的返回值和失败条件见 [MDN: Clipboard.writeText()](https://developer.mozilla.org/en-US/docs/Web/API/Clipboard/writeText)。“先等、再兜底、最后才报失败”这个顺序，来自我优化本站代码块复制按钮时的改动；这里把失败路径做成了可以切换的模拟：模拟模式不会动浏览器权限，“正常写入”模式调用的是真实剪贴板。
