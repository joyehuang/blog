## 核心内容

Cursor 的 Git 基础设施长文（2026-08），从 Linus 设计 Git 的原始场景讲到他们自研的 Continuity 存储系统，最后落到新产品 Origin 的发布。这是一篇罕见地把「为什么 Git 服务器难做」从第一性原理讲清楚的文章——每个失败案例都有具体公司和技术名，每个设计决定都有 why not。作者是 Cursor 的工程师，文中有处自我介绍细节：他的前导师是 Shawn Pearce（JGit 作者、Google 版本控制系统团队）——这条线索贯穿了文中对历史尝试的判断。

## 问题根源：packfile 的物理特性

Git 是分布式版本控制系统——服务器上的仓库和开发者笔记本上的仓库本质相同。这个设计对 Linux Kernel 的去中心化维护者完美（Linus 当年的对标对象 BitKeeper 也必须是分布式的），但对**托管** Git 的公司是噩梦。「来自地狱的信息管理器」是 Git 自己的标语（可以查证），而 GitHub 2008 年的初创标语同样坦白：「Git 代码仓库托管：不再让人痛不欲生。」

噩梦的根源在 packfile，一步步推导：

- packfile 是 Git 存储**和**网络通信的基础构件——push/pull 都以 packfile 传输。这是唯一无法绕开的约束：你可以不服 packfile 的磁盘格式（Linus 不会来检查你服务端怎么存），但所有 Git 操作都要求通过网络发送 packfile
- packfile 里的对象为体积最优而生：关键启发式目标是尽可能缩小体积——对象随机分布在整个包中、被压缩、**大多以同一包内另一对象为基础的增量形式存储**
- Git 仓库是 DAG（有向无环图）：列出近期变更 → 处理 commit → 拿到 tree 根指针 → tree 里是每个文件的指针 → commit 还有指向父 commit 的指针。**遍历的每一步必须先拿到前一个指针才知道下一个**——图上一次逻辑跳转，落到磁盘上要经历多次物理跳转
- 合起来：**跨数 GB 数据的随机遍历发生在每一项 Git 操作里**，这与网络文件系统（无论文件级还是块级复制）天然不兼容；唯一能救的是把整个文件缓存在本地——但同一系统里有数十万个仓库时缓存不可行

## 历史上的三条路线

**1. 分布对象本身（DHT）——死于协议**。Git 是内容寻址存储（SHA-1 为键），天然适合映射到分布式 KV——但不可行。Git 仓库是 DAG，任何操作都要遍历图，每次取指针都是一次分布式往返，成本很快变得极高。最有前景的一次尝试：作者前导师 Shawn Pearce 在 Google 版本控制系统团队用 JGit（Java 写的自定义 Git 实现，抽象了仓库存储的所有细节）把对象放进分布式哈希表。系统能跑、常规操作够用，但 **Git 协议要求传输 packfile** 这一条让 clone 性能差到最终放弃。教训：存储层怎么改都行，网络协议是硬边界。

**2. 分布文件系统（GitHub 早期路线）——被运维痛死**。GitHub（2008，Rails 单体）的办法最务实：保持 Rails 应用不变，把 Git 数据放到分布式 FS，把精力留给交付功能。试过的清单读起来像一部失败史：NFS 集中式服务器（很快放弃——Git 对文件系统语义的假设（锁定、撕裂、同步）在开发机本地文件系统上表现不错，在网络文件系统上既慢又漏洞百出）、一次短暂的 GFS 部署、一次持续更久的 DRBD 块级复制——**全都碰壁**，运维糟糕透顶，性能也不足以弥补。根因还是 packfile：DAG 布局与 packfile 存放位置无关联、对象以增量存储，逻辑跳转×物理跳转的随机遍历与任何网络文件系统不兼容。GitHub 最终转向 RPC 系统（仓库在专用文件服务器、Rails 远程执行全部操作），水平扩展可观，但可用性和最繁忙仓库的性能仍未解决——每个仓库仍然只在一台机器上。

**3. Spokes（2013 起，行业标准）**。GitHub 开发的应用层复制方案，如今大多数 Git 托管服务都采用其某种变体。它能长期运行靠三个后来被证明正确的选择：

1. 不分发 Git 本身，在 packfile 层面运作
2. 所有数据以**真正的 Git 仓库形式**存放在本地 NVMe 磁盘（packfile 的随机读取模式让这几乎是必需的；克隆保持高效；复用上游 Git 生态的全部性能优化，不用维护魔改 Git）
3. 复制数据，但**所有副本始终同步一致**

第三条最反直觉也最关键：**Git 客户端无法很好地应对最终一致性**。推了个 commit 却 fetch 不到？Git 会非常困惑。一百个 CI runner 里三个克隆后找不到本该测的 commit？灾难级体验。所以 Spokes 不惜复杂度保完全一致——共识机制用的是 3PC（三阶段提交）。

这里文章给了个很精彩的工程洞察：**Git 推送天然分成两部分——packfile（对象）和引用事务（ref 更新）**。ref 更新之前，push 的 commit 是不可见的（Git 术语：unreachable）。所以可以先把 packfile 扇出到所有主机（无需同步），再对小小的引用事务跑三阶段提交。Git 本身支持「准备引用事务」：锁定 ref、校验期望值、持锁直到提交或中止。

但 Spokes 的两个缺陷在 2026 年暴露：

- **3PC 水平扩展能力受限**：共识每一步的延迟受最慢节点制约，副本越多推送吞吐越低。当年三副本是甜点；如今企业仓库是巨型 monorepo，CI 流量三副本扛不住；而 agent 时代另一个方向上——海量的小型、一次性、几乎无人使用的仓库——Spokes 又要求每个仓库固定三副本，**下限始终过高，上限始终过低**
- **运维上是「宠物而非牲畜」**：磁盘上的仓库是共识的事实来源，每个副本都至关重要——需要路由表数据库记录每个仓库的位置、给每个仓库算校验和、出问题要抢在丢法定人数之前修好（三个副本坏两个就无法接受推送）。仓库是**宠物，不是牲畜**——运维模型的死穴

## Continuity：WAL 优先的无状态设计

Cursor 的系统叫 Continuity，理念一句话：借鉴 Spokes 的成功之处，解决已知的问题。核心倒转：**不是「仓库 + 复制」，而是「WAL + 无状态副本」**。

### Push 流程：线性化

- 客户端 push → 服务端把增量作为新 WAL 条目写入 S3 → **WAL 完全持久化之前绝不确认 push**
- 每次推送存为独立对象；packfile 同时写入本地磁盘和上传 S3
- 上传 WAL 条目 ≠ 发布：只有在本地副本上成功准备好引用事务、并在 WAL 索引文件（也是 S3 对象）里记录指向该条目的指针后，推送才可见——**这使所有 push 可线性化**
- 刻意避免每次 push 一次 S3 写（S3 PUT 延迟会成为吞吐硬上限）：精心调优的批处理 + 只需把引用事务与单个本地仓库同步（无需法定人数），推送按磁盘允许的最高速度接收

### 共识：不需要

「每个仓库位于哪里？答案是任何地方。这并不重要！」本地磁盘是热缓存，唯一事实来源是 S3 上的 WAL。系统无状态、无路由表（也无需运维关系型数据库——"真是谢天谢地"）。本地没有就从 WAL 还原。生产环境用 rendezvous hashing 把仓库 ID 映射到预期节点列表，但路由所需状态仅是「仓库 ID + 当前健康节点集合」——**状态不同步也没关系，换个节点重建就是**。

主节点选举？同样不重要——**没有状态就没有共识**。任何服务器都可以当主节点，WAL 更新全部通过 S3 的原子 CAS 同步，任何实例接收推送都安全。实践中选 rendezvous 排名第一的当主（避免 CAS 重试），但边缘情况下（部署、故障转移、网络抖动）谁当主都无所谓。设计原则一句话：**降级时始终正确，健康时始终快速**（always correct when degraded, always fast when healthy）。

### 复制：UDP gossip + ETag 条件读

副本数量可以**任意**——都从 S3 追赶。集群内用 **UDP gossip 数据包**做乐观复制，包里带每个副本追赶所需的全套元数据。UDP 不可靠？作者的自问自答很精彩："分布式系统中没有任何东西是可靠的！网络不可靠，路由不可靠，拓扑也不可靠。但没关系：这并不重要。"——每个副本都知道自己已追到的 WAL 索引 ETag，读取时对 S3 发**条件 GET**（预期 ETag）：返回 304（平均 <10ms，纯元数据操作）说明副本最新，立即处理 fetch/clone；返回 200 就先追赶到最新再处理。

**读路径的一致性由 S3 权威仲裁**——gossip 丢了、拓扑变了都不影响正确性。

这带来两个方向的弹性扩展：巨型 monorepo 可以部署数百副本扛 CI 负载；agent 创建的海量小仓库各由一个副本服务（S3 是事实来源，无需多副本保可用）。**空闲仓库甚至不需要副本**——一段时间没流量就从节点磁盘垃圾回收，下次 fetch 时直接从 WAL 重新还原。仓库终于从宠物变回了牲畜。

### 压缩：以带宽换 CPU

WAL 需要定期压缩（否则完整恢复要重放每条记录）；Git 仓库本身也需要定期 repack（每个 packfile 有独立索引，跨 100 个 packfile 查一个对象要逐一打开索引）。Spokes 时代的痛点：重新打包极耗 CPU，必须在所有副本执行，同一仓库意外在两个节点触发维护就容易故障转移。

Continuity 的做法：**只有主节点执行压缩，压缩结果同时应用于磁盘仓库和 WAL**。所有副本跟随 WAL，也就跟随了压缩事件——副本不执行 repack，只从 S3 下载已压缩的 pack，**以带宽换 CPU**。

### 吞吐与扩展的实测数字

- **读扩展**：100 副本合成压测，读性能稳定线性增长，push 吞吐无回归——而且由于所有副本完全一致，不仅能扩展 Git 协议（clone/fetch），还能扩展 Origin 在仓库之上的所有 RPC（Web UI、REST API、agent 接口）
- **写吞吐**：S3 Standard 持续 **120 push/s**（同时压缩+复制）；S3 Express One Zone 上 **300+ push/s**，瓶颈变成磁盘压缩速度。正在探索新的磁盘布局降低压缩影响
- 与 Azure DevOps 路线（packfile 进对象存储 + 引用进 MS SQL Server）的对比：关系库能扛大引用事务，但要运维关系库。**Cursor 选择不依赖任何外部数据库**——因为「Git 数据的一致性比任何其他因素都重要」

### WAL 作为事实来源的溯源回报

这段是全文最有分量的一节，直接引用其要点：生产环境的 Git 仓库会出很多问题——静态数据损坏、repack 缺陷、push 竞争，充满边缘情况，大多数已在 Git 上游解决但**并非全部**。Continuity 的一致性模型能跟踪仓库的每一项基础操作：

- push 完全持久化到 WAL 之前绝不确认；所有 push 线性化；每个仓库视图始终完全一致
- 每次 push 都记录在 WAL → **能看到仓库曾经经历的每个状态**，拥有所有 push 和 repack 的完整溯源，可回退或快进任何副本
- 出 Git 缺陷时（不是「如果」是「当」）能精确定位并还原
- 「我们引入的新缺陷极少，因为整个过程中所有 Git 操作都是用现成工具链在磁盘上的普通 Git 仓库执行的」——**不自造 Git，只在普通 Git 仓库外面套一层**

## Origin：agent 时代的叙事

文章的落点是产品发布 Origin（Git 托管平台）。支撑叙事的是 agent 改变量：**更多代码、更多 PR、更多 CI 运行**——版本控制是这一切的核心，也是最难在短时间内改变的系统。「托管他人的源代码责任重大」——开发人员推不了代码，公司就陷入停摆；CI 宕机五分钟的损失难以用金额衡量。

叙事的赌注值得单独记：agent 让代码产出翻倍后，**基础设施层的瓶颈会依次暴露**——先 CI，再版本控制。而 agent 的用法还在反向塑造存储需求（海量一次性小仓库 vs 巨型 monorepo 两头膨胀，Spokes 的 3PC 恰好两头不讨好——**agent 的使用模式本身就是压垮旧架构的新负载**）。Cursor 在押注「AI 公司的 Git 托管是下一个被重新做的层」。

## 当前理解 / 结论

- **WAL 优先 + 无状态跟随者是一套通用的存储设计模式**（不止 Git）：把「确认写」和「可见」解耦（先持久化 WAL、ref 准备好后才发布），一致性不再靠副本协调而是靠权威日志仲裁（S3 CAS/ETag 条件读），扩展性从「副本数×共识延迟」变成「S3 吞吐×磁盘速度」。和我们在 DeepSeek Harness 里看到的 append-only 事件日志、Cumora 的 seen-cursor，是同一家族的思想：**append-only 日志做唯一真相源，其他一切是投影**
- 「宠物 vs 牲畜」的判据可以迁移：**事实来源在无状态层（S3）时，磁盘副本才能变牲畜**。只要磁盘是事实来源（Spokes），副本就永远是宠物
- Git 推送的「对象 + 引用事务」二分，让 packfile 扇出无需同步、只有引用事务走共识——**利用领域结构把共识的范围压到最小**，这是分布式系统设计的经典手艺
- 文章的方法论本身就是范文：从设计初衷（Linus 为自己设计）→ 约束推导（packfile 物理特性）→ 历史失败案例（每条有具体公司和技术）→ 自己的设计取舍（每个决定都有 why not）→ 实测数字（120/300 push/s、100 副本线性）。讲基础设施故事的标准结构
- agent 时代的基础设施重做清单又添一层：Git 托管（Origin）、eval 基建、记忆系统、观测（trajectory）、CI——「AI 原生的」前缀正在逐层替换上一代设施。判断哪个层会被重做的方法：看 agent 的使用模式是否突破了该层当年的隐含假设（Git 的隐含假设是「人类数量的仓库和 push 频率」）
