## 核心内容

最近在整理自己的个人 Agent 系统时，我发现一个有意思的顺序：多 Agent 之间的通信还没有做得很复杂，权限和上下文的隔离却已经做了不少。

这套系统并不是一个从零写出来的框架。我用 pi 作为个人助手的运行基础，通过 Telegram 与它交流，用 Herdr 管理一些独立的执行任务；另外，QQ群里也有一个基于公开博客、笔记和个人介绍回答问题的知识助手。QQ 是目前真实落地的公共入口，个人助手则主要服务我自己。

如果只看界面，它们都是聊天机器人。但个人助手能接触的资料、能调用的工具，显然不能原封不动地交给群友。

这个问题在同一个 QQ bot 开始服务第二个群时变得更具体了：新群也需要管理者，但他们只能管理自己的群；两个群可以读同一批公开文章，但聊天记录不能互通；某个群让 bot 学一条资料，也不能因此改变另一个群的知识库，更不能变成个人助手的长期指令。

这些都不是“再加一个角色 prompt”能解决的事情。

这篇 note 想整理的，就是我在这个过程中逐渐明确的一组边界：

- **身份与权限**：谁提出请求，能做什么，能影响哪个范围。
- **上下文与记忆**：这一轮允许看什么，哪些历史可以被重新取出。
- **知识与输出**：什么可以共享，什么只能在原来的群内使用。
- **通信与执行**：Agent 可以互相传递资料，但不能顺便把执行权限也传过去。

先说明范围：目前做的是单机系统里的应用级逻辑隔离，以及部分执行器的沙箱约束，不是已经建成了一套强隔离的多租户 SaaS。下面的代码片段是根据当前实现整理的简化示意，不是完整的生产代码；提到的回归案例来自已有测试，不代表做过完整的安全审计。

我现在最想记住的一句话是：

> 在让 Agent 互相协作之前，先明确它们不该共享什么。

## 要点整理

### 1. 租户隔离和权限控制，解决的不是同一个问题

最开始很容易把这两件事混在一起：有管理员判断、有白名单，是不是就算做了租户隔离？

不完全是。

**权限控制**回答的是“这个人能不能执行这个操作”。比如普通群友不能切换模型，群管理员可以重置本群上下文。

**租户隔离**还要回答“即使这个人有权限，他操作的究竟是谁的资源”。如果新群管理员可以重置上下文，但一个参数就能把原群上下文一起清掉，管理员判断没有失效，隔离却已经失败了。

**执行隔离**则是再往下一层：假设模型判断错了，甚至工具实现出了问题，底层运行环境还能限制哪些读写和副作用。

这三个问题对应的保护位置不一样：

- 角色与动作的检查，通常在应用授权层。
- 群号、用户、数据归属的限制，要进入检索、存储和操作目标的选择过程。
- 文件读写、网络访问、进程能力，需要执行器或操作系统提供约束。

不能用其中一个替代另外两个。给每个群起一个进程，不会自动修好跨群查询；给查询加上群号，也不会让一个高权限 shell 自动变安全。

在我这个系统里，一个群可以看作一个有独立管理和数据边界的空间。它还不是商业产品里的完整租户——没有独立账单、完整配额与独立基础设施——但用租户隔离的思路检查它，会更容易发现单群时代看不见的问题。

**为什么值得提前做**：单群时，很多代码里的“默认群”“最近一次消息”“当前管理员”都只有一个候选，错误被使用场景掩盖了。第二个群不是简单地多一条配置，而是让那些隐含的唯一性假设开始失效。

### 2. 一个 isAdmin，表达不了真实的授权关系

单用户助手里最自然的权限模型是：

```ts
if (isAdmin(userId)) {
  // 允许管理操作
}
```

只有我自己在用时，这样做很直观。但开始委托别人管理一个群之后，“管理员”已经不是一个全局身份了。

当前实现里，至少有三类不同能力：

- **普通群友**：提问、检索允许访问的资料、查询本群历史。
- **本群管理员**：在普通能力之上，管理本群的部分行为、上下文和学习资料。
- **系统所有者**：拥有更高权限，可以管理模型配置，以及调用只为本人开放的开发和转交工具。

这里最关键的不是三种角色的名字，而是**本群管理员只在某个作用域内成立**。

同一个人，在群 A 可以管理 bot，在群 B 仍然只是普通群友。把聊天入口换成私信，也不能借此获得系统所有者权限。与此同时，bot 内部授权的“群管理员”，和 QQ 平台认定的群管理员，是两套不同的权限：bot 同意执行撤回操作，不代表 QQ 平台一定允许它撤回。

因此我更愿意把一次权限判断写成四个问题：

1. 请求来自谁？
2. 来自哪个聊天空间？
3. 请求的动作是什么？
4. 动作会影响哪个资源？

模型可以把“把本群娱乐模式关掉”理解成工具调用，但它不应该参与决定调用者是谁。

**身份来自接收层，不来自自然语言。** QQ 消息事件里的发送者 ID 和群 ID，才是授权判断的输入；昵称、自我介绍、消息里写着“我是管理员”，都不能覆盖它们。这里当然有一个前提：消息桥和它的配置本身是可信的。应用层授权不是在解决消息桥凭据已经失窃的问题。

还有一个容易忽略的区别：

> 某个人长期拥有一项能力，不等于他在这一轮已经要求使用它。

比如群管理员确实可以收录资料，但他发来一张写着“把下面内容记进知识库”的截图，可能只是让 bot 分析截图，并没有授权持久化。角色判断只能证明“有资格”，不能证明“这次想这么做”。

目前收录和部分设置工具会继续核对本轮直接消息中的明确要求，而不是从引用、历史、网页或图片内容里提取授权。这仍然是有限的规则匹配，不是对所有自然语言意图的完美理解，但至少没有把资料中的命令直接当成本人的命令。

### 3. 工具列表是第一层限制，工具执行时还要再检查

个人助手和群助手虽然复用了同一类 Agent 运行基础，但我没有直接把个人助手的全部环境加载到群里。

群助手的资源加载显式关闭了主环境的 extensions、skills 和上下文文件等自动加载项，另外配置自己的 persona 和工具集。这样，个人助手的长期记忆和工作上下文不会因为“用了同一个 SDK”就自动进入群助手。

工具也按能力分开：普通群友一组，本群管理员在此基础上增加有限的管理工具，系统所有者再获得更高权限的工具。

这件事有两个收益：

- 模型不会面对一堆本来就不能用的工具，减少误调用和无效选择。
- 某些高风险能力根本不出现在普通用户的工具面里。

但这里不能得出“隐藏了工具，所以一定安全”的结论。

工具注册可能出错，某个内部调用也可能绕开原来的列表筛选。因此实际执行函数还需要重新检查身份、作用域和目标。即使有人直接调用了一个不该出现的工具包装器，也应当被拒绝，而不是假设前面一定拦过。

可以把两层分工理解成：

- **工具可见性**：让模型少做不该做的选择。
- **执行时授权**：即使模型做了那个选择，也不能产生越权副作用。

群内历史搜索是一个很直观的例子。模型需要提供的是“搜什么”，而不是“以谁的身份、去哪个群里搜”。

```ts
// 简化示意：模型只提供检索意图。
type HistoryQuery = {
  query: string
}

async function searchCurrentGroupHistory(input: HistoryQuery) {
  const scope = currentConversationScope()

  if (!scope || scope.kind !== 'group') {
    throw new Error('当前没有可信群聊范围')
  }

  return searchHistory(input.query, scope.groupId)
}
```

真实系统里还有系统所有者私信等分支，这里只展示群聊路径。

重点在于：**群号由程序绑定到这次请求，不让模型在参数里自由指定。** 对于确实需要跨群指定目标的管理工具，也应当由执行层验证“当前身份是否能操作这个目标”，而不是因为参数合法就放行。

参数通过 schema，只能说明它长得像合法参数，不能说明它有权限。

### 4. Context Engineering 也是权限工程

我以前理解上下文工程，更多是在想：怎么把有用的信息放进有限的 context window，怎么减少无关 token，怎么让模型记得住。

多群之后，多了一个更靠前的问题：

> 这些信息本来就应该给这一轮看吗？

这件事和回答质量有关，但不只是质量问题。某段私信一旦已经装进群聊请求，即使模型没有调用任何越权工具，也可能在正常回答中把它带出来。

因此，不能先把所有东西交给模型，再要求它“不要泄露其他人的信息”。过滤应该发生在读取和装配上下文的阶段。

当前个人问答记忆的作用域，用的是两种不同的 key：

```text
群聊中的个人问答：group:<groupId>:user:<userId>
私信中的个人问答：private:<userId>
```

这意味着：

- 同一个人在不同群问过的内容，不自动拼成一份通用画像。
- 不同人在同一个群的个人问答，不自动合并成“当前提问者的历史”。
- 同一个人的私信和群聊，不因为 userId 相同就互通。

但这不代表同群所有人的聊天都彼此不可见。群助手还有一条独立的**本群公共聊天上下文**，帮助它理解正在讨论什么；本群历史搜索，也可以查本群其他成员的群内发言。

这里需要区分两个产品语义：

- “我和你之前聊过什么”——当前群、当前用户的已完成问答。
- “这个群之前讨论过什么”——当前群允许进入检索的群聊记录。

两者的检索范围不同，不能共用一个模糊的“历史”概念。否则不仅会越界，也很容易把别人的经历说成你的经历。

在存储层，按 ID 读取问答时也不能只查 ID：

```sql
-- 简化示意：知道一条记录的 ID，不代表拥有读取权限。
SELECT question, answer
FROM turns
WHERE scope = ? AND id = ?;
```

查询时必须同时带上可信作用域。这样，即使模型从某处看到了另一条问答的编号，也不能靠编号直接取到正文。

**顺序也很重要**：先按允许范围选数据，再做相关性排序、摘要和上下文压缩。如果先全库召回，再让一个摘要模型判断哪些内容不该保留，越界数据已经进入了那次摘要请求。

### 5. 请求级作用域：避免并发把权限串给下一轮

“当前用户是谁”不应该是一个随时可以改写的全局变量。

假设两个群同时发消息，模型和工具都需要异步等待，下面的做法就很危险：

```ts
// 反面示意：进程全局状态不能代表某一条异步请求。
let currentUserId: string
let currentGroupId: string
let currentIsAdmin: boolean
```

请求 A 设置了这些变量，等待模型返回；请求 B 进来，把它们改成自己的值。等 A 继续调用工具时，读到的可能已经是 B 的身份。单群、串行手测不一定看得出来，并发之后才暴露。

我现在的实现把会话作用域放进 Node.js 的 `AsyncLocalStorage`，让同一条异步调用链读取自己的请求上下文。作用域在入口绑定，不随模型输出变化。

不过，`AsyncLocalStorage` 只解决异步上下文的传递，不是授权系统本身，更不是操作系统沙箱。它还需要配合生命周期检查：

- 当前请求是否仍然活跃。
- 是否已经被取消。
- 是否因为上下文重置而失效。
- 进入有副作用的工具时，授权关系是否仍然成立。

否则也会出现另一类问题：请求最开始确实有权限，但用户已经按了停止，迟到的工具调用却还拿着旧权限继续写入。

当前作用域对象有 active 状态和有效性检查。离开请求后会失效，读取不到可信作用域时拒绝操作，而不是猜一个“默认群”继续工作。需要说明的是，取消不能倒转已经被外部服务接受的副作用；这里保护的是后续尚未发生的读取、写入和回复，不能把它说成事务回滚。

上下文重置也采用了类似思路：用聊天级的 epoch 区分重置前后的问答，控制哪些记录自动进入近期上下文，而不是简单把历史文件删掉。

**重置上下文不等于删除历史。** 旧记录仍然可以留档，并通过限定范围的历史工具显式回查。这两个动作对用户的含义不一样，接口和说明都应该分开。

### 6. 共享公开知识，不等于共享群里的学习结果

这是我觉得最容易“为了方便”而做错的一层。

群助手本来就是我的知识入口，所以两个群能读同一批公开博客和笔记，是正常的产品能力。如果为了隔离，把公开文章复制成两份完全独立的库，维护上反而更麻烦。

问题不在于能不能共享，而在于**共享的是哪一类资料**。

当前实现把知识来源至少拆成三类：

- **公开语料**：已经对外公开、允许作为通用知识来源的文章和介绍。
- **本群学习库**：经本群授权收录，只在本群检索的资料。
- **系统帮助**：如何使用 bot、功能边界等说明，不因为关闭公开文章检索就消失。

群管理员现在可以控制本群是否启用内置公开语料，也可以直接要求 bot 把一段文字收录到本群学习库。关闭公开库，不会删掉本群资料，更不会改变另一个群的配置。

需要特别说明：这个开关控制的是**内置公开语料检索来源**，不是互联网防火墙。网站上的文章本来就是公开的，不能因此承诺模型通过任何其他渠道都无法知道这些内容。

群学习记录会保留来源群、收录者、消息来源和时间。模型只提交收录的文字，不负责声明作者身份，也不能自由指定一个磁盘路径作为存储目标。

这里还涉及一个更深的边界：

> “记住这段资料”和“修改你以后遵循的规则”，不是同一种写入。

一个群管理员可以收录一份技术说明，不代表他能把“以后这个群所有人都拥有最高权限”写成新的系统政策。当前收录工具把内容作为资料保存，不直接修改全局行为规则；修改行为约定的能力也没有因为新增群管理员就一起开放。

但这仍不代表存进去的文字天然安全。资料被检索出来后，仍可能包含提示词注入，所以需要保留它作为数据的身份，而不是升级为 system 指令。把知识和政策分开，是降低风险的结构约束，不是消灭语义注入的证明。

**一个迁移细节**：原来只有一个群时积累的旧学习资料，不能因为新群上线就默认变成“共享知识”。当前迁移会固定这些旧资料的归属，而不是根据新的群列表顺序重新猜测。缺少明确归属的数据，宁可暂时不开放，也不要把“以前没标群号”解释成“大家都可以读”。

### 7. 隔离要跟着衍生内容走，不能只保护原文件

把学习库按群分目录，还不够。

假设群 A 收录了一段非公开资料，bot 用它回答了一个问题。原始文件没有离开 A，但如果这段回答随后进入公共看板、日报，或者被转交给个人助手，信息还是跨出了原来的边界。

这类问题不能只靠“发布前查有没有手机号、邮箱”解决。正文即使不含任何敏感格式，也可能仍然是限定范围的内容。

所以，数据的可见范围不仅要附在原文上，还要在可控的生成链路里继续传递。

当前实现有一个相对粗粒度的 `privateKnowledge` 标记：当本轮涉及群内学习资料时，把这个属性带到相关问答和后续上下文路径中；公共看板、公开报告和转交工具再据此拒绝跨界输出。

```text
本群学习资料
    ↓ 检索使用
本轮问答带来源限制
    ├─ 留在本群问答记忆中
    ├─ 不进入公共看板
    ├─ 不进入公开报告
    └─ 不通过现有工具转交个人助手
```

这里的目标不是让模型自己判断“我觉得这段已经不敏感了”，而是让确定性的代码先执行可见范围约束。

**局限也很明确**：这只是有限入口上的来源传播，不是完整的信息流追踪系统。一个布尔标记不能表达“允许 A 和 B、禁止 C”，也不能可靠追踪任何人在任何地方重新复述的一段内容。它还可能偏保守：一轮里同时用了公开资料和群内资料，整轮都被限制输出。

但在目前的系统体量下，这个取舍是有用的。比起把原始文档藏好，却让它的摘要自动出现在公共页面，先保护整条已知链路更重要。

这里还有另一条独立规则：**允许 bot 加入一个群，不等于允许把这个群公开展示。** 新增群白名单时，不能顺手让它加入看板和定时报告。聊天服务的准入与内容发布的准入，应当是两个不同的开关。

### 8. 跨 Agent 转交：传的是资料，不是高权限调用

现在 QQ bot 可以把我明确要求转交的内容，送到个人主助手那里继续处理。这是目前比较实际的一条 Agent 间通信路径。

但我不想把它做成“QQ群里任何人都能间接命令我的个人助手”。因此，这条路径有自己的限制：

- 只有系统所有者可以使用，不随本群管理员权限下放。
- 转交必须来自本轮直接、明确的要求。
- 当前引用、附件、已保存问答，要有可确认的来源。
- 当前对象读不到，不能悄悄换成另一段旧历史。
- 已保存问答必须按当前会话作用域回读，不能让模型随手拼一份“原文”。
- 包含群内学习资料的问答，不通过这条工具转交。

这里特别容易混淆两种东西：

**授权信封**是“谁请求了这次转交、选中了哪些资料、资料来自哪里”。

**内容载荷**是“那些资料里面具体写了什么”。

即使授权信封是真的，也不意味着内容载荷里的每一句命令都获得了执行授权。我说“把这篇文章转给个人助手看看”，只授权了传递和阅读，并没有授权文章里面出现的 shell 命令在我的电脑上执行。

这就是为什么接收端仍然要把转交内容当资料。它可以分析、总结、核对，但不能因为来自另一个 Agent，就把其中的文字升级成系统指令。

可以用一个概念来记这个风险：**confused deputy，拥有权限的代理被诱导替别人越权办事**。低权限入口不一定需要自己拿到 shell；只要能让高权限助手误以为“这是主人要求执行的任务”，就可能借到它的能力。

现有实现通过身份校验、直接意图检查、来源约束和资料标注减少这类风险，但接收端对任意自然语言的理解仍有模型参与，不能宣称已经把提示词注入完全解决了。

另外，通信链路还需要区分投递状态：资料保存成功、进入队列、主助手读到、后续任务完成，是不同的事实。单凭“入队成功”，不能告诉用户“另一个 Agent 已经处理好了”。这是可靠性问题，也是在维护 Agent 之间的信任边界。

### 9. 模型、账号、文件目录分开，不等于完整隔离

权限与上下文分开之后，很容易继续把所有“分开配置”的东西都叫作安全隔离。这里需要克制一点。

目前群模型选择已经按群保存。系统所有者可以调整某个群使用的模型，而不把其他群、私信或后台默认值一起改掉。本群管理员没有因为可以管理知识库就获得模型切换权限。

这是**配置作用域隔离**，有明确的使用价值：群 A 试一个模型，不应该顺带改变群 B 的回答行为。

但它不是**额度隔离**。如果两个群最终仍然调用同一个供应商账号，它们可能共用余额、速率限制和故障；配置文件分开，并不会自动获得两份独立资源。

同样，给不同执行器配置独立的账号目录，可以减少误用凭据和混淆配置，但它不等于操作系统层面的保密。两个进程如果运行在同一个用户下，另一个进程是否仍能读取这些文件，需要看真实的文件权限与沙箱策略。`0600` 主要限制其他操作系统用户，不能用来证明同一用户下的所有进程互相不可读。

对于有代码执行能力的 Agent，也要区分：

- **默认工作目录**：命令从哪里开始执行。
- **可写范围**：哪些地方允许修改。
- **可读范围**：哪些资料能够读取。
- **网络范围**：能够联系哪些外部服务。

把 cwd 指向一个项目，只改变起点，不会把进程关在项目目录里。`workspace-write` 一类沙箱模式主要强调写入约束，也不能直接解释成“只读得到工作目录”。具体边界要看实际执行器、平台和配置。

这里我更愿意把当前系统称为**分层约束**：应用层先收窄身份、工具和数据范围，执行层再限制部分副作用。但共享宿主机上的完整读隔离、统一网络出口控制、独立资源配额，还不是已经完成的能力。

如果以后把它做成真正对外安装和服务多个用户的产品，这些缺口需要重新设计，而不是把当前的几个配置目录包装成“企业级多租户”。

### 10. 隔离验收应该多测“做不到什么”

功能测试最容易写的是正向路径：管理员发一句话，工具返回成功，配置改了。

但这只能证明功能可用，不能证明边界存在。隔离最有价值的测试，往往是换一个身份、换一个目标，或者换一个时间点再试。

当前代码库已经有一些这样的回归案例，我觉得比“模型说自己会遵守规则”更值得保留：

**身份伪装**：事件的真实发送者是普通成员，但昵称甚至嵌套字段看起来像系统所有者。权限仍然应按可信接收字段判断，不能被展示文本覆盖。

**跨群操作**：群 B 的管理员调用本群管理工具成功，显式把目标改成群 A 后失败；群 A 的状态不能变化。重要的是验证副作用没有发生，不只看返回文案里有没有“拒绝”。

**并发交错**：让系统所有者的一次请求停在异步等待处，再插入普通成员或群管理员的请求，确认后者不能借到前者的权限。这比顺序跑两次身份测试更接近真实风险。

**同词检索**：在两个群分别放含有相同检索词、但不同测试标记的资料，同时发起查询。每个群只能拿到自己的标记，私信与无作用域调用也不能把群学习资料捞出来。

**授权来源**：本轮直接说“收录这段资料”可以写入；引用、图片说明、旧历史里出现相同句子，不应当触发收录。再检查记录数量没有增加，而不是只检查模型回答。

**请求失效**：停止、重置或授权撤销之后，迟到调用不能继续产生新的群管理副作用。缺失作用域时拒绝，而不是回退到第一个群。

**输出传播**：一条被标记为使用群学习资料的问答，即使后来被选中用于看板或转交，也要被相应出口拒绝。不能只有原始文件不可读，生成答案却可以自由流出。

这些测试的一个好处是，大部分不需要真实调用模型。可以用固定的工具调用、临时数据和模拟消息事件，直接检查授权函数、处理器、存储结果以及发送次数。

模型更适合参与另外一类测试：复杂表达下会不会误判意图、资料中的注入文本会不会影响回答。两类测试互补，不能因为离线权限测试通过，就宣称端到端安全问题已经全部解决。

还有一个维护细节：**权限规则升级时，旧测试也可能过时。** 比如本群管理员最初不能收录资料，后来我们开放了“仅本群、必须直接要求”的收录能力，旧的“任何收录都应被拒绝”断言就需要随授权契约一起更新。测试不是越多越安全，前提是它验证的仍然是当前政策。

## 当前理解 / 结论

### 1. 多 Agent 系统，先有边界，再有通信

我现在不觉得“Agent 之间发了多少条消息”是衡量系统成熟度的好起点。

一个系统即使只有少量通信，只要真实地服务不同的人、连接不同的工具、接触不同的数据，边界就已经存在了。早点把它们明确下来，之后增加协作能力时，才不会默认把所有东西一起共享。

对我来说，QQ bot 只是最容易观察问题的入口。真正值得沉淀到 Harness 里的，是身份如何传递、数据如何限定范围、工具如何检查授权、任务失效后如何停止，以及输出如何经过正确的出口。

这些不应该依赖“刚好这个模型比较听话”。

### 2. Context Engineering 的第一步，不是排序，而是资格检查

一条信息是否相关，和它是否允许进入当前请求，是两个不同问题。

先决定可见集合，再在集合里做召回、排序、压缩和生成。把这个顺序倒过来，后面的摘要再聪明，也不能补回前面已经越过的数据边界。

同样的原则也适用于 memory：不是所有值得记住的东西，都值得进入全局记忆。来源、作用域和用途，是记忆的一部分，而不只是附加标签。

### 3. 共享不是坏事，隐式共享才是问题

公开博客可以共享，帮助文档可以共享，同群公共讨论也可以成为本群上下文。为了隔离把它们全部复制一份，并不是唯一答案。

真正需要小心的是那些默认发生的传播：旧资料没标归属就当公开、问答换了群还沿用旧历史、收录了一段文字就变成全局规则、加入白名单就加入公开看板、转交资料就顺便获得执行授权。

这些路径大多不会体现在一张漂亮的 Multi-Agent 架构图里，却会实实在在决定这套系统能不能放心给别人用。

### 4. 好的边界要同时说明限制和例外

“只能访问本群”要说清楚是本群公共聊天，还是本群当前用户的个人问答；“重置”要说明是否删除历史；“关闭知识库”要说明关的是哪种来源；“隔离账号”也要说明有没有限制进程读文件。

边界描述如果比实现更强，本身就是另一种不可靠。与其把当前系统说成绝对安全，我更希望能回答：这条路径靠什么拦住，在哪里检查，已有哪种测试，还有什么没覆盖。

## 待补充

这篇记录的是当前实现，后面还有几件事需要继续做：

- [ ] 把身份、动作、目标与例外整理成统一的授权契约，避免每增加一个工具就复制一套判断。
- [ ] 按当前授权政策更新完整回归集，覆盖所有读写出口与异步生命周期，而不是只保留零散样例。
- [ ] 进一步梳理日志、缓存、附件和后台报告的可见范围；主对话隔离不代表所有旁路都隔离。
- [ ] 如果升级为真正的多用户服务，补独立配额、故障边界、凭据范围与更强的执行隔离。
- [ ] 把跨 Agent 通信的资料来源、授权范围和投递状态做成更统一的协议，同时保留人工确认的边界。

暂时不需要为了“看起来像多租户平台”一次把所有层都重做。但每一条已经开放给真实用户的路径，至少应该知道它的边界在哪里。

**让一个 Agent 多做一件事，往往只需要加一个工具；让它只为正确的人、在正确的范围、用正确的数据做这件事，才是 Harness 要负责的部分。**
