## 核心内容

这次回看个人项目的消息投递代码，有一个很小的类型定义让我停了下来：发送结果除了 `sent` 和 `failed`，还有一个 `unknown`。

如果只是写一个脚本，把生成好的内容发出去，这第三个状态看起来有点多余。成功就记成功，抛异常就重试，似乎已经够用了。但把调用过程拆开以后，会发现“调用失败”和“消息没有发出去”不是同一个事实。

假设发送端已经接受了消息，回执在返回途中丢了。调用方看到的是超时，接收端看到的却可能是完整的一条消息。此时再试一次，解决的未必是漏发，也可能是在制造重复。

我现在更愿意把这件事记成一句话：

> **超时告诉我没有拿到确定结果，没有告诉我远端没有执行。**

这篇 note 想解释的就是这个差别，以及围绕它展开的一组实现取舍：

- 什么时候允许重试，什么时候应该暂停；
- 为什么在调用外部服务之前，要先记一笔 `sending`；
- 为什么调用方和发送方各自留账，不一定是重复设计；
- 为什么本地有幂等键，仍然不能宣称“恰好发送一次”；
- 为什么测试里必须保留一个“没有重复，但是也没送达”的案例。

**先交代证据范围。** 本文来自对个人项目源码和测试的回看，不是一次线上事故复盘。我没有为这篇文章读取真实消息记录，也没有统计实际用户遇到重复或漏发的比例。后面出现的状态、计数和中断位置，都是明确构造的离线案例。项目实现只提炼通用机制，示例里的渠道、内容和标识均为虚构；附带的测试是重新写的教学模型，不是私有项目的代码摘录或完整复刻。

## 要点整理

### 1. 从一个看起来合理的 catch 开始

最容易写出来的版本大概是这样：

```ts
// 反例示意，不是本文建议直接采用的发送代码。
try {
  await transport.send(message)
  await markSent(message.id)
} catch {
  await scheduleRetry(message.id)
}
```

这段代码隐藏了一个假设：只要没有执行到 `markSent`，远端就没有完成发送。

但 `try` 里面至少有两段不同性质的工作。第一段产生外部副作用，第二段保存本地认识。两者之间没有天然的原子性。可能外部调用已经成功，本地记录却失败；也可能外部调用成功了，只是成功响应没有抵达当前进程。

于是，下面两个过程在调用方眼里可能长得一样：

```text
过程 A
调用方 ──发送请求──> 远端未接受
调用方 <──超时───── 网络

过程 B
调用方 ──发送请求──> 远端接受并产生消息
调用方 <──回执丢失── 网络
```

两边都进入 `catch`，但正确的下一步并不相同。

如果能证明是 A，重试有意义。如果实际是 B，而且远端不会按同一个请求标识去重，重试可能产生第二条。问题在于调用方通常没有足够信息，从这一个异常区分 A 和 B。

这里不是说所有请求都不能重试。对于一个没有副作用的读取，重复请求往往只是多花一点资源。对于有副作用的请求，需要先问“上一次可能已经做了什么”，然后才是“隔多久再试”。指数退避解决的是节奏，不会补上丢失的执行事实。

我觉得这也是异步代码容易误导人的地方：`await` 把调用写成了顺序，看起来像一个连续动作，但它没有把两个进程、两份存储和网络变成同一个事务。

### 2. 三种结果，分别表示三种证据

为了避免把异常直接翻译成失败，我会先给发送适配器一个明确的结果类型：

```ts
// 概念接口，字段名为讲解简化。
type SendResult =
  | { state: 'sent'; receipt: string }
  | { state: 'failed'; reason: string }
  | { state: 'unknown'; reason: string }
```

三个分支最重要的不是名字，而是各自需要什么证据。

**`sent` 表示拿到了可接受的成功回执。** 这一般是远端返回的消息标识或等价确认。它说明接口约定的发送动作已被确认，不等于收件人已经阅读，也不一定等于所有下游设备都已显示。成功状态要与接口承诺的层级一致。

**`failed` 在这套设计里要有比较窄的含义：能够确定本次没有产生目标副作用。** 比如真正调用传输之前，本地校验就拒绝了输入。若使用远端错误码作证据，也必须先确认那个接口的语义，不能只看“不是 2xx”就认定未执行。

**`unknown` 表示现有证据无法决定是否已经执行。** 请求发出后连接断开、响应无法解析、进程在关键位置中断，都可能落到这里。它不是另一个写法的“失败”，而是下一步自动重发缺少依据。

这三个状态也不直接等于三种调度动作。即使确定未执行，也要区分暂时失败和永久失败。参数永远不合法，重试没有用；暂时资源不足，才可能等一会儿重试。`failed` 是判断可重试性的一个前提，调度还需要原因、预算和下一次尝试时间。

回看源码时，我确认发送侧在记录意图之后捕获到异常，会把结果记为 `unknown`。这个边界很值得保留：一旦跨进可能产生外部效果的区域，就不再根据本地异常推断“肯定没发”。如果某个适配器把含糊的失败错误归到 `failed`，上层再完整的账本也会建立在错误证据上。

因此，这不是只改一个 TypeScript union 就能解决的事。接口类型把问题暴露出来，适配器才负责诚实地回答它。

### 3. 为什么发送之前先写 sending

如果只有完成记录，重启后看见“没有成功记录”，仍然不知道上一次有没有开始。

个人项目里的做法是先持久化发送意图，再调用发送函数，最后保存结果。抽象出来是这样的顺序：

```text
取得本次逻辑投递的独占权
  → 检查已有账本
  → 持久化 sending
  → 调用外部发送
  → 持久化 sent / failed / unknown
  → 释放独占权
```

`sending` 并不表示远端正在处理，更不表示远端已接受。它只是一个本地事实：这次尝试已经越过了预先记录的边界，接下来可能产生副作用。

恢复时如果看到 `sending`，不能简单把它改回 `pending`。因为进程可能在下面任意一个位置结束：

- 已保存意图，还没调用发送函数；
- 已调用发送函数，远端还没处理；
- 远端已经处理，回执尚未返回；
- 回执已经返回，结果还没持久化。

这几种情况共用一个残留的 `sending`。恢复程序没有额外证据时，应当把它视为未解决的尝试。

先记意图的代价也在这里：**它可能把一个实际上没有发出去的任务暂时拦住。** 例如进程恰好在第一种位置结束，远端连请求都没收到，本地却不敢自动重试。这个方案主动接受了一部分活性损失，换取不因结果含糊而重复发送。

如果产品认为漏掉一条低价值通知比重复一条更糟，可以选择另一种策略。但这个选择应该写在系统语义里，而不是藏在一个没有讨论过的 `catch` 里。对不同通知采用不同策略，也比用一条“任何异常都重试”的规则覆盖所有副作用更清楚。

### 4. 逻辑投递身份，不是每次尝试的流水号

账本要发挥作用，需要有一个稳定的键。这个键描述的是“同一件事”，不是“这一次函数调用”。

下面是本文示例使用的身份形状：

```text
digest:edition-a:channel-a:revision-1
```

它表达了一份确定版本的内容，投向一个确定渠道的一次逻辑投递。同一个投递的网络重试仍使用同一个键。换成另一个渠道，是另一笔账；编辑内容形成新版本，也要有明确的新版本语义。

如果每次尝试都随机生成一个全新的投递键，本地账本就会认为它们都是第一次。即使内容一模一样，去重也不会发生。所以“我已经传了一个 id”没有太大说明力，需要继续问：这个 id 在什么时候创建，重试时是否复用，重启后能否找回。

还有一个容易漏掉的问题：键相同，正文变了怎么办？

源码里会同时校验投递身份与内容摘要。这样，旧账本里记录的成功不能被拿来证明另一份正文也已经成功。若同一个键对应了不同内容，当前实现会把这种不匹配留为未知，阻止继续发送，而不是覆盖旧账。

这里的摘要用于绑定本次发送的具体负载，不是用来判断两段话语义是否相近。需要关注的是最终准备交给传输层的文本：标题、链接和格式如果发生变化，就可能已是另一个负载。先生成一份正文再固定下来，比每次重试都重新生成一份“差不多”的内容更容易恢复。

教学测试为方便阅读，直接比较完整的合成字符串，没有实现摘要算法。这能展示“同键不同内容要拦住”的语义，但不能用来验证真实项目如何序列化和计算摘要。

### 5. 两层账本分别知道什么

有时调用链不是一个进程直接调用外部接口，而是任务控制器先调用内部发送服务，再由发送服务去请求外部系统。

这时只在控制器记成功，会留下一个额外窗口：发送服务明明知道成功了，控制器却因为中间的响应丢失一直不知道。

```text
任务控制器             发送服务                 外部系统
    |  逻辑投递请求        |                       |
    |-------------------->|                       |
    |                     |  外部发送请求          |
    |                     |---------------------->|
    |                     |<------成功回执---------|
    |                     |  保存发送侧 sent       |
    |<------响应丢失-------|                       |
    |  仍留下 sending     |                       |
```

在这条路径里，发送服务的本地账本比控制器的记录多知道一个事实。恢复时，如果投递键、渠道和负载都匹配，控制器可以读取发送侧的确定回执，把自己的状态补成成功，不必再产生外部副作用。

我在个人项目的实现和测试里都看到了这种分工：一层记录任务投向各个目标的进度，另一层紧贴发送动作记下意图与结果。目标记录处于 `sending` 或 `unknown` 时，会尝试从匹配的发送侧记录里恢复确定结果。

但这个机制只能关闭**发送侧已经存下回执、调用方却没存下**的窗口。再把中断位置向前挪一点，问题依然存在：

```text
外部系统已接受
  → 成功回执尚未存进发送侧账本
  → 发送进程中断
```

此时两层本地账本都可能不知道真相。增加一层账本没有创造远端事务，也没有把网络变可靠。

因此我不想把它写成“双账本实现恰好一次”。更准确的说法是：发送侧账本给恢复程序提供了一个更靠近副作用的证据源，可以消除部分不必要的重发和悬挂；没有证据的部分仍然保留未知。

另外，恢复程序必须能访问正确的那份账本。在单机共享目录里，这可能只是一次文件读取。跨机器以后，就需要一个可靠的状态查询接口或共享存储。不能把一台机器上的实现直接画成多节点架构，然后默认所有节点都有相同认识。

### 6. “文件写入成功”也要拆开看

源码里的账本不是直接覆写最终 JSON，而是采用临时文件、同步和替换的顺序：

```text
创建独立临时文件
  → 写入完整内容
  → 同步文件
  → 替换最终路径
  → 同步父目录
```

这部分解决的是本地记录的可读性与持久化顺序。读者尽量看到一份完整记录，而不是写到一半的 JSON；恢复时也尽量能够找到已确认保存的路径。

不过，“本地记录写得更稳”和“外部副作用与本地记录原子提交”是不同问题。无论本地记录写得多仔细，只要远端发送和本地保存之间没有共同的提交协议，中间窗口就仍然存在。

我觉得这两个层次很容易在实现介绍里被揉成一句“用了原子写入，所以可靠”。实际上需要分开检查：

- 记录有没有可能半写、损坏或丢失；
- 记录的内容是否准确表达了当前掌握的事实；
- 本地事实和远端执行之间，还剩哪些不可判定的位置。

当前实现也区分“文件不存在”和“文件存在但无法验证”。前者可以表示从未登记过，后者却可能是一次已发生尝试留下的损坏证据。把两者都当作 `null` 然后开始新发送，会把损坏路径变成隐蔽的重发入口。

所以恢复逻辑会额外检查记录是否存在：如果路径存在，但内容、身份或负载校验不通过，就暂停。这也是一种保守选择，代价是需要有人处理损坏记录。

本文的合成测试只用序列化字符串模拟保存，不验证真实文件系统的崩溃一致性，也不模拟断电、磁盘满或网络文件系统。上面这些步骤是源码阅读结论，不能用后面的测试通过数替它们背书。

### 7. 锁解决并发抢跑，账本解决重启遗忘

如果两个执行者同时读取账本，都看到“还没有发送”，它们可能一起产生副作用。仅有一个持久化文件并不足以避免这个竞争。

项目里在读取账本、记录意图和执行发送这一段外面，加了独占锁。这个顺序很关键：如果先在锁外判断“没有记录”，再进锁发送，第二个执行者仍可能带着过期判断进入临界区。

锁与账本各有职责：

- 锁让同时到来的执行者按顺序检查、推进同一笔投递；
- 账本让后来到来的执行者，包括重启后的执行者，知道过去已经推进到哪里。

锁也会遇到恢复问题。原持有者死了，锁还在，怎么办？当前实现只在能够证明记录的进程已经不存在时尝试回收；锁损坏、归属未知或进程仍存活，都保留给后续检查。它还单独串行化旧锁回收，避免两个回收者同时行动，把刚建立的新锁错当成旧锁清掉。

这是一种偏保守的单机实现。我不会把它推广成分布式锁方案。进程标识可能复用，不同主机上的进程标识没有相同含义，文件系统行为也有环境边界。它适合说明“锁的回收本身也有竞争”，不适合拿来证明跨机器的唯一执行。

还有一个很细的区别：没拿到锁，不意味着外部发送失败。只能说当前执行者没有获得推进权；另一个执行者可能正在发送。项目不同层对这种情况会有不同的调度表示，因此不能拿一个上层 `failed` 标签，倒推出远端确定没有执行。判断仍然必须回到产生副作用的那个边界。

### 8. 多个渠道不要共用一个粗糙的成功位

假设一份内容要送到渠道 A 和渠道 B。A 已经成功，B 确定没有发送。如果只保存整份任务的 `done: false`，重跑整个任务很容易把 A 也再发一次。

更合适的状态形状是按目标分别保存：

```text
同一份固定版本内容
  ├─ 渠道 A：sent，有回执
  └─ 渠道 B：failed，确定未产生效果
```

下一次尝试只推进 B。A 的成功记录仍然保留。

如果 B 是 `unknown`，处理方式又不同：A 不动，B 等待核对。不要因为“整个任务还没有完成”，就清空两个目标的状态重新来一遍。

这种拆分还让重试预算更容易表达。任务可以规定最多尝试多少次、最晚推进到什么时候；每个目标保留自己经历过的失败与回执。到期之后留下明确的终止原因，比在后台永远保持一个没有说明的 `pending` 更便于维护。

但预算耗尽与事实未知仍然是两回事。过了某个时间，系统可以决定不再自动处理，却不能因为等待结束就断言消息未送达。调度终止回答“还要不要继续做”，投递结果回答“已经发生了什么”，这两个问题可以放在不同字段里。

## 一个可以离线复现的小实验

为避免只讲状态图，我给这篇 note 写了一个独立的教学测试：

[查看完整合成案例与模型代码](https://github.com/joyehuang/blog/blob/94f91154a568e3018b33b44878dcd17ea6022fb1/demos/delivery-ack/fixture.test.ts)。

运行方式是在本分支的项目根目录执行：

```sh
bun test demos/delivery-ack/fixture.test.ts
```

模型里只有三个角色：

- `World`：模拟远端，用一个数组记录真正产生的效果；
- `Delivery.sender`：模拟发送侧的持久记录；
- `Delivery.caller`：模拟调用方的进度记录。

“重启”通过新建一个执行对象、复制已保存的字符串记录来表达。它是一个确定性的状态转移模型，不是真实进程重启。中断位置由参数直接指定，没有随机故障率，也没有用计时竞争来赌某个分支会不会发生。

实验同时记录 **transport 调用次数** 与 **远端效果数量**。这是刻意拆开的两个计数：一次被明确拒绝的调用会增加前者，不会增加后者。测试只能因为这两个数由 fixture 控制，才知道真实世界里调用方不知道的事。

### 第一组：让错误重试真的产生两次效果

第一个测试故意不用账本。第一次让远端产生效果，然后返回超时；第二次直接重试并成功。

预期是两次调用、两次效果。这是反例，不是方案的成功演示。

它验证的范围很小：**如果接口没有替调用方去重，而且第一次已经产生效果，重试会再次产生效果。** 它没有测量真实网络多常出现这种情况，也没有说所有外部服务都采用同一种行为。

我保留这个测试，是因为没有反例的状态机测试很容易变成自证：只运行我们允许的路径，然后宣布没有问题。这里先让朴素策略明确犯一次错，再看新的状态约束能挡住什么。

### 第二组：相同的 unknown，背后是两个不同世界

两个测试都让调用方得到 `unknown`：

- 第一个：远端已经产生效果，回执丢失；
- 第二个：远端没有产生效果，但调用方同样得不到确定回执。

恢复之后，两者都暂停，不进行第二次传输调用。

结果是：第一个世界有一份效果，第二个世界是零份。这个零非常重要。它说明方案没有从 `unknown` 中推断出远端真相；它只是遵守了“没有新证据，不自动重发”的策略。

因此不能把这组结果写成“成功率提高”或者“保证不漏发”。这里展示的是一个安全性与活性的取舍：在已定义的案例里避免因不确定而重复，但也可能把未送达的任务留给核对。

### 第三组：把中断点挪到不同位置

接着，测试分别在三个位置结束本次尝试：

- 保存发送意图之后、调用传输之前；
- 远端产生效果之后、保存发送侧回执之前；
- 发送侧保存成功回执之后、调用方保存回执之前。

前两个位置都留下未解决的发送意图。恢复对象不会继续调用远端，所以一个可能没有发送，另一个可能已经发送，但都停在未知。

第三个位置不同。发送侧已经有成功证据，恢复对象可以把它补到调用方记录里，最终得到 `sent`，同时保持一次传输调用。

这组测试正好画出了双层记录的边界：它能修补最后一种中断，不能解决前两种缺少证据的状态。

### 第四组：身份与部分成功

剩余案例检查了这些行为：

- 明确未产生效果的失败，允许后续重试；两次调用只形成一次效果；
- 已有成功回执，再执行同一逻辑投递，只返回旧结果；
- 同一个投递键换正文，暂停，不把旧回执套给新内容；
- 已有记录损坏，暂停，不当作首次发送；
- 两个目标只有一个明确失败，恢复只补那个目标；
- **换一个新键就能绕开本地去重**，即使正文没变。

最后一条也是反例。它解释了为什么手工“删记录、换个键再跑”不是普通恢复动作，而是在发起一笔新的副作用。在原结果未知时这样做，仍然有重复风险。

本次离线运行得到 **12 个测试通过，0 个失败**。其中包括两个刻意证明局限的反例测试；“通过”是断言符合预期，绝不表示十二种现实故障都已经修好。

这个模型没有真实并发、锁回收、磁盘故障、网络协议解析，也没有远端幂等实现。它只能支撑本文关于状态、身份和几个中断窗口的推演，不能替代项目的集成测试或线上观测。

## 当前理解与取舍

### 1. 幂等键的有效范围要写出来

如果键只在本地账本里被识别，它能阻止经过同一账本的重复尝试。绕过发送器、换一份账本、删掉记录或换一个键，都可能越过这道约束。

如果远端也提供幂等键支持，系统可以获得更强的能力：用同一键重试时，让远端判断这是既有操作。但仍然需要核对键的有效期、请求体绑定、并发行为和结果查询语义。不能只看到接口里有一个 `idempotencyKey` 字段，就把所有恢复窗口划掉。

本文没有针对某个外部平台做这项协议验证，因此不把远端幂等作为已具备的前提。示例中的远端故意不去重，才能清楚暴露本地策略的边界。

### 2. unknown 需要一个出口，但出口不一定是自动重试

保存未知是第一步，之后至少应该让维护者知道：哪一笔投递、最后停在哪、缺少什么证据、下一步能做什么。

比较合理的后续动作包括：查询远端状态、读取匹配的发送侧回执、根据确定证据修正状态，或者明确放弃本次自动处理。若远端不支持查询，也没有可用回执，就承认暂时无法判定。

这里有两件容易被混淆的事：确认某条消息确实存在，是补充事实；决定即使可能重复也重新发送，是接受新的风险。系统可以允许后者，但应当留下与前者不同的记录。一个泛化的“恢复”按钮不应该把两者混在一起。

这篇文章没有实现操作界面，也没有验证人工核对流程的完整性。把未知保存下来之后，如何让它不过期、不被遗忘，是后续需要补的产品工作。若长期无人处理，保守策略就会变成静默丢失；这一点不能被“避免重复”掩盖。

### 3. 与其只记错误，不如记证据如何变化

调试时，单独一行 `send failed` 给出的信息很少。更有帮助的是沿着同一逻辑投递看到：

- 哪个固定负载准备发送；
- 什么时候持久化了意图；
- 是明确拒绝，还是未拿到可靠回执；
- 发送侧是否持有可匹配的成功记录；
- 哪个目标已经完成，哪个仍需处理。

这些字段不必包含消息正文。稳定身份、内容摘要、状态、原因和回执引用已经能支撑很多恢复判断。正文是否保存，是另一个与隐私和排障需求有关的选择。

我觉得这样的记录方式比“多打一些日志”更具体。我们真正需要的是以后还能解释：为什么这一次决定重试，为什么另一次决定停住。尤其在自动化任务里，调度器不能只留下一个最终标签，还要留下足够让人复核决策的依据。

### 4. 不是所有任务都值得上两层账本

如果只是一个可以重复刷新的读操作，这套机制可能过重。如果外部系统已经提供可靠的幂等请求和状态查询，也可以把一部分复杂度交给远端契约。

对于个人项目，我会先看副作用的代价：重复是否会打扰人，漏发是否可接受，出了问题能否查证，维护者是否有时间处理悬挂状态。然后再决定是简单重试、单层持久记录，还是拆出发送侧证据。

这次源码回看给我的收获，是把一个经常被写成“异常处理”的问题，重新看成“证据不足时如何做决定”。`unknown` 没有让网络更可靠，也没有神奇地保证交付。它让系统停止把不知道的事，当作已经知道。
