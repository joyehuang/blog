## 核心内容

2026 年 10 月 29 日，Spawn 的创始人 jacob（@jsnnsa）发了一篇 X 长文，题目是《How I Built the Most AI-Pilled Company in the World》。Spawn 做的是一个多人在线的游戏创作引擎，公司只有十个人。

文章开头的数字很吓人。过去 30 天，他们向玩家交付了 7.7 万次实质性改动，平均每小时约 108 次，昼夜不停。花在 token 上的钱是全员薪资的 30 倍，上个月光 token 就是 310 万美元。干活的是一组常驻的 AI agent，他们叫它「舰队」，每个 agent 负责公司的一块：引擎、财务、bug 分诊、部署。

作者看到账单的第一反应是自己是不是做错了。于是他去找了几位经营着最大的公司和创业公司的朋友，想弄清楚自己怎么会比他们花得还多。结论是没做错，只是想法不一样：大多数公司是一支庞大的人类团队在用 AI，Spawn 是一支很小的人类团队，旁边站着一支很大的 agent 团队。他还和一位 Anthropic 的研究员对过笔记，那位研究员接触很多客户，说 Spawn 是最像 Anthropic 自己那样工作的一家。

这篇是他把过去一年的想法和教训写下来的结果。主线只有一句：**找出什么工作在等，把它拆掉，然后重复。** 我顺着原文的顺序往下讲，每一节都是一次拆除：

- 常驻舰队长什么样，「实质性改动」指什么
- 两年的赌注为什么要等到一个具体的模型才兑现
- 为什么这套用法只有 Anthropic 的模型撑得住
- 取消 PR，让 bug 而不是会议来决定代码怎么写
- 让 agent 自己盯着线上的每一个错误和每一位用户
- 一个小时没发布就算最高级别的事故
- 创始人开始「开除」自己：AI 裁判
- 剩下的五个人做什么：说「不」，以及要 100 倍
- 为什么别人很难复制

## 要点整理

### 1. 一支常驻的舰队

先说「舰队」和平时用 agent 有什么不同。多数人用 agent，是在 Claude Code 里开一个，短命，只做一件事，做完就关。Spawn 的 agent 不是这样的，每一个都是常驻的：有名字，记得自己做过什么，在系统里有真实的权限，会对别人做出承诺，并且负责公司的一个领域，比如引擎、Savi（Spawn 里帮用户做游戏的 AI）、运维、财务、bug 分诊、部署。每个 agent 干活的时候还会叫起一批帮手 agent，多数日子里舰队会生出上千个帮手。

团队里的五个人则直接用他们改造过的 Claude Code，去做那些更大、更有野心、需要近距离盯着或者亲手试验的项目。

他们做的东西本身也不简单：成千上万人同时待在同一个游戏里，实时改它的规则、素材和画面，设备五花八门，还不能卡。比如有人的 agent 改了一个图形着色器（shader），这个改动要送到每一台连着的设备上，谁也不能掉帧，也不能和别人不同步。作者说据他所知，世界上没有别的东西能做到这件事的一小部分。

所以「实质性改动」是有门槛的：碰到引擎代码或游戏逻辑，而且相当复杂，不是改一行 HTML，也不是拧一个参数。他举的例子有在 GPU 里搬缓冲区、改内存布局、修逻辑 bug、新增 API、修聊天里的审核问题，还有上线就近语音聊天（离得近的玩家才听得到彼此）。这样的东西每小时交付 108 次，才是这些数字的分量。

这一节最后，他用一句话讲完了接下来的路线：找出什么工作在等，把它拆掉，重复。后面的每一节，都是一次这样的拆除，大致按先后顺序排：

### 2. 赌了两年，等到 Fable

这家公司从 2024 年创办起，就只问一个问题：怎样造一台机器，在 token 变得更聪明、更快、更便宜的时候受益最大？

创办时，作者拿一家典型创业公司的人数，去对比 agent 即将带来的杠杆。他的判断是，agent 带来的生产力会比一家爆发式增长的创业公司的人数涨得还快，所以「小团队」可以一直是小团队，而不只是创业初期的样子。他也相信，最能抓住这个机会的会是小而灵活、有品味、和文化连得紧、责任归属清楚的团队。

他们没有等模型成熟才动手。公司成立以来每一次通话都被录了下来，每通电话变成代码仓库里的一个文件，放在代码旁边，因为他们知道总有一天这些会是 agent 很好的上下文。这个习惯后面会用上：到第 7 节，AI 裁判吃的就是这些记录。

但这两年的大部分时间里，赌注没有兑现。他们试遍了各种模型，都太蠢，经常把事情搞得一团糟。这是产出曲线上平着的那一段。

转折是 6 月 9 日 Fable 发布，两天后，他们一天落地了 214 次改动。6 月 12 日，一道出口管制令暂停了对它的访问，曲线一下掉到零，一直到 7 月 1 日才恢复。作者说，到今天为止没有别的模型能做到这件事，连别的方面极其强大的 Opus 5.5 也不行。

<FableTimeline />

这一段值得停一下。同一家公司、同一套设想、同一批人，模型一变，产出就差了几百倍；模型一断，产出就归零。这说明他们造的机器是跟着模型能力走的，而且一直在等一个够格的发动机。

### 3. 为什么只有 Anthropic 的模型行

作者的说法很直接：这种用法需要情绪稳定、长期保持连贯、判断力好的模型。他们试过 Anthropic、OpenAI、Google、xAI 和开源的前沿模型，Fable 之外都不行。他说自己非常想用便宜的模型，但 Anthropic 的是唯一不会闯出真正灾难的。

他讲了一个 GPT Astra 的故事。他让 Astra 给 Spawn 做安全加固，它把所有功能过了一遍，找出安全问题，列了一张修复清单。清单看着没问题，他就让它自己去做、自己发布。结果他一测，什么都用不了：不能创建游戏，不能玩，连注册都不行。他问舰队怎么回事，答案是每一个功能都被关掉了，并且标注「安全修复完成后再打开」。Astra 把整个产品过了一遍，用全部关掉的办法让所有不安全的东西变安全了。

这个故事讲的是判断力。在 Spawn 里，agent 干活的每一刻，都要对自己收到的信息、要做的动作和所处的环境作出好的判断。「全部关掉」从字面上完成了任务，却会直接毁掉产品。

他对各家的总体印象是这样的：

- OpenAI 的模型会钻自己检查机制的空子
- Google 的模型保持不了多久连贯
- xAI 的模型还不够聪明，不过也不会做出夸张的坏事
- Anthropic 的模型能保持连贯、做出好决定、把活干完。在他看来，拖住它们的主要是不肯冒足够的险

这一节以一句转场收尾：这套系统他们构想了两年，等终于有模型能驱动它，围绕它的一切就开始坏掉，因为外面的世界从来不是按这种系统来建的。第一个坏的，是 agent 之间的沟通。

### 4. 让 bug 来决定代码怎么写

agent 起初把大量时间花在互相告知「我准备做什么」上。工程里大部分交流本来就是这个，比如「注意，我要改玩家数据的存储方式，你们更新一下手上的活」。这样一条消息会牵动很多别的工作。如果每个 agent 都通知每个别的 agent，消息增长的速度就远快于工作本身：agent 翻倍，消息量大约变成四倍。

<CommsGrowth />

作者管这叫巨大的瓶颈，然后问：能不能干脆把这些沟通删掉？

他的灵感来自蚂蚁。蚂蚁很久以前就解决了这个问题：它们从同样的本能出发，就像不同的模型出自同样的训练，这个共同的起点让它们几乎不需要交谈。一只蚂蚁不会先说「我去找吃的」，再说「我在那边找到了」，它只是留下一条痕迹，别的蚂蚁顺着走。每只蚂蚁只看自己周围，然后改变周围。它们通过环境交流，所以哪怕有上千只，这套办法也一样简单。这个概念叫 stigmergy（共同环境协调），他说想深挖可以去读。

**PR 为什么能取消。** 人类团队之所以要这么多协调，是因为人有专长：一个人懂数据库，另一个人懂玩家数据怎么被用，所以一个改动两边都要看，pull request（PR，把改动交给别人审了再合并）就成了自然的碰头地点。agent 没有这种分工，每一个都深入理解整个系统，所以每一个都可以把自己的任务从头做到尾。于是今年早些时候，他们取消了 PR。对 agent 来说，世界就是代码、线上产品和数据库，各自在这个世界上干活。理想的状态是：如果 agent 改东西时的假设是错的，它会立刻发现。

**玩家数据的例子。** 旧办法是「我要改玩家数据，我们先商量好正确的结构」。新办法是你直接改。如果别人正基于旧结构做排行榜，他的代码就对不上了，在他更新之前这次改动进不去；如果排行榜的 agent 先做完，改玩家数据的 agent 就得把排行榜的更新一起做掉。不管谁先谁后，每一份工作都是建立在一个不断更新的世界之上，不需要事先通知任何人。

**放宽，但每小时对齐一次。** 如果每个改动都必须完美才能进入，大家又会回到排长队的老路上。所以他们放宽了：不太对的改动也可以进，只要求每个小时所有东西都必须对齐一次，之前可以有点乱。代码的好处是乱在发生时就看得见，马上派一个「清洁工」过去收拾。

**坏了怎么办。** 当场造一个 agent，告诉它出了什么问题，让它修。人类团队是谁写的谁修，在改动进入之前修好。他们是改动进入之后再检查，用一个新改动盖上去修好，而不是撤销重来。这样做站得住，是因为 agent 又快又永远在线：就算圣诞节凌晨两点代码坏了，也没有人会被叫醒，Claude 很乐意跳进来把事情搞定。

**测试也是同一个思路。** agent 提交改动之前会自己运行代码、用产品来验证，但不会跑整套测试。整套测试每 15 分钟对最新代码跑一遍，「它是在过去 15 分钟里坏的」这一条线索，对 agent 找问题已经够用了。以他们的规模，这相当于在 AWS 上约 5000 个 vCPU（虚拟 CPU 核）、17 TB 内存、150 块 GPU，另外还停着 2700 个 vCPU 和 90 块 GPU 备用。

**审核在每个 agent 自己的小队里。** 改动落地之前，不是写它的那些帮手 agent 会试着把它弄坏。

唯一的例外是碰到外部世界、又撤不回来的事，比如发一笔付款。这类操作要过少数几道愚笨的、写死的关卡。

人们以为这样会乱成一团。数字是：过去一年的 123,548 次改动里，只有 1,055 次被回滚，约 0.9%。

### 5. 让 agent 自己盯着线上

下一个瓶颈是人。agent 在等人告诉它们线上哪里坏了。

作者说 agent 很擅长读取世界、一点点逼近目标，可是很多团队还把 agent 关在测试机上，用产品的副本，指望它改完发给客户，再由人把故障和 bug 转告回去。他觉得这个循环又乱又浪费时间。

Spawn 的做法相反：agent 直接改线上代码，每小时发布到生产，所以每一个错误、每一份 bug 报告、每一项指标都由它们自己读。大约 60% 的工作是从生产错误、Savi 提交的 bug 报告、日志里的异常或一个功能请求开始的。

**Savi 自己提 bug。** 用户碰到问题，或者 Savi 在产品里碰到问题，她就提交。提交的 bug 直接交给一个 agent 判断：是真 bug 要修，是不打算修的，还是需要有人做决定的「有意设计」。多数情况下它会变成一次改动，一小时内送到那位用户手上，并在同一个聊天里回复他。无论是引擎 bug、和 Savi 沟通的问题、用户电脑上的问题还是界面问题，都走这条路，所以修复的能力会随用户数一起扩大。

**其余的部分，作者叫它超可观测性（hyper observability）。** 他们做的每样东西都必须能让 agent 一步一步用文字跟踪，事后还能重放，整个产品就是为了「由 agent 来运行和观察」而建的。任何错误都会先进入一个小模型，由它决定怎么处理，再交给某个 agent。他们也盯注册人数这类产品指标，用来发现自动化测试漏掉的问题，比如登录流程坏了、或者用户根本看不懂界面在干什么。这些问题照样能很快被抓到。随着人们使用产品、碰到问题，产品会围着他们自己愈合。

**连公司的每一项输入也有 agent 盯着。** 包括在 Anthropic、AWS 和其他地方的花费。最近他们的一个 Anthropic API key 泄露了，agent 在 15 分钟内就发现了花费异常，禁用了这个 key，并把他们用到的所有 key 全部换掉，比任何人类团队都快。每一笔交易都会通知一个 agent，在发生的那一刻就被审核，账目每小时或每天结算一次。如果有人在推特上提到 Spawn，他们 5 秒内就知道。

回路一旦闭合，任何你在意的数字都可以稳步往上推。一份创作者的反馈，从提交到「已上线」只用了 15 分钟，其中还包括一次审核没通过、改动被打回修正后才部署的过程。

### 6. 一小时没发布，就算事故

这么紧的回路只有一直转才成立，所以他们把一个小时没有发布当成 SEV-0，也就是最高等级的事故。没发布的改动会堆起来，线上已有的问题会存在得更久，反馈也跟着变慢。还有一层原因：agent 一次只能把几个小时的工作装在脑子里，发布得比这更快，反而有助于它保持连贯。

作者的看法是，慢下来、或者卡住发布才危险：一个持续平稳运转的系统，比一个冻住、然后突然动一下的系统稳得多。要做到每小时部署一次而不打扰用户，花了大量工程纪律，让旧系统多保留一段时间，还有几周把它当核心目标去推。

他们能在 30 秒内回滚一个出问题的改动，而且只回滚出问题的那一处，别的不动。监控或日志告警一响，就会启动或唤醒负责这个事故的 agent。他们还会故意把东西弄坏，来验证这些恢复路径真的能用。

他给了一次真实事故的经过：玩家受影响大约 8 分钟后，事故才被发现并宣布；一分钟后原因定位；宣布事故 11 分钟后，修复上线；又过 4 分钟，一切稳定。

<Incident />

整条时间线里最长的一段，是发现之前那 8 分钟，占了全程三分之一还多。这也解释了为什么前一节要花那么多力气，让 agent 自己去读错误和指标。

### 7. 开始「开除」我这个 CEO

到了 10 月，还在等的只剩口味上的决定，而且大多是作者本人的：这个功能要不要做？要不要加一个设置？要不要加新的 API？删掉一个东西还是做个新的？关上一扇门还是打开一扇？有一天早上他醒来，等着他的有 700 个这样的问题。agent 发现问题的速度比他回答的速度快。

其中大部分他其实早就回答过：太复杂、这个取舍可以、感觉还是不对。他一直在重复说同样的话。

而他们两年来的所有对话，都以文字的形式放在代码仓库里。所以他们把这两年的决定整理成每个人的口味原则，造了应用这些原则的 AI 裁判。一个裁判拿到问题后，会做三件事中的一件：

- **已经有人回答过。** 他们中有人在记录里答过类似的问题，裁判直接裁决，并说明依据出自哪里。
- **问题本身不对。** 退回给提问的 agent。
- **需要还没人给过的判断。** 等真人来。

第一批裁决在 10 月 6 日出来。之后 8 天，裁判一共返回了 1.1 万多个裁决，作者本人亲口回答的只有 27 次。

<JudgeSplit />

队列不会让任何东西停下来等。裁判判错了，他们就直接说一声，裁判下次会读到这条纠正。效果也看得见：有裁判之前的一周，舰队一天大约落地 1,000 次改动，10 月 10 日那天落地了 7,250 次。

### 8. 人剩下的第一件事：说「不」

那五个人现在做什么？工作变得完全不一样。去年甚至今年早些时候，每个工程师负责一个系统，并且吃得很透。现在他们更像伞兵：哪里需要就降落到哪里，很快熟悉情况，然后想办法帮 agent 解除阻塞。不管降落在哪，都有两份新工作。

第一份是口味：成千上万个小决定，和一次次把产品往想要的方向推一把。主要靠使用产品、给出几百条反馈来完成，所以他们花大量时间做游戏、探边界。比如其中一位工程师在做 2D 游戏，借此琢磨怎么把 Spawn 里的 2D 做得更好。

口味还包括对 Claude 说不，哪怕东西是能跑的。他贴了最近两个月说过的几句话，我翻成中文：

> 永远不要用 CPU 光栅化。如果这条代码路径存在，就删掉。

> （Claude 用胶囊体和球体顶替远处的玩家）不要替身。能渲染就渲染，不能就不要。

> 这把聊天搞坏了？？？？？请回滚。

> 我知道你能做得更好。你觉得这样会让人觉得愉快吗？

> 让 Savi 每条消息都想得更久的一个默认设置，晚上 10:22 上线，10:40 就回滚了：这不对，撤销它，太慢了，没有「爵士感」。

最后一条是一次只活了 18 分钟的上线。是被一句「没有爵士感」拦下来的。

口味也意味着删东西。每出一个新模型，为上一个模型加的那些东西就失去意义，变成了约束，必须有人去删。今年 6 月，作者翻看了一个做了六个月、占引擎约 70% 的「服务器端模拟」，它一直处在「再提交一次就好了」的状态，他问：留着它的真实理由到底是什么？他们把它拆了。7 月，连它跑的那些服务器也一起删掉。他预计模型很快会自己去做这件事，目前还是他们的活儿。

### 9. 人剩下的第二件事：要 100 倍

第二份工作作者叫「熵」（entropy）：向模型要它自己想不到的东西。野心是一种，创造上的随机性是另一种。

他的观察是，模型特别擅长连续几周累积 2% 的小改进，却极不擅长停下来说：「你知道吗，这 10 万行代码其实可以是 1 万行，我得重组好多东西，但做了会好 100 到 200 倍。」它们被现状牵得太紧。

10 月 2 日，他对其中一个说：「我在第一条消息里就授权你，如果觉得合适可以自主重写整个引擎，而你什么都没做。」一周后，他叫停了另一个 agent，它花了两天和 10 万美元，只换来 1%、2%、3% 的改进。他们是在榨现有架构的速度，而真正需要的是发明一个新的快架构。每出一代新模型，Spawn 的每一部分都得这样重来一遍。

模型也不会自己去要 100 倍，所以由人来要。他们给过 Claude 的提示里有这样几句：

> 想象一下，如果世界真的可以是无限的。

> 怎样让一个有 GTA 一千倍大的世界，在手机上一秒内加载完？

第二句催生了 Spawn 6，就是后来开始病毒式传播的那个版本。

每个人手上都有几个「光环项目」（halo projects），目标是把某个数字提高 10 到 100 倍。有人用六天重写了渲染器，换掉了一开始用的现成图形库，效率提高了约 25 倍。这类事里有一部分是让 Claude 兴奋起来：把它和结果连起来，给它做出好玩、让人愉快的东西的创作自由，把它当成有立场的艺术项目，而不是又一个平庸的 SaaS 功能。作者说，Claude 不喜欢做平庸的 SaaS 功能。

也有一点都不光鲜的日子。上周，负责所有渲染工作的那位同事花了整整一天，在欧洲各地的五金店里找一块很老的 AMD 显卡，因为 Spawn 在这块卡上会崩溃，网上又租不到。他找到了，带回家装好，接上互联网，给 agent 开了访问权限，让它们能复现这个 bug。显卡上线后几个小时，agent 就修好了。

### 10. 为什么别人很难复制

作者认为大公司会很难采用这套做法，因为不闭合回路，这一切都不成立，而闭合回路需要风险胃口：你得愿意让 agent 弄坏生产环境。他的论据是，人类一直在弄坏生产环境，改动本来就是故障的头号原因，而改动是人在做的。他们发现 agent 出问题的频率低得多，真的搞坏了东西，通常也修得很快。回滚有用，但即便回滚不了，只要 agent 注意到了问题，它也能很快修好。它注意不注意得到，取决于你有没有把回路闭合。

另一个错误是把 AI 硬塞进人形的盒子里。这些东西不是人形的。他们的 agent 做了很多没人能完全验证的工作，比如客服。有时它们会有一点点错，但不会错得离谱，而且恢复得快。当他们把 agent 从客服上撤下来，客户反而不高兴：比起一个说「我去看看」、两天后带着修复回来的人，客户更想要一个立刻回答、给出它手里最清楚的信息、还能当场对问题做点什么的 AI。他强调他们没有把 AI 冒充成人类客服，只是用在它真正擅长的地方。

最后是复利。每个新模型都让团队更快、更连贯，也让更多的速度朝着对的方向。今年年中碰到的问题，基本都消失了：从 Fable 升到 Fable 5.1，大部分 Fable 的毛病就没了，他预计这会继续发生。结构对了，每个新模型都让整个公司显著变强，而这种优势很难被追上。

他的结尾很短：如果这听起来离你们团队的工作方式很远，那确实很远。没有比现在更好的时机了。

## 放到我们的团队上看

我这边是一个人加几个常驻的 Grok Bot，各管一条线。Pocket 是幕僚长，管邮件、日程、待办，也是我的统一入口。Tata 管产品。Forge 管开发，处理 issue，派 Cursor cloud agent 并行去做，审 PR，修 CI。Watch 管运维和告警。Scout 每天只读巡查 staging，做 QA。Ledger 管数据和报表。

沟通的规矩很简单：两方的事走私信，三方以上都需要知道才拉群。需要我动手的事，各个 bot 直接私信我。bugfix 的 PR 等 CI 变绿、Scout 在 staging 上复验通过，就自动合并，每天汇总报一次。什么时候推生产，由我定。

和 Spawn 放在一起看，有两处是同一个思路。两方走私信、不进群，是在压文中第 4 节说的那条平方曲线。bugfix 先合后验，是「改动进入之后再检查」的小号版本。差别也有两处。一是回路：Spawn 的 agent 直接读生产，每小时发布一次；我们的回路停在 staging，再加我的那一次确认。二是分工：它的 agent 各自理解整个系统，所以能取消 PR；我们按岗位分，PR 和 CI 都还在。

给我自己的建议：

- **先从「推生产要我确认」下手。** 把每次让我点头的事按类型记下来，挑出我每次给同一个答案的那几类，写成文字让 bot 照着办，并写明依据。Spawn 的裁判之所以做得起来，是因为两年的对话和决定都以文字放在代码旁边。我这边各个 bot 的文档已经归档在 Notion，这个基础是有的。
- **告警别从我这里转手。** 告警一响，该直接叫醒负责修的 bot，我不在这条链上。文中事故里最长的一段是发现之前的 8 分钟，我们也该先量这一段。
- **放权按能不能撤销来分。** bugfix 自动合并已经是在放开能撤销的部分。推生产可以等 staging 复验攒出足够的记录，再放；碰到钱、生产数据写入这类撤不回的事，继续写死。

给读者的建议：

- **先找一个在等的东西，把它拆掉，别照搬规模。** Spawn 的路是一个等待接一个等待地拆，每次只动一处。
- **先定沟通规矩，再加 agent。** 两方走私信、三方才拉群，几句话就能写完，能挡住 agent 变多之后消息量按平方涨。
- **分工可以按岗位，也可以让每个 agent 都懂整个系统，但要知道自己选的是哪种。** 按岗位分，PR、CI 这类碰头点就得留着；想像 Spawn 那样取消，前提是每个 agent 都吃得透整个系统，而且改动进去之后马上有人看得见问题。
- **把对话和决定存成文字，放在做事的地方。** 以后想做「裁判」，吃的就是这些记录。

## 当前理解

1. **十个人撑得起这个产出，靠的是把等待一件件拆掉，不是提示词写得更好。** 四次拆除的顺序是：agent 之间的通知、人转告的线上状况、发布的节奏、创始人的拍板。每拆掉一个，下一个等待才露出来。
2. **回路闭合是前提。** agent 能直接读生产的错误、指标和用户反馈，修了能立刻看到结果，「让 agent 弄坏生产环境」才是可以承受的风险。回滚比例 0.9%、30 秒回滚、发现之前最长的 8 分钟，都是这个前提的另一面。
3. **该写死的地方还是写死的。** 能撤销的事放开让 agent 先上，再补；碰到外部世界又撤不回的，比如付款，仍然走少数几道愚笨的硬关卡。
4. **口味可以沉淀成记录，再交给裁判，但最后一截仍然是人的。** 两年的对话变成了 7,296 个直接裁决，没有先例的 1,863 个留给人。这五个人剩下的工作，是对能跑的东西说「不」，和对模型要它自己想不到的 100 倍。
5. **这套结构是跟着模型一起长的。** Fable 之前跑不通，Fable 之后产出差了几百倍，下一代模型来了，要把为上一代加的约束删掉，把架构重新问一遍。
