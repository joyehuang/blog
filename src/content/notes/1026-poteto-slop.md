## 核心内容

这篇笔记整理 2026 年 10 月 11 日 Lauren Tan（@poteto）的一条长帖，以及帖子下面几条把分歧说清楚的引用和回复。涵盖：

- slop 为什么不是 agent 才带来的，以及「不是我写的」怎样冒充质量判断
- 软件为什么一直在变，硬软件和大多数软件为什么不共用「一次写到完美」
- Good Code 的三条定义，以及形式化地同时保证这三条为什么一直很贵
- agent 移动的是质量分布的平均，不是 Good Code 那一头的成本
- 评论里四件不同的事：责任、连续谱、态度、测试证据
- 要让「平均更好」成立，每个功能该有多正确，验证又要留下什么

原帖自己的判断，和读完评论才能收起来的做法，下面分开写。

先把她的结论记成一句：

> **代码库里一直都有 slop。Good Code 要同时正确、没有 bug、又跑得快且省钱，所以一直很贵。agent 写不出这种代码，但有机会在规模上把平均质量拉高。怎么做到，就是软件工程现在要学的手艺。**

---

## 要点整理

### 1. slop 一直都在，而且经常只是「不是我写的」

长帖的第一句就是判断：codebases have always contained slop。她的理由是，除了任务关键的硬软件（例子是嵌入式），代码很少需要完美，所以这件事一直被接受。

她也写下了 2024 年前后自己的怀疑。写了很久代码的人，包括她自己，当时不相信 agent 能写生产代码。担心的那句是：这些 slop 会不会进到「我们漂亮的代码库」里。

反转紧跟在这句担心后面。人写的 slop 早就很多。说真话的话，大多数人口中的 slop，其实是 "code i didn't write"。她给出的比例是：99% 的人（她把自己算进去）并不知道 Good Code 长什么样，更写不出来。

**「这是 slop」因此常常是作者归属判断，质量判断还没开始。** 别人写的、模型写的、自己多年前写的，都可以让人觉得糟。她点明的那把尺子是代码出自谁手。先把归属和质量拆开，后面谈平均才不会把它们合成一个词。

### 2. 软件在变，所以它很少需要一次完美

她把软件工程和别的工程分开，是因为被建造的东西几乎是有机的，一直在变：

- 用户的口味在变
- 写软件的人对问题的理解在变
- 功能会来，也会走

规格本身在动。今天算正确的行为，下一个季度可能是该删掉的功能。对着一个还会变的目标，追求一次写对、以后永远正确，这个目标本身就不成立。

硬软件贵，也是从机会次数来的。视用途而定，你可能只有一次机会，所以必须一开始就对。大多数软件不是这种形状：还可以再发一版，用户还在，问题的定义也还在变。

| | 硬软件 | 大多数软件 |
| --- | --- | --- |
| 她举的例子 | 嵌入式这类任务关键系统 | 日常在用、持续改的产品 |
| 失败之后 | 可能没有第二次机会 | 可以增量修复 |
| 正确性从哪来 | 一开始就要对 | 接受一些 bug，换速度和进展 |
| 兜底 | 更贵的保证 | 测试和可观测性 |

**机会少，所以硬软件贵。大多数软件用「还能再修」换「一开始不必完美」。**

### 3. Good Code 是三条同时成立，所以尽头一直很贵

她提议的 Good Code 不是一种感觉，是三条要一起有：

- **正确**（correct）
- **没有 bug**（bug free）
- **跑起来快，而且省钱**（fast and cost efficient to run）

缺任何一条都不在这个定义里。正确但慢、快但错、没有 bug 却贵到跑不起，都停在定义外面。第三条是一件事：又快又省，不是「快」和「省」各算一条。

贵的原因她写得很具体。长期以来，没有便宜的办法形式化地保证代码同时具备这三条。写硬软件更难、更贵，就是因为这层保证放不下来，而用途又可能只给你一次机会。

她在这句里点了 @bendlang。这个账号的介绍是 "A fast language that blocks AI mistakes by proof"：一种快的语言，用证明挡住 AI 的错误。原帖没有说这个名字会怎样改变现状，只说它也许能改变「代码没法便宜地同时保证这三条」这件事。这篇不展开这门语言。

接下来她把用户价值和 Good Code 拆开。人们在用的绝大多数软件，不必是 Good Code 也能给用户价值。她还判断：这些软件里的大多数，很可能根本不是形式化可验证的。行业接受一些 bug，换速度和进展，改为依靠测试和可观测性（她写的是 tests and o11y），走增量。

**她称为好事的是这套增量做法，不是 bug 本身。** 测试和可观测性用来把不完美圈在能发现、能修复的范围里。

成本可以想成一条变陡的曲线。横轴是三条同时满足到什么程度，纵轴是为这份保证付出的成本。前半段相对平缓：能跑，出了事故能被测试和可观测性抓住。接近「形式化地同时保证三条」时，曲线抬头。

```
成本
 ^
 |                         /
 |                       /    形式化地同时保证三条
 |                     /
 |                  /
 |              /
 |          /
 |      /
 |  /
 +-------------------------------> 三条同时满足的程度
   能跑    测试 + 可观测性     Good Code
```

**尽头贵，是因为保证本身贵。字是人敲的还是 agent 敲的，改变不了这个尽头的价钱。**

### 4. agent 移动的是分布，不是曲线的尽头

她对 agent 的判断有两层，要分开读。

第一层是速度。agent 让我们动得更快。

第二层是质量，而且带条件。如果接受这个想法，agent 能够帮我们写出更好的代码。那不会是 Good Code，Good Code 仍然贵。但在规模上，平均很可能好很多（much better on average at scale）。

「更好」说的是一大批改动的平均，不是任意一行。「如果接受这个想法」说的是做法，不是打开模型就会自动发生。

```
人写:           [slop ··· 平均 ······]
agent + 验证:        [slop ·· 平均 ········]
                                               Good Code
                     └───── 平均右移 ─────┘    └─ 尽头仍贵
```

右移有一个容易漏掉的推论。生成变快以后，较差的改动，数量也可以同时变多。平均更好，和「仓库里的 slop 变多了」可以同时为真。坏例子变多，推翻不了「平均已经右移」；只拿坏例子，也证明不了平均没有动。

她把接下来的工作定义成手艺：the new craft of swe is to figure out how to do this。现在这就是你的工作。检验标准写得很硬。用 agent 和不用 agent，产出如果没有显著差别，就是有地方做错了。现在开始还不晚，把它当成一棵全新的技能树来学。

原帖没有列出这棵技能树的节点。**产出没变，通常不是少打了几个字，而是周围还按手写代码在运转：任务照旧切，对错仍由同一个上下文凭感觉验收。** 这是对 "you're doing something wrong" 的读法。她要求的是想清楚怎样让平均变好。

### 5. 评论在争的是四件不同的事

引用和回复并不集中在「以前有没有 slop」。真正在争的是：标准按什么分、责任在谁、这句话会把态度带去哪、证据长什么样。

| 在争什么 | 谁说的 | 它补上的一块 |
| --- | --- | --- |
| 这段代码该有多正确 | Dmitrii Kovanikov、Barnir、Ville | 质量是连续的，技能在于判断该给多少 |
| slop 以前有没有主人 | Rares Portan | 有 slop，和有人会为它负责，是两件事 |
| 承认 slop 会不会变成许可 | YT | 「允许不完美」和「允许马虎」不是同一句话 |
| 怎样证明不是感觉 | Boris Kwemo | 没失败过的测试不是证据；测试也看不见形状 |

#### 标准不该只有一档

Dmitrii Kovanikov 用画画做类比：

> Programming is art the same way painting is art. Sometimes you need to draw a hyperrealistic portrait. And sometimes you just need to paint a wall white.

编程是艺术，和画画是艺术是同一个意思。有时要画一张超写实的肖像，有时只需要把一面墙涂白。

Barnir 把同一件事说成技能本身：

> The skill now isn't writing the code, it's knowing how much correctness each feature actually needs.

现在的技能不是写代码，而是知道每个功能实际上需要多少正确性。

Ville 担心的是判断力。代码质量是连续谱；代码库的不同部分、不同的代码库，需求不一样。他不确定软件工程师能不能判断哪里该用哪一档。他还补了一句：帖子里很大一部分描述，谈的其实是完美代码。

> Code quality is a continuum and different parts of the code base and different code bases as you mentioned have different needs. I guess the concern is whether swes are able to determine what is appropriate where. Much of your description seems to discuss perfect code.

三句要一起看。肖像和白墙是在拒绝单一标准。Barnir 把新技能从「写代码」换成「知道每个功能需要多少正确性」。Ville 提醒，Good Code 那三条如果被听成完美，讨论就会从连续谱上滑走。操作问题是人会不会选档。

#### 责任没有跟着代码一起交出去

Rares Portan 承认 slop 一直都有，然后把问题换掉：

> yes, there was always slop. but it was owned by a human. that human was responsible for it. and tried to do better next time.
>
> I remember a colleague laughing while looking at some code, when I asked why he said "i'm looking at code I've written years ago. I was such an idiot"

slop 一直都有，但以前有一个人类主人。那个人为它负责，并且下次想做得更好。他记得同事对着自己多年前的代码笑，说当时的自己是个白痴。

这个例子把「有主人」的含义限定住了。主人回头嫌弃自己的旧代码，说明主人当时也没写出 Good Code。**人提供的是下一次想改好的回路，不是当前这份 diff 的正确性证明。** 生成、读 diff、合并如果共用同一个上下文，这条回路就没有发生，责任只剩下一句「我看过了」。

#### 「可以有 slop」会被听成「可以马虎」

YT 把担心放在态度上：

> I think the attitude of dev is what matters most. Saying it's fine to include slop might give the impression that sloppy engineering is ok, even though those are two different ideas. I'd prefer not to encourage that mindset or split software into critical and non-critical.

开发者的态度最要紧。说「放进 slop 也没关系」，会让人觉得马虎的工程也可以，尽管这是两个不同的想法。他不希望鼓励这种心态，也不希望把软件切成关键的和非关键的。

这里有一对必须留下的张力。肖像和白墙是在分级。YT 拒绝的是另一种切法：切完以后，非关键的那一侧好像就可以不做工程。

**slop 说的是这段没有达到它该有的标准，或者只是这段不是我写的。马虎工程说的是不必再问这段该有什么标准。** 原帖辩护的是前者一直存在。YT 担心的是这句辩护被听成后者。

#### 证据要曾经失败过

Boris Kwemo 给了一个具体习惯：

> One habit that catches a lot of agent slop: make it write the test first and watch it fail. A test that never failed proves nothing. Then we read the diff for what tests can't see, like naming and shape.

先让 agent 写测试，看着测试失败。一个从未失败过的测试什么也证明不了。然后再读 diff，看测试看不见的东西，比如命名和形状。

```
先写测试，看着它失败
        |
        +-- 它没红过 --> 断言和实现可能一起错了，这不是证据
        |
        v
再让实现把测试变绿
        |
        v
换一个上下文读 diff：命名、形状、边界
        |
        +-- 这两步都留下了 --> 这份改动才算被验证过
```

测试的信息量来自一次真实的失败。从一开始就是绿的，只说明当前实现和当前断言一致，不说明断言在看该看的行为。命名、模块形状、依赖方向不会把测试染红，所以还要有一次读 diff。他把这次阅读和写测试分开了：we read the diff。

### 6. 「平均更好」要怎样才成立

原帖止于「想清楚怎么做到是新手艺」，没有给流程。下面四条是把第 4 节的平均右移和第 5 节的评论放在一起之后的结论，用来检查一份改动，不是她列出的步骤。

#### 先定正确性预算，再选验证

把 Barnir 那句收成可操作的说法：**每段改动先有一笔正确性预算。预算决定验证有多重，不决定能不能马虎。** 白墙也有标准，比如盖得住、边缘齐。低预算的意思是不值得为它上形式化证明，不是可以不看。

| 这段改动更像 | 错了会怎样 | 验证至少留下什么 |
| --- | --- | --- |
| 涂白墙：文案、局部样式、边界清楚的机械修改 | 看得见，回滚便宜 | 自动检查，加上一次不是作者做的浏览 |
| 画肖像：权限、钱、迁移、并发、对外的 API | 会留得很久，修复贵 | 先红后绿的测试，独立的审查，上线后能看见的信号 |
| 硬软件：嵌入式、不可逆的操作 | 可能没有第二次机会 | 她说的那种更贵的保证。平均右移不够用 |

第三行对应的，就是她放在「很少需要完美」之外的那种软件。agent 可以推动大量白墙、以及一部分肖像的平均质量。只有一次机会的系统，仍然要买更贵的那种保证。

YT 拒绝把软件切成关键和非关键。这张表要避开的就是那一刀：行与行之间变的是证据的重量，没有一行的标准是空的。

#### 生成和验收不要共用一个上下文

Rares 说的主人，在这里变成一条流程约束。写 diff 的上下文不验收自己的活。验收可以是另一个人，也可以是一条不复用这段推理的自动检查。同一个上下文里的「我看过了」，同时扮演作者和审查者。

#### 合并前要有一次真实的失败

Boris 的习惯可以直接当门槛。测试先红，再绿。从未失败的测试不算跨过这道门槛。实现先写完，测试后补并且一次通过，缺的就是那次失败。

#### 测试看不见的部分单独算

命名、形状、边界要有自己的阅读，不能指望测试顺便完成。能写成 lint、结构测试、CI 的边界，就不要留在读 diff 的手感里。同站的 harness 笔记把工程重心放在环境、边界和反馈回路上，agent 负责执行。和这里接上的只有一句：**感觉不是证据。**

平均右移因此是带条件的。生成变快的同时，验证也要更重，并且和生成分开，分布才会往右。只加快生成时，平均并没有右移，变多的是未经验证的改动。

## 当前理解 / 结论

1. **slop 是质量分布里较差的那一截，不是 agent 的发明。** 用「不是我写的」来认出它，会把归属问题和质量问题合成一个词。
2. **Good Code 贵，是因为正确、没有 bug、跑得快且省钱要同时被保证。** 大多数有价值的软件故意不买这个尽头，用测试和可观测性换速度。她认为这套增量是好事。
3. **agent 的杠杆在平均，不在尽头。** 生成变快时，差改动的数量可以同时变多。平均有没有右移，要看验证有没有一起变重、并且和生成分开。
4. **技能树的第一课是正确性预算。** 要回答每个功能需要多少正确性，以及用什么曾经失败过的证据证明它达到了。用 agent 和不用，产出差不多，就是这笔预算和这些证据还没进流程。
5. **「可以有 slop」不能听成「可以不做工程」。** 前一句说标准不必处处顶到 Good Code。后一句是放弃给这段代码设定标准。分级是为了选择证据的重量，不是为了划出一块免检区。

## 待补充

1. 用证明把「同时保证三条」的成本打下来以后，平均和尽头的关系会怎样变。原帖只点了 @bendlang 的名字，这门语言本身还没读。
2. 命名、形状、依赖方向怎样变成可重复的检查。现在这条还停在「换一个上下文读 diff」，没有展开成一组具体规则。
