## 核心内容

2026 年 10 月 11 日，Lauren Tan（@poteto）发了一条长帖。她从自己 2024 年前后的怀疑写起：agent 会不会把漂亮的代码库写脏。评论把这件事拆成了几件要分开回答的事。

这篇顺着原帖往下走，涵盖：

- 她为什么说 slop 一直都在，以及「不是我写的」怎样冒充质量判断
- 软件一直在变，硬软件和大多数软件为什么不共用「一次写到完美」
- Good Code 的三条，以及保证的成本为什么在尽头变陡
- agent 动到的是一大批改动的平均
- 评论各自补上的一句：分级、责任、态度、曾经失败过的测试
- 这几句合在一起，平均右移要靠什么才成立

## 要点整理

### 1. 长帖从一件旧事写起

开头的判断是：代码库里一直都有 slop。除了任务关键的硬软件，她举的例子是嵌入式，代码很少需要完美，所以这件事一直被接受。

她接着写下 2024 年的怀疑。写了很久代码的人，包括她自己，当时不相信 agent 能写生产代码。担心的是那些 slop 会进到「我们漂亮的代码库」里。

反转放在这句担心后面。人写的 slop 早就很多。说真话的话，大多数人称为 slop 的，是自己没写的那段代码。她给的比例是 99%，并且把自己算进去：并不知道 Good Code 长什么样，更写不出来。

这一步先把两件事拆开。觉得一段代码糟，可能是它没达到这段该有的标准，也可能只是因为它不是自己写的。后者用熟悉度当尺子。后面如果还把「仓库看起来更脏」当成 agent 失败的证据，就得先问脏的是标准，还是作者。别人写的、模型写的、自己多年前写的，都可以触发同一种不舒服。

### 2. 被做出来的东西一直在变

她把软件工程和别的工程分开，是因为被建造的东西几乎是有机的：

- 用户的口味在变
- 写软件的人对问题的理解在变
- 功能会来，也会走

规格本身在动。今天算正确的行为，下一个季度可能是该删掉的功能。对着一个还会变的目标追求一次写对、以后永远正确，追求的对象已经不在了。

硬软件贵，是从机会次数来的。视用途而定，可能只有一次机会，所以必须一开始就对。大多数软件不是这种形状：还可以再发一版，用户还在，问题的定义也还在变。

|              | 硬软件                 | 大多数软件                 |
| ------------ | ---------------------- | -------------------------- |
| 她举的例子   | 嵌入式这类任务关键系统 | 日常在用、持续改的产品     |
| 失败之后     | 可能没有第二次机会     | 可以增量修复               |
| 正确性从哪来 | 一开始就要对           | 接受一些 bug，换速度和进展 |
| 兜底         | 更贵的保证             | 测试和可观测性             |

**机会少，所以硬软件贵。大多数软件用「还能再修」换「一开始不必完美」。** 这是目标函数的差别。它还没有说哪一段可以不看，只是说不该用「一次永恒正确」去要求每一种软件。

### 3. 三条要同时成立，尽头才会那么贵

她提议的 Good Code 不是一种感觉，是三条要一起有：正确，没有 bug，跑起来又快又省。缺任何一条都不在这个定义里。正确但慢、快但错、没有 bug 却贵到跑不起，都停在外面。第三条是一件事，又快又省，不是「快」和「省」各算一条。

贵的原因她写得很具体。长期以来，没有便宜的办法形式化地同时保证这三条。写硬软件更难、更贵，就是因为这层保证放不下来，而用途又可能只给你一次机会。

她在这句里点了 @bendlang。这个账号的介绍把它说成一种快的语言，用证明挡住 AI 的错误。原帖没有讲这个名字会怎样把价钱打下来，只说它也许能改变「代码没法便宜地同时保证这三条」这件事。这篇不展开这门语言。

接下来她把用户价值和 Good Code 拆开。人们在用的绝大多数软件，不必是 Good Code 也能给用户价值。她还判断，这些软件里的大多数很可能不是形式化可验证的。行业接受一些 bug，换速度和进展，改为依靠测试和可观测性，走增量。

**她称为好事的是这套增量做法，不是 bug 本身。** 测试和可观测性把不完美圈在能发现、能修复的范围里。这是一种便宜的、不完整的保证。

<CostCurve />

柱子的形状把话说完了。前两档相对矮，是因为「能跑」和「出事找得到」已经可以靠测试和可观测性买到。第三档突然变高，是因为三条要同时被形式化地保证。**尽头的价钱来自保证本身。字是人敲的还是 agent 敲的，动不了这一档。**

### 4. 她对 agent 说的是平均

判断分两层。

第一层是速度。agent 让人动得更快。

第二层是质量，而且带条件。如果接受这个想法，agent 能够帮人写出更好的代码。那不会是 Good Code，Good Code 仍然贵。但在规模上，平均很可能好很多。

「更好」说的是一大批改动的中心，不是任意一行。「如果接受这个想法」说的是做法，不是把模型打开就会自动发生。

<AverageShift />

右移有一个容易漏掉的推论。生成变快以后，较差的改动，数量也可以同时变多。平均更好，和仓库里的 slop 变多，可以同时为真。坏例子变多，推翻不了平均已经右移；只拿坏例子，也证明不了平均没有动。要看的是那一批改动的中心，以及差的那一批有没有被验过。

她把接下来的工作定义成手艺：想清楚怎样做到这件事，现在就是这份工作。检验写得很硬。用 agent 和不用 agent，产出如果没有显著差别，就是有地方做错了。现在开始还不晚，把它当成一棵新的技能树来学。

原帖没有列出这棵树的节点。产出没变的时候，周围往往还按手写代码在运转：任务照旧切，对错仍由同一个上下文凭感觉验收。这只是一种读法。下面用评论来看，这种读法缺了哪几块。

### 5. 评论各自补了一句

六条回复各自补一件原帖没展开的事。

- Dmitrii Kovanikov：编程有时是画一张超写实的肖像，有时只是把一面墙涂白。
- Barnir：现在的技能不是写代码，而是知道每个功能实际上需要多少正确性。
- Ville：质量是连续谱，他担心工程师判断不了哪里该用哪一档，也觉得帖子有不少其实在谈完美代码。
- Rares Portan：slop 一直都有，但以前有一个人为它负责，并且会回头把自己多年前的代码看成白痴写的。
- YT：说放进 slop 也没关系，会被听成马虎的工程也可以；他不希望这样，也不希望把软件切成关键和非关键。
- Boris Kwemo：先看着测试失败，从未失败过的测试什么也证明不了，然后再读 diff 里测试看不见的命名和形状。

| 补上的一块                           | 它在约束什么                                     |
| ------------------------------------ | ------------------------------------------------ |
| 肖像和白墙，以及每个功能要多少正确性 | 标准按改动分，不按「是不是代码」分               |
| 连续谱，以及会不会选档               | Good Code 那三条如果被听成完美，操作问题就滑走了 |
| 有主人，下次想改好                   | 责任是一条回路，不是当前这份 diff 的正确性证明   |
| 别把 slop 听成马虎                   | 承认不完美，和放弃设定标准，是两句话             |
| 测试要先失败，再读形状               | 证据要曾经红过；命名和边界不会自己把测试染红     |

这几句之间有一对张力，值得留下来。肖像和白墙是在分级。YT 拒绝的是另一种切法：切完以后，非关键的那一侧好像就可以不做工程。分级如果把某一档的标准切成空的，他就说对了。

Rares 的例子把「有主人」限定得很窄。主人回头嫌弃自己的旧代码，说明主人当时也没写出 Good Code。人提供的是下一次想改好的回路。生成、读 diff、合并如果共用同一个上下文，这条回路没有发生，剩下的是一句「我看过了」。

Boris 补的是证据的形状。测试的信息量来自一次真实的失败。从一开始就是绿的，只说明当前实现和当前断言一致，不说明断言在看该看的行为。命名、模块形状、依赖方向不会把测试染红，所以还要有一次分开的阅读。

### 6. 平均右移要这些条件一起在

原帖止于「想清楚怎么做到是新手艺」，没有给流程。下面是把第 4 节的平均和第 5 节的六句放在一起之后，一份改动可以拿来对照的条件。

**先给这段改动一笔正确性预算。** 预算决定验证有多重，不决定能不能马虎。白墙也有标准，比如盖得住、边缘齐。低预算的意思是不值得为它上形式化证明，不是可以不看。

| 这段改动更像                               | 错了会怎样         | 验证至少留下什么                               |
| ------------------------------------------ | ------------------ | ---------------------------------------------- |
| 涂白墙：文案、局部样式、边界清楚的机械修改 | 看得见，回滚便宜   | 自动检查，加上一次不是作者做的浏览             |
| 画肖像：权限、钱、迁移、并发、对外的 API   | 会留得很久，修复贵 | 先红后绿的测试，独立的审查，上线后能看见的信号 |
| 硬软件：嵌入式、不可逆的操作               | 可能没有第二次机会 | 更贵的那种保证。平均右移不够用                 |

第三行就是她放在「很少需要完美」之外的那种软件。agent 可以推动大量白墙，以及一部分肖像的平均。只有一次机会的系统，仍然要买第三档的保证。行与行之间变的是证据的重量。没有一行的标准是空的，这样才接得住 YT 那句。

**写 diff 的上下文不验收自己的活。** 验收可以是另一个人，也可以是一条不复用这段推理的自动检查。同一个上下文里的「我看过了」，同时扮演作者和审查者，Rares 说的那条回路就没有发生。

**合并前要有一次真实的失败。** 测试先红，再绿。从未失败的测试不算跨过这道门槛。实现先写完，测试后补并且一次通过，缺的就是那次失败。

**测试看不见的部分单独算。** 命名、形状、边界要有自己的阅读。能写成 lint、结构测试、CI 的边界，就不要留在读 diff 的手感里。同站那篇讲 harness 的笔记把工程重心放在环境、边界和反馈回路上。和这里接上的只有一句：**感觉不是证据。**

平均右移因此是带条件的。生成变快的同时，验证也要更重，并且和生成分开，分布才会往右。只加快生成时，平均并没有右移，变多的是未经验证的改动。

## 当前理解 / 结论

1. **slop 是质量分布里较差的那一截，代码库里一直有。** 用「不是我写的」来认出它，会把归属问题和质量问题合成一个词。仓库变脏，要先分开这两件事再谈。
2. **Good Code 贵，是因为正确、没有 bug、跑得快且省钱要同时被保证。** 大多数有价值的软件故意不买这个尽头，用测试和可观测性换速度。她认为这套增量是好事。agent 换不掉第三档的价钱。
3. **agent 的杠杆在平均，不在尽头。** 生成变快时，差改动的数量可以同时变多。平均有没有右移，要看验证有没有一起变重，并且和生成分开。
4. **技能树上先要定的是每个功能需要多少正确性。** 用 agent 和不用，产出差不多，就是这笔预算和「曾经失败过」的证据还没进流程。原帖把想清楚这件事定义成现在的工作。
5. **「可以有 slop」不能听成「可以不做工程」。** 前一句说标准不必处处顶到 Good Code。后一句是放弃给这段代码设定标准。分级是为了选择证据的重量，不是为了划出一块免检区。
