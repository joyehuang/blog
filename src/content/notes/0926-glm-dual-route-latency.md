## 核心内容

一次完整的 LLM 网关定责排查。背景：主模型 glm-5.3-flash 同时有两条可用路由——Command Code（套餐内额度）和 OpenRouter（同价，走官方 Z.AI）。用户体感「经常卡死转圈」，需要回答：慢的是模型还是网关？

## 会话数据统计（285 次真实调用）

从 pi session JSONL 提取 2026-08-26~27 六个会话的 LLM 调用，统计口径为「每次调用的纯间隔时间」（上次事件结束 → assistant 消息落盘，剔除 >10 分钟的跨工具执行间隙）：

- **中位延迟**：Command Code 17.8s vs OpenRouter 7.9s——差 2.2 倍
- **P90**：98.0s vs 18.4s——**差 5 倍以上**。CC 约 10% 的调用超 98 秒，这个尾巴就是「体感卡死」的来源
- **输出吞吐**：10.3 vs 34.0 tok/s——差 3.3 倍
- **单次超 3 分钟**：CC 3 次，OpenRouter 0 次

## 「丢包」的直接证据

最慢的单次调用呈现独特模式：**只吐了不到 200 token 却耗了十几分钟**——15 token 花 1258 秒、88 token 花 1283 秒、一连串 70~600 token 各卡 1000 秒以上（连续的「排队窗口」）。

推理排除了模型本身：OpenRouter 底层是同一个 Z.AI 官方端点，跑得飞快。症状是**随机的大延迟毛刺**，指向 CC 网关层的排队/限流/转发问题。

## 实时探测交叉验证

同样的探测请求（"Reply with exactly: OK"）连打三次：

- 第 1 次：CC 52.9s vs OpenRouter 4.9s
- 第 2 次：CC 32.1s（仅 2.2 tok/s）vs 2.2s（17.7 tok/s）
- 第 3 次：CC 2.0s（19.0 tok/s）vs 8.0s

**同一个端点三次之间从 53 秒抖到 2 秒，方差极大；OpenRouter 三次都在个位数秒**——结论定责：问题在 Command Code 链路（网关排队），不在 Z.AI 官方模型。

## 监控方案：让恢复自己找上门

排查变成一个常驻监控 `glm-watch`：每小时用相同小 prompt 同时探测两条链路，记录延迟/token/tok/s/状态码追加 CSV：

- **变坏告警**：CC 连续 2 次失败 → Telegram 推送
- **恢复通知**：最近 6 次探测 CC 全部成功且中位 < 25 秒 → 推一次「可以切回」，之后如再恶化会重置标记再次提醒（**不会只提醒一次就沉默**——这个细节很重要，恢复提醒只发一次的话，错过就永远错过了）
- launchd 每小时跑，人不用做任何事：收到恢复通知后一句话切回省钱链路

## 当前理解 / 结论

- **定责方法论的模板**：① 拆统计口径（纯间隔、剔除工具间隙）② 分位数对比（中位看不出的问题 P90 一眼见）③ 找极端样本看模式（毛刺 vs 均匀慢是不同病因）④ 同请求实时探测交叉验证 ⑤ 结论必须能解释所有证据
- 「同一个模型、两条路由」是难得的受控实验条件——网关层的价值（或危害）只有这样才能被干净地测出来
- P90 尾巴比中位数更影响 agent 体验：agent 是多轮调用，每轮 10% 概率卡 100 秒，一次任务 20 轮调用几乎必然踩到
- 监控告警要设计「恢复通知」：只告警不报平安的监控，会让你永远不敢切回去
