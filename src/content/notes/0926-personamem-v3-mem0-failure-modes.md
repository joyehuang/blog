## 核心内容

PersonaMem-v3（arXiv 2608.21381，Meta × UPenn × MIT 联合推出的全平台个性化智能基准）对商业级向量记忆产品 Mem0 做了系统对照。这张卡记录三件事：论文的评测设置与 4 个维度的完整数据、论文 4.8 节拆出的两个关键失败模式（信息缺失、过期偏好）、以及我们自己的记忆框架迭代中对这两个失败模式的应对——哪些坑我们踩了同款、哪些已经修掉、修掉后实测效果如何。

## 论文背景与评测设置

PersonaMem-v3 的定位是「全平台个人智能」基准：给 agent 一个用户的跨平台完整历史，考核它能不能理解这个人、做对推荐、完成 agentic 任务。它测的不是单轮对话记忆，而是「把一个人完整交给 agent」的场景——这也是为什么它对记忆系统的考验比常规 QA 基准残酷得多。

8 种「模型 × 记忆模式」组合分三类：

- **长上下文基线**：GPT-5.5、Gemini-3.5-Flash 直接把全平台历史（时间排序）塞进 prompt。这是理论上限式的做法——不丢任何信息，但成本爆炸
- **压缩记忆**：① Textual Memory——自演化的文本记忆，把历史迭代压缩成可读 profile；② Mem0 with RAG——向量检索路线的商业级产品
- **Agentic 模式**：Codex（GPT-5.5）、Claude Code（Opus-4.8 / Sonnet-4.6），用 agentic 搜索在平台数据库里翻文件——不给现成记忆，让 agent 自己查

## 4 个维度的结论

### 1. 整体准确率——所有模式都刚过半

最强是 Opus-4.8 + Claude Code（53.7%），GPT-5.5 长上下文 53.4%。Mem0 排在记忆类里，整体也在这个量级。这个数字的含义是：**全平台级别的用户理解仍是未解决问题**，没有任何一种模式真正「解决」了它——记忆系统之间的差距，是 40% 和 53% 的差距，而不是「能用」和「不能用」的差距。

### 2. Token 效率——Mem0 最大的存在价值

- 长上下文基线每 query 烧约 **410k-416k tokens**——把原始历史全喂进去，现实成本不成立
- Mem0 与 Textual Memory 压缩到 **3k-5k tokens**，便宜约**两个数量级**
- 延迟上 Mem0 22.2s，反而不输长上下文的 22.4s（Textual 24.4s）——压缩记忆没有用延迟换成本
- 一个细节：Gemini-3.5-Flash 的 Textual Memory 组合提升最明显，比自家长上下文又快又省又准

这一维度是我们走对方向的确认：记忆的价值恰恰在压缩——如果记忆系统吐出来的 token 数接近原始历史，它就没有存在意义。

### 3. 稳定偏好——能打，但边界清晰

论文结论：Mem0 和 Textual Memory 在**宽泛、稳定的偏好**上很有竞争力——写作风格、长期口味、常见需求这类「重复出现的模式」，向量记忆守得住，适合个性化聊天和本地推荐场景。

但一旦任务依赖以下四类信号就翻车：

- **小对比差异**：两个选项只有细微差别时，检索粒度不够
- **负面证据**：用户「跳过」了某类内容 = 不喜欢——这种「没做」的信号很难被当成记忆存下来
- **精确标题**：需要逐字准确的实体名/标题时，压缩归纳会糊掉细节
- **时间变化**：偏好变了之后，旧偏好和新偏好同时存在，系统分不清哪个是「当下」

## 失败模式拆解（论文 4.8 节）

论文把 Mem0 的失败逐条归因，两个模式最关键：

### 模式一：信息缺失（information missing）

Mem0 的失败里 **23%** 是「需要的信息没被存进去，或没被检索到」——和 Textual Memory 的 22% 几乎同病。这个数字的洞察在于：**这 23% 不是检索算法的问题，而是写入侧和召回侧都有漏**。信息在源头就没进记忆，或者进了记忆但召回 query 根本对不上它。

### 模式二：过期偏好（stale preferences）

这是 Mem0 更特有的坑：检索到的事实**主题相关，但已经不是当下该用的依据**。向量相似度只回答「像不像」，不回答「新不新」——用户两年前喜欢 A、现在喜欢 B，两条记忆都和当前 query 高度相似，纯向量排序分不出胜负。本质是**缺少时间感知的召回**。

## 场景适配边界

把 Mem0 的强项弱项按使用场景摊开：

- **适合**：用户偏好/口味/写作风格的存取（宽泛、稳定、可提炼）、个性化聊天、本地推荐——省 100 倍 token 的价值全在这些场景兑现
- **要打折**：调研/事实检索类任务——记忆只给方向，原文细节必须回源；写代码/项目上下文——项目文件才是真相源，记忆只适合存「项目级决策」（比如包管理器选型、版本 pin）
- **不适合**：小对比差异、负面证据、时间变化类任务——这类任务需要完整上下文，目前只有带全上下文的 agentic 模式能吃下

## 我们的阅读讨论：两个设计问题的答案

读论文的过程中，我们把两个问题讨论透了。

**问题一：memory 和 session search 是什么关系？** 真相源（ground truth）肯定是 session 源文件，那 memory 的存在意义是什么？结论：两者不是替代关系，是**不同抽象层级**——session search 是原始事实检索（逐字准确，但慢、噪声大、无归纳），memory 是归纳后的语义层（「用户是什么样的人」，跨会话提炼，但可能丢细节/过期）。memory 是 session 的「预计算索引 + 提炼」：检索时 memory 优先（快、准），命中但置信度低时**降级到 session search 兜底**。这比纯 session search 或纯 memory 都好。

**问题二：时间权重怎么设计才不是「越久越不重要」的线性衰减？** 三个变量组合：

- **指数半衰（14 天）**：衰减的度量是「距上次强化多久」，不是「绝对年龄」
- **强化次数（reinforcement）**：记忆每次被检索命中就 +1——用户反复提到的偏好，reinforcement 高，即使时间久也压不掉
- **情绪权重**：用户表达强烈态度（「我特别讨厌 X」「这个非常重要」）时记高权重——情绪重的记忆更难被新记忆顶掉

配套原则是 **supersede 而非删除**：过期偏好被新事实顶掉时走软删除，旧条目还能找回——因为「过期」本身可能被推翻。

## 我们的实践对照

论文的两个失败模式，恰好和我们 8 月底的记忆框架迭代一一对应——先踩坑、后修复：

### 对信息缺失：从「自觉」改成「机制」

我们踩过同款坑：mem0 最初走「自觉路线」——靠 agent 自觉调 memory_add，试行十天只主动检索了 3 次，召回形同虚设，写入也漏。这和论文里 23% 的信息缺失是同一个病根：**依赖自觉的写入和召回必然漏**。

修复分两侧：

- **写入侧**：agent_end 钩子自动沉淀（autosediment 扩展），删掉 60s 限流，每轮都尝试；引用消息场景记被引用的回复主体而非「记一下」三个字；LLM 过滤层判定内容是否值得记（根治把「收藏一下 JD」误判成「申请了岗位」这类误沉淀）；每条记忆带 source_ref 可回源到 session
- **召回侧**：v4 升级为多路召回——不再用「最近 recap 的下一步」这种弱 query，改为当前任务描述 + 用户画像关键词 + 最近高频话题多路并发，结果分层注入 system prompt

### 对过期偏好：时间衰减上线

召回侧加了时间衰减权重（指数半衰 14 天）+ 强化次数，采纳上面的 hotness 设计；过期事实靠软删除的 supersede 机制让位，不物理删除。

### 实测效果

用 27 个真实 case 跑记忆 eval：**hit@3 91.7%**——对比修复前「十天召回三次」的状态是质变。过程里还顺带修了一串工程坑：mem0 的 Qdrant EXCLUSIVE 锁冲突（CLI 与 MCP 共存时）、写入时序导致通知不弹、通知内容截断等。

### 对方向本身

论文里压缩记忆省两个数量级 token 的数据，确认了「压缩 + 检索」路线的正确性——我们没有必要羡慕长上下文，也没有必要因为 53% 的准确率否定记忆系统的价值。

## 当前理解 / 结论

- 向量记忆的失败大多不在「检索不够聪明」，而在**写入漏了**和**没考虑时间**——修这两个点比换 embedding 模型收益大
- 主题相关性 ≠ 当前适用性，这是所有无时间感知检索系统的共同盲区
- 记忆系统的 eval 必须包含时间维度（有没有把过期偏好当新偏好用），只测 hit@k 会高估它
- 论文 53% 的上限也说明：全平台个人智能还没人做出来，memory × session search 的分层组合是当前务实解
